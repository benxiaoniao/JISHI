# 图片 —— 基石的第一个第三方包

把图片在 **BMP / PPM / PGM / PNG** 之间转来转去，**纯基石实现，不调用任何外部程序**
（不需要先装 ffmpeg / ImageMagick）。

```jishi
导入 图片 从 本地包

图片.转("照片.bmp", "照片.png")          # 一步到位：读进来、写出去
令 图 = 图片.读("照片.bmp")              # {宽, 高, 像素, 来源格式}
打印(图片.尺寸(图))
打印(图片.取像素(图, 0, 0))              # [红, 绿, 蓝]
图片.设像素(图, 0, 0, [255, 255, 255])
图片.写(图, "改过.bmp")
```

## 装

```bash
jishi 安装 图片 --local-dir examples/packages/图片     # 从目录装
jishi 安装 图片 --local-zip 图片-1.0.0.zip             # 从打包好的 zip 装
```

## 能做什么

| 格式 | 读 | 写 | 说明 |
|---|---|---|---|
| BMP | ✅ | ✅ | 24 位读写；32 位（BGRA）只读、丢掉 alpha；**带调色板的 8 位不支持**（会明确报错） |
| PPM | ✅ | ✅ | P6 二进制、最大值 255 |
| PGM | ✅ | — | P5 二进制灰度，读进来**摊成三通道**（r=g=b） |
| PNG | ❌ | ✅ | 写 8 位真彩色；**读不了**（见下） |

其它接口：`图片.空图(宽, 高, 底色)` · `图片.取像素` / `设像素` / `填充` · `图片.尺寸` ·
`图片.支持格式()`。

## 已知边界（如实写，不粉饰）

1. 🔴 **PNG 只能写、不能读。** 读 PNG 要自己实现 inflate（fixed/dynamic Huffman 解码），
   那是另一个量级的工作。遇到 `.png` 会**明说**「只写不读、要读先转成 BMP/PPM」，
   而不是甩一句「出错了」。
2. 🔴 **写出的 PNG 不压缩**（deflate 的 stored 块）。好处是不用实现 LZ77+Huffman 就能合法；
   代价是**文件跟 BMP 一样大**：128×128 的图 PNG 49,348 字节、BMP 49,206 字节。
3. 🔴 **产品版（`jishi-rs`）现在导入不了包。** 见下面「撞出来的缺口」第 1 条 ——
   这个包目前**只能在 Python 参考实现里跑**。
4. **性能**（Python 参考实现，本机实测三档，不是估的）：

   | 尺寸 | 造像素 | 写 BMP | 写 PNG |
   |---|---|---|---|
   | 32×32 | 66 毫秒 | 59 毫秒 | 202 毫秒 |
   | 64×64 | 274 毫秒 | 226 毫秒 | 730 毫秒 |
   | 128×128 | 1,230 毫秒 | 988 毫秒 | 3,607 毫秒 |

   大致线性 ⇒ **百万像素要几分钟**。定位是「小图 / 图标 / 教学与格式验证」，
   不是「批量处理照片」。

## 这个包撞出来的三个缺口（这是它最大的价值）

写这个包不是为了「有个包」，是为了**逼出包管理的真问题**：

1. 🔴 **产品版导入不了包**（最硬的一条）。`jishi-rs` 能 `安装`，
   但执行 `导入 图片 从 本地包` 直接报「Rust 引擎不支持」；写 `导入 图片`
   又报「没有找到标准库模块」。Node 宿主同理。
   ⇒ **发行版用户装得上、用不了** —— 包生态在产品版上等于不存在。
   五引擎实测：Python 树遍历 ✅ / Python VM ✅ / 字节码 ✅ / **Rust ❌** / **Node ❌**。
2. **`字节` 没有「列表 → 字节」的构造器**。源码里造字节只能
   `编码.十六进制解码("89504E47")` 这样**攒十六进制文本**再解回来。
   本包为此专门写了一层 `_成字节()`（每个字节查 256 项的表），能用但绕。
3. **`包.json` 表达不了「要求基石版本」**。白名单是
   `名字/版本/描述/依赖/入口/许可/作者/主页/关键字`，没有 `基石版本` ——
   所以这个包没法声明「我要 0.2.8 以上才跑」。

这三条都已记进 `docs/包管理与后续路径规划.md` 的 0.2.9（M145 按真需求补）。
