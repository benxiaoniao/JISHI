## 〇、战略定位（2026-09 重要调整）

经过 M0–M16 的完整闭环，重新审视方向后，对北极星做一次**务实调整**：

| | 旧定位 | 新定位 |
|---|--------|--------|
| 北极星 | 「最容易被大模型正确生成、安全执行、自我修复」 | **健全语言自身能力，让编程者方便地实现意图，出问题能快速定位** |
| 「AI 友好」 | 核心驱动 | **辅助线，带着走**（不放弃，但不作为当前主攻方向） |

**为什么调整**：

1. 「容易被大模型正确生成」的影响因素太复杂——涉及模型能力、训练语料、
   提示词工程、评测方法等多个不可控变量，作为唯一北极星会让路线被外部因素牵着走。
2. 基石当前**更本质的价值**，是给中文使用者一门「写起来顺、错了能看懂、能快速找到问题」
   的语言——这个价值不依赖任何模型，也永远成立。
3. 一个语言如果自身不够健壮、报错不够好用，AI 写得再准，用户也难上手。

> **结论**：把力气花在「语言自身」上。AI 友好相关的资产（语言卡 / 评测集 /
> few-shot / 容错解析）继续维护、随需求自然生长，但不再作为路线的主线牵引。

### 1.2 实测发现的真实不足（「找到自身不足」的第一手证据）

> 以下是 2026-09-05 逐场景实测的结果，是本次路线最重要的输入。
> 它们对应新定位的核心诉求「**出问题能快速找到**」。

#### 缺口 A：递归超限错误没有被中文化（最典型）

```jsh
函数 递归(n):
    返回 递归(n + 1)
递归(1)
```

实际输出：

```
错误：程序内部出现未预料的问题（RecursionError）：maximum recursion depth exceeded
```

**问题**：既没有中文解释，也没有「是不是忘了写结束条件？」的建议。
而 `jishi/errors.py` 里其实**已经写了**翻译逻辑
（`RecursionError → "递归层数太深了，是不是函数忘了写结束条件？"`），
但实际执行时这个异常没走到翻译分支，落到了 CLI 的兜底 `except Exception`。

> **根因**：`RecursionError` 在解释器递归调用 `exec_block` 时直接抛到顶层，
> 绕过了 `_as_jishi_error` 的翻译路径。这是一个**真实 bug，不是设计缺失**。

#### 缺口 B：沙箱/统一协议里的错误缺行列与建议

同样的递归超限，在沙箱里：

```json
{"ok": false, "error": {"code": "E2000", "message": "RecursionError: maximum recursion depth exceeded",
                        "line": null, "col": null, "hint": null}}
```

死循环超时：

```json
{"ok": false, "error": {"code": "E2000", "message": "执行超时（2 秒）", "line": null, "col": null, "hint": null}}
```

**问题**：`line`/`col`/`hint` 全是 `null`。对 agent 或用户来说，
「执行超时」没有告诉它**哪里**可能有问题、**怎么改**。

#### 缺口 C：没有调用栈回溯（深层调用链看不出「谁调用了谁」）

```jsh
函数 里层():
    令 x = [1, 2]
    打印(x[10])      # 这里越界
函数 中层():
    里层()
函数 外层():
    中层()
外层()
```

实际只输出越界那一行：

```
错误 E2003：索引越界
  ┌─ _t.jsh:3:9
  3 │     打印(x[10])
```

**问题**：看不到「`外层` → `中层` → `里层`」的调用链。用户定位问题时，
只能靠猜是哪个调用路径触发的。**这正是「出问题快速找到」的最大短板。**

#### 缺口 D：REPL 里错误不显示源码行

在 REPL 里 `打印(1/0)`，输出：

```
错误 E2001：不能除以零
  ┌─ <输入>:1:5
  │
  │          ← 这里本该显示源码行，但空了
```

**问题**：交互式输入没有缓存源码行，导致 `^` 指示和源码显示不出来。

#### 缺口 E：真实项目反哺的 5 个语法别扭点（M15 已记录未修）

无切片 / `最小`只收单列表 / `导入 文本`遮蔽内建 / 正则定界符 / 无 argv，
详见 `examples/projects/README.md`。

### 1.3 核心判断

> **新定位下的三条主线**，按重要性排序：
>
> 1. **出问题能快速找到** —— 缺口 A/B/C/D 全是这一条，是「语言自身健全」的最直接体现。
> 2. **方便实现意图** —— 缺口 E 的 5 个语法别扭点，真实写过项目才痛。
> 3. **拿得到手、跑得起来** —— 三平台发行、开发者工具、生态。
>
> 「AI 友好」作为辅助线，随这三条主线自然生长。

### M17 报错体验补全

#### 17.1 修复递归超限未翻译的 bug（缺口 A）

- 让 `RecursionError` 走通 `translate_python_exception` 的翻译路径
  （`errors.py` 已有翻译，修复传递链路即可）
- 预期输出：

```
错误 E2000：递归层数太深了，是不是函数忘了写结束条件？
  ┌─ _t.jsh:2:12
  2 │     返回 递归(n + 1)
    │            ^
```

- 同步修三执行器（树遍历 / Python VM / C VM），加对拍测试

#### 17.2 调用栈回溯（缺口 C，本梯队最有价值的一项）

- 给解释器维护一个**调用帧栈**：每次进入用户函数时压入
  `(函数名, 调用位置 line/col)`，出错时随错误一起渲染
- 预期输出形态：

```
错误 E2003：索引越界
  ┌─ _t.jsh:3:9
  3 │     打印(x[10])
    │         ^
调用链：
  外层 (第 7 行) → 中层 (第 5 行) → 里层 (第 3 行)
```

- **实现要点**：
  - `Interpreter` 增加 `self._call_stack: list[Frame]`
  - 进入 `_eval_call` 的用户函数分支时压栈，`finally` 里弹栈
  - `JishiError` 增加 `trace: list[Frame]` 字段，`render()` 里渲染
  - 控制深度（比如只显示最近 20 帧），避免深层递归刷屏
- **边界诚实**：三执行器都要做，C VM 需要额外的宿主回调传帧信息，工作量大，
  可分两阶段——先树遍历解释器（默认执行器），C VM 后续跟上

#### 17.3 沙箱/协议错误补全行列与建议（缺口 B）

- 超时错误：`line`/`col` 填「当前执行位置」（若可获取），
  `hint` 填「可能是有死循环，检查循环条件或递归结束条件」
- 递归超限：复用 17.1 的中文翻译，行列来自调用帧栈
- 让 `--json-result` 的错误对 agent 同样友好（不只是人看的报错）

#### 17.4 REPL 错误显示源码行（缺口 D）

- REPL 缓存最近输入的多行源码，出错时填入 `source_line`
- 让 REPL 的 `^` 指示和源码显示与文件模式一致

**验收**：四个缺口各配一个回归测试，报错质量肉眼可见地提升。
**验收脚本**：把 1.2 节的四段代码跑一遍，输出应包含中文解释 + 定位 + 建议。

## 四、第二梯队：表达便利（「方便实现意图」）

> 对应缺口 E，来自 M15 真实项目反哺，是「写过项目才知道的痛」。

### M18 语法体验补全

#### 18.1 切片语法（第一痛点）

```jsh
列表[1:3]      # 取子列表
列表[::-1]     # 倒序（当前要写 反转(列表)）
列表[:2]       # 前两个
列表[2:]       # 从第 3 个到末尾
```

- 实现难点：tokenizer/parser 要在方括号里区分「字典字面量冒号」与「切片冒号」
- 保守方案：先只支持「返回新列表」的切片，不支持切片赋值（降低复杂度）
- 三执行器同步 + 对拍

#### 18.2 命令行参数（argv）

```jsh
# jishi 分析.jsh 成绩.csv --排序 分数
导入 系统
打印(系统.参数())      # ["成绩.csv", "--排序", "分数"]
```

- 让真实项目告别「`输入()` 交互式读路径」
- 只给原始参数列表，复杂解析交给标准库或用户

#### 18.3 `最小`/`最大` 支持多参数

```jsh
最小(5, 3)        # 3（当前报错）
最小([5, 3])      # 3（现有行为，保持兼容）
最小(5, 3, 9)     # 3（变长）
```

#### 18.4 模块遮蔽治理

`导入 文本` 会遮蔽内建 `文本()`（M15 日志统计项目真实踩过）：

- 方案 A（推荐）：导入时若模块名与内建同名，打印一次中文提示
- 方案 B：改名（breaking change，留 2.0）
- 方案 C：只补文档（成本最低，但用户还会踩）

**验收**：每个特性配测试；用新语法重写 `examples/projects/` 三个项目，代码应变短。

### 6.5.1 实测缺口一览（2026-09-12）

| 分组 | 缺失项（实测报错） | 一句话需求场景 |
|------|-------------------|---------------|
| 表达式 | 三元表达式、成员测试 `在`/`不在`、恒等 `是`/`不是`、位运算 `& | ^ << >>` | 判断/筛选写起来绕 |
| 数据结构 | 集合类型、元组、切片赋值、星号解包、字典合并 `\|` | 去重、不可变、批量改 |
| 函数 | 变长参数 `*`/`**`、匿名函数 | 包装函数、map/filter |
| 类 | `超()`、`是实例()`、类变量、多继承、对象可遍历、自定义打印 | OOP 完整性、数据管线 |
| 语句 | 断言、模式匹配、上下文管理器、`全局`、`删除`、生成器 `产出` | 调试、资源管理、惰性 |
| 类型 | 类型标注、枚举、精确小数（`0.1+0.2 == 0.3` 为假） | 错误前置、金额计算 |

### 6.5.2 准入与排序（三关之上补一条）

**关 0（新增）——三执行器成本**：每个**语法特性**都要在树遍历 / Python VM /
C VM 三处实现并对拍（当前 107 项对拍是硬保障），成本是「标准库函数」的
一个量级。因此铁律：**能用内建函数/标准库实现的，不碰语法**；只有「语法
层面才能真正顺手的」才动语法。这决定了下面的分档。

关 1 真实需求、关 2 可度量验收、关 3 投入产出比——沿用不变。

### 6.5.3 分档路线

#### A 档（M23，立即做）：「顺手就能补上的高频缺口」✅ 已完成

低成本、高频率、零争议，一个里程碑内做完，每个都配三执行器对拍：

| 特性 | 形式 | 为什么现在做 |
|------|------|-------------|
| `断言(条件, 消息)` | 内建 → 抛「断言错误」 | 调试刚需，成本极低 |
| 成员测试 `在` / `不在` | 关键字比较运算 | 超高频，替代 `列表.包含()` 的绕法 |
| 恒等 `是` / `不是` | 关键字比较运算 | 判断 `空`、判断同类型，高频 |
| `超().方法()` | 解析期脱糖 + 内建 | 子类覆盖后调父类，OOP 刚需 |
| `是实例(值, 类)` | 内建 | 类型反射，配合错误处理 |
| 类变量（`类 甲：计数 = 0`） | 语法 | OOP 完整性，成本低 |

**实际结果（2026-09-12）**：六项全部落地，探针可用率 **9/38 → 16/39**。

**A 档顺带抓出并修掉的两个既有缺陷**（都不在原计划里，是对拍与实测的收获）：

1. **`非` 的优先级错误**：原先 `非` 是最紧的一元运算，`非 年龄 >= 18`
   被解析成 `(非 年龄) >= 18` —— 恒为假、**静默给错答案**。
   项目教程 `docs/tutorial/03` 自己就踩了这个坑。现按 Python `not` 语义修正。
2. **C VM 函数同一性分歧**：同一函数每次跨 C/Python 边界都新建包装对象，
   `f 是 g` 在 C VM 下与另两个执行器结果相反。现按底层 `JsFunc*` 指针缓存。

> 这两条印证了「关 0」与「对拍优先」的价值：**语法类的改动必须三执行器对拍**，
> 否则会留下只在某一个执行器上出现的语义偏差。

#### B 档（M24）：「面向对象与集合的完整性」✅ 已完成

中成本，每个是「从能写到写好」的台阶：

| 特性 | 实际落地情况 |
|------|-------------|
| 集合类型 | ✅ `{1,2,3}` 字面量 + `集合(列表)` + 集合推导式；**有序去重**；交并差等 11 个方法 |

**额外做了两项（超出原计划，因成本低、价值高）**：

  可遍历却不能求长度/最值，很别扭）。

`bind_args` 里），但改动比预估可控，关键是找对了几个「不动 C」的落点：

| 知道哪个形参是 `*` / `**` | `code_params` 每形参加第 4 个 int32 | 改（读法） |

| 星号解包 | `UNPACK` 闲置的 `b` 操作数传星号位置 | 改（读法） |

#### C 档补课（M27）：「同一件事只留一份实现」

C 档做完后暴露出一类**更隐蔽**的问题：同一个值有两种写法。

`打印(空)` 给 `None`、布尔给 `True`/`False`，而 REPL 回显与 `类型()` 给
中文「空/真/假」。根因不是谁写错了，而是这件事**有两份几乎一样的实现**
（`runtime.jishi_repr` 与 `repl._repr_jishi`），日子久了就漂移；
`文本()` 是第三个漂移源（它直接 `str()`，而插值又脱糖成 `文本()`，
所以插值也跟着给 `None`）。

处理办法是收敛而非打补丁：

1. **合并到一处** `runtime.jishi_repr(v, *, top)`，`打印`、`文本()`、
   插值、容器元素、REPL 回显全走它。`repl._repr_jishi` 改成一行委托。
2. **用 `top` 表达「顶层 / 嵌套」的分工**：顶层文本不加引号（用户要那串字），
   容器内加引号（否则分不清 `['甲']` 里是文本还是变量）——与 Python 的
   `print`/`repr` 分工一致。
3. 字典用半角 `: `，与源码字面量一致：打印结果要能**直接抄回代码**。
4. 连带消除规格里一条「已给边界」（桥接返回的原生 bool 显示不一致）。

**验收结果**：探针可用率 **36/47 → 37/48**；
新增 19 项测试（显示统一 + Node 宿主对拍 + REPL 回显），全量 1011 项通过。

**跨语言宿主同步**（这一步不能省，否则「字节码可移植」名不副实）：
- **Node**：补齐 M26 的四个内建与显示规则，**全部由对拍测试验证**。
  其中精确小数是 JS 侧自己实现的十进制（BigInt 系数 + 28 位有效数字 +
  half-even），所以 `精确("1")/精确("3")` 与 Python **逐字节一致**。
  过程中抓到一个真 bug：`_alignTo` 的指数对齐方向写反，只有「指数不同」
  的运算才暴露（`精确("19.99") - 精确("20")` 算成 20.19），已加回归用例。
- **Rust**：只做能人工确证正确的部分（显示统一）。`精确`/`打开`/上下文内建
  **未做**——零依赖约束下精确小数需手写 BigInt，且**本机 cargo 无法运行**
  （`touch` 源文件后 build，产物时间戳不变），改几百行无法编译验证的代码
  比明确标注未做更糟。

**这一档留下的方法论**：遇到「同一个东西两种表现」时，先搜「这件事有几份
实现」，而不是给每个出口打补丁。漂移几乎都从重复实现里长出来。

#### M27 收尾：Rust 宿主首次真正跑起来

**起因**：`cargo` 命令「执行成功但什么都不做」。根因是 `~/.cargo/bin/` 下
13 个文件都是 **0 字节** —— rustup 在 Windows 上把这些做成指向 `rustup.exe`
的硬链接，链接坏掉后退化成空文件，执行它无输出且 `rc=0`，**极像「命令被沙箱
吞了」**（前两轮就是被这个假象骗过去的，误记成「环境限制」）。重建硬链接后
`cargo 1.98.1` 正常。

**教训**：「命令没输出」不等于「命令不能运行」。要拿**产物时间戳**这类硬证据
判断到底有没有执行（`touch` 源文件后重新 build，产物时间戳不变才是真没编译）。

第一次真正跑起来，立刻抓到两个**阻塞级既有 bug**：

1. `Flow::Return` 被当成「本帧结束请弹帧」和「刚压了新帧别弹」两种含义，
   于是每次函数调用后新帧立刻被弹掉，外层执行那个还没拿到实参的 `CALL`，
   `fn_base` 下溢成 `usize::MAX` → panic。**修前连 `打印(加一(1))` 都跑不了。**
2. `MAKE_FUNCTION` 的默认值对齐按「全部形参个数」算，有 `*参数` 时错位
   （Python 侧 `vm.py` 在 M25 修过同一个坑）。

**顺带更正一处夸大**：Rust 宿主自 M13.3 起写着「最小可运行」，但 `tests/` 里
只有 Node 的对拍、**Rust 从没运行验证过**——bug 1 说明它连函数调用都跑不了。
现在补上 `tests/test_m27_rust_host.py`（21 对拍 + 5 xfail），
`docs/embed.md` 的支持程度表按**实测**重写。

**未做且优先级最高的一条**：**可变容器是「静默算错」**——`Val` 是值类型，
`get_attr` 对列表拷一份再改，所以 `列表.追加` 改的是副本、推导式返回空。
**不报错、结果就是错的**，比「报错」危险。修它要把 `List`/`Dict` 换成
`Rc<RefCell<…>>`，是贯穿全文件的重构（`Val` 的 `Clone` 语义、模式匹配解引用
都要跟着改），所以单列一项待办，而不是顺手改。

**跨宿主一致性的教训**：新增一个宿主，如果不同步添加**对拍测试**，
「支持」二字就是空的——Rust 宿主挂着「已支持」好几个月，实际连函数调用都崩。
M30 在 JS 侧又验证了一次：**方向相反**的问题（Python 侧有、宿主侧漏），
所以「补了新语法必须回跑一遍横向探测」要变成常规动作，而不是出了事再查。

#### M28：Rust 宿主修掉可变容器

上一版修完两个阻塞级 bug 后，剩下一条**「静默算错」**：`列表.追加` 改的是
副本、原变量不动，推导式返回空列表。不报错但结果是错的，比报错危险——
所以单列一个里程碑而不是顺手带过。

**根因**：`Val::List(Vec<Val>)` 是值类型、`Clone` 是深拷贝，`get_attr` 拿到的
`obj` 又是拷贝。改成 `Rc<RefCell<Vec<…>>>` 后 `Val::clone` 只复制指针，
方法里的 `borrow_mut()` 就改到了共享数据。涉及 53 处使用点，编译器逐个把关。

**换共享语义时最容易漏的一处**：Rust 版把「列表自身」当迭代器
（`iter_next` 会 `remove(0)`）。以前靠值拷贝侥幸正确，共享之后如果不显式
快照，`遍历 x 在 a` 会把 `a` 逐元素吃掉。→ `make_iterator` / `unpack_values`
都改成取快照，并专门写了 `test_rust_iteration_does_not_consume` 锁住。

> **一般性教训**：把「值语义」改成「引用语义」时，要**找出所有依赖
> 「拿到手就是独立副本」的地方**——它们不会报错，只会悄悄变错。
> 迭代器/解包这类「看起来只读」的实现尤其容易中招。

**顺带补齐两种完全没实现的比较运算**：写「按首字母分组」这个真实惯用法时，
第一行 `如果 k 在 分组` 就撞墙——`compare` 只处理 0–5，
`在`/`不在`/`是`/`不是` 根本没实现。

- **成员测试**：列表按值、字典按键、文本找子串。
- **同一性**：单例/数字/文本按值，列表字典按 `Rc::as_ptr` 身份。
- **类/实例/函数明确报错**：它们在 Rust 里是值类型、没有身份可谈。
  这里有个取舍——「按内容相等」能让代码跑起来，但会给出和 Python 相反的
  答案（`甲 是 甲`），那就是又一次静默算错。**宁可明确报错。**

**验收结果**：Rust 对拍 21 → 36 项（+4 xfail）；全量 1047 通过 + 4 xfail。

#### M29：Rust 宿主补齐到 Python 侧

把用户上轮点名的三块一起做完：**方法调用 / 列表高阶方法 / 集合·文件·精确小数**。
做完的直接结果：**这个宿主上不再有「静默算错」**，剩下的缺口都是明确报错。

三块里各有一个「不这样写就会静默出错」的点，值得单记：

1. **方法调用**：`BoundMethod::User` 只是个自由函数拿不到 VM，所以要把
   调方法统一成「把实例塞进首参再压帧」；而更隐蔽的是 `Instance` 是值类型
   ——`自身.字段 = 值` 改的是副本，方法里的赋值**全部静默失效**。
   和 M28 的容器是同一类坑：**凡是「改了就希望调用方看见」的东西都要共享**。
2. **数据流水线**：内建要能反过来同步调用用户函数（`VM::call_value`：
   压帧、在自己的帧深停下）。回调前必须先**快照**容器，否则拿 `RefCell`
   借用去回调会撞运行时借用冲突。
3. **精确小数**：零依赖手写 BigInt（base 10^9 小端 + 逐肢二分长除法）。
   `**` 只支持整数指数——非整数次幂是近似运算，各执行器必然漂移，
   宁可报错也不给「看起来能跑、结果对不上」的近似值。

**动手时才暴露的两个既有 bug**（都不是本次引入的，说明「没有对拍就等于没实现」）：

- `execute` 里 `Err(e)` 直接 `return Err(e)`，**绕过了异常分发**——
  于是 `尝试/捕获/最终` 对**内置错误**（除零/越界/类型不符）完全失效
  （`Flow::Error` 变体根本没人构造，写成死代码）。
- `返回` 不跑 finally（缺 Python 侧的 `_return_via_finally`），
  所以「`用` 块里 `返回`」会让文件不关——资源清理形同虚设。

两条都按 Python 的块栈语义补齐（含 `中断` 穿过 finally：信号借
`Val::LoopSignal` 走值栈，`block_seq` 决定「最近循环 vs 最近 try」谁先接）。

**验收结果**：Rust 对拍 36 → **101 项，无 xfail**；全量 **1112 项通过**。
探针不变（37/48）——探针测的是**语言面向用户的能力**，宿主覆盖度由
`docs/embed.md` 的支持程度表负责。

#### M30：JS 宿主补齐到 Python 侧

同一条路子再走一遍（Rust 补完补 JS）。这次先做**横向探测**：写一个脚本把
39 个用例在 Node 与 Python VM 上各跑一遍逐条比对，实测出 **37 处不一致**，
再按实测范围补——不靠印象猜。

探测的价值立刻体现出来：**成员测试 `在`/`不在` 与同一性 `是`/`不是`
在 JS 侧根本没实现**（`vm.js` 的 `CMPOP` 只映射 0–5，6–9 落成 `undefined`），
而上一版 `docs/embed.md` 还给这两行标了 ✅。**这与 Rust 侧 M28 是同一个问题**
——加语义比较运算符时，宿主侧那张「码值映射表」是漏点重灾区。

另外两处是 JS 语义特有的「静默算错」：

- `Boolean([])` 是 `true`，而 Python 的 `bool([])` 是 `False` →
  `如果 列表：` 的判断**整个反过来**；
- `===` 是引用比较，而 Python 的 `==` 对容器按值递归 →
  `[1, 2] == [1, 2]` 给假。

集合实现有个不得不绕的坑：**不能用内建 `Set`**——它的元素相等是
SameValueZero，与 Python 的 `hash/eq` 不一致（Python 里 `{1, 1.0, 真}`
只留一个元素，`new Set([1, 1.0, true])` 会留三个）。所以自己维护
「规范化键 → 原值」的 Map。`tests/test_m30_node_host.py` 里专门锁了这条。

补完这七块后，把 `examples/projects/` 的真实项目拿来在 Node 上跑，
**又撞出三块缺口**——说明「横向探测」也有盲区。于是又补了：

- **切片**（`BUILD_SLICE`）：JS 侧整条指令都没有（`对[::-1]` 报「未知指令 48」）。
- **二元运算的类型分派**：JS 的 `+` 对数组是字符串拼接、`%` 符号与 Python 相反。
- **标准库**：表格 / 文本 / json / 正则 / 系统；`输入()` 从「永远返回空串」
  改成真读标准输入。

**验收标准（M30 起固定下来）**：`examples/projects/` 里的真实项目能在宿主上
**原样跑出与 Python 逐字节相同的结果（含退出码）**——这比任何探针都硬。

**验收结果**：新增 **62 项** Node 对拍（关键语义另加树遍历 / C VM 四路对拍，
含两个真实项目的端到端对比）。`docs/embed.md` 的支持程度表按实测重写，
并新增「JS 宿主剩下的边界」一节。

#### M31：JS 标准库补齐到与 Python 同宽

同一条路子走第三遍（Rust 补完补 JS 的语法，再补 JS 的标准库）。M30 补到
「5 个常用模块」，这轮把剩下 7 个补完：**路径 / 文件 / 日期 / 时间 / 加密 /
压缩 / 网络**。补完的结果是 `examples/projects/` 里的**全部**项目都能在
JS 宿主上跑，包括上轮还明确写着「跑不了」的「网页采集」。

为什么这三块最难，各有一个「无法直接照搬」的原因：

1. **压缩**：**Node 没有内置 zip**。`zlib` 只提供 deflate 流，
   本地文件头 / 中央目录 / EOCD / CRC-32 得按 PKWARE 规范手拼。
   → 测试因此**不只对拍输出**，还拿 Python 的 `zipfile` 当裁判
   （`zf.testzip()` 校验 CRC），双向都测——只对拍「两边一样」是不够的，
   万一两边一起写坏了呢。
2. **网络**：**Node 没有同步 HTTP**。`fetch` 是异步的，而基石没有 `await`，
   标准库不能变成异步函数。→ `spawnSync(process.execPath, ['-e', 脚本])`
   起一个**自身的子进程**跑异步请求，结果经 stdout 回传；零第三方依赖，
   也不要求系统装了 `curl`。代价是每次请求多一次进程启动（约 40ms）。
3. **日期时间**：JS 没有 `strftime`，`toLocaleString` 又依赖系统 locale。
   → 自己实现一个子集（`%U`/`%W` 的周号照 CPython 的公式）。
   `时间.睡眠` 用 `Atomics.wait` 同步阻塞——基石没有 `await` 时的唯一解法。

顺手改掉 Python 侧两个**跨平台不一致**（都是「同一份程序到哪都一样」
这条定位下的欠账）：

- **文件读写改成「换行保真」**：Python 的文本模式在 Windows 上把 `\n`
  写成 `\r\n`，于是同一份程序在两个平台产出的文件字节不同。
  标准库统一显式 `newline=""`。
- **值→文本统一**：`文件.写文本`/`写行`、`加密.摘要` 之前走 Python 的
  `str()`，`写文本(p, 真)` 写出 `True`；改走 `jishi_repr`。

路径模块另有两个细节：`后缀` 不能直接用 `path.extname`（pathlib 对 `a.`
与 `.bashrc` 都算无后缀）；Windows 上 `Path.__str__` 总吐 `\` 而 JS 的
`path` 保留输入里的分隔符，返回值要显式规范化。

**验收结果**：新增 **43 项** Node 对拍（网络用本地 `http.server`，不依赖外网；
压缩含跨宿主互操作）；全量 **1174 → 1217 项通过**。
`docs/embed.md` 的支持程度表改为「14 个模块全量」，并更新 JS 边界一节。

#### M32：核实「剩余边界」，把静默算错清零

把 `docs/embed.md` 的「剩余边界」清单**逐条横向实测**了一遍。这个动作本身
就是上一轮教训的延续——文档会腐烂：M30 那次是「标了 ✅ 其实没实现」，
这次反过来撞到「标着 ❌ 其实早就好了」。

**一、两条过时描述**（删掉）

- 「JS 的 `1` 与 `1.0` 无法区分」：字节码里的小数常量本来就带 `t: "float"`
  标记，`node/index.js` 的 `decodeConst` 早就按它包成 `FloatBox` 了。
  ——**这条被当成「JS 表示层的固有限制」写了好几轮**，其实从来不是限制。
- 「JS 的错误渲染没有源码行」：M30 已规范化成中文。

**二、五处「静默算错」**

排在最前面的两类错（大整数、整数溢出）都属于「**不报错但结果错**」——
这比「明确报错」糟得多，也是本轮优先处理它们的理由。

| 现象 | 根因 |
|---|---|
| JS：`9223372036854775807` → `...776000`、`2 ** 64` 算错 | number 是双精度 |
| Rust：`i64_MAX + 1` → **负数** | `i64` 回绕 |
| C VM：`2 ** 64` → **`0`** | ctypes 边界静默截断 |
| JS：`打印(类)` → `[object Object]` | 类没有 `toString` |
| 三侧：「加减乘超 28 位」给不同的数 | 只有 `div` 做了 context 舍入 |

对策各有一条值得记的：

- **JS 大整数按需切 BigInt**，不是「一律用 BigInt」——后者会把所有整数运算
  拖慢一个量级。判断条件是「任一边已经是 BigInt」或「number 的结果超出
  安全范围」。配套还要改**字节码的常量编码**：超范围的 int 写成十进制字符串，
  因为 `JSON.parse` 在解析阶段就丢精度了，reviver 也救不回来。
- **C 虚拟机那一条根因最绕**：C 侧本来就用 `__builtin_*_overflow` 检测溢出、
  溢出就**回落宿主**计算——机制是对的。问题在回落算完之后，结果超出 i64 时
  在 **ctypes 边界被静默截断**（`c_int64` 字段赋大整数不报错）。
  `JVal` 刻意保持 16 字节布局（M20 的批量转换快路径依赖它），所以不扩宽，
  在 `_jint` 里拦下报错，并提示可以换 Python 虚拟机。
- **精确小数的显示**要按 CPython 的 `__str__` 规则来：`exp <= 0 且
  leftdigits > -6` 才用定点，否则科学计数法。顺带发现 `舍入(n)` 少了
  Python 侧的 `Decimal(format(r, "f"))` 那一步——舍到百位会打出 `1.2E+3`，
  而 Python 给 `1200`。

**三、两处明确报错**

- Rust 的**类型标注校验**：编译器早就把校验发射成函数的前导字节码
  （`检查实参`），Rust 侧没实现这个内建——于是带标注的函数直接报
  「找不到名字「检查实参」」，**完全没法用**。
- Rust 的**同一性对类与函数**：它们在 Rust 里是值类型、`Clone` 是深拷贝，
  没有指针身份。做法是创建时分配递增序号（`Clone` 跟着复制）——内容相同
  且源自同一次创建的两个值就有了同一个身份，正好等价于 Python 的 `id()`。
  **绑定方法仍明确报错**：Python 里 `a.方法 是 a.方法` 为假，而 Rust 侧
  按「实例指针 + 方法名」判会得到真；宁可明确不支持，也不给反直觉的答案。

**顺带发现（本轮未动，如实记下）**：树遍历不支持类体里写 `通过`；
JS 宿主没同步 M23 的「类变量」；类型标注表里的 `空`/`函数` 是关键字、
语法上写不出来（三侧皆然）。

**验收结果**：新增 **40 项**对拍；全量 **1217 → 1257 项通过**。

#### M33：Rust 宿主标准库补齐（14 个模块 / 约 130 个函数）

Rust 宿主原本只剩这一块明显落后：标准库只有数学 / 文本 / 随机三个模块，
而且函数不全。这一轮补到与 Python 侧同宽。`Cargo.toml` 的 `[dependencies]`
**仍然是空的**——所以四块重活全是自己写的：

1. **正则**（`rust/src/regex.rs`）：自写**回溯引擎**。没有 `regex` crate，
   Python 的 `re` / JS 的 `RegExp` 也不在。支持字面量、`.`、字符类（含 `[^…]`
   与区间）、量词（`* + ? {m,n}` 与非贪婪）、分组（`(…)` / `(?:…)` / `(?P<名>…)`）、
   前后查看、锚点、`\b`、反向引用，`\d`/`\w`/`\s` 按 Unicode 判。
   做法是「语法树 + 续延式回溯」（CPS），比编译成字节码少一半代码。
2. **加密**（`rust/src/crypto.rs`）：自写 md5 / sha1 / sha256 / sha512。
   这几个算法的规范很死（常数表都在标准里），自己写反而**好对拍**——
   拿 `hashlib` 当裁判，`abc`、空串这些公开向量逐字节一致。
3. **压缩**（`rust/src/zip.rs` + `inflate.rs`）：这条最值得记——
   **打包写 `stored`（不压缩）**：零依赖下没有 DEFLATE 压缩器（LZ77 + 两套
   霍夫曼树，几百行的活），而 `stored` 在 zip 规范里本来就是合法形式。
   **解压躲不掉**：别人打的包（Python `zipfile`、Node）默认都是 deflate，
   所以 inflate 是完整实现的（stored / 固定霍夫曼 / 动态霍夫曼三种块都支持）。
   测试因此**不只对拍输出**，还要**双向互操作**：Python 打的 deflate 包
   Rust 解得开、Rust 打的包 `zipfile.testzip()` 校验通过。
4. **网络**（`rust/src/http.rs`）：基石的网络是**同步**的（没有 `await`）。
   Windows 上直接绑 `winhttp.dll`（`extern "system"`，**系统库、不是 crate**）
   —— 好处是 **https 也能用**，TLS 是 WinHTTP 内部的事。其余平台走裸
   `TcpStream`：`http://` 完全可用，`https://` 需要 TLS、手写不现实，所以
   **明确报错**并说明原因（绝不静默降级成明文请求）。

`日期`/`时间` 还要绕两处 `std` 没有的东西：**本地时区**（绑 `GetLocalTime` /
`localtime_r`）与 **`strftime` 子集**（`%U`/`%W` 照 CPython 公式）。
`系统版本` 在 Windows 上绑 `RtlGetVersion`（`GetVersionEx` 会撒谎说自己是 6.2）。

##### 探针全绿之后，真实项目又撞出三块

14 个模块补完、113 例对拍 0 不一致之后，按 M30 定下的标准拿
`examples/projects/` 的真实项目跑 —— **又撞出三块**：
**切片指令 `BUILD_SLICE` 整条没有**（M30 只补了 Node，「未知指令 48」）、
**`输入()` 内建不存在**、**`列表.排序` 静默失效**（`Val::partial_cmp` 只处理
数字与精确小数，字符串/列表返回 `None`，而排序把 `None` 当成「相等」→
排了等于没排）。

第三条最隐蔽：**不报错、不错值，只是顺序不对**。它再次说明
**「探针里没有的用例」就是盲区**——M30 的切片、M33 的排序都是这么撞出来的。

##### 顺带修掉三处「跨宿主不一致」

Python 侧有几处在 Windows 上做**换行转换**，于是同一份程序在 Python 侧输出
CRLF、在 Node / Rust 宿主输出 LF（CLI 输出 / `系统.执行` / `json` 读写文件）。
另有 `正则.查找全部` 多分组时漏出 Python 的**元组**（基石没有元组类型）、
`类型(表格)` 漏出 `_Table` 类名——都统一了。

**验收结果**：新增 **58 项**对拍；全量 **1257 → 1315 项通过**；
`examples/projects/` 三个真实项目在 Rust 宿主上原样跑出与 Python
**逐字节相同**的输出。

#### D 档（M34+）：「重特性，先做原型再定」

成本高、需求要再验证，**不提前承诺**，每个先写最小原型测 ROI：

- 生成器 `产出`（惰性/大数据；需要状态机或协程，三执行器工作量大）
- 模式匹配 `匹配/情形`（现代语言标志，但 `如果/否则如果` 已能覆盖教学场景）
- 多继承（MRO 解析复杂度高，单继承已够绝大多数）
- 枚举、`全局` 声明、`删除` 变量（各自成本低但需求弱，攒够再一起做）
- 运算符重载完整版（先靠 `文本()` 等方法覆盖 80% 场景）

#### 明确不做（延续克制清单，理由微调）

| 不做 | 理由（更新） |
|------|-------------|
| JIT / AOT 编译 | 已有 C VM；教学/工具场景性能足够，工程量大 |
| **完整静态类型系统** | 仍与「简单易用」冲突；用 B 档「可选标注」作轻量替代 |
| 多线程 / 异步 | 严重破坏简单性；GIL 限制难绕过 |
| 宏系统 | 中文受众不需要元编程复杂度 |
| 复刻 Python 全部标准库 | `导入 x 从 python` 已兜底 |

### 6.5.4 依赖与风险

| 项 | 说明 | 应对 |
|----|------|------|
| 语法特性三执行器成本 | 每个都要树遍历/VM/C VM 三处 + 对拍 | 关 0 强制「标准库优先」；同批多个特性一起改，摊薄成本 |

| 特性蔓延 | 加太多语法破坏「简单」 | 关 0 + D 档「先原型再定」 |

**如果只做一件事（M35）**：把「**解析期脱糖优先**」当成新语法设计的**第一问**
——M34 又验证了一次：模式匹配与枚举各只动解析器一两百行，三执行器与两宿主
一行不用改。反过来，生成器之所以被搁置，正是因为「脱糖这条便宜路走不通」。
所以候选新特性到手先问：「它能写成既有语句的组合吗？」

顺带记住 M34 的另一半收获：**原型会撞出既有缺陷**（宿主缺类变量、
Rust 信号分发的真 bug、`类型()` 给错名字）。D 档特性要连着**真实用法**
一起验，只写语法规格就收工，留下的会是「语法能用但一用就撞坑」的半成品。
每做完一档，回跑 `probe_capabilities.py` 看 ✅ 占比是否上升——这是
「语言功能是否真的在变强」的硬指标。

**另一条并行的线（同样重要）**：**消除重复实现**。M27 的经验是——语言里
「同一个东西两种表现」几乎都源于「同一件事有几份实现」（`打印` 与 REPL
回显各有一份格式化代码，于是漂移出 `None` 与 `空` 两种写法）。
所以往后每加一个出口（新工具、新宿主、新前端），先问一句「这是不是又一个
拷贝」，能复用就复用。跨语言宿主同理：`docs/embed.md` 的支持程度表是
唯一事实源，不许在别处另写一份。
