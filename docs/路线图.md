## 〇、北极星与定位

- **定位**：一门**中文编程语言**，对标 Python 的易用性。
- **北极星（2026-09 调整后）**：**健全语言自身能力，让编程者方便地实现意图、
  出问题能快速定位**。「AI 友好」由主线降为辅助线（带着走，不卡点）。
- **三条长期铁律**：诚实不吹牛（未度量就写「未度量」）／三执行器语义必须一致／
  能用内建或标准库解决的就不碰语法。

## 二、准入标准（新特性开工前必须过）

**关 0（前置）——三执行器成本**：每个**语法特性**都要在树遍历 / Python VM /
C VM 三处实现并对拍，成本是「标准库函数」的一个量级。所以：**能用内建或标准库
实现的，不碰语法**。

关 1 真实需求（有真实项目或真实用户场景撞到）→ 关 2 可度量验收（说不出
「怎么算完成」就不开工）→ 关 3 投入产出比。

**加分项：解析期脱糖**。新语法若能表达成既有语句的组合，就在 parser 里脱糖
（已用五次：`超()`、集合字面量、`用 … 为`、模式匹配、枚举）——三执行器与
两宿主零改动，行为必然一致。**新语法到手第一问：「它能写成既有语句的组合吗？」**

## 三、当前规划：M36 起

### 3.1 事实基础：探针只剩 9 项，且已逐条判定

`tools/probe_capabilities.py` 当前 **50 项 / 可用 41 / 缺口 9**，且缺口
**全部已判定**（探针自己的汇总行会打印「无悬案」；有未判定项时退出码为 1）。
剩下 9 项不是「还没轮到」，而是**已逐条给出结论**的：

| 探针项 | 判定 | 理由 / 替代 |
|--------|------|------------|
| 三元表达式 | **已做** | ✅ M36 落地为 `甲 如果 条件 否则 乙`（与 Python 同语序，**零新增关键字**；脱糖成匿名函数立即调用，三执行器 + 两宿主零改动）。 |
| 位运算 `& \| ^` | **已做（改内建）** | ✅ M36 已提供 `位与()`/`位或()`/`位异或()`/`位取反()`。 |
| 位移 `<< >>` | **已做（改内建）** | ✅ M36 已提供 `左移()`/`右移()`（位数上限 1000000）。 |
| 元组 `( … )` | **暂缓** | 唯一不可替代的价值是「不可变 + 可当字典键」，需求弱；且要新增容器类型 → **C VM 得动 `JVal` 布局**，成本与收益不成比例。先给 `冻结(列表)` 顶一顶。 |
| 字典合并 `\|` | **已做（加方法）** | ✅ M36 已提供 `字典.合并(别的)`（返回新字典）。 |
| 多继承 | **不做** | 要 C3 线性化 + 重做 `超()`；单继承 + 组合够用（D26）。 |
| `全局` 声明 | **不做** | 需求弱；闭包与参数传递已能表达。 |
| `删除` 变量 | **不做** | 需求弱；用函数边界表达更清楚。 |
| 生成器 `产出` | **搁置** | 脱糖走不通（要状态机/协程，C 侧还要动 `JVal`）；三个真实项目一个都没用到惰性序列（D26）。 |

> 9 项里**只有 1 项真需要新语法**——这本身就是「语法面已收敛」的证据。

### 3.6 新阶段（M40 起）：三个方向

M36–M39 把「语言面收敛（语法冻结）」与「可信工具链」两条线收齐了，接下来的
重心换三个方向。**判据是同一个北极星的两种延伸**：

- **方向一 · 语言能力（内功）**：继续让「方便地实现意图」成立——补正确性缺口、
  补标准库、打磨诊断与性能。这是老主线的延续。
- **方向二 · IDE 可用性（外功一）**：让**人在编辑器里**能顺畅地用基石编程。
  现在只有语法高亮（`editors/vscode-jishi` 是纯语法扩展，`main` 为空），
  语言服务与调试都没接进 IDE。
- **方向三 · AI 可用性（外功二）**：让**AI 在工具链里**能一次写对、错了能自己修。
  现有 `--ai-card` / `--lang-spec` / few-shot / MCP 是散件，缺「机器可读的事实源
  + 自检 + 评测」三件套。

三条线不并列推进，**互相喂料**：语言能力补的缺口来自主线 C 的真实项目；
IDE 与 AI 两个方向共用同一份语言事实（LSP 的补全数据、AI 的 lang-spec 都取自
`ai.build_lang_spec()`）；IDE 里的调试客户端直接用已有的调试器会话。

#### 三个穿插项的归位

| 穿插项 | 归位 | 说明 |
|--------|------|------|
| f-string 内部转换 | **M40** | 语言正确性缺口，且直接挡住最常见的标准库用法（`导入 文本`） |
| 树遍历「赋值即局部」 | **M40** | 三执行器一致性是铁律；`xfail` 已钉住，改完翻成正常断言 |
| ~~C VM 的调试器~~ | **✅ M40 已做** | 原先判定「等真实需求」，M40 按「先把三条线的对拍做齐」提前做了：C 侧加四个只读入口，三执行器会话记录逐字相同。DAP（M43）可以直接复用 |

#### 依赖与顺序的理由

1. **先语言能力，再外功**：IDE 的补全/快速修复、AI 的 lang-spec 都要读语言事实；
   事实本身有缺口（如 f-string 的坑）时，把外功做出去只会把坑放大。
2. **先语言服务，再做编辑器客户端**：扩展里能演出来的每一条能力，都先有协议级
   测试兜着——不然「在 VS Code 里手点一遍」就是唯一的验收方式，改一次坏一次。
3. **AI 方向排在最后不是不重要**：它要消费前面两条线的产物（干净的错误码、
   稳定的语言事实、可脚本化的检查），顺序反了会把返工做两遍。
4. **主线 C 继续在背景里跑**：每个里程碑都要在真实项目上验一遍——
   行数比不升、别扭点清单变短，才算真进步。

## 四、明确「不做」的事（克制清单）

| 不做 | 理由 |
|------|------|
| 位运算 / 位移**语法** | 日常罕见，用内建替代（关 0） |
| 元组类型 | 需求弱，且要动 C VM 的 `JVal` 布局 |
| 多继承 | C3 线性化 + 重做 `超()`，单继承够用 |
| `全局` 声明 / `删除` 变量 | 需求弱 |
| 生成器 `产出` | 脱糖走不通，真实项目未用到（D26） |
| JIT / AOT 编译 | 已有 C VM，教学与工具场景性能足够 |
| 自研垃圾回收 | Python 前端已有 GC，ROI 极低 |
| 多线程 / 异步 | 严重破坏简单性，GIL 限制难绕过 |
| 宏系统 | 中文受众不需要元编程复杂度 |
| 复刻 Python 全部标准库 | `导入 x 从 python` 已兜底（D5） |
| 追求「完全自主」 | 木兰的教训；D1 已定：技术栈透明，不 fork/patch CPython |
| 完整静态类型系统 | 与「简单易用」定位冲突；用可选标注做轻量替代 |

## 六、风险与诚实边界

| 风险 | 说明 | 应对 |
|------|------|------|
| 调试器跨三执行器工作量大 | C VM 要宿主回调传帧 | 分阶段：树遍历 → Python VM → C VM，每阶段可独立交付 |
| 真实项目投入产出不确定 | 业余时间写项目未必撞到「值得改语言」的点 | 项目选**自己真要用的**，不为写而写 |
| 语法冻结后被现实打脸 | 冻结后仍可能出现必须加语法的新需求 | 冻结是「默认不加」不是「永不加」；新需求仍走准入三关 + 关 0 |
| 特性蔓延破坏「简单」 | 见第四节 | 准入三关 + 不做清单 |
| 三平台 CI 成本 | macOS runner 分钟数消耗大 | 可接受；必要时改为按需构建 |
| 杀软误报 | PyInstaller 产物常见 | 已有 wheel / 源码途径，不承诺绝对不报毒 |
| 文档「总结偏差」 | README/AGENTS 里的数字易过时 | 里程碑推进后同步「技术栈声明 / 性能数据 / 能力清单 / 项目结构」四块 |

**如果只做一件事（M36）**：把探针做成「无悬案」——不是为了数字好看，而是
**逼自己给每个缺口一个明确态度**。悬着的缺口会变成「用户以为有、其实没有」
的陷阱；判定清楚之后，语法面就能安心冻结，精力全部转到工具链与真实项目上。

**M37 的同类逻辑**：调试器不追求「三执行器全支持」的对称，而是**先在最划算的
一处（树遍历）做扎实**——那里「一个语句 = 一次 `exec_stmt`」是天然的暂停点，
一个钩子就换来断点、单步、变量与调用栈；字节码执行器要另建一套（没有语句边界
事件），等真实需求说话再做（B5）。**为对称而做的功能，往往是最贵的**。
