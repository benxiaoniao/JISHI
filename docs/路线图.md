# 基石语言路线图（M7–M15）

> **北极星：把基石做成「最容易被大模型正确生成、安全执行、自我修复」的中文编程语言。**
> 人读得顺，AI 写得对，Agent 敢执行。

---

## 0. 为什么是现在：一门语言的新竞争维度

大模型改变了编程语言的竞争规则。一门语言的成败不再只取决于「人写起来爽不爽」，
还取决于三个新维度：

| 维度 | 含义 | 传统语言的做法 |
|------|------|----------------|
| **生成** | LLM 一次生成该语言代码的准确率 | 靠海量训练语料（Python/JS 碾压） |
| **自愈** | 生成出错后，LLM 能否根据报错自行修复 | 报错是给人看的，agent 难以程序化消费 |
| **执行** | agent 能否安全地把该语言当工具调用 | 子进程跑 Python：慢、依赖面大、有全局状态 |

绝大多数语言在这三个维度上是「被动」的——没人专门为 LLM 设计过报错格式、
沙箱协议和语言速查卡。**这是空白，也是基石的机会。**

### 中文关键字 × LLM：诚实评估

- **优势**：中文关键字语义自解释（`打印`＝输出、`遍历…在…`＝for-in），
  LLM 无需记忆「token → 语义」映射，理解与讲解成本趋近于零；
  中文任务描述 → 中文代码，语义损耗低。
- **劣势（必须承认）**：训练语料里 Python 是海洋、中文编程语言是水洼，
  生成准确率的「底子」不如 Python。硬拼生成准确率没有胜算。
- **结论（差异化定位）**：不在「生成更准」上死磕，而在
  **「错了能自愈 + 执行更安全 + 语义更透明」** 上建立护城河。
  生成侧则通过「语言卡 + few-shot 示例 + 容错解析」把底子劣势补到可用。

## 1. 设计准则：每个新特性必须过「LLM 三问」

1. **生成更准了吗？** 语法歧义是否更少？LLM 高频错误模式是否被容错或清晰报出？
2. **错了能自愈吗？** 报错是否机器可读？修复建议是否可直接替换执行？
3. **能被安全调用吗？** 是否有确定性行为、资源上限、可结构化返回结果？

三问皆否的特性，排到最低优先级。

## 3. 差异化定位（一句话版）

> **Python 是 LLM 的母语；基石要做 LLM 的「工作语言」——
> 生成靠语言卡补课，纠错靠结构化报错闭环，执行靠轻量沙箱。**

三个可防守的据点（按投入产出排序）：

1. **M9 沙箱执行器 + MCP 集成**：让 agent 一行配置就能安全跑基石，
   这是「被大模型调用」的最终形态，也是 C VM 存在的最好理由；
2. **M8 AI 原生工具链**：语言卡 / llms.txt / JSON 报错 / few-shot 库，
   全行业没人为中文语言做过这一套；
3. **M7 表达力 + 容错**：提升表达密度（同语义更少 token）并消化 LLM 高频错误。

## 4. M7 表达力打磨（人写更顺，AI 生成更省）

目标：补齐 Python 级易用性的最后一批高频语法；同时针对性消化
LLM 生成中文代码的最高频错误。

### 7.1 多赋值与解包
- `令 a, b = 1, 2`；`令 a, b = 返回两个值()`；数目不符报错并提示。
- 验收：对拍用例 ≥6 个；错误信息含实际/期望数目。

### 7.2 默认参数
- `函数 打招呼(名字, 语气 = "你好")`；默认值在定义处求值一次（与 Python 一致）。
- 验收：默认值可引用先前定义的名字；对拍 ≥4 个。

### 7.3 列表/字典推导式
- `[x * 2 遍历 x 在 列表 如果 x % 2 == 0]`；字典推导 `{键: 值 遍历 …}`；
  支持多层 `遍历` 与多个 `如果`。
- 设计原则：复用现有关键字（遍历/在/如果），不引入新关键字——LLM 零学习成本。
- 验收：对拍 ≥8 个；报错行号准确。

### 7.4 文本插值（设计决策 D13，待定稿）
- 需求：`"你好，{名字}，今年 {年龄} 岁"`，编译期转为拼接，`{{`/`}}` 转义字面量。
- **定界符候选**（普通字符串不能带插值，否则破坏现有语义）：
  - **方案 A（推荐）：反引号 `` `你好，{名字}` `` = 插值串**。
    理由：JS 模板串在 LLM 语料中海量存在，映射最强；与现有普通引号区分清晰；
    tokenizer 已支持反引号定界但无人使用，改动零破坏。
  - 方案 B：`『…』` 双书名号 = 插值串（全中文视觉，但 LLM 关联弱）。
- 验收：`{表达式}` 内可写任意表达式；对拍 ≥6 个。

### 7.5 容错解析强化（LLM 高频错误消化，设计决策 D14）
- **英文关键字误写 → 中文建议**：LLM 写中文代码时最常 fallback 到英文关键字。
  写 `print` / `def` / `if` / `for` / `return` / `class` / `import` / `try` 等约 20 个
  高频词时，报错并直接给出中文对应（复用 M3 的 True/False 建议机制）。
  只报错不建议自动执行，保持纯中文语义。
- **引号混配容错**：LLM 常写 `“文本"`（中文开英文闭）——归一化后仍闭合失败时，
  报错并指出两端的引号字符。
- **常见结构性错误专项**：漏冒号、全半角逗号混用等已有覆盖，补齐快照。
- 验收：新增错误快照 ≥10 个；每条含可操作的中文修复建议。

### 7.6 机器可读语言规格
- `jishi --lang-spec --format json`：输出关键字表、运算符优先级、语句/表达式
  文法的 JSON 描述（版本号 + 内容哈希），供 agent 校验自己生成的代码。
- 验收：JSON 可被 JSON Schema 校验；文档站同源生成。

**M7 可演示成果**：一条命令 `python tools/ci.py` 全绿 +
`examples/14_语法糖.jsh` 演示全部新语法 + 评测集首批 10 题通过。

## 5. M8 AI 原生工具链（差异化核心，全行业空白）

目标：让任何 LLM 在 5 分钟内学会写基石、10 秒内定位并修复自己的错误。

### 8.1 语言卡（Language Card）
- `jishi --ai-card` 输出 ~3K token 的 Markdown 速查卡：
  语法全表 + 内建/标准库 API 签名 + 5 个惯用法示例 + 常见错误对照。
- 版本化：卡首行带 `{版本, 内容哈希}`，语言变更即更新，可作系统提示词直接粘贴。
- 验收：把语言卡贴进 3 个主流 LLM，评测集一次通过率 ≥60%（M7 前基线对比）。

### 8.2 llms.txt 输出
- 文档站生成器（M6b 基础上）追加 `site/llms.txt`（索引）与
  `site/llms-full.txt`（全文），遵循 llms.txt 社区规范；
- 让爬取文档站的 LLM 自动获得结构化语料。

### 8.3 结构化报错（自愈闭环的另一半）
- `jishi run x.jsh --json-errors`：
  `{"ok":false,"errors":[{"code":"E2002","line":3,"col":8,
    "message":"类型错误（…）","hint":"…","fix":{"line":3,"col":8,
    "old":"整数(","new":"小数("}}]}`
- `fix` 字段可选，优先覆盖：名字建议、关键字误写、标点归一。
- 验收：agent 循环（生成→执行→读 JSON→改码→再执行）在评测集上
  两次尝试内自愈率 ≥80%。

### 8.4 few-shot 示例库
- `examples/ai/`：20+ 个「任务描述 → 基石代码」精炼对，覆盖
  文本处理/列表统计/文件读写/类与异常/Python 桥接高频场景；
- 语言卡引用示例编号，形成「卡 + 例」组合提示。

### 8.5 官方系统提示词
- `docs/ai/system-prompt.md`：教 LLM「你是基石专家」的角色设定、
  语法要点、禁止事项（英文关键字、tab 缩进…），与语言卡配套。

### 8.6 基石评测集（JishiEval）
- `bench/ai-eval/`：50 个任务，每个含 `任务.md` + `标准答案.jsh` + `断言.json`
  （stdout/行为断言）；脚本一键跑「指定 LLM × 评测集」产出通过率报告；
- 作为语言演进的回归指标：**语法改动不得使主流模型一次通过率下降**。

**M8 可演示成果**：WorkBuddy 里用自然语言指挥 agent 写基石脚本并自动修复
（全程无人工改码）；评测集报告一份。

## 6. M9 安全执行与 MCP 集成（「被大模型调用」的落地形态）

目标：agent 一行配置即可把基石当工具用；执行结果确定、可结构化、有资源上限。

### 9.1 沙箱运行器
- `jishi run x.jsh --sandbox`：超时（默认 5s）、stdout 上限、
  禁文件写/禁网络/模块白名单（`导入` 白名单外报错）、递归深度上限；
- 树遍历执行器用 Python 资源机制实现；C VM 天然无 IO，是最强沙箱后端。

### 9.2 统一执行结果协议
- `{"ok":true,"value":…,"stdout":"…","duration_ms":…}` /
  `{"ok":false,"error":{…同 8.3…}}`；单文件 `jishi/protocol.py` 定义并文档化。

### 9.3 MCP Server（重点工作项）
- `jishi-mcp`（stdio 传输，Python 实现）：工具
  `run_script(script, sandbox_opts)` / `eval_expr(expr)` / `describe_language()`；
- 直接接入 WorkBuddy / 任意 MCP 宿主——**这是基石进入 agent 生态的入口**；
- 沙箱默认开；每次执行独立 VM 实例，无状态残留。

### 9.4 C VM 嵌入模式
- jsvm.dll/so 的 C ABI 稳定化 + 版本号；第三方宿主（Node/C#/Rust）可直嵌
  基石脚本引擎（比起子进程 Python 快一个数量级）。

**M9 可演示成果**：在 WorkBuddy 中通过 MCP 调用 `run_script` 跑基石脚本
（含一次故意报错 → agent 读 JSON 报错 → 自修复 → 成功）。

## 8. M11 性能与分发

- **C VM 热路径扩充**：benchmark 显示列表/字符串场景 C VM 反而慢于树遍历
  （每步 ctypes 回调）→ 把高频方法（追加…）下沉为 C 指令；
  结果（7 场景实测）：6 场景 ≥1.5x（最高 47x），列表 0.58x→**1.7x**；
  **字符串拼接是透明架构边界**——字符串是 HOST 句柄，C 侧无法直接操作
  Python str，每次拼接都回调 Python，而树遍历直接调 C 级 str.__add__，
  故该场景 C VM 无法超过树遍历（非待修缺陷）。
- **wheel 内带预编译 DLL/SO**（Windows/Linux/macOS 矩阵），
  `pip install jishi` 即含 C VM，无 gcc 也能跑满三执行器；
- 启动时间优化（stdlib 懒加载，可选）。

### 12.1 评测集扩到 50 题

## 8.6 M13 跨语言字节码分发（兑现 M9.4 遗留）✅

> 主线第三条纵深：扩大「被调用」的覆盖面。M9.4 只把 C ABI 就绪了，
> 字节码序列化仍由 Python 侧完成，Node/Rust 宿主尚不能真正跑基石。
>
> **现状（2026-09-05 已完成）**：13.1 序列化 ✅、13.2 Node ✅、13.3 Rust
> （最小可运行）✅、13.4 文档 ✅。**技术路线有调整**：13.2/13.3 从路线图
> 原文的「ffi 加载 jsvm.dll」改为「纯 JS/Rust 解释器消费 JSON 字节码」，
> 原因是 jsvm.dll 是宿主驱动架构（~40 语义回调），ffi 方案工作量巨大；
> JSON 字节码是纯数据，纯解释器更简洁且真零依赖（详见 docs/embed.md）。

### 13.1 字节码序列化格式
- 定义跨语言字节码中间格式：编译产物（consts / names / instrs / code 元数据 /
  kwargs 表）→ 一个平台无关的扁平二进制或 JSON 数组，附版本号 + 校验和；
- Python 侧产出该格式（`compiler` 新增 `dump_binary`），C 侧加载
  （`jsvm_load_module` 复用，或新增 `jsvm_load_binary`）。
- 验收：同一份字节码在 Python C 绑定与独立 C 宿主里执行结果一致。

### 13.2 Node.js 绑定
- `node/` 目录：Node 加载 jsvm.dll（ffi-napi 或 N-API），
  `run(code)` 直接跑基石字节码，无需子进程、无需 Python；

### 16.2 独立可执行发行包（核心工作项，设计决策 D22）

目标产物：

| 平台 | 文件名 |
|------|--------|
| Windows x64 | `jishi-0.0.1-windows-x64.zip` |
| Linux x64 | `jishi-0.0.1-linux-x64.tar.gz` |
| macOS arm64 | `jishi-0.0.1-macos-arm64.tar.gz`（x64 视 CI 能力再定） |

包内结构：

```
bin/jishi          # CLI 主程序（前端 + 三执行器 + 标准库全部打进可执行文件）
bin/jishi-mcp      # MCP Server（装完即可被 agent 宿主调用）
bin/jsvm.dll | libjsvm.so | libjsvm.dylib   # C VM，随包分发，用户无需 gcc
share/ai-card.md   # 离线语言卡（不依赖源码树）
share/system-prompt.md
share/logo.png     # 品牌资产（源 assets/基石_logo.png，见 16.6）
install.sh | install.ps1      # 安装脚本
uninstall.sh | uninstall.ps1  # 卸载脚本
README.md  声明（LICENSE）
```

构建：`tools/build_release.py`
- 用 PyInstaller 打包，`--onefile` 与 `--onedir` 二选一（D22，按冷启动实测定）；
- 必须显式带上 stdlib、AI 资源、C VM 动态库（否则运行时找不到）；
- 资源访问统一走 `importlib.resources`，**禁止用 `__file__` 硬拼路径**
  （打包后路径布局会变，这是 PyInstaller 最常见的坑）；
- 构建期依赖不进运行时：PyInstaller 只在打包时用，
  基石**运行时仍保持零第三方依赖**（需在 README 明示这一点）。

诚实边界（必须写进发布说明，不美化）：

- **体积**：单文件预计 30–60MB（内含 Python 运行时），远大于 Go/Rust 编写的
  语言；这是「前端用 Python 实现」这一既定技术选型的直接代价；
- **冷启动开销**：onefile 模式每次启动需解压到临时目录，冷启动慢于纯 Python；
  实测数字写进 README，若不可接受则改 onedir；
- **杀毒软件误报**：PyInstaller 产物误报常见，需同时提供 wheel / 源码两条
  替代途径，并**不承诺「绝对不报毒」**。

### 16.3 安装脚本与 PATH 集成（设计决策 D23）

- `install.ps1`（Windows）/ `install.sh`（Linux/macOS）；
- 默认装到**用户目录**（`~/.jishi`），仅 `--system` 才装系统级（避免权限问题）；
- 流程：解压 → 把 `bin` 加入 PATH（Windows 改用户环境变量；Unix 追加到
  shell rc 并提示 `source`）→ 自检 `jishi --version` → 打印下一步指引；
- `uninstall` 脚本：干净移除，**包含 PATH 还原**，不留残余；
- 新增 `jishi 医生` 子命令做环境自检：安装位置 / 版本 / C VM 是否加载成功 /
  终端编码 / MCP 可用性，异常直接给中文修复建议——延续「中文报错」一贯体验。

### 16.4 发布渠道与产物校验

## 12. 风险与应对

| 风险 | 应对 |
|------|------|
| LLM 英文语料优势短期不可逆 | 差异化押注执行侧（M9）与纠错闭环（M8.3），不硬拼生成 |
| 评测集被「刷分」心态污染 | 评测任务来自真实使用场景，随版本扩充不重置 |
| 评测接入外部 LLM 有成本/依赖 | 用 OpenAI 兼容接口可换底座；本地 mock 先跑通，再上真模型 |
| 沙箱被绕过（Python 桥接即逃逸） | 白名单模式默认关桥接；文档明示边界，绝不夸大安全性 |
| 跨语言绑定易腐（多语言 FFI） | 先把 C ABI 稳定为唯一契约，各语言绑定只做薄壳 |
| 远端包引入恶意代码 | 沙箱默认开 + 包来源白名单 + 下载即审计 |
| 指标自嗨（用预估数字充数） | 未度量就写「未度量」；通过率/自愈率必须有脚本可复现 |
| 打包后资源路径失效（stdlib/AI 卡/DLL 找不到） | 资源访问统一走 `importlib.resources`，禁 `__file__` 硬拼；每版必须在干净机器跑完整冒烟清单 |
| 杀毒软件误报 PyInstaller 产物 | 同时提供 wheel / 源码两条替代途径；发布说明明示，不承诺不误报 |
| 体积与冷启动拖累第一印象 | 实测数字写进 README 与发布说明，不美化；onedir/onefile 按实测切换 |
| 跨平台矩阵搭不全（本机只有 Windows） | 先打通 Windows + Linux（CI 容器）；macOS 能力不足则明确延后并记录 |
| 版本号混乱（pyproject 0.1.0 vs 发行 0.0.1） | 16.1 动工前先把版本号单一来源定死并全仓同步 |
| 维护带宽（一个人 + AI） | 每阶段只做可演示的最小闭环；对拍测试兜底回归 |
| 生态冷启动 | 绑定 MCP 生态冷启动：agent 用户不需要「学习」一门新语言 |
