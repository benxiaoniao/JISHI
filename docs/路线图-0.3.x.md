## 二、实测基线（2026-11-01 · 本机 · 两条命令可复跑）


### 2.1 语言本体：**4 危险 · 2 缺口 · 1 安全**

> 这是「**一段输入能不能把程序打爆**」的那类问题 —— 和沙箱、包管理器无关，是语言/标准库自己的属性。

| # | 类型 | 判定 | 实测证据 |
|---|---|---|---|
| 1 | **整数/浮点边界** | ✅ **安全** | 超 i128 给 `E2005`（中文、带位置）；除零给 `E2001`；`1e308*10`→`inf`、`-0.0` 正常。**没有静默回绕** |
| 2 | **正则回溯（ReDoS）** | 🔴 **危险** | `(a+)+$` 配「a×N + b」：20 个 a **0.14s** → 24 个 **1.02s** → 28 个 **>15s 没返回**。**每加 4 个 a 涨 10 倍 = 标准指数回溯** |
| 3 | **压缩炸弹** | 🟡 缺口 | 39 KB 的 zip 解出 **40 MB**，没有任何上限或提示（真实世界 1 GB 会直接吃光内存） |
| 4 | **解压路径穿越** | 🔴 **危险** | 条目 `../被穿越.txt` **写到了目标目录之外**（`压缩.解压` 不校验条目名） |
| 5 | **SQL 注入** | 🟡 缺口 | 结构化条件**按值匹配**（注入串返回 0 条）✅；但 `执行(库, SQL)` / `执行查询(库, SQL)` **没有参数化入口** ⇒ 用户自己拼字符串就中招 |
| 6 | **畸形字节码** | 🔴 **危险** | 给 4 份坏 JSON：校验和错、指令越界 → 中文报错 ✅；**`main` 越界、常量池清空 → Rust panic（rc=101）** |
| 7 | **递归深度** | 🔴 **危险** | **没有上限**：`返回 1 + f(n+1)` 能跑到 **300 万层**（12 秒实测到 **1500 万层**），既不报错也不崩 ⇒ 无限递归**静默吃内存**直到被系统杀掉 |

**四条危险的共同点**：不是「算错」，是**一段输入就能让程序卡死 / 崩掉 / 吃光内存**。
而且用户看到的现象最糟 —— 没输出、没报错、只能 Ctrl-C（或整机变卡）。

**两条缺口的共同点**：实现没错，但**没有引导用户走安全路径**（解压不限量、裸 SQL 无参数化）。

### 2.3 性能：vs CPython 几何平均 **0.91–0.95x**

两份等价实现、交替取样、单轮 ≥400ms、扣掉启动后取 min，两次独立跑：

| 场景 | 第一次 | 第二次 | |
|---|---:|---:|---|
| **递归斐波那契** | **0.30x** | **0.38x** | 🔴 慢 3 倍 |
| **函数调用密集** | **0.52x** | **0.37x** | 🔴 慢 2–3 倍 |
| **列表构建与遍历** | **0.73x** | **0.63x** | 🔴 慢 1.4–1.6 倍 |
| 文本切片 / 下标 / 字典写入 | 0.65–0.97x | 0.80–0.84x | 🟠 慢 |
| 整数循环 / 内建调用 / 浮点遍历 | 1.06–1.41x | 1.38x 上下 | ✅ 快 |
| **几何平均** | **0.95x** | **0.91x** | 🔴 总体不如 CPython |

**三个根因（指到行）**：① `call_frame` 每次递归进 `execute()`（`lib.rs:2946`）；
② `LIST_APPEND` 走 `get_attr("追加")` + `BoundMethod` 分配（`lib.rs:2569`）；
③ 文本下标/切片无字符索引（UTF-8 上按需扫描）。

### M160 · 解压安全：一个根因，两处修补（主菜 🥇）

**根因只有一个**：解压时把「zip 里的条目名」直接当路径拼上去，不校验。

| 位置 | 现在 | 改成 |
|---|---|---|
| `压缩.解压`（标准库） | `../` 条目写到目标外 | 逐条校验：拒绝绝对路径、`..` 段、驱动器号；**规范化后再比前缀** |
| `install_package_zip`（包安装） | 同上 | 同上（**共用一份校验函数**，别写两遍） |

再做两件配套：

- **解压前报总量**：`列出内容` 已是现成的 —— 解出体积超过「包体积 × 50 或 512 MB」就**先问一句**（脚本里给 `--是`），别静默解 1 GB；
- `--local-zip` 安装**提示「这个包没有校验和」**（现在静默装上）。

**做完是什么样**：恶意 zip 装不进来、解不开；报错直接说「第 3 个条目 `../../x` 越出了目标目录」。
**判据**：`probe_zip_slip.py` 变绿 + `audit_language.py` 第 4 条变绿 + 一条「炸弹包要提示」的用例。

> ✅ **M160 已完成（2026-11-01）**：三处修完，`audit_language.py` 的
> 第 3 条（压缩炸弹）与第 4 条（解压穿越）**已转绿**；判据 `tests/test_m160_zip_slip.py`（9 条）。
> 顺带发现并修掉一处**口径不一致**：Node 原来按「实际解出的字节数」算总量（炸弹要先解出来才判），
> Python / Rust 按「中央目录声明的大小」—— 现在三处统一读声明大小，且 Node 改成**先读目录再解数据**。

### M161 · 一段输入别把程序打爆（主菜 🥇）

三条一起做，因为它们**都是「资源没有上限」**：

| 问题 | 改法 | 判据 |
|---|---|---|
| **ReDoS**（正则指数回溯） | 回溯加**步数上限**（超了报「正则太复杂，请改写模式」），或换线性引擎 | 28 个 a 必须在 **1 秒内**给出结果或明确报错 |
| **递归无上限** | 加**调用深度上限**（默认 10 万层，可配置）：超了报「递归太深（第 100000 层），检查有没有漏掉的结束条件」 | 300 万层那条变绿 |
| **畸形字节码 panic** | `main` 越界 / 常量池越界改成**中文报错**（`E2xxx`），不许 `panic` | 4 份坏 JSON 全部中文报错、rc=1 |

⚠️ **递归深度与 M163 的调用扁平化在同一片代码里** —— 先做 M161（加上限），
M163 再改调用协议时，这个上限就是它的天然护栏（改写期间不会一崩就是栈溢出）。

**做完是什么样**：写错的递归、恶意正则、坏字节码，**都只得到一句中文报错**，不卡死、不崩、不吃光内存。
**判据**：`audit_language.py` 的 2/6/7 三条全绿。

> ✅ **M161 已完成（2026-11-01）**：四条全修 —— 正则 2000 万步上限（28 个 a 从 >15s
> 变成 0.85s 报错）· Rust 补上 1000 层递归上限（能跑到 1500 万层的洞）· 畸形字节码从
> **panic** 改成中文报错（`main` 越界 / 常量池清空 / 指令流截断）· Node 网络改
> **Worker + Atomics**（`EBUSY` 根除）。顺带发现「指令流截断会静默跑完」（比 panic 更隐蔽）。
> 判据 `tests/test_m161_input_hardening.py`（10 条）。`audit_language.py` 现在
> **✅6 · 🟡1 · 🔴0**（只剩 SQL 那条「引导缺口」）。详见 CHANGELOG。

> ✅ **M162 已完成（2026-11-01）**：`tools/bench_vs_python.py` 能出**结构化快照**
> （`bench/baseline_cpython.json`，带机器指纹/时间/启动成本/逐场景），判据
> `tests/test_m162_perf_baseline.py`（3 条，进串行节）。
> 🔴 **顺带修掉一个方法学上的坑**：第一版每轮都按当时负载**动态算「重复几次」**，
> 于是两次跑的根本不是同一道题 —— 同一台机器同一份代码能读出 0.94/0.95/1.06（差 11%）。
> 改成「**从基线读固定重复次数**」后是 1.07/1.06（<1%）。⇒ 判据里的 `--用基线` 不是可选装饰。

### M163 · 函数调用扁平化（主菜 🥇，最大靶子）

`call_frame` 不再递归 `execute()`，改成「压一帧、主循环继续」（CPython 的 CALL 做法）。
**目标**：递归斐波那契 0.30x → ≥1.2x；函数调用密集 0.37x → ≥1.5x。

⚠️ **风险**：牵动异常栈展开 / 调试器断点 / `finally`。判据不只看快：
五引擎对拍 0 不一致 + **调试器会话记录与改写前逐字相同**。

> ⚠️ **M163 部分完成（2026-11-01）**：函数调用已扁平化（同一循环换帧，不再返回重进），
> 实参绑定零分配。结果：**几何 1.06 → 1.10x**，慢场景 **6 → 5**，递归斐波那契 **0.49 → 0.65x**。
>
> 🔴 **但目标没达成，而且我猜错了三次**（分配 2.6% / 生命周期往返 10.8% / 每步写 ip 1.4%）。
> 决定性证据：**0 参数调用也要 398 ns**（每多一个参数只 +50 ns）⇒ 固定开销在
> **「指令分派 + 帧管理」本身**，一次调用约等于 22 条指令的代价（纯循环每条约 20 ns）。
>
> ⇒ 剩下的 3 倍差距要单开一站：**帧字段拆平行数组（SoA）+ `Val` 从 32 字节瘦身
> + 指令分派表优化**。这条路比「改一处」重得多，放进 M165 之后的新站（暂记 M165b）。

### M164 · 容器与文本快路径（配菜 ×2）

`LIST_APPEND` 直通（不再 `get_attr("追加")` + `BoundMethod`）；文本下标/切片加字符索引（或 ASCII 快路径）。
**目标**：列表构建 0.63x → ≥1.3x；文本下标 0.66x → ≥1.2x。

> ✅ **M164 完成（2026-11-01）**：三处热路径 —— `LIST_APPEND` 直通 push（+8.6%）、
> 文本切片不再先 `Vec<char>` 全量拆（+9.8%）、文本下标非负不数一遍（持平）。
>
> 🔴 **方法学教训（重要）**：这台机器的固定负载波动就有 **15.5%**，基准写进文件的倍数会被
> 放大到 +38%（真实 +8.6%）。⇒ **判断一处改动值不值，要编两份二进制同刻交替跑**
> （`build/jishi-old.exe` vs `jishi-new.exe` 那套），别只看基准表。这条已记进 CHANGELOG。

### M165 · 数字与字典热路径（配菜）

> ⚠️ **M165 部分完成（2026-11-02）**：目标里**算术拿到了、字典没拿到**。
>
> **① `//` `%` 撞出两个真 bug（比性能值钱）**
> Rust 宿主原来一律转 f64 算：`-7 % 3` 给 `-1`（Python 是 2）、`9007199254740993 // 1`
> 丢精度、`-7.5 % 2` 连类型都错。**只有 Rust 错** —— Python / Node / C 都对。
> 现在整数走整数路径（`floor_div` / `floor_mod`，余数符号跟除数），有浮点参与才转 f64。
> Node 那边同时修了「负数零」：`0 * -1`、`-6 % 3` 会印成 `-0.0`，Python 是 `0`。
>
> **② 为什么活了这么久**：`tests/cases/01_算术.jsh` 只有 `7 // 2`、`7 % 2` —— 全正数。
> 已补负数 / 浮点 / 2^53 以上 / 负零共 16 行，并加了**源码级护栏**（删了语料就红）。
>
> **③ 性能：算术 +12.8%（0.90 → 1.06x，跨过 1.0）；字典 +1.1%（噪声内）**
> 字典把 `get`+`insert`（算两遍哈希）换成 `entry`，但实测被**内存布局**盖过去：
> 写新键 394 ns vs 写入同一键 168 ns（差 226 ns），文本键比整数键再贵 91 ns
> （每次读写克隆一个 `String`）。20 万条的字典 = 16 MB，全在 cache 外。
>
> ⇒ **字典要真提速，得改数据结构**：哈希只存一遍（或索引表用 u32）、
> 键共享引用（`Rc<str>` 而不是每次 clone）、entries 紧凑。**并入 M165b**。
>
> **④ 「小整数缓存」这条规划不成立**：那是 CPython 的招（`PyObject` 装箱需要它）；
> 基石的 `Val::Int(i64)` 是**值类型**，没有堆分配可省。不做，不是没来得及。

### M165b · 值表示与帧管理（性能补课）

> ✅ **M165b 完成了一半（2026-11-02）**：值层做完，帧层没动。
>
> **① `Val::Str` 从 `String` 换成 `Rc<str>`（这一站的主菜）**
> 原来 `Val::clone()` 对字符串**深拷贝整串**，而 VM 每读一次字符串变量、每次压栈、
> 每次传参都在 clone。实测：读整数 124 ns、读 5 字串 **387 ns**、读 1000 字串 **655 ns**
> —— 那 263 ns 的固定差就是一次 malloc（CPython 这里是引用计数 +1）。
>
> 同刻 A/B：**字符串拼接 +167%** · 读长串 +44% · 文本比较 +33% · 内建调用 +27% ·
> 文本列表遍历 +27% · 读短串 +26% · **字典文本键 +20%/+21%**。
> 整体几何 **0.95x → 1.01x**，慢场景 **11 → 7**。判据 `tests/test_m165b_string_rc.py`（5 条）。
>
> **② `Val` 没能从 32 降到 24** —— `Int(i128)` 的**对齐是 16**，enum 对齐跟着是 16，
> 24 不是 16 的倍数 ⇒ 编译器补到 32。两个 24 字节变体（`Builtin` 的胖指针、
> `ExcType(String)`）已清掉，但省下的字节被对齐吃掉，**没换来空间**。
> ⇒ 要真降到 24，得把 `Int` 改成 `i64` + 溢出走 `Rc<i128>`（见 M165c）。
>
> **③ 「遍历文本」试了活迭代器，无效，已回退**：+1.7% / −4.5%。根因是
> **每个字符都要返回一个 `Val::Str`（一次分配）**，迭代器怎么写都省不下来。
> 真要解决要 `Val` 支持内联短字符串（SSO）。
>
> **还没做（M165c 候选）**：
> - **帧字段 SoA**：`Frame` 现在 ~270 字节、7 个 `Vec`，每次 push/pop 都要搬；
>   M163 定位的「一次调用 398ns ≈ 22 条指令」还没动（M165b 后仍是 407ns）；
> - **`Val` 真瘦身**：`Int(i64)` + `Rc<i128>` 溢出分支 ⇒ Val 32 → 24；
> - **指令分派**：每条指令约 20 ns（CPython 5~10 ns）；
> - **字典紧凑布局**（M165 遗留）：哈希只存一遍 / 索引 u32 / entries 紧凑。

### M165c · 函数值 `Rc<Func>`（性能补课第二站）

> ✅ **M165c 完成一半（2026-11-02）**：调用开销砍掉一半，`Val` 瘦身没做。
>
> **① `Val::Func` / `BoundMethod::User.func`：`Func` 值 → `Rc<Func>`**
> `push_func_frame(func: Func, …)` 是按值收的，而 `Func` 是 88 字节、里面有
> `name: String` + `cells: Vec` + `defaults: Vec` —— **clone 一次三次 malloc**，
> 而每调用一次函数就要 clone 一次（`实例.方法()` 也是）。
>
> 同刻 A/B：**0 参数调用 +57%（461 → 294 ns）** · 1 参数 +48% · 递归斐波那契 +23%。
> 整体几何 **1.01x → 1.09x**，慢场景 **7 → 5**，「函数调用密集」掉出名单。
> 判据 `tests/test_m165c_fn_rc.py`（4 条，含闭包独立性与默认参数两条行为护栏）。
>
> **② `Val` 瘦身没做**：要降到 24 得把 `Int(i128)` 改 `i64` + 溢出走 `Rc<i128>`
> （`i128` 对齐 16 ⇒ 24 不是 16 的倍数）。波及全部算术语义 + 序列化 + C VM 对拍，
> **留到 0.4.0 与 JIT 一起规划**（JIT 会改变值表示的前提）。
>
> **③ 帧 SoA 没做**：一次调用 294 ns 里，帧管理仍占 ~190 ns（约 18 条指令）。
> 但实测「Frame 瘦身」（280→232 字节）预计只值几 ns —— memcpy 不是瓶颈，
> 所以**没有盲改**。真要再降，方向是「把热字段缓存在局部变量里」而不是拆结构。
>
> **剩下的慢场景（5 个）与它们各自的门槛**：
> 递归 0.49（要 JIT/内联缓存）· 字典写入 0.93（要紧凑布局）· 内建 0.90（内建实现本身）·
> 文本下标 0.96（字符定位是 O(n)）· 遍历文本 0.80（每个字符一个堆对象，要 SSO）。
> 五条**没有一条是「再改一处」能解决的** ⇒ 0.3.0 的性能就到这儿，如实记。

⚠️ **难点不在 DOM API，在同步/异步的缝合**。基石的 VM 是同步的，浏览器事件是异步的

> **一次事件 = 一次完整执行。**
> 您写 `函数 点击_提交()：…`，事件来的时候 wasm 侧**重新进入 VM** 跑这个函数 ——

| 方向 | 接口 |

| 请求 | `浏览器.请求(地址, 处理函数)` —— **完成时回调另一个基石函数**（异步不硬塞进同步） |

**带方法的宿主对象**（`耗时()` / `停()`）并且要支持**上下文协议**
（`进入` / `退出`）。而三个宿主的上下文查找只认「Jishi 实例」与「内建容器」，
标准库直接返的宿主对象走不通 —— **这是对象模型的缺口，不是补一个函数**。
当初判断「改写成基石库模块后天然是 Jishi 实例，缺口结构性消失」，但基石库层
要求「零宿主原语」，而计时必须调 `perf_counter`（宿主原语）⇒ 那条路走不通。

**它怎么被藏住的**：`examples/projects/排序跑分/排序.jsh` 用了它，而这条语料
**在 `check_engines` 的豁免表里**，理由是「打印墙上时间」。⇒ 三个宿主上它
**根本跑不通**这件事，对拍工具从来没报过。
（2026-11-02 复核豁免时发现，已把理由改准确，并拆掉一条按文件名的隐式豁免后门。）

**修它的两条路**（都要动宿主对象模型，估 1–2 天）：
1. **给标准库对象一个「方法分派」口子**：宿主返回的 `Val` 携带一张方法表，
   `get_attr` / 上下文协议都认它 —— 一次改动三个宿主都能受益（将来的
   `数据库.连接` 这类「返回对象」的 API 也走它）；
2. **退一步**：把 `计时` 改成**两个函数**（`开始计时()` 返回编号、`计时结束(编号)`），
   不返回对象 —— 便宜，但语言卡要改、示例要改，且「上下文协议」的便利没了。

📌 **判据**：修完必须让 `examples/projects/排序跑分/排序.jsh` 在三个宿主上**跑得起来**
（输出仍然豁免，理由是墙上时间；但「跑不起来」与「数字不同」是两件事）。

### 8.1 性能的**终点**：与原生 Rust 对齐（用户 2026-11-01 定）

> **「vs CPython」只是第一级台阶，不是终点。** 终点是**和原生 Rust 一个量级**。

台阶要一级一级上，每级的判据不一样：

| 台阶 | 判据 | 现在（**2026-11-08 实测，0.3.2**） |
|---|---|---|
| ① 不输 CPython | 17 场景全 ≥1.0x | **16/17** —— 只剩递归 **0.61x** |
| ② 稳定领先 CPython | 几何 ≥1.5x（0.3.0 收口线） | ✅ **1.75x**（M180 带 JIT；关掉 JIT 是 1.66x） |
| ③ 接近原生 | 同算法 vs 原生 Rust，**差距 <3 倍** | ❌ 实测 **7.8x**（M179 新造的 `tools/bench_vs_rust.py`，8 对等价程序） |
| ④ 对齐原生 | 差距 <1.5 倍 | ❌ 远（③ 先过再说） |

📌 **③④ 的地位变了**：2026-11-07 之前它们只能算「方向」，因为**没有尺子**；
现在尺子有了（`bench_vs_rust.py`），所以升级成**可验证的目标** ——
但 **0.3.3 只追到「浮点」这一步**（M183），**对象 / 函数调用 / 跨帧内联仍是 0.4.0 的量级**（见 §十一）。

**底层加速的三条候选路线**（用户提到的自举编译器、LLVM 都在这张表里）：

| 路线 | 解决什么 | 对**运行时速度**的收益 | 我的判断 |
|---|---|---|---|
| **内联缓存 + 单态特化** | 每次 `GET_ATTR` / `GET_ITEM` 都重新判断「这是不是列表」 | **最大**（解释器里最热的那几跳直接省掉） | **先做这个**：不动工具链、不改语义、能拿 M163–M165 的成果接着走 |
| **JIT**（热点字节码 → 机器码） | 解释循环本身的开销（每条约 5–20ns） | 大，但要处理**动态类型推断**与去优化 | 第二顺位；先有 ③ 的度量再谈 |
| **AOT 到 LLVM**（把字节码编成 .o） | 同样解决循环开销，且离线做 | 大，但**动态类型是硬伤**（不特化就没收益，特化就要类型系统让步） | 与 JIT 二选一，别两个都上 |
| **自举编译器**（用基石写基石） | 「不依赖别的语言」+ 编译速度 + 可信根 | **几乎为零**（它编出来的还是同一种字节码） | 它是**独立路标**，别拿它当性能方案 |

📌 **一句实话**：动态语言要「对齐原生 Rust」，真正的墙不是解释器写得快不快，
而是**每个值都得装箱、每个运算符都得判类型**。所以顺序必须是
「**先特化、再 JIT**」—— 反过来的话，JIT 编出来的也是「一堆类型判断」的机器码。

⚠️ **③④ 需要一把新尺子**（vs 原生 Rust 的等价程序），还没写。
在那把尺子出现之前，③④ 只能算方向，不算目标 —— 本项目的老规矩：**没度量就不算数**。

## 9.0 为什么是这两件（用户 2026-11-04 提的）

两条都是**真实项目撞出来的**，不是想当然：

| # | 用户的意思 | 现在的实情 |
|---|---|---|
| **打包** | 「我们能不能也有打包能力（现在是依赖 Inno Setup 做的）」 | Windows 安装包靠 **Inno Setup** 编 `tools/installer.iss`；Linux/mac 是 `install.sh` + tar.gz。**语言侧只有 `压缩.打包`（一个 zip）**。用户要给自己写的程序打包时，**一个工具都没有**，只能手写 `.iss` |

📌 这两件其实是同一件事的两半：**「做成一个能装、能双击打开的桌面程序」**。
所以 0.3.1 的验收就该是**一个真程序**：写完 → `jishi 打包` → 干净机器装 → 双击 → 有窗口能用。

### 现在到底谁在干什么（先认账）

| 环节 | 谁做的 | 我们能不能接手 |
|---|---|---|
| 打 zip / tar.gz | `压缩.打包` + `build_release.py` | ✅ 已经是我们的 |
| 版本清单 + SHA256 | `tools/build_version_manifest.py` | ✅ 已经是我们的 |

> 🔑 **关键发现**：`jishi 卸载 --自身` 和 `jishi 升级` **早就实现了**（M110）。
> 也就是说 Inno 真正不可替代的只剩「**把一个 exe 和一堆文件塞进一个双击能跑的东西里**」。
> 那块我们用**自解压 stub** 接掉，剩下的全是现成的。

### 两层设计（说清哪部分不是基石写的）

| 层 | 用什么写 | 为什么 |
|---|---|---|
| **清单 / 布局 / 版本 / 校验 / 安装脚本** | **基石**（`打包` 模块） | 这些是「事实与规则」，正该是语言能力 |
| **自解压 stub**（`jishi-pack-stub.exe`，几十 KB） | **Rust**（`rust/src/packstub.rs`，独立 bin） | ⚠️ **必须承认**：安装器要能脱离基石运行（用户还没装基石），所以它只能是一个静态原生程序。这跟 `jishi.exe` 本身是同一类东西 —— **引擎级**，不是语言级 |

stub 干的四件事（就这四件，别扩）：
1. 读**追加在自己末尾**的 zip（`argv[0]` 尾部找魔数 + 长度）；
2. 解到 `--目标 目录`（默认 `%LOCALAPPDATA%\Programs\<名字>`），**默认不需要管理员**；
3. 写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\<名字>`，
   `UninstallString` **指向程序自己**：`"<目录>\jishi.exe" 卸载 --自身 --是`；
4. 加 PATH（HKCU\Environment）、建开始菜单快捷方式（`.lnk` 直接写二进制格式）。

### 产物矩阵

| 目标 | 产物 | 说明 |
|---|---|---|
| Windows | `名字-版本-setup.exe` | stub + zip：双击装、`/S` 静默装、`/D=目录` 换目录 |
| Windows | `名字-版本-便携.zip` | 解压即用（现在也有，保持） |
| macOS | `名字.app/` + `名字-版本-macos-<arch>.tar.gz` | **`.app` 就是目录**：`Contents/MacOS/<可执行>` + `Info.plist` + 图标 —— 我们生成得起 |
| Linux | `名字-版本-linux-x64.tar.gz` + `install.sh` | `install.sh` 由**基石生成**（幂等：装/升级/卸载三段） |

### 判据（都不是「看起来对」）

1. `test_打包两次字节相同` —— 可复现（沿用 M168 那条规矩：**落盘不带时间戳**）；
2. `test_setup里的zip能解出来` —— 不需要装 Windows：读尾部 → 解 → 文件清单 + sha256 与清单一致；
3. `test_装完能跑_卸载干净`（Windows CI）：静默装到临时目录 → `jishi --version` → 卸载 → **注册表项 / PATH 条目 / 目录**三样都不留；
4. `test_升级保留用户数据` —— 升级不碰 `~/.jishi/packages` 与用户自己的文件。

### 明确不做（这一版）

- ❌ **代码签名 / macOS 公证**：那是买证书 + 走 Apple 流程，**不是语言能力**（我们只保证「有签名位」：`打包.清单` 留 `签名` 字段，给外部工具填）。
- ❌ **MSI / deb / rpm**：优先级低于「自己的 setup.exe」；真要了再按同一个 stub 思路接。
- ❌ **图形化安装向导**：stub 先做**静默 + 一个进度条**（控制台）。向导 UI 等 C 线的窗口能力落定再做 —— 那时安装器自己就是一个基石程序。

## 9.4 C 线：窗口（M173）

### 两条路，先摆清楚

| 方案 | 做法 | 像不像桌面程序 | 成本 | 三平台 |
|---|---|---|---|---|
| **① 应用窗口**（推荐先做） | 起本地服务 / 读本地文件 → 用系统浏览器的 **app 模式**开窗（`msedge --app=…` / `chrome --app=…` / mac `open -na`） | 8 成：**没有地址栏**、有独立任务栏图标、可固定 | **小**（~300 行，零新依赖） | 依赖装没装 Chrome/Edge；没有就退回默认浏览器标签页 |
| **② 原生窗口**（0.4.0） | `wry`（Rust）：Windows WebView2 / macOS WKWebView / Linux WebKitGTK | 10 成：真窗口 + 菜单 + 托盘 + 文件对话框 + 拖放 | **大**：新依赖树、Linux 要 `libwebkit2gtk`、CI 要装系统库、还要新 ABI | 三平台差异最大的一块 |

**用户 2026-11-04 拍板：两个都要，分两步** —— 先把「能开窗」做出来，同一版里再换成真窗口。

⚠️ 这么排的前提是**两代共用一套东西**，否则第二步等于重做：

```
          ┌──────────── 页面（html 构件拼的）────────────┐
          │  按钮/表格/输入框 —— 都是 M166 的构件        │
          ├──────────── wasm 引擎（jishi_wasm.wasm）─────┤
          │  程序逻辑；事件 = 一次完整执行（M167 的模型）│
          └──────────────────────────────────────────────┘
                  ↑ 页面 + 引擎 完全不变，只换"外壳"
   外壳 v1：系统浏览器的 app 模式（无地址栏）
   外壳 v2：wry 原生窗口（WebView2 / WKWebView / WebKitGTK）
```

⇒ v1 写完的页面与逻辑**一行不改**就能跑进 v2。这也是为什么第二步值得做 ——
不是推倒重来，是**换个壳**。

### v1 的接口（就 5 个，别扩）

| 函数 | 干什么 | 备注 |
|---|---|---|
| `窗口.打开(选项)` | 开一个应用窗口：`{"标题", "宽", "高", "页面" 或 "服务"}` | 返回句柄；同一程序再开一个 = 复用（单实例） |
| `窗口.关闭(句柄)` | 关掉 | |
| `窗口.等(句柄)` | **阻塞到窗口关掉** | 没有它，脚本跑完就退、窗口一闪没了 |
| `窗口.在运行(句柄)` | 查活着没 | 轮询用 |
| `窗口.全部关闭()` | 收尾 | `等` 之前/之后都安全 |

📌 **平台差异如实写在卡里**：app 模式**改不了窗口标题**（那是浏览器的）、没有原生菜单、
不能拖文件进窗口 —— 这三条正是 ② 要补的。

### 验收：把「计算器」写成示例

`examples/desktop/计算器.jsh` + `计算器.html`：页面用 `html` 构件拼，逻辑跑在 wasm 引擎里
（M167 的 `浏览器` 模块），`jishi 计算器.jsh` → 出窗口 → 点 `1 + 2 =` 显示 `3` → 关窗进程退出。

这条判据**一箭三雕**：验 `窗口`、验 `浏览器`（真事件循环）、验 `打包`（它能被打成 setup.exe）。

### v2：原生窗口（M174–M175）—— 换壳，不重做

| 事 | 具体 | 备注 |
|---|---|---|
| **窗口外壳** | `wry` + `tao`：Windows 走 **WebView2**、macOS 走 **WKWebView**、Linux 走 **WebKitGTK** | 新增依赖树，锁版本 |
| **ABI 3** | `jishi_native(操作, 参数) → i32`：wasm 侧要「改标题 / 关窗口」时调宿主 | 现有 ABI 2 只管 DOM 与事件；**新的这一路只走"宿主能力"**，别混进去。⚠️ 原计划是 `→ JSON`（带回值），实际做成**单向** —— wasm 执行是同步的、IPC 天生异步，要回值得把执行模型改成异步续体，而需要的两条命令恰好都是单向的（见 `docs/设计决策.md` D104 第四节） |
| **`窗口` 模块双实现** | 宿主（Rust）：真的开窗；wasm：转发成 ABI 3 | 命令行 / Node 上调 `窗口.X` ⇒ **明确报错**（"要窗口请用 `jishi 应用.jsh --窗口`"） |
| **桌面集成** | 文件对话框（打开/保存）、菜单、托盘、拖放文件进窗口、单实例唤醒、任务栏进度 | 分期：M174 = 窗口+对话框+标题；M175 = 菜单/托盘/拖放/单实例 |

**平台代价（提前记账）**：

| 平台 | 代价 | 处理 |

## 10.0 为什么是这三件（用户 2026-11-06 拍板）

## 10.1 开工前必须知道的底细（都是今天核过的）

### 10.1.1 打包：能出四类产物，但包里没有运行时

`打包` 现在的选项只有五个字段（`rust/src/stdlib/pack.rs` 的 `选项`）：
`名字` / `版本` / `平台` / `入口` / `基础`。

**没有「要不要带运行时」这一维。** 所以 `jishi 打包 examples/desktop` 打出来的包里
就是 `计算器.jsh` / `计算器.html` / `清单.json` 三个文件 —— 实测过，见 CHANGELOG。

⚠️ `清单.json` 的**文本是契约**（Python / Rust / Node 三份实现逐字节对拍）。
加字段 = 三份一起改，一处漏了就红。

### 10.1.2 窗口：**脚本层其实已经是多句柄了**，墙在宿主

这一点很关键，决定了 M178 比想象中小：

- `rust/src/stdlib/window.rs` 里已经有 `表() -> Mutex<Vec<Option<记录>>>`，
  **句柄 = 下标 + 1**，`打开` 返回 `i128` 句柄，`关闭(句柄)` / `等(句柄)` / `收尾(句柄)`
  全都按句柄操作；
- 每个句柄一个 `记录`，各自带着自己的 `网址` / `目录` / 小服务 ——
  服务是按**页面目录**共享的（同目录只起一个），这层也已经是多窗口就绪的。

**真正的墙只有一处**：`rust/src/native_window.rs` 的

```rust
static 全: RefCell<Option<全局>> = RefCell::new(None);   // 一个进程一个
```

以及它里面那句「一个程序只能有一个原生窗口（多窗口还没做）」。

底层能力是够的：`tao` 的**一个 `EventLoop` 可以建多个 `Window`**
（`WindowBuilder::build(&event_loop)` 可以重复调），`wry` 每个窗口一个 `WebView`。
所以「单事件循环 + 多窗口」这条路线成立 —— 不需要多线程、不需要多进程。

⚠️ 但 `等()` 的语义要重新定（见 10.2 M178），这不是纯技术问题。

### 10.1.3 性能：几何 1.39x，欠 0.11

17 场景里 6 个慢于 CPython，最硬的三个：

| 场景 | 现在 | 卡在哪 |
|---|---|---|
| 递归 | **0.49x** | 一次调用 ≈ 22 条指令的固定开销（指令分派 + 帧管理） |
| 字典写入 | 0.93x | 要紧凑布局（不是 JIT 能救的） |
| 内建函数 | 0.90x | 内建实现本身 |

既有论证（本文 §8.1）已经定了顺序：**先特化、再 JIT** ——
反过来 JIT 编出来的也是「一堆类型判断」的机器码。

⚠️ **「vs 原生 Rust」那把尺子还不存在**。没有它，「JIT 值不值」就只能靠感觉。

### 10.1.4 依赖账（这次会变）

现在 9 个随发行版走的 crate（README「外部依赖（全部清单）」）。

~~**JIT 会带来第 10 个**，除非手写后端~~ → **实测选了手写**（M180）：

### M177 · 打包自带运行时（主菜 🥇）—— ✅ **2026-11-07 完成**

**目标（已达成）**：`jishi 打包 examples/desktop --自带运行时` → 装到空目录 → 双击 →
有窗口能用。真机验过：`页面到了` + `wasm 引擎起来了`。

**实际做出来的**（与下面原规划的差异，如实记）：

- ✅ 包内 `bin/` + `app/` 两层、`运行时.json`、缺素材当场报错 —— 按原计划；
- ✅ **没注册 `.jsh` 关联**（原计划里是待拍板的第二件，最后决定默认不做）：
  全局副作用，装两个程序会互相覆盖；快捷方式带参数已经够用。
- ➕ **额外修了一个真缺陷**：示例的页面路径写死仓库相对路径，装到别处必然找不到。
  `窗口.打开` 的解析加了「相对脚本目录」兜底（**只 Rust 宿主**，Python/Node 没这场景）。
- ⏳ **没做**：图形化向导、共享运行时、跨平台产物各自的引擎裁剪（都在 10.5）。

**原规划（留作对照）**：

要做四件：

1. **收引擎**：`std::env::current_exe()` 拿到当前 `jishi.exe`，
   `找引擎()`（`window.rs` 已有，现在只找 wasm 两件）扩成找**三件**：
   `jishi-wasm.js` / `jishi_wasm.wasm` / `WebView2Loader.dll`。
   少一件就**当场报错**，不许出包 —— 「白窗口、零报错」的坑不能再踩一次。
2. **包内布局**：
   ```
   bin/jishi.exe            ← 运行时（跟着走）
   bin/jishi-wasm.js        ← 引擎素材

   app/计算器.jsh            ← 用户文件，原样

   ```
3. **装完能双击**：`setup.exe` 装完在开始菜单（可选：桌面）建快捷方式，
   目标 = `<安装目录>/bin/jishi.exe`，参数 = `"<安装目录>/app/计算器.jsh"`，

### M178 · 多窗口（主菜 🥇）—— ✅ **2026-11-07 完成**

**目标（已达成）**：一个进程开三个窗口，各有标题、各有菜单，关掉中间那个不影响另外两个。
真机验过：三窗各自改标题（`GetWindowTextW` 问回来）· 点 A 的菜单**只到 A 的页面** ·
关中间那个另两个照样收事件 · 页面里的 `关闭()` 只关自己 · `等` 真的等所有窗口。

**实际做出来的**（与下面原规划的差异，如实记）：

- ✅ `全` → 按窗口号索引的四张表（窗口 / WebView / 就绪 / 待发），事件带号 —— 按计划；
- ✅ 菜单每窗口一套、托盘仍进程级 —— 按计划；
- ❌ **没做 ABI 3 → 4，也没注入 `__jishiWinId` 让它回传**：`with_ipc_handler` 本来就是
  每窗口一个闭包，宿主当场就知道消息来自哪个 WebView。让页面自报一遍是把已知信息
  绕一圈，还多两种失败模式。**shim 与 wasm 一行没改**。
- ➕ 顺带定死两个「用血换的」顺序：`muda::Menu::drop` 必须在窗口销毁**之后**
  （否则 `DrawMenuBar` 打在正在销毁的窗口上 → `0xC0000409`）；判据点菜单要允许重投。
- ⚠️ macOS 菜单栏归应用（`init_for_nsapp`），多窗口时最后设的那套生效 —— 系统行为，
  没真机证据。

**原规划（留作对照）**：

技术路线（单事件循环 + 多窗口，**不开线程**）：

| 改哪 | 怎么改 |
|---|---|
| `native_window.rs` 的 `全` | `Option<全局>` → `HashMap<u64, 全局>`，键就是窗口 id |
| `事件` 枚举 | 每条都带 `id`（`关窗(id)` / `页面(id, 事件名, 参数)` / `菜单(id, 动作)` …） |
| `派发` | 按 id 找那一份 `网`（每个窗口自己的 `WebView` 才能真正隔离事件） |
| `等` | 见下 |
| 菜单 | 每窗口一套 `muda::Menu`（本来就支持） |
| 托盘 | **全局一个**（系统托盘本来就没有「每窗口一个」的概念） |
| 单实例 | 不变（进程级） |

🔴 **`等()` 的语义必须定死，这是这一站唯一的设计决策**：

一个进程只有一个 `EventLoop`，`run_return` 跑起来之后，**所有窗口一起活着**。
所以「等某个窗口关掉就返回」做不到 —— 返回了循环就停，其它窗口会**假死**
（画面还在、点了没反应），那比报错还糟。

定成：

```
窗口.等(句柄)   →  跑到「最后一个窗口关闭」才返回（不管传的是哪个句柄）
窗口.等()       →  同上（0.3.2 新允许无参）
```

⚠️ 这是**已知的不完美**：`等(窗A)` 在 A 关了、B 还开着时不会返回。
文档里必须写清一句「**`等` 是等所有窗口**」，否则用户会写出「关了 A 之后
后面的代码为什么不跑」的 bug。

🔴 **页面里的 `窗口.关闭()` 要能关「自己」**：现在 ABI 3 的 `关闭` 是无参命令，
宿主只知道「有个窗口要关」。多窗口后必须知道是哪一个 —— 做法是宿主在页面初始化时
注入 `window.__jishiWinId = <id>`，shim 回传时带上。**ABI 要动（3 → 4）**，
但仍是**单向**（页面 → 宿主），消息还是 JSON。

**判据**：

- 开三个窗口 → 三个句柄不同 → 分别设标题（`GetWindowTextW` 读回来各不相同）；
- 关中间那个 → 另外两个还能收事件（真机：点菜单，页面函数真的跑了）；
- `全部关闭()` → 循环退出、进程正常结束；
- 事件**不串窗**：A 窗口的菜单点击只到 A 的页面（这条最容易写成「看起来对」）；
- 单窗口的老用法**一行不改**照样跑（`test_m173` / `test_m174` / `test_m175` 全绿）。

### M179 · 单态特化（性能第一段）—— ✅ **2026-11-07 完成**

**目标（已达成）**：几何 ≥1.5x，同时**语义逐字节不变**（五引擎对拍）。

**实际做出来的**（与下面原规划的差异，如实记）：

- 🔴 **路线图的 1.39x 是旧口径**：开工时用固定规模量 M178 的二进制是 **1.59x** ——
  「≥1.5x」这个数字目标**开工前就达到了**。所以这一站改成「先量再改，只留赢的」。
- ✅ 三处改动：单字符 `Val` 缓存（文本下标 179→103 ns）· `CALL` 实参复用缓冲
  （函数调用 266→224 ns）· 无命名参数时不再多拷一份（内建调用 146→89 ns）。
  A/B 同口径中位：**1.59 → 1.63x**。
- ❌ **`GET_ATTR` 的内联缓存没做**：`甲.追加(x)` 早被编译器特判成 `LIST_APPEND`，
  不走 `GET_ATTR` ⇒ 对基准几乎无影响，而在几十纳秒的操作上加缓存表容易净亏。
- ❌ 字典换快哈希、`CALL_METHOD` 新指令：都记进 D108「没做的」，各有明确理由。
- ➕ **配菜「vs 原生 Rust」尺子**（`tools/bench_vs_rust.py`，8 对等价程序）：
  本机几何 **7.8x**。这是 M180 判「JIT 值不值」的标尺。
- 🔴 顺带确认一条硬规矩：**跨版本比较必须固定规模**（`--用基线`）+ 3 轮取中位。
  动态标定让同一二进制跑出过 1.54 / 1.32 / 1.61。

**原规划（留作对照）**：

做的是「让解释器少猜」：现在每次 `取属性` / `取下标` / `调用` / 二元运算，
都要现场判断「这是列表还是字典还是对象」。缓存上一次的类型与处理分支，
命中就直接走 —— 不一致就退回慢路径（**这就是「单态」**）。

落点（按收益排）：

| 指令 | 现在每次要做什么 | 缓存什么 |
|---|---|---|
| `调用` | 判是不是内建、是不是方法、是不是函数值 | 上次的「直接跳哪」 |
| `取属性` | 判类型 → 找方法名 → 绑 self | 类型的 vtable 槽位 |
| `取下标` | 判列表 / 字典 / 文本 / 字节 | 上次命中的分支 |
| 二元 `+` | 判两边类型再选实现 | 上次的类型对 |

⚠️ **`iter` 与递归那 22 条指令的固定开销，IC 只能砍掉一部分**。
递归 0.49x 想翻身得靠 JIT —— 所以这一站的目标定「几何 ≥1.5」，
**不承诺**每个场景都上去。

**判据**：

- `check_engines` 0 不一致、`conformance` 全绿（**语义不变是硬线**）；
- `bench_vs_python.py` 17 场景：几何 ≥1.5x，**且把逐场景数字贴出来**（不许只报几何）；
- 加一条「缓存不许泄漏」：跑 10 万次不同类型交替，缓存反复失效不能崩、不能变慢一个量级。

**配菜（必须有）**：**「vs 原生 Rust」那把尺子**（`§8.1` 的 ③④ 台阶要用它）。
写 8–10 个等价程序（同一算法，一份 `.jsh` 一份 `.rs`），量出「差距几倍」。
没有它，M180 的 JIT 收益没法判断值不值。

### M180 · JIT v0（性能第二段）—— ✅ **2026-11-07 完成**

**目标（已达成）**：**第一个能用的 JIT**，不是「完整的 JIT」。

**实际做出来的**（与下面原规划的差异，如实记）：

- ✅ **手写 x86-64 发射器**（约 400 行，零依赖）—— 照 §10.4 ① 的建议做原型，
  **没有引 cranelift**。范围：`当` 循环 + 整数 `+ - *` + 六种比较 + 任意嵌套表达式。
- ✅ **热点识别**只认回边计数（阈值 1000），**局部变量与顶层全局变量都支持**
  （后者是关键：脚本与示例里的循环大多写在最外层）。
- ✅ **类型守卫 + 溢出即去优化（且不写回）+ 失败即黑名单** 三道闸。
- ✅ **可关**：`--不用jit` / `JISHI_JIT=0`；排障 `JISHI_JIT=调试`。
- 📊 **实测**：5000 万次整数循环 **120x**（6970 → 58 ms），2 亿次 **174x**；
  17 个基准场景的几何 **1.66 → 1.75x**（`当循环倒计数` 1.65 → 3.78x）。
- ❌ **没做**：ARM 后端（ARM 上 JIT 自动等于关）、`遍历` / 函数调用 / 字典的编译、
  寄存器分配、跨帧内联 —— 都写进 D109 的「没做的」。
- 🔴 **踩的坑**（都记进 D109）：第一版只认扁平表达式 ⇒ `s + i * 3` 编不了；
  改成栈式后慢一倍 ⇒ 加两条压扁拉回来；`mov rbp, rsp` 写反了一次
  （`mov rsp, rbp` = 把栈指针设成垃圾值，立刻段错误）。

**原规划（留作对照）**：

范围砍到最小：

- **热点识别**：只认「循环回边」计数（超过阈值 → 编）；
- **只编一种形态**：整数算术 + 局部变量 + 比较 + 跳转的循环；
- **带类型守卫**：进入前查一次操作数类型，不是整数 → 立刻**退回解释器**（去优化）；
- **可关**：`--不用jit` 或环境变量，随时退回去对比。

先不做的（写清楚，别让人以为有）：浮点 JIT、方法调用内联、字典/列表特化、
多态内联缓存、寄存器分配优化、跨平台后端全覆盖。

**判据**：

- 指定基准（如整数循环累加 1 亿次）**明显快于**解释器 —— 快多少要**实测后写**，不许先写目标；
- 未优化的路径语义**逐字节不变**（`conformance` + `check_engines` 全绿）；
- 去优化路径有判据（故意传浮点进去，结果必须正确）；
- 崩溃/超时不能出现（JIT 出事是**段错误**，不是异常 —— 所以每条判据都要有超时）。

⚠️ **这一站的真实风险**：JIT 的 bug 是**内存安全级**的（生成的代码出错 = 进程崩），
不是「算错个值」。所以「先能跑、再加优化」的顺序不能反。

## 11.1 开工前必须知道的底细

### 11.1.1 JIT 现在只认一种形状（有具体位置）

- `rust/src/jit.rs` **单文件 879 行、单后端**（手写 x86-64 发射器，零依赖）；
  `支持()` 是**编译期**判断：`cfg!(all(target_arch = "x86_64", any(windows, linux, macos)))`。
- 编的形态：整数 `当` 循环；`+ - *`（含取负）、六种比较、**任意嵌套表达式**；
  局部槽与顶层全局槽都支持。
- **不编**：浮点 / 文本 / 列表 / 字典 / 函数调用 / 属性 / 下标 / `遍历` / `如果` / `中断` /
  `继续` / `/ % **` / `当 真`。
- 0.3.2 实测：17 场景几何 **1.66（关 JIT）→ 1.75x（开 JIT）**；唯一被编到的场景
  `当循环倒计数` **1.65 → 3.78x**；单个循环最快 **174x**（2 亿次累加）。
- 📌 **这一版收益从哪来，一眼能算**：17 个场景里凡是「循环体里有 `如果`」、
  「用 `遍历` 写」或「算的是小数」的，**现在一个都没被编**。M182/M183 就是去开这三类。

### 11.1.2 `遍历` 的迭代器是「私有快照」—— 这是能编它的钥匙

- `遍历` 编成 `GET_ITER` + `FOR_ITER`（`rust/src/lib.rs:2953`）；`GET_ITER` 走 `make_iter`
  → `make_iterator`，对列表 / 文本都**造一份私有快照**（`rust/src/lib.rs:3411`）。
- 🔑 **`范围()` 不是惰性对象**：它当场物化成一份整数 `列表`（`rust/src/lib.rs:4651`）。
  ⇒ 「支持 `遍历` 整数列表」**顺手就把 `范围` 覆盖了**。
- 🔑 **机器码不用碰 `Val` 的内存布局**（v0 最怕这个 —— 加一个变体就悄悄错位）：
  进 JIT 前把快照里那串整数**摊平成 `[i64]`**（一次 O(n)），循环体按索引读。
  循环变量被重新赋值**不回写**列表（解释器也一样）⇒ 语义安全。
- **不编**：`遍历 文本`（每项一次 UTF-8 解码）、字典、自定义 `迭代()` 对象。

### 11.1.3 浮点：`Val::Float(f64)` 早就有，但 JIT 的缓冲是 `[i64]`

- 值层面不缺（`rust/src/lib.rs:428` 的 `Val::Float(f64)`），**缺的是机器码这条路**：
  v0 的做法是「进 JIT 前把用到的槽摊平成 `[i64]`，跑完再写回」——
  浮点混进来，这个缓冲就得变成**双缓冲**（`[i64]` + `[f64]`，槽位一一对应，按槽的静态类型选）。
- 为什么值得单独立一站（M183），而不是塞进 M182：三个语义坑各不相同，且都**必须逐字节对拍**：
  1. **混合提升**：`1 + 2.5` 要出 `3.5`，`整数 + 浮点` 的提升规则要和解释器一致；
  2. **`nan`**：`nan != nan` 为真、`nan < x` 为假 —— `ucomisd` 的 CF/ZF/PF 组合**天然不是**
     语言语义，得显式处理（写成「NaN 一律比成假」）；
  3. **`-0.0` 与 `inf`**：`0.0 == -0.0` 为真、`1e308 * 10` 是 `inf`（**不报错**）；
     但 🔴 **`1.0 / 0.0` 报 `E2001`**（不是 `inf`）—— 与整数除零同一条规矩。
     ⚠️ 这句原来写的是「`1/0.0` 是 inf」，**是错的**（M183 开工查 `binop` 才发现：
     那里是 `if b == 0.0 { return Err }`）。文档按代码改。
- 📌 **这条线不做，图形与游戏那条线接不上**：游戏里的坐标、速度、重力**全是小数**，
  用整数写游戏是自找麻烦。所以 M183 排在图形之前。

### 11.1.4 画图不用动 ABI（但页面上要真有一块画布）

- `浏览器` 的全部 DOM 操作走**一条通道** `jishi_host_call(请求JSON)`，shim 里是 `_doOp`
  一张 `switch`（`wasm/jishi-wasm.js:314`）。⇒ 图形只是**加 case**，不碰 `ABI_VERSION`。
- 原生窗口（wry）与「系统浏览器 app 模式」**共用同一页面 + 同一个 wasm 引擎 + 同一个小服务**
  ⇒ 图形能力**两边天然都能用**，不用写两遍。
- ⚠️ **HiDPI 是第一个坑**：直接按 CSS 像素建画布，Retina 上会糊。`图形.准备` 要按
  `devicePixelRatio` 把**位图尺寸**放大、CSS 尺寸不变，并把坐标统一成**逻辑像素**
  （游戏代码不该关心 DPR）。这条写进设计，否则每个示例都要自己乘一遍。
- ⚠️ 页面里得有一块 `<canvas>`：`图形.准备()` 找不到就**自己插一块**并铺满窗口。

### 11.1.5 🔴 「帧循环」跟现在的执行模型**直接打架**（这一版唯一的硬骨头）

现在的模型是**一次事件 = 一次完整执行**：

```rust
// wasm/src/lib.rs:194   jishi_call(src, fn, 参)
let full = format!("{src}\n\n{name}({实参})\n");   // ← 整个程序 + 处理函数拼起来，重跑
```

- 点一次按钮重跑一遍：没问题（还顺带让「刷新数据还在」自然成立）。
- **60 帧/秒重跑一遍**：不行。全局状态每帧重建、`重绘()` 每帧白跑、帧耗时随程序变长而涨。
- ⇒ 必须有「**常驻 VM**」：`jishi_run` 之后**不 drop** 虚拟机，新增导出 `jishi_frame(ts)`，
  由 shim 的 `requestAnimationFrame` 驱动，直接调已登记的函数。
  **这是这一版唯一的结构性改动**。

✅ **设计已定（2026-11-09）：`docs/设计决策.md` D110**。要点先摆在这儿：

| 问题 | 定了什么 |
|---|---|
| 谁进常驻 | **只有 `图形.运行(...)`**；其它程序一个字不改（两条执行模型并存） |
| 事件怎么办 | 常驻之后**不再重放**，直接在这个 VM 上调处理函数（否则点一下按钮分数就归零） |
| 谁泵帧 | JS 的 `requestAnimationFrame` + 一个导出 `jishi_frame(ts)`；`ABI_VERSION` 3 → 4 |
| `dt` | **clamp 到 100 ms** —— 后台切回来的那一帧可能是几十秒，不 clamp 会让球穿墙 |
| 预算 | **按帧重置**（不是整个会话累计）；出错**只报一次**然后停 |
| JIT | 这次会话的阈值 **1000 → 60**（否则要 17 秒才热起来） |
| 边界 | 常驻期间不许再开窗口、不许从事件里进常驻、不许两个循环 |
| 绘制 | v1 **直发**；平均 > 16 ms 或最坏 > 33 ms 才改「一帧一批」 |
- 代价如实说：常驻模式下「刷新页面数据还在」**不再自动成立**（顶层只跑一次），
  要自己 `存档.存` / `浏览器.存本地`。所以它**必须 opt-in** —— 只有调
  `图形.运行(初始化, 每帧)` 才进常驻模式，其它程序**一个字都不用改**。

### 11.1.6 浏览器「给不了」的三件事（都得 shim 补）

| 想要的 | 现在 `浏览器` 的样子 | 补在哪 |
|---|---|---|
| **全局键盘** | `绑定(选择器, 事件, 函数)` 要一个**能 querySelector 到的元素** ⇒ 抓不到 `document` 上的按键 | `图形` 自己挂 `window` 的 `keydown/keyup`（轮询表 + 边沿表），不走 `浏览器.绑定` |
| **滚轮 / 鼠标坐标** | 没有 | 同上，挂在 canvas 上（坐标要按 DPR 与 canvas 位置换算） |

### M182 · JIT v1：一个 IR，长出分支与 `遍历`（主菜 🥇）—— ✅ **2026-11-08 完成**

**实际做出来的**（与下面原规划的差异，如实记）：

- ✅ `rust/src/jit.rs` 拆出后端 `rust/src/jit/x86_64.rs`；IR **16 条**（栈机），
  不做寄存器分配、不做优化 —— 只为 M184 的 ARM 后端共享。
- ✅ 新编：`如果/否则/否则如果`（可嵌套）· `中断` · `继续` · `遍历` **整数列表**
  （`范围()` 走的同一条路）· `//` `%`。
- ❌ **`/` 没编**（规划里写的是「`/ %`」）：整数 `/` 的结果是**浮点**，槽的类型会变
  —— 那要等 M183 的浮点 JIT。这一版只编 `//` 与 `%`。
- ➕ **`//` `%` 比规划复杂**：x86 的 `idiv` 是**截断**，基石是**向下取整**
  （`-7 // 3 == -3`）⇒ 多一段「商减一、余加除数」的修正；且 `idiv` 的两条错误
  （除零、`MIN / -1`）是 **SIGFPE**（进程直接死）⇒ 三道检查必须在 `idiv` 之前。
- ➕ **顺手还了一笔 0.3.2 的老账**：`记一步` 原来只在计数刚好到阈值那次返回真
  ⇒ 编好的循环**再也不会进 JIT**（函数调用 100 次只有 1 次受益）。现在钉成
  `已编好` 哨兵，每次回边都进。
- 🔴 **撞了两个「静默不对」的 bug**（都不崩、不报错）：① `如果` 的假分支落在
  回跳那条 `JUMP` 上 ⇒ 标签没打 ⇒ `rel32 = 0` ⇒ 分支失效（数字翻倍）；
  ② 修 ① 时给每条指令都打标签 ⇒ `压扁` 的融合全失效（58 ms → 131 ms）。
  两条都写进 CHANGELOG。
- 📊 **实测**（`bench_jit.py`，50M）：累加 114x · 乘加 102x · 双变量 135x ·
  **带如果 32.8x** · **带中断 78.5x** · **遍历（1M，含造表）2.5x**（纯循环 10x）；
  几何 **46.6x**。
- ⚠️ **`遍历` 的摊平是每次进 JIT 一次 O(n)**：列表大、又反复遍历时会被摊薄
  （这就是「整程序 2.5x / 纯循环 10x」的差额）。要不要缓存摊平结果，等有真实
  程序撞上再说 —— 缓存要处理「列表被改」的失效，那是 M183 之后的事。

**原规划（留作对照）**：


**为什么先重构、而不是直接加功能**：v0 是「边认边发」—— 一个 `当` 循环、一个条件跳转，
补丁随手就打。一旦要加「循环体里的 `如果`」（块结构）和 `遍历`（索引 + 长度判断），
两个后端各维护一套补丁表**必然分叉**。所以先抽一份**很小的 IR**：

| 层 | 干什么 | **不该**干什么 |
|---|---|---|
| 前端（认形状） | `当` / `遍历` 两种抬头 → 摊平用到的槽 → 每条语句变成 IR | 不认文本 / 调用 |
| IR（约 16 条） | 立即数 · 装载 · 存 · 加减乘除模 · 比较 · 标签 · 跳 · 条件跳 · 除零检查 · 返回（+ 浮点 4 条留给 M183 加） | **不做寄存器分配**（继续「每个变量一个栈槽」），不做公共子表达式消除 |
| 后端（发射） | IR → 机器码 + 溢出/除零的退出补丁 | 不认语言语义 |

⚠️ **别把 IR 做大**：它只为让两个后端共享，不是写优化器。IR 一旦长出十几条「方便优化」的指令，
M184 的 ARM 后端就得跟着实现一遍 —— 白干。

**这一站编什么**（碰任何一条不满足就**不编**，退回解释器 —— 慢但一定对）：

- `如果 / 否则 / 否则如果`（在循环体里，可嵌套，深度 ≤ 4）
- `中断`（跳到出口）/ `继续`（跳到回边）
- `遍历` 一个**全整数**列表（`范围()` 造的也算 —— 见 §11.1.2）

- 仍然只认整数：`+ - *` 与六种比较

**判据**（JIT 的 bug 是**段错误级**的，所以每条都得有）：

1. `conformance` + `check_engines` **0 不一致**（语义不变是硬线）；
2. `tools/bench_jit.py` 扩三组：`遍历累计` / `循环体带如果` / `带中断的查找`
   （同一二进制只差 `JISHI_JIT`，各 3 轮取中位；**逐组贴前后数字，不许只报几何**）；
3. **去优化三条**：循环里混进浮点 / 除零 / 溢出 —— 结果必须与解释器**逐字节相同**

4. 每条判据都有 **subprocess 超时**（条件编错 = 死循环，不是异常）；
5. `JISHI_JIT=调试` 能说清「这个循环为什么没编」（新增的三类理由都要有人话）。

**风险与对策**：`如果` 编错的表现是**死循环或算错**，不是崩溃 —— 更难发现。
⇒ **先把「同一脚本开/关 JIT 各跑一遍、逐字节比输出」做成一条通用判据**，再开始写发射器。

- 🔴 **三个专项**：`nan`（补 `setnp`/`setp`）、`-0.0`（`xorpd` 翻符号位）、
  `inf`（`mulsd` 自己溢成 inf）。**除零按代码改成「报 E2001」**，不是 inf。
- 📊 实测：**浮点累加 39.9x**（20M：4116 → 103 ms）· **浮点积分 21.1x**
  （15M：4328 → 205 ms）· 整数那几档没退（121x / 114x / 153x）· 几何 **43.4x**。

- ⚠️ 连带改了 `test_m180` 的两条老断言（「浮点不编」「分支不编」——
  契约变了，M182/M183 起它们会编），只留「结果一致」。

**原规划（留作对照）**：

**做什么**：让**小数**也能编。理由见 §11.1.3 —— 不编浮点，图形与游戏这条线接不上。

- **槽的双缓冲**：用到的槽按**静态类型**（这一轮推断出来的）分到 `[i64]` / `[f64]` 两张缓冲，
  槽号一一对应；写回时按 `Val::Int` / `Val::Float` 各写各的。
- **指令**：`movsd` / `addsd` / `subsd` / `mulsd` / `divsd` / `comisd`（x86-64 的 SSE2 标量）。
  提高/降级只在我们**明确允许**的两种形态里做（整数槽 → 浮点槽，反向不做）。
- **范围**：浮点 `+ - * /`、六种比较；`**` 不编（i64/f64 的溢出与精度都难说清）。

**三个必须逐字节对齐的专项**（这是这一站的核心判据）：

| 专项 | 解释器的语义 | 机器码容易错成 |
|---|---|---|
| `nan` 比较 | `nan != nan` 为**真**，`nan < 1` 为**假** | `comisd` 的 CF/ZF/PF 组合直接当 `<` / `>` 用 ⇒ 全反 |
| `-0.0` | `-0.0 == 0.0` 为真；`1 / -0.0` 是 `-inf` | 用整数化的位比较 ⇒ 判成不等于 |
| `inf` | `1 / 0.0` = `inf`（**不报错**，与整数除零不同） | 复用整数除零检查 ⇒ 直接抛错 |

**判据**：

1. 上面三个专项各一条，**开/关 JIT 输出逐字节相同**；
2. `bench_jit.py` 加一组「欧拉积分」基准（N 个浮点 `x += vx * dt`，正是游戏每帧干的事）；
3. 混合算术 `1 + 2.5` / `2.5 + 1` / `1 * 2.5` 三种顺序都对；
4. 溢出/除零/类型变化仍然走「去优化不写回」（沿用 v0 的闸）。

**风险**：浮点的「看起来对」最坑 —— 打印出来都是 `3.5`，但 `-0.0` 会打印成 `-0`
（解释器如此）。所以判据**比原始输出**，不比「数值差不多」。

**🔴 关键设计一：常驻 VM（D110）** —— 见 §11.1.5。调 `图形.运行` 之后：

```jsh
导入 图形

令 球 = {"x": 100.0, "y": 100.0, "vx": 3.0, "vy": 2.0, "半径": 10.0}
令 分 = 0                      # ← 这些全局变量**每一帧都在**（常驻 VM 保住它们）

函数 初始化()：
    图形.准备({"宽": 800, "高": 600, "背景": "#101820"})

函数 每帧(帧号, 间隔)：
    令 dt = 间隔 / 1000.0
    球["x"] = 球["x"] + 球["vx"] * dt * 60.0
    ...

图形.运行(初始化, 每帧)
```

⚠️ **必须写进文档的三条**：
1. `图形.运行` **之后的代码只在启动时跑一次**，不会被每帧重跑（和事件模型不一样）；
2. 常驻模式下**刷新页面不回状态** ⇒ 要存就 `存档.存` 或 `浏览器.存本地`；
3. 进常驻模式之后**不能再开第二个窗口**（一个 VM 一个循环；0.3.3 不碰「多窗口 + 多循环」）。

**🔴 关键设计二：一帧几次通道？**（先量，别猜）

- 一帧画 200 个矩形 = 200 次 `jishi_host_call`（每次过一遍 JSON）。看着多，但每次只有
  几十字节 —— **先量**：800×600、200 个矩形、连续 600 帧，看平均帧耗时。
- **门槛**：平均帧耗时 **≤ 16 ms**（60fps 的预算），且**最坏帧 ≤ 33 ms**（不允许偶发卡顿）。
- 达不到就改「**一帧一批**」：`图形` 在 Rust 侧把绘制指令攒进数组，**帧末一次发**，
  shim 拿数组顺序执行。这条**写在计划里**，因为它决定 `图形.X` 是「直发」还是「攒」
  —— 事后改等于把 20 个函数全重写一遍。
- ⚠️ **未度量**：16 ms 是按人眼 60fps 反推的。**开工第一件就是量它**（比写 20 个函数都靠前）。

**判据**：

1. **wasm 里真跑**（沿用 M167 的办法：Node + 假 DOM + **假 canvas**，记录调用序列），
   断言「清屏 1 次 + 矩形 3 次 + 子矩形参数正确」这种**可核对的事实**，不是「没报错」；
2. 命令行 / Node 上每个函数报**同一句中文平台错**（三宿主逐字相同，`test_m51` 一致性要过）；
3. **帧循环的状态保持**：第 1 帧把计数加 1，第 60 帧读回来是 60（验的正是常驻 VM）；
4. **相机换算**：设相机 `{x:100,y:0}` 后画 `矩形(0,0,10,10)`，假 canvas 收到的实际坐标是 `-100`；
5. **HiDPI**：假 `devicePixelRatio=2` 时，位图尺寸翻倍而逻辑坐标不变；
6. 帧耗时门槛（上面那两条）：达不到就**如实写「未达标」并附数字**，不许悄悄放宽。
