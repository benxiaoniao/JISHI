### 2.1 语言本体：**4 危险 · 2 缺口 · 1 安全**

> 这是「**一段输入能不能把程序打爆**」的那类问题 —— 和沙箱、包管理器无关，是语言/标准库自己的属性。

| # | 类型 | 判定 | 实测证据 |
|---|---|---|---|
| 1 | **整数/浮点边界** | ✅ **安全** | 超 i128 给 `E2005`（中文、带位置）；除零给 `E2001`；`1e308*10`→`inf`、`-0.0` 正常。**没有静默回绕** |
| 2 | **正则回溯（ReDoS）** | 🔴 **危险** | `(a+)+$` 配「a×N + b」：20 个 a **0.14s** → 24 个 **1.02s** → 28 个 **>15s 没返回**。**每加 4 个 a 涨 10 倍 = 标准指数回溯** |
| 3 | **压缩炸弹** | 🟡 缺口 | 39 KB 的 zip 解出 **40 MB**，没有任何上限或提示（真实世界 1 GB 会直接吃光内存） |
| 4 | **解压路径穿越** | 🔴 **危险** | 条目 `../被穿越.txt` **写到了目标目录之外**（`压缩.解压` 不校验条目名） |
| 5 | **SQL 注入** | 🟡 缺口 | 结构化条件**按值匹配**（注入串返回 0 条）✅；但 `执行(库, SQL)` / `执行查询(库, SQL)` **没有参数化入口** ⇒ 用户自己拼字符串就中招 |
| 6 | **畸形字节码** | 🔴 **危险** | 给 4 份坏 JSON：校验和错、指令越界 → 中文报错 ✅；**`main` 越界、常量池清空 → Rust panic（rc=101）** |
| 7 | **递归深度** | 🔴 **危险** | **没有上限**：`返回 1 + f(n+1)` 能跑到 **300 万层**（12 秒实测到 **1500 万层**），既不报错也不崩 ⇒ 无限递归**静默吃内存**直到被系统杀掉 |

**四条危险的共同点**：不是「算错」，是**一段输入就能让程序卡死 / 崩掉 / 吃光内存**。
而且用户看到的现象最糟 —— 没输出、没报错、只能 Ctrl-C（或整机变卡）。

**两条缺口的共同点**：实现没错，但**没有引导用户走安全路径**（解压不限量、裸 SQL 无参数化）。

### 2.3 性能：vs CPython 几何平均 **0.91–0.95x**

两份等价实现、交替取样、单轮 ≥400ms、扣掉启动后取 min，两次独立跑：

| 场景 | 第一次 | 第二次 | |
|---|---:|---:|---|
| **递归斐波那契** | **0.30x** | **0.38x** | 🔴 慢 3 倍 |
| **函数调用密集** | **0.52x** | **0.37x** | 🔴 慢 2–3 倍 |
| **列表构建与遍历** | **0.73x** | **0.63x** | 🔴 慢 1.4–1.6 倍 |
| 文本切片 / 下标 / 字典写入 | 0.65–0.97x | 0.80–0.84x | 🟠 慢 |
| 整数循环 / 内建调用 / 浮点遍历 | 1.06–1.41x | 1.38x 上下 | ✅ 快 |
| **几何平均** | **0.95x** | **0.91x** | 🔴 总体不如 CPython |

**三个根因（指到行）**：① `call_frame` 每次递归进 `execute()`（`lib.rs:2946`）；
② `LIST_APPEND` 走 `get_attr("追加")` + `BoundMethod` 分配（`lib.rs:2569`）；
③ 文本下标/切片无字符索引（UTF-8 上按需扫描）。

## 四、里程碑（M160–M169）

### 推进节奏（用户 2026-11-01 拍板：**先并行三站**）

| **第二波（串行）** | **M163 → M164 → M165** | 都在动 VM 主循环，`check_engines`（175 语料 × 5 引擎）每轮必跑，并行只会互相拖 |

### M160 · 解压安全：一个根因，两处修补（主菜 🥇）

**根因只有一个**：解压时把「zip 里的条目名」直接当路径拼上去，不校验。

| 位置 | 现在 | 改成 |
|---|---|---|
| `压缩.解压`（标准库） | `../` 条目写到目标外 | 逐条校验：拒绝绝对路径、`..` 段、驱动器号；**规范化后再比前缀** |
| `install_package_zip`（包安装） | 同上 | 同上（**共用一份校验函数**，别写两遍） |

再做两件配套：

- **解压前报总量**：`列出内容` 已是现成的 —— 解出体积超过「包体积 × 50 或 512 MB」就**先问一句**（脚本里给 `--是`），别静默解 1 GB；
- `--local-zip` 安装**提示「这个包没有校验和」**（现在静默装上）。

**做完是什么样**：恶意 zip 装不进来、解不开；报错直接说「第 3 个条目 `../../x` 越出了目标目录」。
**判据**：`probe_zip_slip.py` 变绿 + `audit_language.py` 第 4 条变绿 + 一条「炸弹包要提示」的用例。

> ✅ **M160 已完成（2026-11-01）**：三处修完，`audit_language.py` 的
> 第 3 条（压缩炸弹）与第 4 条（解压穿越）**已转绿**；判据 `tests/test_m160_zip_slip.py`（9 条）。
> 顺带发现并修掉一处**口径不一致**：Node 原来按「实际解出的字节数」算总量（炸弹要先解出来才判），
> Python / Rust 按「中央目录声明的大小」—— 现在三处统一读声明大小，且 Node 改成**先读目录再解数据**。

### M161 · 一段输入别把程序打爆（主菜 🥇）

三条一起做，因为它们**都是「资源没有上限」**：

| 问题 | 改法 | 判据 |
|---|---|---|
| **ReDoS**（正则指数回溯） | 回溯加**步数上限**（超了报「正则太复杂，请改写模式」），或换线性引擎 | 28 个 a 必须在 **1 秒内**给出结果或明确报错 |
| **递归无上限** | 加**调用深度上限**（默认 10 万层，可配置）：超了报「递归太深（第 100000 层），检查有没有漏掉的结束条件」 | 300 万层那条变绿 |
| **畸形字节码 panic** | `main` 越界 / 常量池越界改成**中文报错**（`E2xxx`），不许 `panic` | 4 份坏 JSON 全部中文报错、rc=1 |

⚠️ **递归深度与 M163 的调用扁平化在同一片代码里** —— 先做 M161（加上限），
M163 再改调用协议时，这个上限就是它的天然护栏（改写期间不会一崩就是栈溢出）。

**做完是什么样**：写错的递归、恶意正则、坏字节码，**都只得到一句中文报错**，不卡死、不崩、不吃光内存。
**判据**：`audit_language.py` 的 2/6/7 三条全绿。

> ✅ **M161 已完成（2026-11-01）**：四条全修 —— 正则 2000 万步上限（28 个 a 从 >15s
> 变成 0.85s 报错）· Rust 补上 1000 层递归上限（能跑到 1500 万层的洞）· 畸形字节码从
> **panic** 改成中文报错（`main` 越界 / 常量池清空 / 指令流截断）· Node 网络改
> **Worker + Atomics**（`EBUSY` 根除）。顺带发现「指令流截断会静默跑完」（比 panic 更隐蔽）。
> 判据 `tests/test_m161_input_hardening.py`（10 条）。`audit_language.py` 现在
> **✅6 · 🟡1 · 🔴0**（只剩 SQL 那条「引导缺口」）。详见 CHANGELOG。

> ✅ **M162 已完成（2026-11-01）**：`tools/bench_vs_python.py` 能出**结构化快照**
> （`bench/baseline_cpython.json`，带机器指纹/时间/启动成本/逐场景），判据
> `tests/test_m162_perf_baseline.py`（3 条，进串行节）。
> 🔴 **顺带修掉一个方法学上的坑**：第一版每轮都按当时负载**动态算「重复几次」**，
> 于是两次跑的根本不是同一道题 —— 同一台机器同一份代码能读出 0.94/0.95/1.06（差 11%）。
> 改成「**从基线读固定重复次数**」后是 1.07/1.06（<1%）。⇒ 判据里的 `--用基线` 不是可选装饰。

### M163 · 函数调用扁平化（主菜 🥇，最大靶子）

`call_frame` 不再递归 `execute()`，改成「压一帧、主循环继续」（CPython 的 CALL 做法）。
**目标**：递归斐波那契 0.30x → ≥1.2x；函数调用密集 0.37x → ≥1.5x。

⚠️ **风险**：牵动异常栈展开 / 调试器断点 / `finally`。判据不只看快：
五引擎对拍 0 不一致 + **调试器会话记录与改写前逐字相同**。

> ⚠️ **M163 部分完成（2026-11-01）**：函数调用已扁平化（同一循环换帧，不再返回重进），
> 实参绑定零分配。结果：**几何 1.06 → 1.10x**，慢场景 **6 → 5**，递归斐波那契 **0.49 → 0.65x**。
>
> 🔴 **但目标没达成，而且我猜错了三次**（分配 2.6% / 生命周期往返 10.8% / 每步写 ip 1.4%）。
> 决定性证据：**0 参数调用也要 398 ns**（每多一个参数只 +50 ns）⇒ 固定开销在
> **「指令分派 + 帧管理」本身**，一次调用约等于 22 条指令的代价（纯循环每条约 20 ns）。
>
> ⇒ 剩下的 3 倍差距要单开一站：**帧字段拆平行数组（SoA）+ `Val` 从 32 字节瘦身
> + 指令分派表优化**。这条路比「改一处」重得多，放进 M165 之后的新站（暂记 M165b）。

### M164 · 容器与文本快路径（配菜 ×2）

`LIST_APPEND` 直通（不再 `get_attr("追加")` + `BoundMethod`）；文本下标/切片加字符索引（或 ASCII 快路径）。
**目标**：列表构建 0.63x → ≥1.3x；文本下标 0.66x → ≥1.2x。

> ✅ **M164 完成（2026-11-01）**：三处热路径 —— `LIST_APPEND` 直通 push（+8.6%）、
> 文本切片不再先 `Vec<char>` 全量拆（+9.8%）、文本下标非负不数一遍（持平）。
>
> 🔴 **方法学教训（重要）**：这台机器的固定负载波动就有 **15.5%**，基准写进文件的倍数会被
> 放大到 +38%（真实 +8.6%）。⇒ **判断一处改动值不值，要编两份二进制同刻交替跑**
> （`build/jishi-old.exe` vs `jishi-new.exe` 那套），别只看基准表。这条已记进 CHANGELOG。

### M165 · 数字与字典热路径（配菜）

> ⚠️ **M165 部分完成（2026-11-02）**：目标里**算术拿到了、字典没拿到**。
>
> **① `//` `%` 撞出两个真 bug（比性能值钱）**
> Rust 宿主原来一律转 f64 算：`-7 % 3` 给 `-1`（Python 是 2）、`9007199254740993 // 1`
> 丢精度、`-7.5 % 2` 连类型都错。**只有 Rust 错** —— Python / Node / C 都对。
> 现在整数走整数路径（`floor_div` / `floor_mod`，余数符号跟除数），有浮点参与才转 f64。
> Node 那边同时修了「负数零」：`0 * -1`、`-6 % 3` 会印成 `-0.0`，Python 是 `0`。
>
> **② 为什么活了这么久**：`tests/cases/01_算术.jsh` 只有 `7 // 2`、`7 % 2` —— 全正数。
> 已补负数 / 浮点 / 2^53 以上 / 负零共 16 行，并加了**源码级护栏**（删了语料就红）。
>
> **③ 性能：算术 +12.8%（0.90 → 1.06x，跨过 1.0）；字典 +1.1%（噪声内）**
> 字典把 `get`+`insert`（算两遍哈希）换成 `entry`，但实测被**内存布局**盖过去：
> 写新键 394 ns vs 写入同一键 168 ns（差 226 ns），文本键比整数键再贵 91 ns
> （每次读写克隆一个 `String`）。20 万条的字典 = 16 MB，全在 cache 外。
>
> ⇒ **字典要真提速，得改数据结构**：哈希只存一遍（或索引表用 u32）、
> 键共享引用（`Rc<str>` 而不是每次 clone）、entries 紧凑。**并入 M165b**。
>
> **④ 「小整数缓存」这条规划不成立**：那是 CPython 的招（`PyObject` 装箱需要它）；
> 基石的 `Val::Int(i64)` 是**值类型**，没有堆分配可省。不做，不是没来得及。

### M165b · 值表示与帧管理（性能补课）

> ✅ **M165b 完成了一半（2026-11-02）**：值层做完，帧层没动。
>
> **① `Val::Str` 从 `String` 换成 `Rc<str>`（这一站的主菜）**
> 原来 `Val::clone()` 对字符串**深拷贝整串**，而 VM 每读一次字符串变量、每次压栈、
> 每次传参都在 clone。实测：读整数 124 ns、读 5 字串 **387 ns**、读 1000 字串 **655 ns**
> —— 那 263 ns 的固定差就是一次 malloc（CPython 这里是引用计数 +1）。
>
> 同刻 A/B：**字符串拼接 +167%** · 读长串 +44% · 文本比较 +33% · 内建调用 +27% ·
> 文本列表遍历 +27% · 读短串 +26% · **字典文本键 +20%/+21%**。
> 整体几何 **0.95x → 1.01x**，慢场景 **11 → 7**。判据 `tests/test_m165b_string_rc.py`（5 条）。
>
> **② `Val` 没能从 32 降到 24** —— `Int(i128)` 的**对齐是 16**，enum 对齐跟着是 16，
> 24 不是 16 的倍数 ⇒ 编译器补到 32。两个 24 字节变体（`Builtin` 的胖指针、
> `ExcType(String)`）已清掉，但省下的字节被对齐吃掉，**没换来空间**。
> ⇒ 要真降到 24，得把 `Int` 改成 `i64` + 溢出走 `Rc<i128>`（见 M165c）。
>
> **③ 「遍历文本」试了活迭代器，无效，已回退**：+1.7% / −4.5%。根因是
> **每个字符都要返回一个 `Val::Str`（一次分配）**，迭代器怎么写都省不下来。
> 真要解决要 `Val` 支持内联短字符串（SSO）。
>
> **还没做（M165c 候选）**：
> - **帧字段 SoA**：`Frame` 现在 ~270 字节、7 个 `Vec`，每次 push/pop 都要搬；
>   M163 定位的「一次调用 398ns ≈ 22 条指令」还没动（M165b 后仍是 407ns）；
> - **`Val` 真瘦身**：`Int(i64)` + `Rc<i128>` 溢出分支 ⇒ Val 32 → 24；
> - **指令分派**：每条指令约 20 ns（CPython 5~10 ns）；
> - **字典紧凑布局**（M165 遗留）：哈希只存一遍 / 索引 u32 / entries 紧凑。

### M165c · 函数值 `Rc<Func>`（性能补课第二站）

> ✅ **M165c 完成一半（2026-11-02）**：调用开销砍掉一半，`Val` 瘦身没做。
>
> **① `Val::Func` / `BoundMethod::User.func`：`Func` 值 → `Rc<Func>`**
> `push_func_frame(func: Func, …)` 是按值收的，而 `Func` 是 88 字节、里面有
> `name: String` + `cells: Vec` + `defaults: Vec` —— **clone 一次三次 malloc**，
> 而每调用一次函数就要 clone 一次（`实例.方法()` 也是）。
>
> 同刻 A/B：**0 参数调用 +57%（461 → 294 ns）** · 1 参数 +48% · 递归斐波那契 +23%。
> 整体几何 **1.01x → 1.09x**，慢场景 **7 → 5**，「函数调用密集」掉出名单。
> 判据 `tests/test_m165c_fn_rc.py`（4 条，含闭包独立性与默认参数两条行为护栏）。
>
> **② `Val` 瘦身没做**：要降到 24 得把 `Int(i128)` 改 `i64` + 溢出走 `Rc<i128>`
> （`i128` 对齐 16 ⇒ 24 不是 16 的倍数）。波及全部算术语义 + 序列化 + C VM 对拍，
> **留到 0.4.0 与 JIT 一起规划**（JIT 会改变值表示的前提）。
>
> **③ 帧 SoA 没做**：一次调用 294 ns 里，帧管理仍占 ~190 ns（约 18 条指令）。
> 但实测「Frame 瘦身」（280→232 字节）预计只值几 ns —— memcpy 不是瓶颈，
> 所以**没有盲改**。真要再降，方向是「把热字段缓存在局部变量里」而不是拆结构。
>
> **剩下的慢场景（5 个）与它们各自的门槛**：
> 递归 0.49（要 JIT/内联缓存）· 字典写入 0.93（要紧凑布局）· 内建 0.90（内建实现本身）·
> 文本下标 0.96（字符定位是 O(n)）· 遍历文本 0.80（每个字符一个堆对象，要 SSO）。
> 五条**没有一条是「再改一处」能解决的** ⇒ 0.3.0 的性能就到这儿，如实记。

### 8.0 `时间.计时` 缺口（✅ **2026-11-02 已修，M165d**）

> **修完了，留在这里当复盘材料。**下面「症状 / 为什么一直没修 / 怎么被藏住的」
> 是当时的事实，末尾是实际做法。
>
> **实际做法**：两个宿主各加「自带方法表的宿主对象」（Rust `NativeObj` /
> Node `JishiNative`），属性查找 / 方法调用 / 上下文协议都认它。
> 顺带修了 Rust 的 `lookup_method` 不找 `进入` 的老问题。
> ▶ 结果：`test_m51_consistency` 的 `KNOWN_GAPS` **清零** —— 三宿主标准库
> 第一次完全同宽；`排序跑分` 示例在 Rust 上整张跑分表都能出来。
> 判据 `tests/test_m165d_native_obj.py`（7 条）。详见 CHANGELOG。
>
> ⚠️ **一处更正**：下面原文说「三个宿主都没有」是错的 —— C VM 与 Python 侧
> **本来就能跑**（标准库走 Python 回调），缺的只有 Node 与 Rust。

**症状**：语言卡（`--lang-spec` / `--ai-card`）里写着 `时间.计时(名字='')`，
**Python 侧也有实现**，但 **Node / C VM / Rust 三个宿主都没有** —— 三个宿主上
`用 时间.计时("建表") 为 t：` 直接报「模块「时间」里没有「计时」」。

**为什么一直没修**（CHANGELOG M51 与 `docs/冒烟清单.md` 都记着）：它返回的是
**带方法的宿主对象**（`耗时()` / `停()`）并且要支持**上下文协议**
（`进入` / `退出`）。而三个宿主的上下文查找只认「Jishi 实例」与「内建容器」，
标准库直接返的宿主对象走不通 —— **这是对象模型的缺口，不是补一个函数**。
当初判断「改写成基石库模块后天然是 Jishi 实例，缺口结构性消失」，但基石库层
要求「零宿主原语」，而计时必须调 `perf_counter`（宿主原语）⇒ 那条路走不通。

**它怎么被藏住的**：`examples/projects/排序跑分/排序.jsh` 用了它，而这条语料
**在 `check_engines` 的豁免表里**，理由是「打印墙上时间」。⇒ 三个宿主上它
**根本跑不通**这件事，对拍工具从来没报过。
（2026-11-02 复核豁免时发现，已把理由改准确，并拆掉一条按文件名的隐式豁免后门。）

**修它的两条路**（都要动宿主对象模型，估 1–2 天）：
1. **给标准库对象一个「方法分派」口子**：宿主返回的 `Val` 携带一张方法表，
   `get_attr` / 上下文协议都认它 —— 一次改动三个宿主都能受益（将来的
   `数据库.连接` 这类「返回对象」的 API 也走它）；
2. **退一步**：把 `计时` 改成**两个函数**（`开始计时()` 返回编号、`计时结束(编号)`），

（输出仍然豁免，理由是墙上时间；但「跑不起来」与「数字不同」是两件事）。

### 8.1 性能的**终点**：与原生 Rust 对齐（用户 2026-11-01 定）

> **「vs CPython」只是第一级台阶，不是终点。** 终点是**和原生 Rust 一个量级**。

台阶要一级一级上，每级的判据不一样：

| 台阶 | 判据 | 现在 |
|---|---|---|
| ① 不输 CPython | 17 场景全 ≥1.0x | 部分达标（几何 ≈1.06x，还有 6 个场景慢） |
| ② 稳定领先 CPython | 几何 ≥1.5x（0.3.0 收口线） | 待 M163–M165 |
| ③ 接近原生 | 同算法 vs 原生 Rust，**差距 <3 倍** | 未度量（要新增一把「vs 原生 Rust」的尺子） |
| ④ 对齐原生 | 差距 <1.5 倍 | 需要 JIT / AOT |

**底层加速的三条候选路线**（用户提到的自举编译器、LLVM 都在这张表里）：

| 路线 | 解决什么 | 对**运行时速度**的收益 | 我的判断 |
|---|---|---|---|
| **内联缓存 + 单态特化** | 每次 `GET_ATTR` / `GET_ITEM` 都重新判断「这是不是列表」 | **最大**（解释器里最热的那几跳直接省掉） | **先做这个**：不动工具链、不改语义、能拿 M163–M165 的成果接着走 |
| **JIT**（热点字节码 → 机器码） | 解释循环本身的开销（每条约 5–20ns） | 大，但要处理**动态类型推断**与去优化 | 第二顺位；先有 ③ 的度量再谈 |
| **AOT 到 LLVM**（把字节码编成 .o） | 同样解决循环开销，且离线做 | 大，但**动态类型是硬伤**（不特化就没收益，特化就要类型系统让步） | 与 JIT 二选一，别两个都上 |
| **自举编译器**（用基石写基石） | 「不依赖别的语言」+ 编译速度 + 可信根 | **几乎为零**（它编出来的还是同一种字节码） | 它是**独立路标**，别拿它当性能方案 |

📌 **一句实话**：动态语言要「对齐原生 Rust」，真正的墙不是解释器写得快不快，
而是**每个值都得装箱、每个运算符都得判类型**。所以顺序必须是
「**先特化、再 JIT**」—— 反过来的话，JIT 编出来的也是「一堆类型判断」的机器码。

⚠️ **③④ 需要一把新尺子**（vs 原生 Rust 的等价程序），还没写。
在那把尺子出现之前，③④ 只能算方向，不算目标 —— 本项目的老规矩：**没度量就不算数**。

## 9.0 为什么是这两件（用户 2026-11-04 提的）

两条都是**真实项目撞出来的**，不是想当然：

| # | 用户的意思 | 现在的实情 |

### 两层设计（说清哪部分不是基石写的）

| 层 | 用什么写 | 为什么 |
|---|---|---|
| **清单 / 布局 / 版本 / 校验 / 安装脚本** | **基石**（`打包` 模块） | 这些是「事实与规则」，正该是语言能力 |
| **自解压 stub**（`jishi-pack-stub.exe`，几十 KB） | **Rust**（`rust/src/packstub.rs`，独立 bin） | ⚠️ **必须承认**：安装器要能脱离基石运行（用户还没装基石），所以它只能是一个静态原生程序。这跟 `jishi.exe` 本身是同一类东西 —— **引擎级**，不是语言级 |

stub 干的四件事（就这四件，别扩）：
1. 读**追加在自己末尾**的 zip（`argv[0]` 尾部找魔数 + 长度）；
2. 解到 `--目标 目录`（默认 `%LOCALAPPDATA%\Programs\<名字>`），**默认不需要管理员**；
3. 写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\<名字>`，
   `UninstallString` **指向程序自己**：`"<目录>\jishi.exe" 卸载 --自身 --是`；
4. 加 PATH（HKCU\Environment）、建开始菜单快捷方式（`.lnk` 直接写二进制格式）。

### 产物矩阵

| 目标 | 产物 | 说明 |
|---|---|---|
| Windows | `名字-版本-setup.exe` | stub + zip：双击装、`/S` 静默装、`/D=目录` 换目录 |
| Windows | `名字-版本-便携.zip` | 解压即用（现在也有，保持） |
| macOS | `名字.app/` + `名字-版本-macos-<arch>.tar.gz` | **`.app` 就是目录**：`Contents/MacOS/<可执行>` + `Info.plist` + 图标 —— 我们生成得起 |
| Linux | `名字-版本-linux-x64.tar.gz` + `install.sh` | `install.sh` 由**基石生成**（幂等：装/升级/卸载三段） |

### 判据（都不是「看起来对」）

1. `test_打包两次字节相同` —— 可复现（沿用 M168 那条规矩：**落盘不带时间戳**）；
2. `test_setup里的zip能解出来` —— 不需要装 Windows：读尾部 → 解 → 文件清单 + sha256 与清单一致；
3. `test_装完能跑_卸载干净`（Windows CI）：静默装到临时目录 → `jishi --version` → 卸载 → **注册表项 / PATH 条目 / 目录**三样都不留；
4. `test_升级保留用户数据` —— 升级不碰 `~/.jishi/packages` 与用户自己的文件。

### 明确不做（这一版）

- ❌ **代码签名 / macOS 公证**：那是买证书 + 走 Apple 流程，**不是语言能力**（我们只保证「有签名位」：`打包.清单` 留 `签名` 字段，给外部工具填）。
- ❌ **MSI / deb / rpm**：优先级低于「自己的 setup.exe」；真要了再按同一个 stub 思路接。
- ❌ **图形化安装向导**：stub 先做**静默 + 一个进度条**（控制台）。向导 UI 等 C 线的窗口能力落定再做 —— 那时安装器自己就是一个基石程序。

## 9.4 C 线：窗口（M173）

### 两条路，先摆清楚

| 方案 | 做法 | 像不像桌面程序 | 成本 | 三平台 |
|---|---|---|---|---|
| **① 应用窗口**（推荐先做） | 起本地服务 / 读本地文件 → 用系统浏览器的 **app 模式**开窗（`msedge --app=…` / `chrome --app=…` / mac `open -na`） | 8 成：**没有地址栏**、有独立任务栏图标、可固定 | **小**（~300 行，零新依赖） | 依赖装没装 Chrome/Edge；没有就退回默认浏览器标签页 |
| **② 原生窗口**（0.4.0） | `wry`（Rust）：Windows WebView2 / macOS WKWebView / Linux WebKitGTK | 10 成：真窗口 + 菜单 + 托盘 + 文件对话框 + 拖放 | **大**：新依赖树、Linux 要 `libwebkit2gtk`、CI 要装系统库、还要新 ABI | 三平台差异最大的一块 |

**用户 2026-11-04 拍板：两个都要，分两步** —— 先把「能开窗」做出来，同一版里再换成真窗口。

⚠️ 这么排的前提是**两代共用一套东西**，否则第二步等于重做：

```
          ┌──────────── 页面（html 构件拼的）────────────┐
          │  按钮/表格/输入框 —— 都是 M166 的构件        │
          ├──────────── wasm 引擎（jishi_wasm.wasm）─────┤
          │  程序逻辑；事件 = 一次完整执行（M167 的模型）│
          └──────────────────────────────────────────────┘
                  ↑ 页面 + 引擎 完全不变，只换"外壳"
   外壳 v1：系统浏览器的 app 模式（无地址栏）
   外壳 v2：wry 原生窗口（WebView2 / WKWebView / WebKitGTK）
```

⇒ v1 写完的页面与逻辑**一行不改**就能跑进 v2。这也是为什么第二步值得做 ——
不是推倒重来，是**换个壳**。

### v1 的接口（就 5 个，别扩）

### 9.6 M176 演练记录（2026-11-06，Windows 真机）

用**真的要发的那个安装器**（Inno）跑：装 0.3.0 → 跑脚本 / `jishi 医生` / 开窗 →
覆盖装 0.3.1 → 再跑一遍 → 卸载。脚本：`python tools/drill_install.py`（发版前的一次性验收，不进 CI —— 它会真装真卸真开窗）。

| 步骤 | 结果 | 备注 |
|---|---|---|
| 装 0.3.0、跑脚本、`jishi 医生` | ✅ | |
| 0.3.0 开窗 | ❌ | **白窗口**：那一版发行包没带 `jishi-wasm.js` / `jishi_wasm.wasm` / `WebView2Loader.dll` |
| 覆盖装 0.3.1 | ✅ | 版本、exe、三份素材全部就位 |

⚠️ **这个演练没覆盖的**（如实记，别当成"验过了"）：

- **不是真·干净机器**：本机装着 Rust / Python / Node，只是没让它们参与。真要验
  「没有任何开发环境的机器」，得用一台干净 Windows 虚拟机。
- **只有 Windows**：macOS / Linux 的 tar.gz + install.sh 走的是另一条路（M172 的判据覆盖了
  文本与清单，但**没有真机装过**）。
- **UAC 提权 / 非管理员账户 / 杀软拦截**：都没试。装到 `C://Program Files` 需要提权，
  这条路径没走过（演练用的是临时目录）。
- **升级路径只验了「0.3.0 → 0.3.1 覆盖装」**，没验跨大版本、没验「先卸再装」。

### 9.7 0.3.1 没达成的一条（进 0.4.0 待办）

0.3.1 的验收句是「写完 → `jishi 打包` → 干净机器装 → 双击 → 有窗口能用」。
**后半段没成**：`jishi 打包` 只打**用户自己的文件**（.jsh / .html / 清单.json），
**不带运行时**（`jishi.exe` + 两份 wasm 素材 + `WebView2Loader.dll`），也不注册
`.jsh` 关联。所以装到没装过基石的机器上「双击没反应」。

要做成一整条，得给 `打包` 加「**自带运行时**」模式：复制引擎与素材 → 生成入口 →
安装注册关联 → 卸载回收，并守住 `清单.json` 的三宿主契约。**一整站**，排进 0.4.0，
不在收口站开工。

**节奏与切分线**：

- **M170 与 M173 可并行**（一个动 AST/错误渲染，一个加新模块）；
- **M171 → M172 串行**（同一套产物）；**M174 → M175 串行**（同一套 ABI）；
- 🔴 **可切分线在 M173 与 M174 之间**：M170–M173 做完，0.3.1 的承诺（能装、能开窗）**已经兑现**；
  M174/M175 万一撞墙（wry 在某个平台编不过、CI 系统库搞不定），**整段顺延 0.4.0，0.3.1 照发** ——
  版本号不带「半成品」，但也不让一个依赖问题把整版卡死。
- ⚠️ **诚实提示**：一版里塞了「打包 + 两代窗口」三件大事，比 0.3.0 的密度还高。
  上面这条切分线就是为它留的保险 —— **别硬撑**。
