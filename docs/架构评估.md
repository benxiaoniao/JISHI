# 多引擎架构评估（M51 候选 · 内部文档，未公开）

> **缘起（2026-09-25 用户提问）**：「三执行器、五引擎这块，是不是现在继续维持和开发的
> 代价太大了？我们是不是要对这个架构进行优化了？当然还是以我们基石语言的设计核心为主。」
>
> 本文是**先量后答**的产物：所有结论都来自本轮实测，不掺估计值。
> 事实源：本文 + `PROGRESS.md` + `docs/设计决策.md`（D13/D14/D15/D16）。

## 一、先摆事实：五引擎现在是多大一块

| 层 | 文件 | 行数 | 谁维护 |
|----|------|------|--------|
| **共享层** | | | |
| 编译器 | `jishi/compiler.py` | 1134 | 一份，五引擎共用 |
| 运行时（语义 + 内建 + 值系统） | `jishi/runtime.py` | 2513 | 一份，五引擎共用 |
| 标准库（Python 侧） | `jishi/stdlib/*.py` | 3166 | 一份，**只有三执行器共用** |
| **执行层** | | | |
| 树遍历执行器 | `jishi/interpreter.py` | 826 | 三执行器之一 |
| Python VM 执行器 | `jishi/vm.py` | 905 | 三执行器之一 |
| C VM（C 代码） | `cvm/src/jsvm.c` | 2403 | 三执行器之一 |
| Node 宿主 | `node/*.js` | 5220 | 跨语言宿主 |
| Rust 宿主 | `rust/src/**` | 12145 | 跨语言宿主 |

**核心层（共享 + 三执行器）= 10947 行；宿主层（Node + Rust）= 17365 行。**

> ⚠️ **宿主层已经比核心层大了 1.6 倍。** 这是本次评估最刺眼的一个数字。

### 1.1 宿主层的行数构成（决定优化靶子在哪）

| 宿主 | VM 内核 | 标准库 | 系统原语（JSON/正则/加密/压缩…） |
|------|---------|--------|--------------------------------|
| Node（5220） | ≈ 659（vm.js 指令分派） + runtime.js 部分 | **≈ 2282** | 复用 JS 内置 |
| Rust（12145） | **3227**（lib.rs：VM + 值系统） | **5488** | **3391**（全自写，零依赖） |

**Rust 宿主有 73% 的代码（8879 / 12145 行）与「标准库」有关。**
Node 宿主也有一半以上（2282 / 5220）是标准库函数表。

## 二、代价到底有多大：两类改动对比

用实际提交量数据（都是本项目的真实提交）：

| 改动类型 | 实际提交 | 改动文件 | 行数 |
|---------|---------|---------|------|
| **加一个语言特性 / 指令**（M48 方法调用融合） | `a129953` | 12 个 | **564 行** |
| **加 6 个标准库模块 · 只做 Python 侧**（M50 第一批） | `733f715` | 21 个 | **2035 行** |
| **同一批补齐 Node + Rust**（M50 第二批） | `9c88f15` | 17 个 | **2604 行** |

**关键结论**：

1. **加「语言特性」很便宜** —— 564 行，而且**五引擎里有四个不用改**（编译器 + 三个执行器
   共用 `opcodes.py`；宿主只消费字节码，新指令只要不让默认产物变就行）。
2. **加「标准库」很贵** —— 一批 6 个模块，**先 2035 行（Python 侧），再 2604 行（补两个宿主）**。
   **补宿主比写第一版还多 28%**。这是真正的大头。

### 2.1 频率数据（近 60 个提交）

- 改动 `node/` 或 `rust/` 的提交：**18 / 60 = 30%**
- 改动 `cvm/` 的提交：**17 / 60 = 28%**
- 改动三执行器任一的提交：**25 / 60 = 42%**

也就是说：**约三成的提交要为宿主服务，四成为执行器服务。**

### 2.2 漂移风险是**静默**的（这是最危险的一点）

- 全仓**没有**「某个标准库模块必须五引擎都有」的检测测试。
- M50 第一批就是这样：Python 侧做完，Node / Rust **静默缺失**，
  `导入 统计` 会报「没有找到标准库模块」——**是我手工去测才发现的**，
  不是测试报出来的。
- 已有缺口实例：`加密.摘要("abc", 算法="md5")` 在 Node / Rust 上
  **静默用默认 sha256**（Python 给 `900150…`、两宿主给 `ba7816bf…`）。

> **也就是说：现在的架构不是「贵」的问题，是「错了不会报警」。** 这比贵更要紧。

## 三、但先别急：三执行器 ≠ 三份重复劳动

要分清哪些是**真重复**、哪些是**架构必需**。

### 3.1 三执行器：共享 80%，各自只写「执行内核」

三个执行器**共用**编译器、运行时、标准库（实测：`interpreter.py` / `vm.py` /
`cvm_bind.py` 全部 `from . import runtime as R`，且都走 `compile_source`）。

各自独有的：

| 执行器 | 独有部分 | 为什么不能省 |
|--------|---------|-------------|
| 树遍历（826 行） | AST 遍历 + Python try/except | **默认执行器**、调试器默认路径、语义最直观的参考实现 |
| Python VM（905 行） | 字节码分派 | **编译器产物的参考解释器**；调试器与 C VM 的语义基准 |
| C VM（2403 行） | C 字节码 VM + 宿主回调桥 | **性能天花板**（纯计算比树遍历快 9–46 倍）；真实项目实际加速来源 |

**三执行器的价值是「互相验证」**：`tests/test_cvm.py` 的 130 余项对拍，抓住过
无数语义分歧（M47 的内存泄漏、M48 的错误列号、M50 的上下文管理器缺口都是它抓的）。
**这是本项目最值钱的测试资产。**

### 3.2 两个跨语言宿主：重复的是**标准库**，不是 VM

- Node / Rust 各自实现 VM 内核（659 + 3227 行）—— 这部分**真正重复**，
  但**量不大**（合计不到 4000 行），且是「跨语言分发」的**核心卖点**：
  没有它，基石只是个 Python 包。
- 重复的大头是**标准库**：Node 2282 + Rust 8879 = **11161 行**，
  而这部分是**同一份逻辑写三遍**（Python / JS / Rust）。

## 四、关键实测：标准库可以写一遍、五引擎共用吗？

**可以。本轮做了 POC，结论是肯定的。** 这是本次评估最有价值的发现。

### 4.1 POC 做了什么

把 `统计` 模块（官方版 167 行 Python）用**基石自己**重写（68 行 `.jsh`），
编译成字节码，看三个引擎能不能都跑对：

| 引擎 | 输出 |
|------|------|
| 官方 Python 版（对照） | `1010 / 202.0` `2 2.5` `4 3` |
| 树遍历（跑字节码） | 同上 ✅ |
| **Node 宿主** | 同上 ✅ **逐字节一致** |
| **Rust 宿主** | 同上 ✅ **逐字节一致** |

**一行宿主代码都没写。** 因为库代码全是**语言自身的语义**，而语义在三个执行器
+两个宿主上**本来就必须一致**（这是硬约束 §1.2 保证的）。

### 4.2 代价：性能慢约 7 倍

同机同口径实测（C VM 调「求和」3000 次，10 个数）：

| 实现方式 | 每次耗时 | 相对 |
|---------|---------|------|
| 官方 Python 版标准库（走宿主回调） | **17.7 µs** | 1x |
| 基石版（纯字节码，零宿主标准库回调） | **130.9 µs** | **7.3x 慢** |

### 4.3 但这个代价**在真实项目里几乎不体现**

实测四个真实项目的标准库调用次数与总耗时：

| 项目 | 总耗时 | 标准库调用次数 |
|------|--------|--------------|
| 基石自述站/生成.jsh | 374ms | **26 次** |
| 排序跑分/排序.jsh | 1828ms | **4 次** |
| 待办清单/待办.jsh | 8ms | 5 次 |
| 成绩分析/分析.jsh | 5ms | 10 次 |

**标准库调用在真实项目里是「个位数到几十次」量级**，而耗时大头在**循环体内**。
即便把库函数改成慢 7 倍的版本，`生成.jsh` 也只会多几十毫秒（<10%），
而**热循环一次都不受影响**。

> ⚠️ 反过来说：**性能敏感的库函数不能这么改**。`排序` 那种被 10 万次调用的
> （如果将来有）必须留在宿主侧。所以要做**分层**，不是一刀切（见 §5）。

### 4.4 哪一类库可以「写一遍」——按 Rust 侧代码归类

| 类别 | Rust 行数 | 能否用基石写 |
|------|----------|-------------|
| **纯逻辑**（统计 / 编码 / html / 对比 / 配置 / 标识 / 迭代 / 容器 / 文本 / 参数 / 日志 / 数学 / 随机） | **2942** | ✅ 完全可以（POC 证明了） |
| **系统原语**（正则 / 加密 / 压缩 / JSON / 精确小数 / 文件 / 路径 / 系统 / 日期 / 表格） | **4770** | ❌ 需要宿主能力（OS / 大整数 / 正则引擎） |

**可移植比例约 38%**（按 Rust 侧行数）。按**模块数**算更高——25 个模块里，
纯逻辑的占 13 个（52%）。

## 五、三个方案（含取舍）

### 方案 A：维持现状，**补上「漂移检测」**（最小改动，先做）

**做什么**：加一个测试，遍历 Python 侧的 `jishi/stdlib/__all__` + `--lang-spec`，
断言「每个模块名在 Node 的 `STDLIB` 表与 Rust 的 `lookup()` 里都有」。
再补一个「同名函数的参数个数一致」的检查。

**收益**：
- 把**静默漂移**变成**测试红灯**——这是当前最大的风险，且修它最便宜。
- 不动任何架构，零性能代价。

**代价**：不减少任何重复劳动（照样要写三遍）。

**结论：无论选哪个方案，这一条都该先做。** 它是「止血」，不是「治病」。

---

### 方案 B：**「基石写的标准库」层**（推荐主线）

**做什么**：把标准库**分两层**：

```
jishi/stdlib/           ← 宿主原语层（Python/JS/Rust 各写一遍）
  ├── 正则.py / 加密.py / 压缩.py / json.py / 日期.py / 文件.py / 路径.py / 表格.py
  │     ↑ 必须宿主原生（OS / 大整数 / 正则引擎）
  └── __init__.py       ← 加载器：先查「基石库」，再查宿主层

stdlib-jishi/           ← 新增：基石写的标准库（**写一遍，五引擎共用**）
  ├── 统计.jsh / 编码.jsh / html.jsh / 对比.jsh / 配置.jsh / 标识.jsh
  └── 迭代.jsh / 容器.jsh / 参数.jsh / 日志.jsh
        ↑ 纯逻辑，编译进字节码，宿主零改动
```

**技术前提已全部验证**：
- ✅ 字节码天然支持多 code 对象（`payload.codes` 是数组，`main` 指入口）
- ✅ 三个引擎都能执行编译产物（POC 三处输出逐字节一致）
- ⚠️ **待补**：让 `导入 X` 能加载「预编译的基石模块」（现在宿主的 `IMPORT`
  只认内建表，`src==2`（本地包）在 Node/Rust 上直接报错）。
  需要设计一个「标准库字节码随程序一起打包」的机制。

**收益**：
- **纯逻辑模块的维护量从 3 份降到 1 份**：以 M50 那批为例，2604 行 → 约 900 行
  （只剩测试与加载器）。
- **一致性从「靠对拍发现」变成「结构上不可能不一致」**（同一份字节码）。
- 顺带一个战略收益：**基石的库用基石写**，是「自举」的实证，
  对「AI 便于调用」也是更好的示范（AI 读到的库源码就是目标语言）。

**代价**：
- 性能：这些库慢约 7 倍（§4.2）。**但真实项目调用次数是个位数到几十次**（§4.3），
  实际影响 <10%；**性能敏感的库不进这层**。
- 工程：要设计「库字节码的加载与缓存」（可复用 M47 的 AST 缓存的思路）。
- 调试体验：库内部出错时，栈帧要能正确显示 `.jsh` 库源码（现在调试器只认主脚本）。

**结论：推荐作为 M51 主线**，但它是个**中等规模工程**（比一个里程碑大），
建议拆两步：**先做一个模块打通链路（如 `编码`），再批量迁移**。

---

### 方案 C：**砍掉 Python VM 执行器**（不推荐）

**理由**：Python VM（905 行）看起来最「可砍」——它性能不如 C VM（0.65–1.1x），
功能上又被树遍历覆盖。

**为什么不推荐**：
1. 它是**编译产物的参考解释器**：C VM 有 bug 时，靠它判「是编译器错还是 C VM 错」
   （M47 的迭代器泄漏、M48 的错误列号都是这么定位的）。
2. 调试器的字节码路径依赖它（`jishi 调试 --执行器 vm`）。
3. Node / Rust 宿主的对拍**基准**是它（「与 Python VM 逐字节一致」是本项目
   所有跨宿主测试的判据）。
4. 砍掉只省 905 行（不到总核心层的 8%），却拆掉**最值钱的验证资产**。

> **唯一值得考虑的是**：如果将来 C VM 的调试器完全对齐、Node/Rust 的对拍基准
> 改成「与 C VM 一致」，可以重新评估。**现在不是时候。**

---

### 方案 D：**砍掉某个跨语言宿主**（明确不推荐）

**Node 宿主**：5220 行，但它是**唯一能跑在浏览器/无 Python 环境**的引擎——
那正是「跨语言分发」这个卖点的落地形态。砍掉它，基石就只是 Python 生态里的一个包。

**Rust 宿主**：12145 行（最大一块），但它是：
- **零依赖分发的唯一希望**（不装 Python 也能跑基石）
- 顺带产出的一批**手写实现**（正则引擎 935 行、JSON 259 行、inflate 276 行…）
  本身就是可复用的资产
- ⚠️ 但它**性能极差**（纯计算慢 C VM 约 1000 倍，见 AGENTS.md）——
  **它现在更像「语义参考实现」，不是性能选项**

> **结论：两个宿主都不砍**，但**不要把资源平均分给它们**。
> 方案 B 正好能大幅削减它们的标准库工作量（11161 行 → 只剩系统原语）。

## 六、以「设计核心」为准则复核

项目的两条设计核心（`AGENTS.md` §0.5）：**① 遵循中文语法习惯、发挥中文优点；
② 便于被大模型调用**（冲突时先保 ①）。三个方案逐条对照：

| 准则 | 方案 A（补检测） | 方案 B（基石库层） | 方案 C/D（砍引擎） |
|------|-----------------|-------------------|-------------------|
| **① 中文语法习惯** | 中性 | ✅ **加分**：库源码就是中文程序，是最有说服力的示范 | 中性 |
| **② 便于 AI 调用** | ✅ 加分：漂移会让 AI 生成「在 A 引擎能跑、B 引擎报错」的代码 | ✅ **加分**：AI 读一份中文库源码就够，不必读三份语言实现 | ⚠️ **减分**：砍引擎会缩小基石的可用面 |
| 跨语言分发（战略） | 中性 | ✅ **加分**：库随字节码走，分发物更完整 | ❌ **减分**：砍宿主直接削弱这条 |

**方案 B 与两条设计核心同向，且强化战略定位。这是推荐它的最主要理由。**

## 八、风险与诚实边界

1. **性能代价是真的**：基石库慢约 7 倍。§4.3 说真实项目影响 <10% 是**估算**
   （只量了 4 个项目、调用次数），**迁移后必须逐项目复测并公布**。
2. **加载机制是新增复杂度**：字节码模块的加载、缓存、失效、错误定位都要设计。
   **别低估这一块**——它的工程量可能超过迁移库本身。
3. **调试体验不能倒退**：库里出错时若栈帧显示不出 `.jsh` 源码，是**体验倒退**，
   必须在 M53 一并解决。
4. **Rust 宿主的 3391 行系统原语砍不掉**（零依赖的代价）。这是它的定位成本，
   如实保留。
5. **本评估未做的事**：没有实测「迁移后用真实项目跑分」（POC 只跑了 1 个模块）。
   迁移前应补一次完整的可行性验证。

> **三执行器不该动**（它是本项目最值钱的验证资产，砍它省 905 行却拆掉对拍基准）；
