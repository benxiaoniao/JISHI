# 前端契约（R1）—— 产物长什么样、怎么验收

> **一句话**：R 线要把前端从 Python 换成 Rust。这份文档规定
> **「前端每个阶段要产出什么」**，让两边（以及将来任何实现）用同一把尺子量。
>
> 工具：`tools/conformance.py`（`compare --from <目录>`）· 基线：`tests/conformance/`
> · 迁移路径见 `docs/架构迁移路径.md` · R0 的说明见 `docs/一致性夹具.md`
>
> ⚠️ 按 R1 的定义：**这一步不改任何行为，只定义接口。**

---

## 一、为什么要有「契约」

R0 的 `check` 验的是「**Python 前端还是老样子**」。从 R2 起要验的是
**「Rust 产出的产物，与 Python 的行为一致吗」** —— 于是需要两样东西：

1. 一个**「拿任意来源的产物来比」**的入口（`compare`）；
2. 一份说明**产物长什么样**的文档（本文）。

没有契约，两边会各写各的：Rust 侧照着「看起来对」的格式产出，
`compare` 报一堆差异，却分不清「是**实现**错了」还是「**格式**本来就不一样」。

---

## 二、版本号与变更规则

`FORMAT_VERSION = 2`（定义在 `tools/conformance.py`）

| 版本 | 变更 |
|---|---|
| 1 | R0 起：`tokens` / `ast` / `bytecode` / `diagnostics` 四阶段 |
| **2** | **R4**：`diagnostics` 补 `下划线` / `修正` / `渲染`（见 §4.4） |

| 情况 | 要不要 +1 |
|---|---|
| **产物结构**变了（加/删字段、改字段含义、改编码） | **要** |
| 只是某个字段的**值**变了（那是行为变了） | **不要** —— 该重冻基线 |

版本对不上时，`check` 与 `compare` 会**直接报「需要重新冻结」**，
不会拿旧基线硬比（那样会得出一堆假差异）。

## 三、顶层结构

**每个语料一个 JSON 文件**，文件名 = 语料的**扁平 id**：

```
tests/cases/01_算术.jsh         →  tests__cases__01_算术.json
examples/projects/待办清单/待办.jsh  →  examples__projects__待办清单__待办.json
jishi/stdlib-jishi/统计.jsh      →  jishi__stdlib-jishi__统计.json
```

（规则：去后缀 → 把 `/` 换成 `__`。`corpus_id()` 就是干这个的。）

文件内容：

```json
{
  "语料": "tests/cases/01_算术.jsh",
  "内容哈希": "sha256:1a2b3c4d5e6f7a8b",
  "tokens":  [...],      // 词法：token 数组
  "ast":     {...},      // 语法：AST 根节点
  "bytecode": {...},     // 编译：字节码 body
  "diagnostics": null    // 诊断：null 或一个诊断对象
}
```

### ⚠️ 四个阶段各自独立，「跳过」与「失败」必须分开

某语料在**词法**就报错 → 它的 `tokens` 是 **`null`**（**不是空数组**！），
`ast`/`bytecode` 也是 `null`，而 `diagnostics` 有内容。

这样读的人一眼能分出三种情况：

| 值 | 意思 |
|---|---|
| `[...]` / `{...}` | **这个阶段正常产出了** |
| `null` + `diagnostics` 有内容 | **这个阶段报了错**（如实记录失败在哪一步） |
| **键不存在** | 这一阶段**没提供**（`compare` 会报「未提供」，**不算通过**） |

## 四、四个阶段

### 4.1 `tokens` —— 词法单元数组

每个 token：

```json
{
  "类型": "Token",
  "type": "KEYWORD",          // 词法类别（见 `jishi/tokenizer.py` 的 TT_*）
  "value": "令",              // 词面（字符串 token 给**已解转义**的值）
  "line": 2,                   // 1 起
  "col": 1,                    // 1 起，**按码点计**（见 §5.3）
  "end_col": 1,                // 结束列（含）
  "source_line": "令 a = 7"    // 该 token 所在行的**原文**（不带换行）
}
```

`类型` 是给 AST 共用的「这是个什么节点」标记（token 恒为 `"Token"`）。

**实际会出现的 `type` 一共 10 种**：
`INDENT` `DEDENT` `NEWLINE` `NUMBER` `STRING` `NAME` `KEYWORD` `OP` `FSTRING` `EOF`。
⚠️ `jishi/tokenizer.py` 里那个 `TOKEN_TYPES` 集合**漏了 `FSTRING`**（M7 加插值
字符串时没补），别拿它当清单用 —— 少一种的后果是 Rust 侧直接 panic（故意的，
宁可不跑也别给错值；见 `core/src/lib.rs` 的 `kind_name_index`）。

**`value` 的四种形态**：大多数字符串 token 给 `str`；`NUMBER` 给 `int`/`float`；
`INDENT`/`DEDENT` 给 `int`（缩进宽度）；`EOF` 给 `null`；
**`FSTRING` 给分段列表** `[["text", …], ["expr", …], …]`（见 §4.1.1）。

#### 4.1.1 `FSTRING` 的分段表

```json
{"type": "FSTRING", "value": [["text", "你好，"], ["expr", "谁"], ["text", "！"]]}
```

它由 `{{` / `}}` 的字面花括号、嵌套花括号的表达式、以及空文本段共同决定 ——
分段少一项、多一项都是行为差异，所以专门有语料钉住
（`tests/cases/16_插值字符串边界.jsh`）。

### 4.2 `ast` —— 语法树根节点

**序列化规则**（通用，递归）：dataclass → `{"类型": 类名, ...字段}`
（`ast_nodes.py` 里 34 个节点类都按这个走）。

```json
{
  "类型": "Program",
  "line": 1, "col": 1,
  "body": [
    {"类型": "Assign", "line": 2, "col": 1,
     "targets": [{"类型": "Name", "line": 2, "col": 5, "名字": "a"}],
     "value": {"类型": "Number", "line": 2, "col": 9, "value": 7}}
  ]
}
```

⚠️ **难点在这儿**：`line`/`col` 要在**每个节点**上都对，
而且**脱糖的时机与位置**（`超()`、`匹配/情形`、推导式、条件表达式）
必须与 Python 侧**完全一致** —— 否则会出现「AST 一样、行为不一样」的隐蔽偏差。
这也是为什么 R5 的字节码对比**不能省**。

### 4.3 `bytecode` —— 字节码 body

**注意**：冻结进基线的是 `serialize.dump_json()` 的 body **去掉 `opcode_names`**
（那是引擎级常量表，73 个文件各抄一份纯属浪费；它在 `MANIFEST.json` 里记**一份**）。

```json
{
  "format": "jishi-bytecode",
  "version": 2,
  "checksum": "…",
  "payload": {
    "consts": [{"t": "int", "v": 7}, {"t": "str", "v": "你好"}],
    "names": ["打印"],
    "kw_names": [],
    "codes": [{
      "name": "<模块>", "params": [], "param_idx": [], "param_local": [],
      "param_cell": [], "param_kind": [],
      "nlocals": 1, "local_names": ["a"], "cellvars": [], "freevars": [],
      "firstlineno": 1,
      "instrs": [1,0,0,0,2,1, …]      // 扁平：每条 6 个 int32 = (op,a,b,c,line,col)
    }],
    "main": 0,
    "filename": "tests/cases/01_算术.jsh"
  }
}
```

**常量编码**（`_const_to_json`）：`{"t": "none"} | {"t":"true"} | {"t":"false"} |`
`{"t":"int","v":…} | {"t":"float","v":…} | {"t":"str","v":…}`。

⚠️ **超出 `Number.MAX_SAFE_INTEGER` 的整数按十进制字符串编码**
（`{"t":"int","v":"9223372036854775807"}`）—— JSON 的数字在 JS/Rust 里都是双精度，
直接写数字会丢精度。读取方按「`v` 是字符串就用大整数」处理。

### 4.4 `diagnostics` —— 第一个错误

```json
{
  "阶段": "语法",              // 词法 / 语法 / 编译（抛它的那一步）
  "码": "E0203",               // 错误码
  "标题": "这里少了冒号「：」",
  "消息": "…",
  "行": 1, "列": 1,
  "提示": "…",                 // 可能为 null
  "下划线": [4, 4],            // ← v2：`^` 指示的列区间（1 起、闭区间），可能为 null
  "修正": null,                // ← v2：{"old","new"} 文本替换建议（给模型自愈用）
  "渲染": "错误 E0203：…\n  ┌─ …\n  1 │ 如果 真\n    │     ^\n  │"
                               // ← v2：**用户真正看到的那段多行文本**
}
```

⚠️ **v2 为什么加 `渲染`**：它是上面那些「事实」的**下游产物**，看着冗余，
其实是**兜底** —— 哪天给错误加了一个事实字段却忘了列进本契约，两个实现的渲染
立刻就不一样；而「某个字段没进契约」这件事**本身是看不出来的**
（R3 就栽在「漏了一个字段，比对还是绿的」）。
**挑那个能连坐整个类的不变量，是一次就够的检查。**

⚠️ **只有基石自己的错误（`JishiError`）才配进这里**。
前端抛别的类型 = **实现有 bug**，`freeze` 会**拒绝冻结**
（理由见 `docs/一致性夹具.md`：不能把 bug 升格成标准）。

## 五、确定性要求 —— **做不到就没法比**

产物必须**逐字节可复现**，否则每次跑都不同，比对毫无意义。四条硬要求：

### 5.1 键排序 + 中文原样

`json.dumps(..., ensure_ascii=False, indent=2, sort_keys=True)`

- 键**排序**（不依赖插入顺序）；
- 中文**不转义**（`"令"` 而不是 `"\u4ee4"`）。

### 5.2 行尾一律 `LF`

写文件要显式 `newline="\n"`，`*.json` 在 `.gitattributes` 里钉成 `eol=lf`。
（2026-09-30 的教训：Windows 检出时被转成 CRLF，CI 上那条「行尾必须 LF」的
测试就红了，而本地是绿的。）

### 5.3 位置按**码点**计

「一个字符 = 一个 Unicode 码点」（M55 定的口径）——
`col`、`end_col`、字符串下标都按码点。⚠️ 这条对 **JS 宿主是陷阱**
（JS 字符串是 UTF-16，`s.length` 对 emoji 给 2）；Rust 侧按 `char` 数即可。

### 5.4 特殊浮点与路径

- `NaN` / `±Infinity` 写成字符串标记 `"@NaN"` / `"@Infinity"` / `"@-Infinity"`
  —— JSON 里没有这些字面量，**Rust 的 `serde_json` 会直接拒收**；
- 所有 `filename` 用**相对路径**（绝对路径换台机器就全变，还会把个人目录写进仓库）。

## 六、Rust 侧要产出什么（照着做就行）

**约定**：给你的实现一个「产出产物」的模式，把每个语料的结果写成
**一个 JSON 文件**，放在**一个目录**里，文件名用 §3 的规则。

然后验收：

```bash
python tools/conformance.py compare --from <你的产物目录>
# 只做了分词（R2 阶段）时：
python tools/conformance.py compare --from <你的产物目录> --stage tokens
```

**最小示例**（R2 只做分词时的产物，一个文件）：

```json
{
  "语料": "tests/cases/01_算术.jsh",
  "tokens": [
    {"类型": "Token", "type": "KEYWORD", "value": "令",
     "line": 2, "col": 1, "end_col": 1, "source_line": "令 a = 7"}
  ]
}
```

三条规矩：

1. **只提供你做到的那一阶段也行** —— 但 `compare` 会**如实报「未提供」**，
   默认（不带 `--stage`）时那就是**没过**。想只看分词就显式带 `--stage tokens`。
2. **语料覆盖要齐** —— 每个语料都要产出（现在是 **88** 个；漏一个报一条「外部未产出」）。
3. ⚠️ **别为了让 `compare` 变绿而改基线** —— 基线是「Python 现在的行为」，
   它变了意味着**Python 这边**动了，要单独解释（`freeze` 前先看 `git diff`）。

## 七、已知风险（还没解决，别踩）

| # | 风险 | 说明 |
|---|---|---|
| 1 | **浮点的打印口径** | 基线里 `float` 直接写成 JSON 数字；Python 的 `repr` 与 Rust 的 `serde_json` 在**极值**上可能给出不同文本（如 `1e+30`）。语料里目前没触发，R2 之后要用「含浮点的边角语料」专门验一次 |
| 2 | **`ast` 的脱糖时机** | 见 §4.2 —— 结构一致不代表行为一致（所以 R5 的字节码对比不能省） |
| 3 | **编译期诊断只覆盖到「第一个错」** | 多错并存时，谁先报取决于遍历顺序 —— 目前三方一致，但没有专门语料钉住 |
| 4 | **运行期诊断不在本契约内** | 本契约只管**前端**（词法/语法/编译）。运行期错误（除零、越界…）在 R6 纳入夹具 |

## 八、这份契约与 R 线的关系

```
R0 一致性夹具 ── 产出：基线（数据）    ✅ 已交付
R1 前端契约   ── 产出：契约（本文）+ compare（尺子）   ✅ 已交付
R2 分词器     ── 按本契约产出 tokens，用 compare --stage tokens 验收   ✅ 已交付
R3 语法       ── + ast（顺带把 diagnostics 的**语法**分支也一起比）   ✅ 已交付
R4 报错       ── diagnostics 补齐 下划线/修正/渲染（契约 v2）   ✅ 已交付（见 §十一）
R5 编译器     ── + bytecode（四项全给）                    ✅ 已交付（见 §十二）
```

**R1 完成之后，R2–R5 的验收方式就固定了**：改完 → 产出 → `compare` → 看差异定位。

## 九、R2 实测：Rust 分词器（2026-10-01）

### 9.1 怎么跑

```bash
python core/build.py                      # 编译 Rust 前端为 Python 扩展（要 Rust 工具链）
JISHI_FRONTEND=rust python -m jishi.cli 程序.jsh   # 用 Rust 前端跑（默认仍是 python）

python tools/conformance.py emit --frontend rust --out build/产物目录
python tools/conformance.py compare --from build/产物目录 --stage tokens   # ← R2 的验收
python tools/bench_frontend.py           # 吞吐
```

### 9.2 结果

| 项 | 结果 |
|---|---|
| 语料 | **85** 个（R0 的 73 + R2 新造的 12 个；R3 之后是 88，见 §10.2） |
| **逐 token 一致** | **85/85** ✅（另有 2 万组随机源码对拍，**0 处分歧**）；R3 之后扩到 **88/88** |
| 端到端吞吐（2.07 万行 / 734 KB） | 490.8 → **132.0 ms**（**3.72x**） |
| 纯分词核心吞吐 | 490.8 → **69.6 ms**（**7.05x**） |
| ⚠️ **端到端天花板** | **4.23x** —— 见 9.3 |

### 9.3 ⚠️ 为什么「端到端 ≥5 倍」够不着（这条要记住）

`rust/src` 的验收线原本写的是「分词吞吐 ≥ 5 倍」。实测下来**核心达标（7.05x）、
端到端不达标（3.72x）**。这不是实现不够好，**是接口决定的**：

```
端到端 = Rust 纯核心（69.6 ms） + 把 Token 对象交回 Python（62.4 ms）
                                  其中 **46.4 ms 是「纯造对象」的地板**
                                        （Python 里凭空造 11.7 万个 Token 就要这么多）
天花板 = 490.8 ÷（69.6 + 46.4） = 4.23x   ← 与实现无关
```

也就是说：**只要 `tokenize()` 还得把 `Token` 对象交回 Python，这两块就省不掉。**
把核心优化到 0 也只有 490.8 ÷ 46.4 = 10.6x 上限，而核心不可能到 0；
换句话说，**5 倍是这一层接口上的假想值**。

真正的收益在 R5/R8：那时下游（compiler 起的整条链路）不再需要 Python 对象。

✅ **2026-10-01 已拍板**：R2/R3 这一层的验收线 =「**纯核心 ≥5x 且产物逐项一致**」，
**「端到端 ≥5x」移到 R5** 验收 —— 那时端到端才有意义，在这层接口上是够不着的。

> 📌 这一条是**量出来的**，不是估的。数字与推导直接印在
> `tools/bench_frontend.py` 的输出里 —— 每次跑都会重新算一遍天花板，
> 免得以后有人拿着旧结论去追一个不存在的目标。

### 9.4 R2 新造的边角语料（12 个）

R0 的语料里 **emoji 一个都没有**（M56 的教训原话：「只在 ASCII 上测位置 = 没测」），
而列号口径恰恰是这次迁移的头号风险。于是补了：

| 语料 | 钉住什么 |
|---|---|
| `tests/cases/11_emoji与码点.jsh` | emoji 之后同一行的 token 列号按**码点**算 |
| `tests/cases/12_多行注释.jsh` | `#- … -#` 的跨行 / 同行 / 缩进块内三种形态 |
| `tests/cases/13_全角标点归一化.jsh` | `《》【】、．（）＋＊` 等归一化（**共 44 项**，容易只抄前 30 项） |
| `tests/cases/14_三引号独占行.jsh` | M39 那个「收尾引号独占一行不补 NEWLINE」的坑 |
| `tests/cases/15_数字写法.jsh` | `1.` / `1.e5` / `.5` / `1e-3` / `2^53+1`（跨语言丢精度的老坑） |
| `tests/cases/16_插值字符串边界.jsh` | FSTRING 分段表：`{{`/`}}`、嵌套花括号、空文本段 |
| `tests/error_cases/36–40` | E0105 无法识别的字符；E0104 的四个变体（三引号未闭、插值表达式未闭、插值字符串未结束、转义符没内容） |
| `tests/frontend_cases/01_超范围整数.jsh` | **新语料类别**：编译得过、但某个执行器**有意拒绝**（超 i64 ⇒ C VM 报 E2005，两个 Python 执行器是任意精度）。⚠️ 契约 §4.3「超过安全整数按十进制**字符串**编码」那条分支，**只有它走得到** |

⚠️ **CRLF / 孤立 `\r` / BOM 进不了语料目录**：`Path.read_text` 默认做通用换行，
`\r\n` 会被**悄悄归一化**掉，文件里存不住。这类输入一律写进
`tests/test_m59_tokenizer_rust.py` 的**字符串级**测试（那里有 24 条）。

### 9.5 ⚠️ `frontend` 这个语料类别是 R2 加的

`tests/cases/*.jsh` 有一套不成文的约定：**三个执行器都要能跑**（`test_cvm.py`
与黄金文件都按这个前提写）。于是「C VM 有意拒绝、但前端必须处理」的语料无处安放 ——
而 R3/R5 恰恰需要它们。所以单开一类：
**编译得过、但某个执行器可能拒绝**的语料放 `tests/frontend_cases/`，
只进一致性夹具，不进黄金/对拍测试。

## 十、R3 实测：Rust 解析器（2026-10-01）

### 10.1 结果

| 项 | 结果 |
|---|---|
| 语料 | **88** 个（R2 的 85 + R3 新造的 3 个，见 §10.2；R4 又补 2 个 → 90） |
| **AST 逐项一致** | **88/88** ✅（另有 **5 万组随机源码对拍 0 分歧**；40 个脚本端到端跑出来也一样）；R4 之后扩到 **90/90** |
| 语法阶段诊断一致 | **88/88** ✅（码 / 行列 / 文案 / 提示 / `^` 下划线逐字）；R4 之后扩到 **90/90** 且字段更全 |
| 端到端吞吐（2.07 万行 / 735 KB） | 823.3 → **270.6 ms**（**3.04x**） |
| 纯语法核心吞吐 | 823.3 → **145.9 ms**（**5.64x**） |
| ⚠️ 端到端天花板 | **4.73x**（同一套算法：纯核心 + 纯造 AST 对象的地板） |
| 转对象占比 | **46%**（7 万个 AST 节点 ≈ 125 ms，其中纯构造地板 28 ms） |

> 口径说明：语法这一项量的是**整条前端**（源码 → AST，含分词），两边都是。
> 所以「Python 基线 823 ms」≈ 分词 498 ms + 语法 325 ms。
> 与 R2 一样，**别拿端到端倍数判成败** —— 天花板 4.73x 是接口给的。

### 10.2 R3 新造的 3 个错误语料

这三个都是 R3 对拍时**先发现分叉、才补成语料**的（顺序很重要：语料是结果，不是计划）：

| 语料 | 钉住什么 |
|---|---|
| `tests/error_cases/41_块首后空行.jsh` | **`如果 真：` 后面跟一个空行** ⇒ 报错行号必须是 **2:1**（不是 1:1）。这正是「Rust 侧反拼出来的源码短了一行」那个坑的表现 |
| `tests/error_cases/42_类外超.jsh` | 类外 `超()` 那条错的**源码行与 `^` 下划线**（它由解析**之后**的补检查抛出，不走 `Parser._err`，一开始漏了两样） |
| `tests/error_cases/43_整行插值字符串.jsh` | 插值字符串落在**语句位置**时的文案必须是「**插值字符串**」，不许出现 `[('text', …)]` 这种内部结构 |

### 10.3 ⚠️ 接口改了：`parse_source(源码)` 才是生产入口

R3 开工时按「`parse(tokens, source_lines, filename)` 的第二参反拼源码」做，
**跑到一半发现这个前提是假的**：

* `source_lines` 是**有损**载体 —— `incremental.split_lines` 会去掉末尾空行，
  反拼出来的文本比原文短，于是 **EOF 行号偏移、报错行号整体少一行**
  （实测 9 个样例里错 4 个，全落在「块首后面跟空行」这类形状上）。
* 而且 LSP 那条路（增量分词）**本来就拿到的是 `inc.lines`**，它正是丢末尾空行的那种。

于是改成：

1. Rust 侧 `parse` **吃源码文本**（AST 只由文本决定，`tokens` 是冗余的）；
2. 新增 **`parse_source(source, filename)`** 作为生产入口 —— CLI / 检查器 /
   LSP / 调试器 / 沙箱 全部改走它。**顺带省掉一次重复分词**（原来调用方先
   `tokenize`、Rust 侧 `parse` 又自己分词，同一份源码要扫两遍）；
3. `parse(tokens, lines, f)` 保留给 **LSP 增量分词**（它手里已经有 tokens），
   并加**精确守卫**：拿 token 流末尾 EOF 的**行号**当标尺去量反拼出来的文本
   —— 对不上就**当场抛错**，不猜、不静默。

> 📌 守卫为什么能做得「精确」：词法器给 EOF 记的行号**恒等于**它算出来的
> 「原文行列表长度」（末尾空行去掉），这是 `Tokenizer.__init__` 的确定行为。
> 于是「EOF 行号 ≠ 反拼文本的行数」等价于「丢了内容」——没有一个假阳性。
> ⚠️ 判据要连**剥开头 BOM** 一起算（`"\ufeff"` 这种输入剥完是 0 行），
> 少一步就会对**合法**输入误报。**误报比不报更糟**：走对路的人被拦住之后，
> 大家会把守卫关掉。

### 10.4 R4 的范围随之变了

R3 交付时**顺手把「语法阶段」的 `diagnostics` 也纳入了比对**（同一个 parse 出口，
不花额外成本）。所以 R4 要做的不是「报错全都比对一遍」，而是：

- **把比较面补全** —— 事实不止六个字段（见 §十一）；
- **把「哪些码真的会出现」查清楚**（§11.2：「表里有」≠「会出现」）；
- **执行期 / 编译期**的报错留给 R5/R6（那时才有产物）。

## 十一、R4 实测：前端报错（2026-10-01，契约升 v2）

### 11.1 把「比较面」补全

v1 的 `diagnostics` 只比六个事实（码 / 标题 / 消息 / 行列 / 提示），而用户看到的
是 `render()` —— 里面有**源码行**与 **`^` 下划线**。所以 v2 补了三样：

| 字段 | 是什么 |
|---|---|
| `下划线` | `^` 指示的列区间 `[起, 止]`（1 起、闭区间） |
| `修正` | 机器可读的替换建议 `{"old","new"}` |
| `渲染` | **用户真正看到的那段多行文本**（`render()` 的结果） |

⚠️ `渲染` 看着冗余，其实是**兜底**：哪天给错误加了一个事实字段却忘了列进契约，
两个实现的渲染立刻不一样 —— 而「字段没进契约」这件事**本身是看不出来的**。
R3 就栽在这里（漏字段、比对仍是绿的）。

### 11.2 🔴 「表里有这个码」≠「这个码真的会出现」

新工具 `tools/probe_errcodes.py` 做的就是这个体检 —— **以前从来没人查过**。
前端（词法 E01xx + 语法 E02xx）共 **13 个码**，第一次跑的结论：

| 档 | 数量 | 说明 |
|---|---|---|
| ① 语料钉住 | **11**（E0205 接上后） | 该码在冻结基线的某个语料里出现过（最硬：两个实现必须逐字一致） |
| ② 登记为不可达 | **2** | `E0100` / `E0200`：家族根，只作 `isinstance` 用 |
| ③ 缺口 / 死码 | **0** | —— |

🔴 **E0205「括号没有闭合」是死码**：`ParseUnclosedError` 的定义在、`errcodes.py`
的说明文案在、`jishi 错误 E0205` 也查得到，**但全仓库没有任何触发点**
（括号没闭合其实报 `E0201`）。也就是说：这是一份**永远兑现不了的承诺** ——
用户照着查一个不可能发生的错，模型照着一份描述去猜不存在的故障。

✅ **2026-10-01 拍板接上**（见 §11.5）。

🔴 **E0204「这里需要一个名字」可达、却一个语料都没有**：八个形状能触发它
（`令 = 1` / `甲.()` / `函数 ()：` / `类 ：` / `导入 ` …）。R4 补了两个进语料。

⚠️ **「不可达」必须登记且经得起复核**（本项目的老规矩）：
`verify_unreachable()` 会静态复核「实现代码里是不是真没人引用它」——
哪天有人把 E0205 接上了，这条登记就会**报红提醒复核**，而不是悄悄过期。

### 11.3 🔴 两条还原路径各抄一份字段清单 → 词法那条漏了「修正」

R2/R3 时，「扩展事实 → `JishiError`」有**两个出口**，各自抄了一份字段清单：

* 语法那条（`parser._make_parse_error`）读了 `修正` ✅
* 词法那条（`tokenizer._rust_tokenize`）**没读** ❌ —— 而当时**恰好没有一个
  词法错误带 `fix`**，所以怎么测都是绿的。

这是「**两份清单并存 + 恰好没用到**」的典型缺口：**测不出来，不代表没问题**。

处置：收成一个出口 `errors.from_extension`，字段表 `EXTENSION_FIELDS` 作单一来源；
再用**字段表往返测试**（`tests/test_m61_frontend_errors.py`）把七个字段
在**两条路径**上都验一遍 —— 加字段的人只改一处，测试立刻盯着他。

### 11.4 验收做法

```bash
python tools/conformance.py emit --frontend rust --out build/产物目录
python tools/conformance.py compare --from build/产物目录 --stage diagnostics
python tools/probe_errcodes.py        # 错误码体检
python -m pytest tests/test_m61_frontend_errors.py
```

结果：**90/90 语料**在两前端上 `tokens` / `ast` / `diagnostics` 三阶段逐字一致
（含 `下划线` / `修正` / `渲染`）。

### 11.5 ✅ 把死码 E0205 接上（2026-10-01 拍板）

体检把 E0205 标成「死码」之后，作者拍板**接上**（另一条路是删掉）。

**规则**：期望右括号（`)` / `]` / `}`）而**已经到文件末尾** ⇒ `E0205`。

⚠️ **只认「走到文件末尾都没等到」这一种**。中途撞上别的 token 时（

```
令 乙 = [1, 2
令 丙 = 3
```

）仍报 `E0201`「这里需要「]」，但看到了「令」」—— **那时「看到了什么」
比「括号没闭合」更有用**：它直接指出冲突发生在哪里。别为了把码归拢而把信息丢掉。

**报错位置指向那个没闭合的开括号**（而不是 EOF）：

```
错误 E0205：括号没有闭合（这里需要「)」，但已经到文件末尾了）
  ┌─ x.jsh:1:7
  │
  1 │ 令 甲 = (1 + 2
    │       ~^
  │
  提示：给这里这个「(」补上对应的「)」。
```

为什么非要往回找：**EOF 那个 token 的位置是「最后一行第 1 列」、`source_line`
还是空的** —— 指着它对用户毫无帮助，连源码行都显示不出来。实现是错误路径上的
一次 O(n) 回溯扫描（找最近的那个没闭合的开括号），正常解析走不到。
两个前端各一份（`parser.py` 的 `_find_unclosed_opener` / `parser.rs` 的同名方法）。

**顺带修掉一处同类毛病**：EOF 的 `value` 是 Python 的 `None`，不给它名字就会印进
中文报错（「这里需要一个值，但看到了「**None**」」）。现在 `_tok_text` 的标签表里
`EOF → 文件末尾` —— 和 R3 那个「插值字符串把分段表泄出来」是同一类毛病：
**凡是内部表示，都不许落到用户眼前**。

结果：E0205 有语料了（`46_括号没闭合` / `47_方括号没闭合`），
**11 个可达码全部有语料钉住、0 个死码**，两个前端在 92 个语料上三阶段逐字一致。

## 十二、R5 实测：Rust 编译器（2026-10-02，四阶段全给）

### 12.1 结果

| 项 | 结果 |
|---|---|
| 语料 | **92** 个（与前几步同一批，**没有新增**） |
| **字节码逐字节一致** | **92/92** ✅（**连 `checksum` 都相同** —— 它是 payload 的 SHA-256） |
| 另 | tokens / ast / diagnostics 也都 **92/92**（前面几步的成果没被破坏） |
| 随机源码对拍 | **3 万组 0 分歧** |
| 编译端到端（2.07 万行 / 735 KB） | 2035.0 → **378.9 ms（5.37x）** |
| （对照）Rust 也做一份对象产物 | 400.2 ms（5.08x）—— 那是 VM/CVM 那条路，仍要付地板 |

✅ **「端到端 ≥5x」这条验收线（2026-10-01 从 R2 挪过来）在 R5 兑现了。**

### 12.2 🔴 为什么在 R5 才兑现：**换的是产物的形态**

R2/R3 的端到端倍数一直撞在一堵墙上：

```
天花板 = 基线 ÷（纯核心 + 把对象交回 Python 的地板）      ← 与实现无关
```

「造 Python 对象」这一项省不掉，因为 `tokenize()` / `parse_source()` 的**返回值**
就是 Python 对象。

R5 的产物是**字节码 JSON 文本** —— 文本没有「对象构造」这一步，于是这条路
**没有地板**。这不是「Rust 更快了」，是**接口换了**：
`compile_to_json()` 全程原生（Rust 解析 + Rust 编译 + Rust 拼 JSON）。

⚠️ 但 **Python VM / C VM 那条路仍要对象**（`compile_source()`），所以那条路依旧有地板
（5.08x vs 5.37x）。**别拿它判 R5 的成败** —— 口径要说清楚。

### 12.3 ⚠️ `compile_module()` 不是多余的

本可以让 `compile_source()` 「拿 JSON 反序列化回来」了事 —— **不行**：
`Code.local_hints` **不在字节码 JSON 里**（格式没有这个字段），而字节码执行器
报错时要用它：

```
外层也有一个叫「甲」的变量。在这个函数里给它赋过值，它就成了这个函数的
局部变量，赋值之前不能读取
```

只给 JSON 的话，rust 前端跑 VM/CVM 时这句话会**静默消失** —— 两个前端就有了
语义差异。所以 Rust 侧**另给一份真对象**，并有测试盯着（`test_局部提示没丢`）。

> 📌 通用形式：**「契约产物」与「调用方真正需要的东西」未必是同一个**。
> 用 JSON 当唯一出口时，先问一句「有没有哪个字段是格式装不下、但下游在用的」。

### 12.4 🔴 移植时抓到的一个既有 bug（**与 R5 无关，逐字复刻、待拍板**）

`jishi/compiler.py` 的 `_collect_stmt` **没有 `Try` 分支**（`Raise` / `Break` /
`Continue` / `Pass` 也没有）。于是「只在 `尝试` 块里赋过值的名字」进不了
`scope.bound`，会被编成**全局**：

```
令 甲 = 100
函数 f()：
    尝试：
        令 甲 = 1
    捕获 值错误：
        通过
    返回 甲
打印(f())
打印(甲)
```

| 执行器 | 输出 |
|---|---|
| 树遍历 | `1` `100`（`甲` 是 f 的局部） |
| Python VM | `1` `1`（`甲` 是全局，被 f 改掉了） |
| C VM | `1` `1` |

**三个执行器语义不一致** —— 违反项目的第一条硬约束。R5 的做法是
**逐字复刻、一个字都不动**（改它就改变了既有行为，那是另一件事、要单独拍板），
并把它记在这里。修法很小（`_collect_stmt` 加一个 `Try` 分支：body / handlers /
finalbody 都按语句收集），但会动基线、要重跑三执行器对拍。

> 📌 这条是**逐行移植**的副产品：为了搬对，得把每一行都读懂 ——
> 读懂了，就看见了这个缺口。**「移植」本身就是一次最彻底的代码审查。**
