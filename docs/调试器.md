# 基石调试器（M37 · 主线 B1）

> 目标：兑现北极星的后半句「**出问题能快速定位**」。M17 把报错与调用栈做扎实了，
> 但「程序跑错了但没报错」这类问题一直只能靠 `打印()` 大法。现在可以设断点、
> 单步、看变量与调用栈了。

```bash
jishi 调试 脚本.jsh                 # 停在第一句，之后听你指挥
jishi 调试 脚本.jsh --断点 12        # 直接跑到第 12 行
jishi 调试 脚本.jsh --断点 12,20 --不停在入口
jishi 调试 脚本.jsh -b 12 --命令 "变量；查看 单价 * 数量；继续"   # 自动跑一遍（演示/脚本化）
```

暂停时长这样：

```
暂停（命中第 2 行的断点） 第 2 行 · 函数「倍」
→  2 │     令 果 = 值 * 2
（输入「帮助」看命令）
调试 > 变量
当前帧（函数「倍」）的变量：
  值 = 10
  （另有 37 项内建/临时变量没显示，要看用「变量 全部」）
调试 > 继续
```

## 一、命令一览

| 命令 | 别名 | 作用 |
|------|------|------|
| `继续` | `c` | 跑到下一个断点（没有断点就跑完） |
| `单步` | `s` | 执行下一条语句，**会进入**被调用的函数 |
| `下一步` | `n` | 执行到本帧的下一条语句，**不进入**函数 |
| `跳出` | `o` | 跑完当前函数，回到调用它的地方 |
| `断点` | `b` | 列出断点；`断点 12`、`断点 12,15` 加断点 |
| `取消断点 12` | `d` | 删掉某个断点；`清空断点` 全删 |
| `变量` | `v` | 看当前帧的变量（`变量 全部` 连内建与脱糖临时变量） |
| `查看 表达式` | `p` | 在当前帧里求值，例如 `查看 单价 * 数量`、`查看 长度(列表)` |
| `栈` | `bt` | 调用栈（由内到外，每层标着它当前停在哪一行） |
| `源码 [行号]` | `l` | 看当前行（或指定行）附近的源码 |
| `帮助` | `h` / `?` | 命令表 |
| `退出` | `q` | 结束调试会话（程序不再往下跑；`最终` 块会照常执行） |
| *(直接回车)* | | 重复上一条命令 |

停顿处的三种入口：`--断点 行号`、入口自动停（`--不停在入口` 可关）、
以及命令里现加（`断点 12`）。

## 二、出错时会看到什么

调试会话里程序出错时，会**先打一份调试现场**，再打正式的中文报错：

```
程序在第 3 行出错了 —— 出错时的现场（最后执行到 第 3 行 · 函数「倍」）：
当前帧（函数「倍」）的变量：
  值 = 10
  果 = 20
调用栈（由内到外）：
  #0 第    3 行  函数「倍」
  #1 第    6 行  函数「主」
  #2 第    9 行  模块顶层
（想复盘就改脚本、带上同一组断点再跑一次）

错误 E0301：找不到这个名字（找不到名字「无此名字」）
  ┌─ 演示.jsh:3:12
  │
  3 │     返回 果 + 无此名字
    │            ^
  │
调用链（从外到内）：
  倍 ← 第 6 行
```

两段是**互补**的：正式报错说「错在哪」，调试现场说「**错的时候变量是什么**」
——后者才是定位问题的关键信息。

## 三、现状与边界（如实说明）

| 能力 | 现状 |
|------|------|
| **树遍历执行器**（`jishi 脚本.jsh` 默认那条路） | ✅ 断点 / 单步（进/过/出）/ 变量 / 调用栈 / 表达式求值 |
| **Python VM**（`--load-bytecode` 等字节码路径） | ❌ **暂不支持调试** |
| **C VM** | ❌ **暂不支持调试** |
| Node / Rust 宿主 | ❌ 不适用（它们是字节码执行器，同上） |
| 条件断点（`断点 12 如果 x > 3`） | ❌ 未做（B1 之外；现在可以用「断点 + 查看」，或用 `--命令` 脚本） |
| 观察点（值被改写时停下） | ❌ 未做 |

**为什么只有树遍历能调试？** 树遍历里「一个语句 = 一次 `exec_stmt`」是天然的
暂停点，一个钩子就同时给出断点、单步、局部变量与调用栈；字节码执行器（Python VM
/ C VM）是栈机，只知道指令、没有「语句边界」事件，要么每步比对行号表、要么加新
指令，C VM 还得先让宿主回调把帧传出来。所以主线 B1 先落最见效的一处，
字节码执行器的调试器列入后续（路线图主线 B）。

**另外两条已知边界**：

- **块关键字行不能设断点**：`否则：`、`捕获：`、`最终：` 这些行是块的一部分、
  不是独立语句（`否则` 那一行在 AST 里连节点都没有），断点加在上面**不会触发**。
  CLI 加断点时会明确提示「这一行没有可停的语句」，而不是静默无效。
- **从 Python 侧回调进来的基石函数不会在其中暂停**：例如
  `列表.映射(列表, 函数(x)：…)` 里的那个函数——它是由 Python 侧的 `__call__`
  进入的，不在 `_call_stack` 上（与 M17 的错误调用栈同一限制）。
  直接调用（`函数(x)：…` 显式调用）不受影响。

## 四、实现说明（给改这个模块的人）

- 钩子只有两个：`interpreter.exec_stmt` 开头的 `before_stmt`，以及
  `interpreter._eval_call` 里的 `push_frame` / `pop_frame`。
  **它们只读不写**——不改变任何语义，所以「带调试器跑」与「不带」的输出必须
  逐字节相同（`tests/test_m37_debugger.py` 里有用例钉住）。
- 单步的三种语义全都由「帧深」推出：`单步` 停在任意深度的下一条语句、
  `下一步` 停在 `深度 ≤ 暂停时深度`、`跳出` 停在 `深度 < 暂停时深度`。
- **出错现场是「执行每条语句前」留的快照**：错误是在语句执行到一半时冒出来的，
  等它传到 `run()` 时帧已经被 `finally` 弹干净了，那时再问「当前帧」只会得到
  模块顶层（实现时真实踩到过）。
- **「退出」用 `DebugQuit`（`BaseException`，不是 `JishiError`）**：否则用户程序里
  一句 `捕获：` 就能把「退出」吞掉。配套地，`interpreter._do_try` 里把它与
  `中断`/`继续`/`返回` 并列显式放行（那边的 `except BaseException` 是为翻译
  Python 异常写的），于是「退出」也会照常执行 `最终` 块。
- **命令输入按「字节 → UTF-8」解码**：管道输入的中文命令若走文本层，在中文
  Windows 上会按 GBK 解码成乱码（与 M23 的源码 stdin 同一坑）；管道输入还会
  自己回显一遍命令，否则记录里读不出「哪句是用户敲的」。
