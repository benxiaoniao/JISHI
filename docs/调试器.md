# 基石调试器（M37 · 主线 B1；M39 补字节码执行器；M40 补 C VM）

> 目标：兑现北极星的后半句「**出问题能快速定位**」。M17 把报错与调用栈做扎实了，
> 但「程序跑错了但没报错」这类问题一直只能靠 `打印()` 大法。现在可以设断点、
> 单步、看变量与调用栈了——**三个执行器都有**，而且同一个程序、同一组断点、
> 同一串命令，三者的会话记录**逐字相同**。

```bash
jishi 调试 脚本.jsh                     # 停在第一句，之后听你指挥（默认树遍历）
jishi 调试 脚本.jsh --断点 12           # 直接跑到第 12 行
jishi 调试 脚本.jsh --断点 12,20 --不停在入口
jishi 调试 脚本.jsh --执行器 vm         # 换字节码执行器（Python VM）调
jishi 调试 脚本.jsh --执行器 cvm        # 换 C 虚拟机调（需先构建 jsvm 动态库）
jishi 调试 脚本.jsh -b 12 --命令 "变量；查看 单价 * 数量；继续"   # 自动跑一遍
```

暂停时长这样：

```
暂停（命中第 2 行的断点） 第 2 行 · 函数「倍」
→  2 │     令 果 = 值 * 2
（输入「帮助」看命令）
调试 > 变量
当前帧（函数「倍」）的变量：
  值 = 10
  （另有内建/临时变量没显示，要看用「变量 全部」）
调试 > 继续
```

## 一、命令一览

| 命令 | 别名 | 作用 |
|------|------|------|
| `继续` | `c` | 跑到下一个断点（没有断点就跑完） |
| `单步` | `s` | 执行下一条语句，**会进入**被调用的函数 |
| `下一步` | `n` | 执行到本帧的下一条语句，**不进入**函数 |
| `跳出` | `o` | 跑完当前函数，回到调用它的地方 |
| `断点` | `b` | 列出断点；`断点 12`、`断点 12,15` 加断点 |
| `取消断点 12` | `d` | 删掉某个断点；`清空断点` 全删 |
| `变量` | `v` | 看当前帧的变量（`变量 全部` 连内建与脱糖临时变量） |
| `查看 表达式` | `p` | 在当前帧里求值，例如 `查看 单价 * 数量`、`查看 长度(列表)` |
| `栈` | `bt` | 调用栈（由内到外，每层标着它当前停在哪一行） |
| `源码 [行号]` | `l` | 看当前行（或指定行）附近的源码 |
| `帮助` | `h` / `?` | 命令表 |
| `退出` | `q` | 结束调试会话（程序不再往下跑；`最终` 块会照常执行） |
| *(直接回车)* | | 重复上一条命令 |

停顿处的三种入口：`--断点 行号`、入口自动停（`--不停在入口` 可关）、
以及命令里现加（`断点 12`）。

## 二、出错时会看到什么

调试会话里程序出错时，会**先打一份调试现场**，再打正式的中文报错：

```
程序在第 3 行出错了 —— 出错时的现场（最后执行到 第 3 行 · 函数「倍」）：
当前帧（函数「倍」）的变量：
  值 = 10
  果 = 20
调用栈（由内到外）：
  #0 第    3 行  函数「倍」
  #1 第    6 行  函数「主」
  #2 第    9 行  模块顶层
（想复盘就改脚本、带上同一组断点再跑一次）

错误 E0301：找不到这个名字（找不到名字「无此名字」）
  ┌─ 演示.jsh:3:12
  │
  3 │     返回 果 + 无此名字
    │            ^
  │
调用链（从外到内）：
  倍 ← 第 6 行
```

两段是**互补**的：正式报错说「错在哪」，调试现场说「**错的时候变量是什么**」
——后者才是定位问题的关键信息。

## 三、现状与边界（如实说明）

| 能力 | 现状 |
|------|------|
| **树遍历执行器**（`jishi 脚本.jsh` 默认那条路） | ✅ 断点 / 单步（进/过/出）/ 变量 / 调用栈 / 表达式求值 |
| **Python VM**（`--执行器 vm`） | ✅ 同上（M39 补齐） |
| **C VM**（`--执行器 cvm`） | ✅ 断点 / 单步 / 变量 / 调用栈（M40 补齐）；**就地求值暂不支持**（C 侧没有「在任意帧上求表达式」的入口，会明确说明而不是给错值） |
| Node / Rust 宿主 | ❌ 不适用（它们跑的是 Python 侧编译好的字节码，调试在 Python 侧进行） |
| 条件断点（`断点 12 如果 x > 3`） | ❌ 未做（现在可以用「断点 + 查看」，或用 `--命令` 脚本） |
| 观察点（值被改写时停下） | ❌ 未做 |

**三个执行器的会话记录逐字相同**：同一份脚本、同一组断点、同一串命令，
`--执行器 树遍历` / `vm` / `cvm` 的输出**一字不差**（含变量表、调用栈、
出错现场、`退出` 行为）。这不是巧合，是 `tests/test_m39_vm_debugger.py`
（树遍历 vs VM）与 `tests/test_m40_cvm_debugger.py`（三者）里逐项对拍的结论
——包括三种循环写法、闭包、类体、空块、回调、`尝试/捕获/最终`。

### 字节码执行器怎么会有「语句边界」（B5 的做法）

栈机只知道指令，但**编译器知道**：`compile_stmt` 会给每个语句的**第一条指令**
打一个标（指令上的 `stmt_line`），调试器只在标记处暂停。标「首指令」而不是
「语句范围内的每一行」是刻意的：

- 循环的回边（`遍历`→FOR_ITER、`当`→条件、`循环 n 次`→计数器判断）都落在
  语句**中部**，不落在首指令上，于是**循环头只停一次**、循环体每轮都停——
  与树遍历里 `A.For`/`A.While` 只被 `exec_stmt` 进入一次完全一致；
- 空块 `:` 与类体里的方法定义行，编译器会补一条「空操作」指令（常量入栈再
  弹出）专门用来挂标记，否则那些行在字节码里停不住、在树遍历里停得住。

不变式：**打标行的集合 == AST 里语句行的集合**。`tests/test_m39_vm_debugger.py`
拿 `examples/` 与 `tests/cases/` 全量对拍这条不变式——破了就意味着「某一行在
一个执行器停得住、在另一个停不住」。做 B5 时这条不变式抓出过两个真问题
（类体里的方法定义行、空块 `:` 行，原先两边都停不住）。

**代价**：挂上调试器（哪怕从不暂停）比不挂慢约 13%；不挂调试器时每条指令
只多一次 `is not None` 判断（几十纳秒）。

### C VM 也补上了（M40）——做法与 Python VM 同源

C 侧的栈帧、局部槽都在 C 里，Python 侧看不见，所以 M39 当时把它判为「暂不做」。
M40 补上了，思路是**不让调试器去猜执行器内部**，而是给 C 侧加四个最小的只读入口
（`cvm/include/jsvm.h`）：

| 入口 | 作用 |
|------|------|
| `jsvm_set_stmt_marks` | 收下**语句起始表**（与指令流等长，非 0 = 该指令是某语句的第一条） |
| `jsvm_set_stmt_hook` | 装**语句钩子**：每条语句首指令执行前回调一次 |
| `jsvm_frame_meta` | 问一帧的「代码下标 + 调用点行列」（调用栈要用） |
| `jsvm_dump_locals` / `jsvm_dump_globals` | 把一帧的局部槽与单元、或全局变量交给宿主转换 |

三处刻意的设计：

1. **语句起始表是单独一张 int32 数组**，不往指令里加字段。指令宽度（6 个 int32）
   是跨语言字节码格式的一部分（Node / Rust 宿主也按它读），为一个调试功能改公开
   契约不划算。
2. **钩子的「是不是语句起始」判断放在 C 主循环里**，而不是每条指令都回调 Python：
   不挂调试器时只多一次指针判空；挂了也只多一次数组查表。
3. **值的所有权用「借用」**：`debug_local` 回调收到的 `JVal` 是借的，宿主当场
   转成 Python 对象，不引入第二套所有权规则。

**「退出」是这里最麻烦的一处**，值得单独说：它必须像另外两个执行器那样**穿过
`最终` 块、又不能被 `捕获` 接住**。做法是把 `DebugQuit` 当成一种**卸载类信号**
（宿主 `is_signal` 返回 3）交给 C 侧的异常分发：

- 分发时**跳过循环**（`中断`/`继续` 才归循环接）；
- 直接跳到该帧的 `finally_ip` 跑 `最终`，**不经过捕获检查**；
- `最终` 跑完由 `END_FINALLY` 检查「有没待重抛的异常」继续向外。

踩到的两个坑（都已写进 `AGENTS.md §2`）：

- **`END_FINALLY` 里不能用 `SYNC_FRAME`**：它会先 `SAVE_IP()`，把刚设好的跳转
  目标冲掉（此时 `ip` 还指着 `END_FINALLY` 的下一条）——表现是 `最终` 里的打印
  执行了、程序却「正常结束」；
- **退出流程里不能再请求一次中止**：`最终` 块的第一条语句会再次触发钩子，
  若又返回「请求中止」，`最终` 一行都不会执行（实测踩到）。所以会话记一个
  `_aborted_by_quit`，进了退出流程就不再请求。

**代价**：挂调试器（哪怕从不暂停）比不挂慢约 8%（C 侧只多一次判空 + 查表）。
**没做的**：`查看 表达式`（就地求值）——C 侧没有「在任意帧上求一个表达式」的
入口，要做得把编译好的求值代码塞进当前帧执行，属另一件事；会话会明确说
「C 虚拟机暂不支持就地求值」，而不是给个错值。

### 其它已知边界

- **调试会话与被调试程序共用标准输入**：程序里写 `输入()` 读数据时，它和你敲的
  调试命令抢同一个 stdin（gdb 也是这个行为）。要稳定复现，用 `--命令` 脚本化，
  或让程序改成从文件 / 命令行参数读数据。
- **块关键字行不能设断点**：`否则：`、`捕获：`、`最终：` 这些行是块的一部分、
  不是独立语句（`否则` 那一行在 AST 里连节点都没有），断点加在上面**不会触发**。
  CLI 加断点时会明确提示「这一行没有可停的语句」，而不是静默无效。
- **自由变量（从外层捕获进来的名字）不进「变量」表**：树遍历那边的函数环境里
  只有本函数自己绑定的名字，字节码这边保持一致（`变量` 里看不到 `基数`，但
  `查看 基数` 读得到）。要看就用「查看」。

## 四、实现说明（给改这个模块的人）

模块结构是「**一套会话 + 三个执行器**」：`debugger._Session` 放执行器无关的部分
（断点表、命令循环、单步判定、源码显示、变量渲染、出错现场），子类只提供
「当前帧有多深、叫什么、变量怎么取、表达式怎么求」：

| | `Debugger`（树遍历） | `VmDebugger`（Python VM） | `CvmDebugger`（C VM） |
|---|---|---|---|
| 钩子 | `interpreter.exec_stmt` 开头的 `before_stmt` + `_eval_call` 里的 `push_frame`/`pop_frame` | `vm._execute` 主循环里的 `dbg.before_statement(line, frame)` | C 主循环里调宿主回调（`jsvm_set_stmt_hook`） |
| 触发条件 | 每个语句 | **只有语句首指令**（`Instr.stmt_line != 0`） | 同左（查 C 侧的语句起始表） |
| 帧 | 自己存一份 `DebugFrame`（多带 env） | 直接用 `vm.frames`（不另存，弹帧不会失步） | 向 C 侧问：`(深度, 代码下标)` 当句柄 |
| 变量 | 读 `Environment.vars` | 读帧的局部槽 + 单元 | `jsvm_dump_locals` / `jsvm_dump_globals` 回调 |
| 求值 | `interp.eval_expr` | 把表达式编译成小代码对象，与所在帧**共用局部槽与单元**（`vm.eval_in_frame`） | ❌ 不支持（明确说明） |

- **钩子只读**：不改变任何语义，所以「带调试器跑」与「不带」的输出必须
  逐字节相同（`tests/test_m37_debugger.py`、`tests/test_m39_vm_debugger.py`、
  `tests/test_m40_cvm_debugger.py` 都钉了）。
- 单步的三种语义全都由「帧深」推出：`单步` 停在任意深度的下一条语句、
  `下一步` 停在 `深度 ≤ 暂停时深度`、`跳出` 停在 `深度 < 暂停时深度`。
  三个执行器的「深度」都指**用户函数**层数（模块顶层 = 0）。
- **出错现场是「执行每条语句前」留的快照**，而且**变量当场复制一份**：
  错误是在语句执行到一半时冒出来的，等它传到 `run()` 时帧已经被弹干净了，
  那时再问「当前帧」只会得到模块顶层（实现时真实踩到过）；C VM 更严格——
  帧是按「第几层」编号的，弹帧后那个编号指向别的帧或越界，事后问只会得到空表。
- **「退出」用 `DebugQuit`（`BaseException`，不是 `JishiError`）**：否则用户程序里
  一句 `捕获：` 就能把「退出」吞掉。三个执行器都要显式放行它：
  树遍历在 `interpreter._do_try` 的控制信号元组里带上它；Python VM 在
  `vm._dispatch_exception` 里让它**跳过循环目标、只走处理器链**，并且
  `vm.THROW` 不许把它包装成用户异常；C VM 把它当**卸载类信号**（`is_signal`
  返回 3）直接跳 `finally_ip`，且 `make_error` 不许包装它。三边合起来的效果
  一样：**`最终` 块照跑，`捕获` 接不住**。
- **命令输入按「字节 → UTF-8」解码**：管道输入的中文命令若走文本层，在中文
  Windows 上会按 GBK 解码成乱码（与 M23 的源码 stdin 同一坑）；管道输入还会
  自己回显一遍命令，否则记录里读不出「哪句是用户敲的」。
- **回调进来的基石函数也登记帧**（M39）：`实例.方法()`、`列表.映射(基石函数)`、
  `类(参数)`（进 `初始化`）都会经 `UserFunction.__call__`；那里按调用方递进来的
  `_pending_call_site` 登记一帧，于是「我在哪一层、从哪一行被调进来」都显示得对。
  只有「可能进基石函数」的那几类调用才更新调用点——否则回调体里的一句 `打印(x)`
  会把调用点改成它自己，第二次回调进来时栈上显示上一句 `打印` 的行号（踩到过）。
  C VM 侧同理由 `_cb_call` 记 `_pending_call_site`，重入建帧时用它
  （`jsvm_call_function` 多了两个参数）。
- **「变量」里隐藏的条数不写数字**（M40）：各执行器「看得见的全局」本来就不同
  ——C 侧的名字表只收程序用到的名字，树遍历 / Python VM 那边把整套内建都放进来。
  写数字会让三个执行器的记录对不上，而这数字对用户没有意义。

## 五、拿真实项目试过

`examples/projects/基石自述站/生成.jsh`（用基石写的静态站生成器，读仓库真数据
生成一套介绍基石的网页）就是 B5 的靶子：在它上面断点、单步、看变量、
看调用栈都正常，而且**三个执行器跑出来的产物逐字节相同**
（`tests/test_m39_selfsite.py`）。
