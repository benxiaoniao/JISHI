# 版本收口流程

> 2026-10-24 立（M132）。每次发版照这张单子走，**顺序不能乱**。
> 起因：这几轮反复踩「bump 了版本号但没重编产物」「改了扩展没 bump 版本」「收口完才发现全量没跑」。
> ⇒ 把顺序写死，不靠记性。

---

## 〇、开始之前：确认这一版**有主菜**

按 `AGENTS.md` §1 第 11 条，先说清「这版最大的是什么」。
说不出就别发——那不是一版，是「顺手改了改」。

---

## 一、代码侧（按顺序，错了会留下不一致的产物）

### 1. 版本号 **六处 + 一个产物**

改语言版本号是**六处**，漏一处 `test_m111_release.py` 会红：

| # | 文件 | 说明 |
|---|---|---|
| 1 | `pyproject.toml` | **唯一来源** |
| 2 | `oracle/jishi/version.py` → `__FALLBACK__` | 读不到 `pyproject` 时的兜底 |
| 3 | `frontend/Cargo.toml` | |
| 4 | `core/Cargo.toml` | |
| 5 | `rust/src/langdata.rs` | ⚠️ **生成的**，别手改 —— 跑 `python tools/gen_langdata_rs.py` |
| 6 | `tests/test_m90_langspec_rust.py` | 两处写死的期望 |

⚠️ **`rust/Cargo.toml` 的 `0.1.0` 别动** —— 那是 **crate 自己**的版本，不是语言版本。

**顺序**（一步都不能跳）：

```bash
# ① 改完 1–4 之后
.venv/Scripts/python -m pip install -e .        # 让 version.py 读到新的
# ② 重生成语言卡（会改 langdata.rs）
.venv/Scripts/python tools/gen_langdata_rs.py
# ③ 重编 Rust（langdata 变了，必须重编，否则二进制里还是旧版本号）
cd rust && cargo build --release && cd ..
# ④ 重编 C 扩展（core/ 是 pyo3，版本号写进了模块）
.venv/Scripts/python core/build.py
```

⚠️ **不重编的后果**：`jishi --version` 说 0.2.7，但 `jishi-rs --version` 说 0.2.6 ——
**两个发行物不一致**，而 pytest 可能**全绿**（因为它测的是 Python 侧）。

### 2. CHANGELOG 定版

把 `## [未发布]（0.2.x · …）` 改成 `## [0.2.x] - YYYY-MM-DD（主菜）`，并在最上面新开一个空的 `[未发布]`。

⚠️ 头部**不要写死分类计数**（「新增 5 项」那种）—— 内容一改就错，改成让读者自己数。

### 3. README 同步（四块，缺一块就是「总结偏差」）

- **技术栈声明**（实现几套、发行形态）
- **性能数据**（有新数字就更新，没有就留着并注明日期）
- **能力清单**（模块数 / 函数数 / 命令列表 —— 新命令要加进去）
- **项目结构**（新目录 / 搬走的目录）

⚠️ **三个字面串是契约**，改 README 时必须保留（否则站点数字**静默变空**）：

| 字面串 | 谁在读 |
|---|---|
| `测试现状：N 项` | 站点首页 |
| `（当前 **42/50 可用**` | 站点首页 |
| `N 项，N 通过` | 站点首页 |

### 4. 文档清理（M132b）

- 去掉**不必要的** Python 对照（判据：删掉这句 Python，这句话还站得住吗）；
- 清掉陈旧数字（模块数 / 函数数 / 测试项数 / 版本号）；
- **跑一遍** `python tools/audit_tests.py`（文档和测试是同一件事的两面）。

⚠️ **例外**：`docs/设计决策.md` 的历史论证**不改** —— 那是当时怎么想的记录。

## 二、测试（**收口走串行**；并行能跑但**结果不可信**）

用户 2026-10-24 定：**收口时用串行，不并行**。2026-10-24 实测**证实了这个决定**：

| 跑法 | 结果 |
|---|---|
| **串行**（`-m "not 计时"` → 再 `-m 计时`） | **3845 通过 + 计时 17 项全绿**，19 分钟 —— **唯一可信的** |
| 并行 `-n 4 --dist loadfile` | 跑到 **99%** 时 `[gw0] node down: Not properly terminated`，**永久卡住** |
| 并行 `--分块 4`（7.3 分钟） | 第 3、4 批都 `node down`；那 3 条「失败」**单独串行重跑 10 项全过** ⇒ **误标** |

⇒ **根因不是我们的测试写错**，是 pytest-xdist 的 worker 在 CPU 饥荒下**静默硬崩**
（上游 #784 / #1313 / #1401），而 `--dist loadfile` 会**永久等那个死掉的 worker**。
崩之前刚跑完的那种更坏：**pytest 退 0、看着全绿，其实有些测试根本没跑**。

### 收口用这个（串行，两条都要看完整数字）

```bash
.venv/Scripts/python -m pytest tests/ -m "not 计时" -p no:cacheprovider
.venv/Scripts/python -m pytest tests/ -m "计时"
```

📌 **判据**：**必须看到「N passed」的完整数字**。看到 `timeout`、`killed`、
`node down`、或者只有半截输出，**都等于没跑** —— 不许当成绿。

### 想用并行时（只为快，**不作为收口依据**）

```bash
.venv/Scripts/python tools/test_all.py --只并行 --分块 4
```

工具现在会做三件兜底（2026-10-24 加的）：
1. **逐行 tee 到 `build/test_all_*.log`** —— 以前继承 stdout，卡住了既看不到也查不了；
2. **整节墙钟上限**（并行 1800 秒 / 每块 1200 秒 / 串行 1800 秒）：卡住就杀掉判失败；
3. 🔴 **`node down` 命中就立刻停 + 判红 + 明说「结果不可信」**
   （实测：不等的话要白等 30 分钟才轮到整节超时）。

⚠️ **已知待查（不是本版的事）**：`node down` 出现在第 3 批（`test_m41_stdlib` … `test_m74`）
与第 4 批（`test_m75_walk` … `test_tutorial`）—— 说明**某个文件在并行下会把 worker 拖崩**。
定位它（逐个文件加 `-n 4` 跑）之后，把它标 `计时` 挪进串行节，并行才可能真的稳。

## 三、AI 跑分（试题 + 实测）

1. **题库要跟得上能力**：这一版新增了什么能力，就补对应的题
   （`evals/tasks/*.json`，每题 `题目` / `标准输出` / `考点`）。
   ⚠️ **`标准输出` 必须是真跑出来的** —— 手算的标准答案是错的判据。
2. 跑：`python tools/eval_ai.py …`（按脚本的用法，模型 + 题库）
3. 结果更新到 `evals/跑分表.md`，并写清**模型名 / 日期 / 通过数**。

⚠️ **报告头别写死分类计数**（题库会扩，写死的数会变谎话）。

⚠️ **推理模型**（思考吃 token 的那种）`content` 可能是 `null` ——
评测器要 `--最大令牌 16384+`，否则会误判成「答不出来」。

### 通道配比：**先量延迟，再定并发**（2026-10-24 实测，别凭感觉）

跑分慢的时候**第一种反应常常是错的**：以为是「服务商限流」，于是调低 `--每分钟`。
实测发现**第一层瓶颈是并发太少**；但**并发抬过 60 次/分钟就会打爆配额**。

| 模型 | 单次请求延迟 | 说明 |
|---|---|---|
| `gemma4:31b` | **约 4 秒** | 输出短，**是目前唯一能在本通道上跑完 80 题的** |
| `nemotron-3-nano:30b` | 约 9 秒 | 写长（completion 4.4k token） |
| `gpt-oss:20b` | 约 13 秒 | 写长；**并发一抬就被限速到几乎不动**（25 分钟 19 题） |

**实测三档（同一通道、同一套 80 题）**：

| 参数 | 结果 |
|---|---|
| `--并发 3 --每分钟 40` | 单模型 20 分钟以上；**3 模型 42 分钟没跑完** |
| `--并发 10 --每分钟 120` | gemma 只要 **69 秒**，但**跑完就撞 429**，随后变 **526**，89 题被跳过 ⇒ 结果作废 |
| **`--并发 6 --每分钟 40`** | **gemma 155 秒跑完 80 题**，39 次/分钟、**0 重试、0 跳过** ⇒ **推荐** |

📌 **结论（写死，别再试）**：
1. **默认 `--并发 6 --每分钟 40`**。这套通道的**真实上限约 40–60 次/分钟**，
   抬到 120 会「先给你跑完一个模型，再把你锁在门外」——**看起来成功，实际把配额花光了**；
2. **慢的时候先看「实际速率 / 上限」**：远低于上限 ⇒ 抬 `--并发`；
   已经贴上限 ⇒ **别再抬了，那是在借配额**。脚本会把这三个数打出来；
3. **本版只测 `gemma4:31b`**（用户 2026-10-24 定）。另两个模型在这套通道上不可用，
   **跑分表里不写它们** —— 宁可少一个数，不留一个假数；
4. **别用 `| tail` 接跑分命令** —— 输出全被缓冲住，几十分钟看不到任何进度。
   要看得见就重定向到 `evals/_跑分日志_<版本>.txt`（或 `| tee`）；
5. ⚠️ **局部跑（`--限制` / `--类型`）默认不写 `跑分表.md`**：探路的 2 题通过率
   会**整份覆盖**历史记录。要写就显式 `--写报告`，或者 `--输出 <别的路径>`；
6. ⚠️ **`5xx` 一律重试**（含 526）。526 是 CDN 边缘抖动，原来不算可重试 ⇒
   那批题被记成「跳过」，而「跳过」看起来像「模型不会做」。

## 四、VSCode 扩展（**生成 vsix，用户自己上传**）

> 用户 2026-10-24 定：**收口时生成扩展包，上传由他本人做**（网页手传）。

```bash
cd editors/vscode-jishi
./node_modules/.bin/vsce package        # 产出 vscode-jishi-<版本>.vsix
```

🔴 **硬规矩**：

1. **改过扩展就必须 bump `editors/vscode-jishi/package.json` 的 `version`** ——
   否则商店里还是旧版，而用户「明明装了新的」；
2. **语言新增模块/关键字，必须同步 `syntaxes/jishi.tmLanguage.json`**
   （新模块名要进那条模块清单，否则 `test_m43` 红）；
3. **vsix 是产物，不进 git**（`.gitignore` 里已有），但**要在 Release 里附上**或单独交给用户；
4. ⚠️ **不要自动上传** —— 没有商店凭据，且发布动作该由人确认。

📌 **判据**：`ls editors/vscode-jishi/*.vsix` 有文件，且版本号 == 语言版本号。

## 附：这一流程自己的判据

- **每一步都有「怎么验证」**，不是「记得做」；
- **顺序有理由**（版本号 → 重生成 → 重编），不是仪式；
- ⚠️ **流程会过期**：某个坑修好了（比如以后不再需要六处同步），**回来删掉那一条** ——
  留着「已经没有意义的步骤」会让整张单子失去可信度。
