## 一、代码侧（按顺序，错了会留下不一致的产物）

### 1. 版本号 **七处 + 一个产物**

改语言版本号是**七处**，漏一处会红（前六处 `test_m111_release.py` 盯着，
第七处由 `--locked` 构建盯着）：

| # | 文件 | 说明 |
|---|---|---|
| 1 | `pyproject.toml` | **唯一来源** |
| 2 | `oracle/jishi/version.py` → `__FALLBACK__` | 读不到 `pyproject` 时的兜底 |
| 3 | `frontend/Cargo.toml` | |
| 4 | `core/Cargo.toml` | |
| 5 | `rust/src/langdata.rs` | ⚠️ **生成的**，别手改 —— 跑 `python tools/gen_langdata_rs.py` |
| 6 | `tests/test_m90_langspec_rust.py` | 两处写死的期望 |
| 7 | **四个 `Cargo.lock`** | `frontend` / `core` / `rust` / `wasm` —— 锁文件里记着每个包**自己的版本号**。M176 起它们进了仓库、构建一律 `--locked`，所以改完 `Cargo.toml` 不刷新锁，`cargo build --locked` 会当场报错（`cannot update the lock file because --locked was passed`）。 |

⚠️ **`rust/Cargo.toml` 的 `0.1.0` 别动** —— 那是 **crate 自己**的版本，不是语言版本。

刷新锁（**先不带 `--locked` 让它更新，再带 `--locked` 复验**）：

```bash
for d in frontend core rust wasm; do
  (cd $d && cargo metadata --format-version 1 > /dev/null \
            && cargo metadata --locked --format-version 1 > /dev/null) || echo "$d 锁不对"
done
```

**顺序**（一步都不能跳）：

```bash
# ① 改完 1–4 之后
.venv/Scripts/python -m pip install -e .        # 让 version.py 读到新的
# ② 重生成语言卡（会改 langdata.rs）
.venv/Scripts/python tools/gen_langdata_rs.py
# ③ 重编 Rust（langdata 变了，必须重编，否则二进制里还是旧版本号）
cd rust && cargo build --release && cd ..
# ④ 重编 C 扩展（core/ 是 pyo3，版本号写进了模块）
.venv/Scripts/python core/build.py
```

⚠️ **不重编的后果**：`jishi --version` 说 0.2.7，但 `jishi-rs --version` 说 0.2.6 ——
**两个发行物不一致**，而 pytest 可能**全绿**（因为它测的是 Python 侧）。

### 1.5 语言卡审计（**M169 起，发版必跑**）

```bash
.venv/Scripts/python tools/audit_ai_card.py
```

查四件事：**假默认值**（卡上写着可省、实际省略就报参数不够）/ **两层签名不一致**
（`参数`/`容器`/`统计`/`迭代` 有宿主层 `.py` 与基石库层 `.jsh` 两份实现，
卡是从 `.py` 生成的，而 Python 侧**跑的是 `.jsh`**）/ **卡自身坏掉**（签名解析不出）/
**模块清单对不上**。

> 起因：2026-11-03，一个模型在别的机器上用基石写「文档检索工具」，
> **第一条**就撞在 `参数.解析(句柄, 参数们=空)` 上 —— 卡说可省，省略就报错。
> 卡是给模型看的唯一依据，**卡错 = 模型必错**，而且它没有别的办法自救。

📌 **这一版的「新增功能」也要过一遍**：加了什么函数、改了什么默认值、
有没有新模块 —— 跑完看卡里是不是真的这么写（`jishi --ai-card` 和
`jishi --lang-spec` 都读同一份事实源，跑 `--ai-card 模块名` 最快）。

### 2. CHANGELOG 定版

把 `## [未发布]（0.2.x · …）` 改成 `## [0.2.x] - YYYY-MM-DD（主菜）`，并在最上面新开一个空的 `[未发布]`。

⚠️ 头部**不要写死分类计数**（「新增 5 项」那种）—— 内容一改就错，改成让读者自己数。

### 3. README 同步（四块，缺一块就是「总结偏差」）

- **技术栈声明**（实现几套、发行形态）
- **性能数据**（有新数字就更新，没有就留着并注明日期）
- **能力清单**（模块数 / 函数数 / 命令列表 —— 新命令要加进去）
- **项目结构**（新目录 / 搬走的目录）

⚠️ **一个正则形状是契约**，改 README 时必须保留（否则站点数字**静默变空**）：

| 形状 | 谁在读 |
|---|---|
| `测试现状：N 项，M 通过` | 官网 `build_site.py` 的 `re.search(r"测试现状：(\d+) 项，(\d+) 通过")` |

📌 2026-11-18 校正：以前这里列了三个字面串（含 `（当前 **42/50 可用**`），
**实测官网只正则抓上面那一条** —— 能力探针那句只是正文，站点不解析它。
把它从「契约」里删掉，免得以后有人为了保一个没人读的数字而写错事实。

## 二、测试（**收口走串行**；并行能跑但**结果不可信**）

用户 2026-10-24 定：**收口时用串行，不并行**。2026-10-24 实测**证实了这个决定**：

| 跑法 | 结果 |
|---|---|
| **串行**（`-m "not 计时"` → 再 `-m 计时`） | **4084 通过 + 计时 23 项全绿**，约 25 分钟（0.2.10 实测）—— **唯一可信的** |
| 并行 `-n 4 --dist loadfile` | 跑到 **99%** 时 `[gw0] node down: Not properly terminated`，**永久卡住** |
| 并行 `--分块 4`（7.3 分钟） | 第 3、4 批都 `node down`；那 3 条「失败」**单独串行重跑 10 项全过** ⇒ **误标** |

⇒ **根因不是我们的测试写错**，是 pytest-xdist 的 worker 在 CPU 饥荒下**静默硬崩**
（上游 #784 / #1313 / #1401），而 `--dist loadfile` 会**永久等那个死掉的 worker**。
崩之前刚跑完的那种更坏：**pytest 退 0、看着全绿，其实有些测试根本没跑**。

### 收口用这个（串行，两条都要看完整数字）

```bash
.venv/Scripts/python -m pytest tests/ -m "not 计时" -p no:cacheprovider
.venv/Scripts/python -m pytest tests/ -m "计时"
```

📌 **判据**：**必须看到「N passed」的完整数字**。看到 `timeout`、`killed`、
`node down`、或者只有半截输出，**都等于没跑** —— 不许当成绿。

### 再加一条：**用基石自己写的运行器对一遍**（M135 起，约 3 秒）

```bash
jishi 自测 --被测 rust/target/release/jishi-rs.exe   # 推荐：它会记住「谁被测」
jishi tools/自测.jsh --被测 rust/target/release/jishi-rs.exe   # 等价写法（不记忆）
jishi tools/自测.jsh                                          # 被测 = Python 参考实现，~30 秒
```

📌 **M137 起可以用 `jishi 自测`**：它把「谁跑运行器（固定版）、谁被测」**记住**，
下次一条 `jishi 自测` 就跑完 —— 发版收口这几天要反复跑同一批，记一次就够。
`jishi 自测 --看` 看现在记着什么，`--忘掉` 清掉。
⚠️ **固定版找不到时它会直接 rc=2**（不会悄悄退回「当前版」）—— 那正是「拿自己考自己」的闸。

它跑的是 `tests/cases` + `tests/error_cases` 那 **126 条黑盒用例**，判据口径与
`test_golden` / `test_error_snapshot` **逐条对齐**，但**起真进程**比 stdout/stderr/退出码。

📌 **为什么值得多跑这 3 秒**：pytest 那两条是**在同一个进程里**跑的 —— 它能测
Python 参考实现，**测不了 Rust / Node 引擎**。而 `--被测` 换个路径就能测任意一版：
发版前顺手对一遍 Rust，比出问题后再查快得多。

⚠️ 汇总行里 **`豁免 N` 不算通过**：那是登记过的「真实边界」（`tools/自测豁免.txt`）。
⚠️ **豁免表跨机器用时要显式 `--标签 <名字>`**：默认标签取自**被测程序文件名**
（Windows `python.exe` → `python`，macOS / Linux `python3.13` → `python3.13`）——
不钉住它，同一张表在本地绿、在 CI 上全对不上（v0.2.7 就这么红过一次）。
N 变大值得看一眼；被豁免的用例哪天过了，运行器会**红着喊你删掉那一行**。

### 再加一条：**下游回归**（M201 起，约 6 秒）

```bash
python tools/下游回归.py --报告 build/下游报告.md
```

拿**真实下游项目**（现在是 `基石数据库`）跑一遍这一版语言：自检 / 冒烟 / 对拍。
语言自己的判据全绿、下游坏掉 —— 那是发版后一周才被用户发现的那种事，
这一条就是为它准备的。

📌 **为什么发版必跑**：下游是用**上一版**语言写的；这一版改的每一句文案、
每一个语义细节，都可能在它身上变成红的。而 CI 上暂时**没有**这一步
（M201 时推不上去：GitHub 不允许 OAuth 令牌 / `gh` 的 `gho_` 令牌创建或修改
workflow 文件，报 `refusing to allow an OAuth App to ... workflow`），所以这里
是**唯一的闸门**。

📌 **想把 CI 那一步补上**：在 `ci.yml` 的 `pytest` 那一步**之后**贴这三行
（`if:` 是为了只在 Windows 跑 —— 下游只在 Windows 上真验过）：

```yaml
      - name: 下游回归（M201）
        if: runner.os == 'Windows'
        run: python tools/下游回归.py --报告 build/下游报告.md
```

改动 workflow 需要**带 `workflow` scope 的凭据**。两条路：
① GitHub 网页直接编辑 `ci.yml` 贴上去；② `gh auth refresh -h github.com -s workflow`
之后用 `gh` 的令牌推。

⚠️ 它要联网 clone（公开仓库）。离线时用 `--清单` 只校验清单结构。
⚠️ 认准 **rust 引擎**（默认）。`--引擎 python` 会红 6 条 —— 那是「Python 内置
`数据库`」的文案与 Rust 不一致（M112 老账），**不是下游坏了**。

### 想用并行时（只为快，**不作为收口依据**）

```bash
.venv/Scripts/python tools/test_all.py --只并行 --分块 4
```

工具现在会做三件兜底（2026-10-24 加的）：
1. **逐行 tee 到 `build/test_all_*.log`** —— 以前继承 stdout，卡住了既看不到也查不了；
2. **整节墙钟上限**（并行 1800 秒 / 每块 1200 秒 / 串行 1800 秒）：卡住就杀掉判失败；
3. 🔴 **`node down` 命中就立刻停 + 判红 + 明说「结果不可信」**

⚠️ **已知待查（不是本版的事）**：`node down` 出现在第 3 批（`test_m41_stdlib` … `test_m74`）
与第 4 批（`test_m75_walk` … `test_tutorial`）—— 说明**某个文件在并行下会把 worker 拖崩**。
定位它（逐个文件加 `-n 4` 跑）之后，把它标 `计时` 挪进串行节，并行才可能真的稳。

### 3.1 为什么是「文档」而不是别的

这一条是从真实的坑里长出来的，写在这里免得下次又忘：

| 撞出来的事 | 根子在哪 |

⇒ **文档不是说给人听的介绍，是模型和人共用的唯一事实源。** 它错了，后面全错。

### 3.2 六块清单（逐块勾，别跳）

> 方法：**按关键词通篇搜，不按位置列清单**（位置会变，关键词不会）。
> 比如改技术栈就 `grep -n "Python 前端\|CPython\|C 内核\|薄壳" README.md docs/*.md`，
> 而不是「我记得第 1114 行有个 D1」。

| 块 | 查什么 | 怎么验 |
|---|---|---|
| **① 技术栈声明** | 实现有几套、哪套是**权威**、发行形态是什么、Python 现在是什么角色 | 逐句问「这句话今天还成立吗」。见 §3.3 的现状口径 |
| **② 外部依赖** | `README` 的依赖表与四个 `Cargo.toml` 一致；「已摆脱」的要真的删掉了 | `pytest tests/test_m176_hygiene.py -k 依赖`（自动对账） |
| **③ 性能数据** | 表里的数字**有日期**、是这一版或明确标注的旧版；没量的写「未度量」 | 有 `bench_vs_python` 新数字就换掉旧的并改日期 |
| **④ 能力清单** | 模块数 / 函数数 / 命令列表 / 内建 / 对象方法 | `jishi --lang-spec` 数一遍，与 README 数字逐个比 |
| **⑤ 项目结构** | 目录树与实际一致（前端在哪、宿主在哪、C VM 在哪） | `ls` 对照，删掉的目录不许还留在树里 |
| **⑥ 扩展 README 与其它文档** | `editors/vscode-jishi/README.md` 的命令 / 支持范围 / 版本；`docs/语言规格.md` 的事实；`docs/测试跳过说明.md` 的条数 | 见 §3.4 |

📌 **文档里「历史」与「现状」要分开**：`docs/设计决策.md` 的旧论证、
`CHANGELOG` 的历史条目、`docs/版本历史/` **不改写**（那是当时怎么想的记录）。
要改的是**描述现状的那一层**：README、语言规格、扩展 README、`docs/embed.md`、
卡（`--ai-card`）。

### 3.3 技术栈的**现状口径**（写文档时照这个，别自己发挥）

一句话：**一门语言，多套执行器；发行版是 Rust 单二进制；Python 是判据基准，不是产品。**

| 层 | 是什么 | 在发行版里吗 |
|---|---|---|
| **前端**（词法 / 语法 / AST / 字节码生成） | **Rust**（`frontend/` crate），各宿主共用同一份 | ✅ |
| **发行宿主** | **Rust**（`rust/`，单二进制 `jishi`），内含 VM + 标准库 + JIT + 窗口 | ✅ 就是它 |
| **C 虚拟机** | `cvm/`（自研栈式 VM）：**判据** + 纯计算性能对照 | ❌ 随源码走，用户不需要 |
| **Node 宿主** | `oracle/node/`：吃同一份字节码，验证「语义在字节码里，不在某个宿主里」 | ❌ |
| **Python 参考实现** | `oracle/jishi/`：树遍历 + 字节码 VM，**语义基准与判据**（`jishi-py` 入口） | ❌ |
| **wasm** | 同一份 Rust VM 编到 wasm，供网页试玩 / 窗口内页面 | ✅（`窗口` 靠它） |

⚠️ 这套东西里**已经没有任何「CPython 内核」**，也**没有「Python 生态桥接」**作为
主路径（`从 python 导入` 只在 Python 宿主上可用，跨语言宿主明确报错）。
写 README / 扩展 README 时，凡是「Python 前端」「C 内核」「薄壳」「靠 Python 生态」
这类说法，**要么删掉、要么改成上表的口径**。

## 四、VSCode 扩展（**必做** · 生成 vsix，用户自己上传）

4. ⚠️ **不要自动上传** —— 没有商店凭据，且发布动作该由人确认。
