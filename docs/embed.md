# 基石引擎嵌入指南（M13）

> 本文介绍如何把基石引擎嵌入**任意宿主**，脱离 Python 编译前端独立执行基石代码。
> 核心思路：**字节码是平台无关的中间格式**，各语言各自实现执行引擎。

## 1. 架构总览

```
基石源码 ──(Python 编译前端)──> JSON 字节码（M13.1）──┬─> Python VM（jishi/vm.py）
                                                        ├─> C VM（jsvm.dll，宿主驱动）
                                                        ├─> JS VM（node/，零依赖）
                                                        └─> Rust VM（rust/）
```

字节码格式（M13.1）是唯一契约：

- **format** = `jishi-bytecode`，**version** = 1，附 `sha256` 校验和；
- **opcode_names**：指令号 → 名字表（48 条指令）；
- **payload**：常量池（只含标量：文本/整数/浮点/空/布尔）、名字表、
  关键字名表、代码对象数组（每条指令 6 个 int32：op/a/b/c/line/col）。

产出一份字节码：

```bash
jishi 你的脚本.jsh --dump-bytecode > 脚本.json
```

## 2. C 宿主（M9.4）

C 宿主直接链接 `jsvm.dll`（`cvm/include/jsvm.h`），这是**宿主驱动**架构：
C 侧不链接 libpython，所有字符串/列表/字典/打印/异常通过 `JsHost` 回调表
回传给宿主实现。

最小示例见 `examples/embed/hello.c`，要点：

```c
#include "jsvm.h"
// 1. 创建 VM、传入 JsHost 回调表
JsVm *vm = jsvm_create();
jsvm_set_host(vm, &host);
// 2. 加载字节码（扁平数组）
jsvm_load_module(vm, consts, nconsts, nnames, globals_in,
                 instrs, ninstrs, code_meta, ncodes, code_params,
                 kw_flat, kw_off, nkw, main_idx);
// 3. 运行
jsvm_run(vm);
```

C 宿主的约束：常量池里的字符串等非数值对象，须由宿主预先分配句柄；
所有 I/O 与 Python 生态对象操作都要宿主回调实现。适合对性能有极致要求、
愿意实现完整回调表的宿主。

## 3. Node.js 宿主（M13.2）

Node 宿主用**纯 JS 解释器**（`node/` 目录），零第三方依赖，消费同一份 JSON
字节码：

```bash
node node/index.js 脚本.json
```

详见 `node/README.md`。这是最省事的跨语言方案——JS 的 `Map` 天然对应字典、
`Array` 对应列表、`BigInt` 可扩展大整数。

**为何不是 ffi 加载 jsvm.dll**：jsvm.dll 是宿主驱动架构（~40 个语义回调），
ffi 方案要把 `runtime.py` 整个翻译成 JS，工作量约 3 倍。纯 JS 解释器只需
翻译指令分发 + 12 内建 + 方法表。

## 4. Rust 宿主（M13.3）

Rust 宿主同样消费 JSON 字节码，自行解析后解释执行（零第三方依赖，
`rust/Cargo.toml` 的 `[dependencies]` 是空的），`rust/` 目录提供
`jishi-ffi` crate。

### 构建与运行

```bash
cargo build --manifest-path rust/Cargo.toml --release
# 产物：rust/target/release/jishi-rs.exe
rust/target/release/jishi-rs.exe 字节码.json   # 由 jishi --dump-bytecode 产出
```

工具链是 `stable-x86_64-pc-windows-gnu`，链接器用 gcc。把提供 gcc 的目录
加进 PATH 即可（IDE 自带的 MinGW 也行，或用环境变量 `JISHI_MINGW` 指定
——`tests/test_m27_rust_host.py` 认这个变量，不写死任何本机路径）。

> **踩过的坑（2026-09-13）**：`cargo` 命令一直「执行成功但什么都不做」。
> 原因是 `~/.cargo/bin/` 下 13 个文件（`cargo.exe` / `rustc.exe` …）
> 都是 **0 字节**——rustup 在 Windows 上把这些做成指向 `rustup.exe` 的硬链接，
> 链接坏掉后退化成空文件，于是执行它没有任何输出且 `rc=0`（很像「命令被沙箱
> 吞掉了」）。真身在 `~/.rustup/toolchains/<toolchain>/bin/`。
> 修复：`ln -f rustup.exe cargo.exe`（依次重建 13 个），
> 或用「把 `rustup.exe` 复制成这些名字」的等价做法。

### 曾经的「最小可运行」是夸大的（已如实修正）

修好 cargo、第一次真正跑起来后立刻发现：**函数调用整个是坏的**。
`Flow::Return` 被当成两种含义——「本帧结束请弹帧」和「刚压了新帧别弹」——
于是每次调用后新帧立刻被弹掉，外层去执行那个还没拿到实参的 `CALL`，
`fn_base` 下溢成 `usize::MAX` 直接 panic。修前连
`函数 加一(x)：返回 x + 1` + `打印(加一(1))` 都跑不了。

也就是说：M13.3 到 M27 之间，Rust 宿主**只有编译验证，没有运行验证**
（`tests/` 里只有 Node 的对拍）。现在补上了
`tests/test_m27_rust_host.py`——到 M29 为止是 **101 条对拍**，不再有 xfail。

### JS 宿主剩下的边界

> **M32 删掉了两条过时描述**：「`1` 与 `1.0` 无法区分」（字节码里的小数常量
> 本来就带 `t: "float"` 标记，`decodeConst` 早就按它包 `FloatBox` 了）与
> 「错误渲染没有源码行」（M30 已规范化成中文）。大整数也从「需 BigInt 扩展」
> 变成了真的扩展好了。**文档也会过时，边界清单要按实测更新。**
>
> **M34 又删掉一条**：「类变量未同步」——枚举脱糖要用「类体外给类设属性」
> 才把它撞出来（M23.3 的特性一直没同步）。补法很省事：Python 侧的类变量
> 本来就是靠 `SET_ATTR` 实现的，宿主补 `getAttr`/`setAttr` 的类分支即可。

1. **`导入 x 从 python` / `从 本地包`**：JS 引擎没有 Python 运行时，报中文错。
   这是架构决定的，不会变。
2. **`打印` 之外的错误渲染**：JS 宿主只打印「错误（类型）：消息 + 行列」，
   不像 Python 侧那样带源码行与修正建议。
3. **`网络` 是子进程封装**（M31）：Node 没有同步 HTTP，所以 `获取`/`提交`/
   `获取JSON` 会 `spawnSync` 起一个自身的子进程跑异步 `fetch`，结果经 stdout
   回传。语义与 Python 侧一致（同步、有超时、错误是中文），代价是每次请求
   多一次进程启动（本机实测约 40ms）。另外 `fetch` 会自动跟随重定向、
   Python 的 `urllib` 也跟随，这一点两边一致。
4. **标准库覆盖 14 个模块**（M31 起与 Python 侧同宽），但实现细节有个别妥协：
   `随机整数` 固定返回下界（对拍友好）、日期时间按本地时区（JS 的 `Date`
   没有时区对象）。

### Rust 宿主剩下的边界（明确、不是遗漏）

> **M33 把标准库补齐到与 Python 侧同宽**（14 个模块、约 130 个函数），
> 所以这一节只剩「表示层的限制」与「刻意的取舍」了。

1. **整数到 `i128` 就到边界**（约 1.7e38）：超出时明确报错
   （「整数运算结果太大…」），不是静默给错值。Python / JS 是任意精度。
3. **`是`/`不是` 对绑定方法**（`a.方法`）明确报错：Python 里每次取属性都是
   新对象（`a.方法 是 a.方法` 为假），而 Rust 侧按「实例指针 + 方法名」判
   会得到真——宁可明确不支持，也不给反直觉的答案。
4. **精确小数的 `**` 只支持整数指数**：非整数次幂是近似运算（Python 的
   `Decimal` 走 `context.power`，用 `exp`/`ln` 实现），各执行器一定会漂移，
   所以报中文错而不是给近似值。
5. **`类型标注` 表里 `空` / `函数` 两条写不出来**：它们是关键字，语法上不能作
   类型名（三个侧同样如此，不是 Rust 独有）。
6. **`压缩.打包` 写的是 `stored`（不压缩）条目**。零依赖下没有 DEFLATE
   **压缩器**（LZ77 + 两套霍夫曼树，几百行的活），而 zip 规范里 `stored`
   本来就是合法形式。**解压**躲不掉——别人打的包默认都是 deflate，
   所以 inflate 是完整实现的（三种块都支持）。结果：Rust 打的包**文件大一点、
   但完全合规**，Python 的 `zipfile` 读得出来（测试里拿它当裁判）。
7. **非 Windows 平台上 `https://` 用不了**：那边走裸 `TcpStream`，没有 TLS，
   于是 `网络.获取("https://…")` **明确报错**并说明原因（不静默降级成明文）。
   Windows 侧绑 `winhttp.dll`，`https` 正常。

> **可变容器的坑（M28 已修，值得记住）**：以前 `Val::List(Vec<Val>)` 是
> **值类型**，`Clone` 是深拷贝，而 `get_attr` 拿到的 `obj` 又是拷贝——
> 于是 `a.追加(3)` 改的是副本、原变量纹丝不动：**不报错、结果就是错的**，
> 比直接报错危险得多。修法是把容器换成 `Rc<RefCell<Vec<Val>>>`（`Val::clone`
> 只复制指针），方法里用 `borrow_mut()` 改共享数据。
>
> 换过去之后有**一个必须做对的配套改动**：Rust 版把「列表自身」当迭代器
> （`iter_next` 会 `remove(0)`）。以前靠值拷贝侥幸正确（`Val::List(l)`
> 天然是独立副本），共享之后如果不显式快照，`遍历 x 在 a` 会把 `a`
> 逐元素吃掉。所以 `make_iterator` 改成 `list_new(l.borrow().clone())`。
> 解包同理（`unpack_values` 也取快照）。`tests/test_m27_rust_host.py`
> 里 `test_rust_iteration_does_not_consume` 专门锁这一点。
>
> **`是` / `不是` 对类与函数明确报错（不做静默降级）**：Rust 版的
> `Class` / `Func` 都是值类型、**没有对象身份可谈**。
> 硬按「同内容即同一」算，`甲 是 甲` 会给出和 Python 相反的答案——
> 那又是一次「静默算错」。宁可直接报「Rust 宿主暂不支持对「…」用「是/不是」」。
> 数字/文本按值、列表/字典/集合按 `Rc::as_ptr` 身份、实例按 `Rc` 身份，
> 这几类都实现且对拍过。
>
> **`用 … 为` 顺带修掉两个真 bug（M29）**：脱糖出来的代码是
> 「尝试/最终」，一跑就发现 Rust 侧的异常机制有两处从来没走通——
> ① `execute` 收到 `Err(e)` 直接 `return Err(e)`，**绕过了异常分发**，
> 于是 `尝试/捕获/最终` 对内置错误（除零、越界、类型不符）完全失效
> （`Flow::Error` 这个变体根本没人构造）；
> ② `返回` 不跑 finally（缺 Python 侧的 `_return_via_finally`），
> 所以「`用` 块里 `返回`」会让文件不关。
> 现在两条都按 Python 的块栈语义补齐（含 `中断` 穿过 `用` 块时先清理）。

## 6. 性能对比（基准数据）

| 场景 | 树遍历 | Python VM | C VM | JS VM |
|------|--------|-----------|------|-------|
| 整数循环（20000 次） | 1x | ~0.6x | **~9x** | **~2x** |
| 递归斐波那契（n=22） | 1x | ~1x | **~18x** | ~1x |

> 数据来源：`tools/benchmark.py`（前三列，M20 后）与 JS VM 补测
> （Node v22，已扣除约 143ms 的 Node 进程启动基线；20000 次整数循环净
> 执行约 15.7ms，斐波那契 n=22 约 57.6ms）。
> JS VM 定位于「跨语言分发 / 语义对齐」，性能与树遍历同量级；
> **C VM 是性能天花板**（纯计算场景比树遍历快 9–46 倍）。
