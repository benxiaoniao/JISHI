# 设计决策记录

> 记录基石语言每次语法/架构取舍的来龙去脉，避免后人重复踩坑。

## D1. 为什么 Python 前端 + C 内核（技术栈透明）

- 木兰语言（2020）翻车的根源不是"基于 Python"，而是宣称"完全自主"造假。
- 本语言在 README 第一屏如实声明：前端 Python、执行内核 C 字节码 VM、桥接 Python 生态。
- 前端 Python 是为了中文报错体验可控；C 内核（MinGW-w64 gcc）是为了长期性能。
- 绝不 fork/patch CPython（中蟒、草蟒均因此停更）。

## D2. 分词消歧：关键字后必须有分隔

- 中文没有空格，「如果分数」会被贪婪读成标识符。方案对比：
  - sigil 前缀（青语言 `#变量`）：零歧义但有符号噪音，不够像 Python
  - 定界符（文言 `｢甲｣`）：零歧义但繁琐
  - **关键字后必须有分隔（本方案）**：一段连续 CJK 恰等于关键字才作关键字；以关键字为前缀的词报"粘连"错误并给出修正建议
- 代价：关键字不能拼在标识符前面（`如果分数` 报错），接受——几乎没人想用关键字作变量名前缀。
- 复合关键字（否则如果）整体命中关键字表，不误报。
- **修订（M1）**：粘连检查只针对**多字关键字**（`如果`/`循环`/`导入`…）。单字关键字（`类`/`当`/`真`/`空`/`非`/`令`…）与海量常用词冲突（`类型`/`当时`/`真实`/`空间`/`命令`…），若也做前缀检查，这门语言将无法书写日常词汇。多字关键字的粘连才是用户真正常犯的错，误报率低、提示价值高。

## D3. 全角标点接受，全角空格在缩进中拒绝

- 中文输入法产出全角标点，解释器在字符串与注释外做一对一归一化（`＝`→`=` 等），写作零切换。
- 全角空格 U+3000 在缩进中宽度语义不明（视觉上像 2 格），会造成隐形缩进 bug → 直接报错并提示改用半角。
- 中文引号（“”『』「」）作字符串定界符，支持配对。

## D4. 执行模型演进路线

- 阶段一：Python 树遍历解释器（当前）。语义正确、报错优秀，性能约 CPython 的 1/50–1/100。
- 阶段二（M4）：同一前端产出字节码，C 栈式虚拟机执行。语法不变。
- 对拍测试保证两套执行器输出一致。

## D5. 标准库策略：薄封装，不重造轮子

- 中文标准库模块内部调用 Python 实现（如 `随机.随机整数` → `random.randint`）。
- 绝不自建整套标准库（易语言死因之一）；中文 API 只是薄壳，真实价值来自 Python 生态。

## D6. 缩进实现

- 缩进栈 + INDENT/DEDENT（参考 CPython 词法规范）。
- 空行与纯注释行不发 token；括号内换行降级为 NL 并忽略缩进；反斜杠续行。
- Tab 与空格同文件混用报错；缩进层级对不上报缩进错误。

## D7. 对象方法分派（M1）

- 方法表按类型分派（list/dict/str → 中文方法名 → Python 实现），在 `_eval_attr` 返回闭包。
- 方法报错信息也是中文：参数个数、找不到元素、类型不匹配都有专门消息。
- 方法名保持 Python 语义（列表方法原地修改、文本方法返回新值），教程中明确说明，避免中文用户混淆。

## D8. REPL 回显与多行输入（M1）

- 顶层表达式语句的值通过解释器 `_last_value` 捕获，非空即回显；`打印(...)` 返回空不回显，避免重复。
- 显示值中文化：`True/False/None` 显示为 `真/假/空`，文本带引号、列表/字典递归美化。
  （M27 起统一到 `runtime.jishi_repr` 一处，`打印`/`文本()`/插值/REPL 回显/
  容器元素共用；顶层文本不带引号、容器内带引号——与 Python 的 print/repr 分工一致。）
- 多行输入用缩进栈模拟判断"块是否已闭合"：冒号结尾、括号未闭合、块内缩进行都继续读；**空行强制结束**（这是用户主动结束块的标准方式）。

## D9. Python 桥接采用「薄桥接」而非对象包装器（M3）

- 原计划：独立 bridge.py + PyObject 包装器拦截属性/下标/调用。实际实现更轻：
  - Python 模块属性直接放入 `Module.attrs`（下划线成员不暴露）；
  - `_eval_attr` 先查基石中文方法表，未命中回落 `getattr`（渐进过渡：基石列表也能用 Python 原生方法）；
  - 调用走 `callable(fn)` 分支；回调靠 `UserFunction.__call__`。
- 理由：基石基础值就是 Python 值（int/str/list/dict），包装反而制造双重世界、破坏与 Python 生态的零成本互操作。木兰重现版 ulang 也走类似路线。
- 代价：基石类型会暴露 Python 原生方法（`a.append` 与 `a.追加` 并存）——视为特性而非缺陷，文档已说明。

## D10. 关键字参数：调用内 `名字 = 值` 的歧义处理（M3）

- 调用括号内没有赋值语句语义，`f(a = 1)` 一律解析为关键字参数（parser 在调用循环里前瞻 `NAME =`）。
- 基石函数按参数名绑定，未知参数名/缺参数均给中文报错并列出可用参数。
- 这是 `json.dumps(x, ensure_ascii=假)` 保住中文的关键能力，也是中文用户调用 Python 生态的高频需求。

## D11. 异常处理的对象模型：异常即 JishiError 实例（M5a）

- **不另造一套异常类**：基石的「异常对象」就是 `jishi/errors.py` 里的
  `JishiError` 实例。这样运行时抛出的中文错误与用户 `抛出` 的对象是同一种东西，
  `捕获` 天然能接住内建错误（除零、索引越界、文件找不到…）。
- **类型名即捕获条件**：每个错误类有中文 `title`（`类型错误`/`值错误`/
  `索引错误`/`键错误`/`除零错误`/`文件错误`…），`捕获 类型错误 为 e:` 就按
  title 匹配（实现为 `isinstance` 检查，因此**基类能抓子类**）。
  `异常` 对应 `JishiError` 基类，抓得住一切。
- **抛出任意值**：`抛出 表达式` 的值若不是异常对象，自动包装成「异常」，
  原值留在 `e.消息` 里。这样 `抛出 "余额不足"` 也能被 `捕获 异常 为 e` 接住，
  规则只有一条，不用解释「哪些东西能抛」。
- **异常对象属性**：`e.消息`（中文说明）、`e.类型`（如「值错误」）。
  `打印(e)` 输出与未捕获错误一致的带位置渲染（`__str__ = render()`），
  因此对拍测试比较 `str(e)` 时行列号仍在检验范围内 —— 这点刻意保留。
- **`最终` 的执行顺序**与 Python 一致：无论正常结束、被 `捕获`、被 `返回`/
  `中断`/`继续` 穿透，都执行；`最终` 里的 `返回`/`中断` 会覆盖原有的离开原因。
- **三执行器一致性**：树遍历靠 Python 的 try/except；字节码 VM 与 C VM 在帧内
  维护「异常处理器栈」，出错时逐层弹帧匹配（与 Python 的传播顺序一致）。
  这是 `tests/test_cvm.py` 对拍覆盖的场景之一。

## D12. 语法用中文助词而非括号（M5a）

- 继承写 `类 狗 继承 动物:`，捕获写 `捕获 类型错误 为 e:` —— 复用已预留的
  `继承`/`为` 关键字，不引入 `狗(动物)` 这类括号形式。
- 理由：与既有「遍历 x 在 y」「导入 x 从 python 为 y」同一风格，
  全中文助词让句子能朗读出来，也避免中文输入状态下频繁切括号。
- 方法首参约定名 `自身`（普通标识符，不是关键字），构造方法约定名 `初始化`，
  与 Python 的 `self`/`__init__` 地位相同但可读。

## D13. 跨语言字节码用 JSON 而非扁平二进制（M13.1）

- 编译产物（常量池/名字表/指令流/代码元数据/kwargs 表）序列化成 JSON 字节码，
  附 format 标记 + version 号 + sha256 校验和 + opcode_names 指令表。
- 关键前提：**常量池只含标量**（文本/整数/浮点/空/布尔），列表与字典是运行时
  `BUILD_LIST`/`BUILD_DICT` 构造的，不在常量池里——这让字节码纯数据化成为可能，
  任意语言（Node/Rust）都能轻松解析，无需处理 Python 任意对象序列化。
- 选 JSON 而非扁平二进制的理由：可读、易调试、Node/Rust 都能用标准库直接解析，
  延续项目「零依赖 + 可调试」气质；二进制优化（更小更快）留作后续可选。

## D14. Node/Rust 宿主走「纯解释器」而非「ffi 加载 jsvm.dll」（M13.2/13.3）

- 路线图原文设想「Node 用 ffi-napi 加载 jsvm.dll」，但调研 C 源码确认：
  **jsvm.dll 是宿主驱动架构**——不链接 libpython，字符串/列表/字典/打印/异常/导入
  全部通过约 40 个函数的 `JsHost` 回调表回传宿主实现。ffi 方案意味着用 JS 重新
  实现全部语义回调，工作量巨大且极易错（C 结构体对齐、句柄代际号防悬垂）。
- 改为：Node/Rust 各写一个**纯解释器**，消费 D13 的 JSON 字节码，只翻译
  指令分发 + 内建函数。工作量约 1/3，真零依赖，且更贴合「字节码是中间格式、
  各语言有自己的执行引擎」的本意。
- 结果：Node 版 71 个 SNIPPETS + 10 个 cases 与 Python VM 逐字节一致；
  Rust 版「最小可运行」。已写入 docs/embed.md 诚实记录。

## D15. Rust 值语义 vs 基石引用语义的边界（M13.3）

- Rust 的 `Val::List(Vec)` 按值传递，`call_bound` 拿到的是列表副本，
  `列表.追加(x)` push 到副本上，不反映回原变量——与基石（同 Python）的
  可变引用语义冲突。
- 完整对齐需把 `Val::List`/`Val::Dict` 改为 `Rc<RefCell>`，是一次较大类型重构。
- 决策：Rust 版先「最小可运行」（能跑纯算术/内建/列表字典字面量），可变容器
  语义的 `Rc<RefCell>` 重构留作后续迭代。Node 版无此问题（JS 对象天然引用语义），
  这正是「先做 Node 再做 Rust」顺序的价值。
- **后续（M28/M29）**：这个重构已经做了——`Val::List`/`Val::Dict` 与
  `Instance` 都换成 `Rc<RefCell<…>>`（实例也必须共享，否则 `自身.字段 = 值`
  改的是副本、静默失效），迭代器/解包改成显式快照。M29 又补齐了方法调用、
  高阶方法、集合、文件与上下文、精确小数（零依赖手写 BigInt）。
  教训：当时的「最小可运行」其实是**夸大**的——`测试` 里没有 Rust 的对拍，
  真正跑起来才发现连函数调用都 panic、异常机制根本没接上。
  **新增宿主必须同时加对拍测试**，否则「支持」二字是空的。

## D16. 包管理分两步走：先本地 + 静态索引，后远端拉包（M10.2 / M14）

- M10.2 先做「本地包导入」（`导入 X 从 本地包`）+ 包清单 `包.json` +
  远端索引格式定义（`jishi-package-index` JSON，先静态文件托管、不建站）；
- M14 再补 `jishi 安装/卸载/列表` 命令，从远端索引「读索引→下载→解压→安装」。
- 版本约束语法：`*` 任意 / `1.2.3` 精确 / `==`/`>=`/`<=`/`>`/`<` / `^` 主版本锁定。
- 依赖解析：递归加载 + 版本满足性检查 + 循环依赖检测（报中文错），依赖包对象
  注入到模块命名空间（`依赖名.成员` 免重复导入）。
- 决策理由：不一步到位做完整包注册表/站点，先用最小可用形态验证「装包即导入」
  的闭环，避免在生态尚小时过度建设。

## D21. 发行版版本号定稿 0.1.0（M16.1）

- 路线图原文设想首发「0.0.1 技术预览」，但到 M16 动工时 M0–M15 已全部完成、
  语言规格已收敛 v1.0、功能相当完整，再标 0.0.1 反而低估现状。
- 决策：首发 **0.1.0**，0.x 阶段仍允许 breaking change，每个版本在
  `CHANGELOG.md` 列清变更与迁移指引。
- **版本号单一来源**：新增 `jishi/version.py`，通过 `importlib.metadata`
  从 `pyproject.toml` 读版本；`jishi --version`、语言卡、MCP Server、构建脚本
  共用同一值；PyInstaller 打包后无元数据时回退内置常量 `__FALLBACK__`。
  消除「cli.py 硬编码 0.1.0、pyproject 写 0.1.0」这类多处不一致的历史隐患。

## D22. 发行包用 PyInstaller onedir 而非 onefile（M16.2）

- onefile 每次启动解压到临时目录，冷启动慢于纯 Python；onedir 启动快、体积
  适中（实测 Windows x64 发行包 16MB）。
- 资源访问统一走 `sys._MEIPASS`（打包后）→ 包内 `_native/` → 源码树 `cvm/bin/`
  三级回退；标准库源码用 `_stdlib_dir()` 兼容打包（源文件在 `_MEIPASS/jishi/stdlib`）。
- **关键坑**：PyInstaller 直接打包「包内模块」`jishi/cli.py` 作入口会因相对导入
  （`from .errors import ...`）报「no known parent package」。解法：用包外的
  入口脚本 `tools/entry_cli.py` 绝对导入 `from jishi.cli import main`。
- 构建期依赖 PyInstaller 不进运行时：基石运行时仍零第三方依赖（README 明示）。

## D23. 安装默认用户目录 + `jishi 医生` 自检（M16.3）

- 安装默认到 `~/.jishi`（`--system` 才装系统级，避免权限问题）；
  安装脚本把 `bin` 加入用户 PATH（Windows 改用户环境变量，Unix 追加 shell rc
  并提示 source）；卸载脚本**包含 PATH 还原**，不留残余。
- 新增 `jishi 医生` 子命令做环境自检（版本/Python/安装位置/C VM 加载/终端编码/
  MCP 可用性），异常给中文修复建议，延续「中文报错」体验。
- **Windows 控制台 GBK 编码坑**：打包产物在 GBK 控制台 print emoji（✅/❌）会
  `UnicodeEncodeError` 崩溃。解法：入口脚本 `reconfigure(encoding='utf-8')` 强制
  UTF-8 输出 + `医生`/安装脚本里的 emoji 一律换纯文本 `[OK]`/`[警告]`。

## D24. 大整数与整数溢出的取舍（M32）

**背景**：Python 的 `int` 是任意精度，所以「对标 Python」就意味着
`2 ** 64` 该给 `18446744073709551616`。但三个宿主的整数表示各不相同，
探测时发现三边在超大整数上全都**静默给错值**（不是报错）：

| 宿主 | 表示 | 原来的表现 |
|---|---|---|
| Python VM / 树遍历 | 原生 `int` | ✅ 任意精度 |
| Node 宿主 | `number`（双精度） | `2 ** 64` → `18446744073709552000` |
| Rust 宿主 | `i64` | `i64_MAX + 1` → **负数**（回绕） |
| C 虚拟机 | `int64_t` | `2 ** 64` → **`0`**（ctypes 边界截断） |

**决策**：

1. **能到任意精度的就到**。JS 用 `BigInt`（原生任意精度）；Python 本来就有。
   但**不「一律用 BigInt」**——那会让每个整数加法都往返于 BigInt 与 number
   之间，JS 宿主的整数性能掉一个量级。改为**按需切**：任一边已经是 BigInt，
   或 number 算出来的整数结果超出 `Number.isSafeInteger`。
   代价是判断分支多两个 `typeof`，普通路径零额外开销。
2. **到不了任意精度的，就明确报错**。Rust 提到 `i128`（覆盖 `2**62`/`2**64`
   这些常见写法）+ `checked_*`；C 虚拟机保持 `int64_t`（**`JVal` 的 16 字节
   布局不能动**，M20 的批量转换快路径依赖它），在 ctypes 边界检查范围。
   两者越界都是**中文报错**，不是静默截断。
3. **字节码里的 int 常量按需换成字符串**。JSON 的数字在 JS 的 `JSON.parse`
   里就已经丢精度了（reviver 拿到的是已经解析过的值），所以超出宿主安全
   整数范围的 int 要写成十进制字符串，由宿主按需还原。旧产物（`v` 是数字）
   继续能读——**不升版本号**，因为新格式是旧格式的超集。

**边界**：C 虚拟机与 Rust 宿主在超大整数上是「明确报错」而不是「给值」。
这属于「宿主能力子集」（与「精确小数的 `**` 只支持整数指数」同一类），
在 `docs/embed.md` 的支持程度表里逐条标注。**宁可报错，也不给一个错的数**。

## D25. 「剩余边界」清单要按实测维护，不能只靠读（M30/M32）

**两次教训方向相反**：

- M30：`docs/embed.md` 给 JS 的「成员测试 `在`/`不在`」标了 ✅，
  实测发现**根本没实现**（`CMPOP` 只映射了 0–5，语义比较码 6–9 落成
  `undefined`）。
- M32：embed.md 写着 JS「`1` 与 `1.0` 无法区分」，实测发现**早就分得清**
  （字节码里的小数常量带 `t: "float"` 标记，`decodeConst` 早按它包了
  `FloatBox`）——这条被当成「表示层固有限制」写了好几轮。

**决策**：把「跑一遍横向探测」变成**改边界清单前的固定动作**，而不是出了事
再查。具体做法：写一个脚本让**所有宿主跑同一段代码、逐条比对输出**，
输出三类结果——

1. **不一致且都不报错** → 静默算错，最高优先级；
2. **一边报错一边给值** → 明确分歧，次优先（要么补齐，要么如实标注）；
3. **都不报错且一致** → 一致，从清单里删掉。

修完复跑，直到只剩「刻意的设计差异」（如精确小数的非整数次幂）。
这比读文档可靠，也比「凭印象判断哪些还缺」省时间。

## D26. D 档四类特性的 ROI 结论（M34）

路线图对 D 档的定调是「**重特性，先写最小原型测 ROI，不提前承诺**」。
M34 给四个候选各做了一轮评估（两个真做了原型落地，两个只做纸面评估后就搁置）。

### 做掉的两个：模式匹配、枚举

**两者都选「解析期脱糖」实现**，理由是同一个：它们能表达成既有语句的组合，
于是**三个执行器 + 两个跨语言宿主一行都不用改**。这是本项目第四次、第五次
用这个手法（前三次：M23 `超()`、M24 集合字面量、M26 `用 … 为`）。

| 特性 | 脱糖成 | 实际改动 |
|------|--------|----------|
| 模式匹配 | `__匹配_N__ = 待匹配值` + `如果/否则如果/否则` 链 | 只动 `parser.py`（约 200 行） |
| 枚举 | `类 X：`（初始化/文本）+ `X.成员 = 新建 X(…)` + `X.全部 = […]` | 只动 `parser.py`（约 120 行） |

代价也是同一类：**脱糖能表达的语义上限就是既有语法的上限**。
所以这两个特性都只做到「够用」：

- 模式匹配**不做**解构绑定（`情形 [甲, 乙]：` 里绑定名字）——
  那需要新的绑定语义，脱糖做不出来（`==` 不能同时绑定）。容器模式只能按值相等匹配。
- 枚举**不做**成员方法、不做 `值查成员`（`颜色.按值(1)`）、不做标志位组合。
  要那些就直接用「类」——枚举是「一组有名字的值」，不是「简化的类」。

**这个取舍是明确的**：宁可要一个「三执行器行为必然一致、实现只有两百行」
的够用版本，也不要一个「语义更全但要在三处各写一遍、还可能对不上」的完整版本。
将来真有需求，再单独评估要不要升级成原生实现。

### 搁置的两个（附理由）

**生成器 `产出`**（惰性序列）——**成本高，且脱糖路线走不通**：

- 它需要「函数执行到一半挂起、下次从挂起处继续」的状态机，三种执行器的
  实现方式完全不同（树遍历要 CPS 变换、Python VM 要把帧存起来、C VM 要
  改 `JVal` 布局并新增协程状态）。参考项目历史上新增一个 `Val` 变体就要
  在四处 match 里各接一次（M33 的 `Date`/`Table`/`Slice`），而生成器要动的
  是**整个调用协议**，不是加一个分支。
- 需求侧也不硬：三大真实项目（成绩分析/日志统计/网页采集）**一个都没用到**
  惰性序列；它们要的是「读大文件不炸内存」，而这个已经由 `文件对象按行迭代`
  （M26）解决了——那条路径不需要生成器。
- 结论：**先不做**。如果将来出现「必须惰性生成无限/超大序列」的真实项目，
  再开一档专门做，届时优先选「只在 Python VM 做、另两个执行器明确报错」
  的分期路线（与集合 M24 的做法一致）。

**多继承**——**MRO 复杂度与语言定位冲突**：

- 要正确处理菱形继承就得实现 C3 线性化，还要处理 `超()` 在多继承下的
  语义（Python 的零参数 `super()` 依赖 MRO 里的「下一个」）。M23.4 的
  `超()` 脱糖成 `超(自身, "定义类名")`，那个设计**建立在单继承上**，
  多继承要重新设计。
- 需求侧：单继承 + 混入式组合（持有别的对象）已经覆盖绝大多数场景；
  三个真实项目没有一个用到多继承。
- 结论：**先不做**。真要做也不是「加个语法」，而是要重新设计 `超()`。

### 明确不做（成本低但需求弱）

- **`全局` 声明**：基石的作用域读时是闭包式的（函数里能读外层变量），
  只有「写」的问题。Python 要 `global` 是因为赋值默认创建局部变量；
  基石的函数体如果没有 `令`，赋值就写外层——用 `非局部` 那样的显式声明
  在中文语境里反而绕。真需要时用可变容器（列表/字典）当载体就够了。
- **`删除` 变量**：Python 的 `del` 在带 GC 的语言里主要用于「提前释放」
  和「删字典键」，前者对脚本语言意义不大，后者已有 `字典.移除()`。
  加一个只能删名字的语句，收益看不清。
- 这两条**攒够需求再说**：单独为它们各来一轮（要动三执行器）不合算。

### 一条方法论沉淀

M34 再次验证了「**先写最小原型**」的价值，但方式与预期不同：真正的收获不在
「原型证明了可行」，而在**原型撞出了三处既有缺陷**（宿主缺类变量、
Rust `继续` 后无法 `中断`、Rust `类型()` 给错名字）。这些都不是 M34 引入的，
是「一直没被真实代码走到」的路径。

> **结论**：D 档特性要连着**真实用法**一起验。写个语法规格就收工，
> 只会留下一堆「语法能用但一用就撞坑」的半成品。

## D27. 类体校验放「解析期」一处拦下（M35）

### 背景：一个真实的「三执行器语义分歧」

写 M35 的收尾时顺手做了个对照测试（同一个类体在各执行器里跑一遍），
结果发现**同一段代码，三个执行器给的答案互不相同**，而且一个比一个糟：

| 类体里写了 | 树遍历 | Python VM / C VM |
|-----------|--------|------------------|
| `打印("…")` | 报「不支持 ExprStmt」 | **静默忽略**（副作用没发生） |
| `x += 5` | 报「不支持 Assign」 | 当成 `x = 5` **静默算错** |
| `x[0] = 1` | 报「不支持 Assign」 | 抛英文内部错 `'Subscript' object has no attribute 'id'` |
| `"说明"` | 报「不支持 ExprStmt」 | 静默忽略 |

这违反了项目的第 1 条硬约束（三执行器语义必须一致）。而其中
**最危险的不是「报错」，是「静默算错」**——`x += 5` 被悄悄当成 `x = 5`，
用户看到的是「程序跑通了，但结果不对」。

### 决策：在 parser 里校验，而不是在三个执行器里各挡一次

理由与前几次「解析期脱糖」**同一个逻辑**：**三个执行器都要过 parser**，
所以在 parser 一处校验，三处自动一致，且**字节码/树都不用改**。

规则定得尽量窄——类体只允许：

1. **方法**（`函数 …`）——OOP 的主体；
2. **类变量**（`名字 = 值`，只认一次性的 `=`）——注意 `+=`/下标/属性赋值
   都不算「声明」，要写进方法里；
3. **空类占位**（单独一行 `:`）。

其余一律在解析期报「类体里只能写什么」并给出正确写法示例。错误定位用
`_err_at`（按 AST 节点的行列合成 token），因为块解析完之后 `self._peek()`
已经指到块后面去了，直接用会把下划线画到下一行。

### 顺带澄清一条被误记的「缺陷」

M32 的文档里记着一条「**树遍历不支持类体里写 `通过`**」。M35 查清了：
**这是误判**——`通过` 从来不是关键字（词法器里根本没有它），它是个普通名字；
`如果 真：
    通过
` 在**三个执行器**里都报「找不到这个名字」。
所以「类体里的 `通过`」不是「树遍历少支持了一个特性」，而是
「一个未定义的名字被字节码执行器静默忽略了」。

处理：**不把 `通过` 升级成关键字**（空块已经有 `:`；为它加一个关键字
要动三执行器 + 两宿主 + 关键字表 + 粘连检查表，收益不值）。
但**报错时点名**——因为从 Python 过来的人确实会写 `通过`：

```
错误 E0201：这里出现了不能写的内容（类体里不能写「通过」——它不是关键字，
只是个普通名字）
  2 │     通过
    │     ~^
  提示：空类用「单独一行冒号」占位：
类 空类：
    :
```

> **结论**：「静默」比「报错」危险。凡是发现「某个写法在一个执行器报错、
> 在另一个执行器被悄悄忽略」的地方，**统一到解析期**是最省事也最一致的修法；
> 顺带把错误信息写成「说清原因 + 给出正确写法」，比单纯拒绝有价值。

## D28. 调试器只做树遍历执行器 + 钩子只读（M37）

### 决策一：只在树遍历执行器上做，不追求「三执行器对称」

路线图 B1 的目标是「断点 / 单步 / 看变量 / 看调用栈」，而基石有三个执行器
（树遍历 / Python VM / C VM）与两个宿主。**要不要一次做全？不做。**

树遍历里「一个语句 = 一次 `exec_stmt`」是**天然的暂停点**：在 `exec_stmt` 开头挂
一个 `before_stmt` 钩子，断点、单步（进/过/出）、局部变量与调用栈**全都由它推出**；
三种单步只是「帧深」比较（`下一步` = 深度 ≤ 暂停深度、`跳出` = 深度 <），
实现里不需要第二处特判。

字节码执行器没有这种「语句边界」事件：栈机只知道指令，要么每步比对行号表
（慢且脆），要么加新指令；C VM 还要先让宿主回调能把帧传出来。**同一份功能在
字节码侧的成本高一个量级。**

于是 B1 只做树遍历，`docs/调试器.md` 与路线图**如实标注**「Python VM / C VM
暂不支持」，并把「字节码执行器的调试器」列为 B5 —— 等真实需求说话再做。
**为「三个执行器对称」而做的功能，往往是最贵的那类**：本项目已经在 M29/M33
为「补宿主」付过一轮长期投入，工具链不该再走一遍。

对比另一条路：用 Python 的 `sys.settrace` 做通用调试，连 C VM 都能顺带被调试到，
但它会侵入用户程序、性能不可控、行为依赖 CPython 实现细节。自己的语言自己插桩，
才谈得上「语义可控」（与 D1「技术栈透明」一脉相承）。

### 决策二：钩子只读 —— 调试器不许改变语义

钩子只读语句行号与环境，暂停时也不动环境。因此**「带调试器跑」与「不带」的程序
输出必须逐字节相同**，由 `tests/test_m37_debugger.py` 钉住（含 `中断/返回/尝试`
混在一起的控制流）。这条纪律比功能多少更重要——调试器要是能改变被调试程序的
行为，它给出的所有信息都不可信。

### 决策三：「退出」用 `BaseException`（`DebugQuit`），并且照跑 `最终`

`DebugQuit` 刻意不继承 `JishiError`：否则用户程序里一句 `捕获：` 就能把「退出」
吞掉（`_do_try` 里那句 `except BaseException` 是为把 Python 异常翻译成中文写的）。
配套在 `_do_try` 的控制信号元组里（与 `中断/继续/返回` 并列）显式放行它，
于是「退出」会照常执行 `最终` 块——**像一次正常的控制流离开，而不是硬杀**。

### 决策四：出错现场用「语句级快照」

错误是在语句执行到一半时冒出来的；等它传到 `run()`，`_eval_call` 的 `finally`
已经把帧弹干净了，此时再问「当前帧」只会得到模块顶层、变量还是上一帧的
（实现时真实踩到：错误出在函数「主」里，快照却写着「模块顶层」）。
所以 `before_stmt` 每执行一条语句就**复制**一份现场（行号 / 帧标签 / 环境引用 /
栈链），出错时用这份快照。

> **结论**：工具链功能**先在最划算的一处做扎实**，把成本高的部分明确列成待办，
> 而不是硬凑对称；同时用测试把「不影响语义」这条纪律钉死。

## D29. 增量同步：先量后做，「只做一半」要如实标注（M38）

### 背景：路线图写着「大文件有卡顿」——到底卡不卡？

先测再改（项目纪律：别猜瓶颈）。实测 LSP 每收到一次编辑（整文件 tokenize + parse）：

| 行数 | 253 | 1253 | 5003 | 20003 |
|------|----:|-----:|-----:|------:|
| 每键成本 | 9.9 ms | 44 ms | 182 ms | 759 ms |

**一千行以上就有可感卡顿**——路线图的说法成立，值得动手。

### 决策一：只做「分词」的增量，`parse` 保持全量，并在文档里写明

编辑只影响改动行**之后**的内容，所以前缀的 token 与词法状态可以复用
（依据是 `tokenizer.LineAnchor` 的七个值：缩进栈 / 括号深度 / 跨行三引号累积内容
与起点 / 是否在多行注释里）。实测改末行 18001 行从 **359.7ms → 8.5ms**（40 倍以上）。

但 `parse` 仍是全量的（5000 行约 78ms）。**增量解析**要维护「每个语法节点的子树
缓存 + 编辑后的失效范围」，复杂度高一个量级，而当前收益只有几十毫秒，路线图也没
要求。所以：**做成一半，并把另一半明确标出来**（`docs/工具链.md` 与路线图都写了）。
半成品的危害在于「看起来都优化了」，而不是「只优化了一半」。

### 决策二：前缀由**自己算**，不听客户端说的改动范围

客户端给的 `range` 只对**它自己的文本**成立；我们这边的文本可能因为版本乱序之类
的原因已经不一样了。所以增量起点用「按行文本比较求共同前缀」——这是**自证**的：
前缀相同的行，分词结果必然相同。代价是一次行级比较（远低于分词本身）。

### 决策三：位置单位按 LSP 默认的 UTF-16 码元

中文在 BMP 内一个字符算 1 个码元，emoji 这类天文平面字符算 **2**。要是按 Python
字符下标去应用编辑范围，光标在 emoji 之后就会**改在错位置**，而文档一旦被改坏，
后续所有诊断都是错的。所以入向（应用编辑）与出向（诊断/悬停位置）都换算，
并且专门钉住「emoji 前后两个边界」。

### 决策四：REPL 的行编辑核心与平台解耦，按键可注入

Windows 没有 `readline`，要自己用 `msvcrt` 逐键读；POSIX 可以交给 `readline`；
非终端必须退回 `input()`（脚本与 CI 不能被行编辑打扰）。三套路径如果混在一起写，
就变成「只能在真终端里手测」的代码。

做法：把 `History` / `Completer` / `LineEditor` 写成**纯逻辑**（按键序列与输出都
可注入），平台差异收在最外层 `read_line` 一个函数里。于是「上键取历史、Tab 补全、
退格删汉字、Ctrl-C 放弃当前输入」都能在单测里断言，Windows 那条真路径也能用
假 `msvcrt` 喂按键跑一遍。

### 决策五：格式化器只依赖词法层，不做完整语法分析

`如果 真`（漏冒号）这种半成品照样排版——用户可能正写到一半，格式化器不该因为
「还没写完」拒绝服务。相应地，「处理不了」只对应**词法**错误（未闭合字符串、
非法字符），报告时也分开说（「没格式化」要跑 `--write`，「处理不了」得先改代码）。

> **结论**：性能类改动**先量后做**；做不完整就**明确标注缺口**；
> 凡是「只能在特定环境手测」的逻辑，都要想办法把核心抽成可注入、可单测的纯逻辑。

## D30. 调试器扩到字节码执行器：靠「语句起始标记」，不靠猜行号（M39）

**背景**：D28 把调试器先落在树遍历上，理由很硬——那里「一个语句 = 一次
`exec_stmt`」是天然的暂停点。字节码执行器（Python VM / C VM）是栈机，
没有这种事件。于是问题变成：**怎么让栈机也有「语句边界」？**

**候选**：

1. **每步比对行号表**：指令带 `line`，行号一变就当语句边界。问题是行号一变
   的地方远多于语句边界（一条语句跨多行、表达式内部换行），会停在不该停的地方；
   循环回边（`遍历` 跳回 FOR_ITER、`当` 跳回条件）会让**循环头每轮都停一次**，
   而树遍历只停一次——同一个断点在两个执行器里行为不同，正是最该避免的事。
2. **加一条「语句」指令**：要动 C VM 的指令集与 ABI，代价立刻上一个台阶。
3. **在指令上打标**：编译器本来就知道「这条指令是某个语句的第一条」，
   把它记在指令上（`Instr.stmt_line`），VM 主循环一次属性读取就够。

**决策**：选 3。并且**只标语句的首指令**——循环回边落在语句中部，不落在首指令上，
于是循环头只停一次、循环体每轮都停，**与树遍历的暂停点严格对齐**。

**配套的两个小决定**：

- **空块 `:` / 类体里的方法定义行，补一条「空操作」指令挂标记**。它们本身不产生
  指令，不补的话「树遍历能停、字节码停不住」。补完之后的**不变式**是
  「打标行的集合 == AST 语句行的集合」，并拿 `examples/` + `tests/cases/` 全量对拍。
  这条不变式在实现时抓出两个真问题：类体里的方法定义行、空块行，**原先两个执行器
  都停不住**（`statement_lines` 却说它们可停 → 一个静默失效的断点）。
- **「可停的行」由字节码标记反推**（`mark_lines`），不再单独解析一遍 AST：
  它天然就是执行器真正停得下来的那些行。

**验收方式选的是「逐字对拍」**：同一脚本、同一组断点、同一串命令，
两个执行器的**会话记录必须一字不差**（含变量表、调用栈、出错现场、`退出` 行为）。
这条测试比「各自看起来对」强得多——它把「两个执行器行为一致」变成了可执行的断言。

**C VM 的判定**：**暂不做**。它的帧与局部槽都在 C 侧，要做等于把「一个只读钩子
+ 一张标记表」换成「结构体字段 + 宿主回调 + 中断约定」；而收益只是「用同一套
调试体验去调 C VM」。按「别为对称而做」，列为 B 线待办（细节见 `docs/调试器.md`）。

## D31. M39 顺手挖出的四个潜伏缺陷：都不报错，只是「你以为有」（M39）

做 B5 的过程里，被「对拍」和「拿真实项目试」逼出来四个**长期存在、谁都没发现**
的问题。它们的共同点是：**文档没写、测试没跑、一写就踩**。

| 问题 | 后果 | 修法 |
|------|------|------|
| **跨行三引号字符串收尾引号独占一行时不补 NEWLINE** | 多行字符串**整个特性**不可用（解析器把下一行并进同一句，报「这一行没写完」）。语料里没人真跑过它，只有格式化的用例碰到过 | `tokenizer` 去掉一个多出来的 `and rest`（M39） |
| **类体里的方法定义行两个执行器都停不住** | `语句行` 说它可停、断点加在上面却从不停——静默失效 | 解析/编译期补「空操作」+ 树遍历在类体循环里也调 `before_stmt`（M39） |
| **类变量求值顺序与源码顺序不一致** | 字节码执行器先造类、再按源码顺序求值；树遍历按源码顺序求值。带副作用的类变量在两个执行器里**执行顺序不同**（都不报错） | 字节码侧改成「在源码位置求值、存临时槽，最后挂上」（M39） |
| **`导入 文本` 会打断 f-string** | f-string 插值脱糖成 `文本(值)`；模块「文本」正好遮蔽这个内建，于是**任何 f-string 都报「模块「文本」不能直接调用」**。`文本` 是本项目最常用的标准库名 | **尚未修**，先用 `导入 文本 为 文本库` 绕开；正解是给插值一个不会被遮蔽的内部转换（要动三个宿主），列入路线图 |

**另外，一条「明确分歧」被对拍抓出来并如实标注**（按 D25 的分类属于第 2 类
「一边报错一边给值」）：函数里给**外层同名变量**赋值时，字节码执行器按
「赋值即局部」报「找不到这个名字」，树遍历却按「先向外找、找到就用」静默算出
另一个结果。修树遍历要给它加一遍「赋值名收集」（语义改动，得配全量对拍），
所以 M39 只标注不修：`tests/test_cvm.py::test_inner_assignment_to_outer_name_is_local`
用 `xfail(strict=True)` 钉住现状，**哪天补齐了这条测试会失败，提醒把它改成正常断言**。

> **结论**：功能「写完了」不等于「能用」。**两个执行器 + 一个真实项目 + 一条
> 全量不变式**，比再读一遍代码有用得多——这四个问题一个都不是读代码能读出来的。

## D32. 补上 D31 里那条分歧：树遍历的「赋值即局部」（M40）

**背景**：M39 的对拍挖出一条明确分歧——函数里给**外层同名**变量赋值时，
字节码执行器按 Python 的「赋值即局部」报「找不到这个名字」，树遍历却按
「先向外找、找到就用」静默算出另一个结果。当时判定为「一边报错一边给值」，
按纪律只能先如实标注（`xfail(strict=True)`），因为补它属**语义改动**。

**做法**：进函数时，把「本函数体里**被赋过值**的名字」全部先占上未绑定哨兵
（`interpreter._Unbound`）。于是：

- 赋值**之前**读它 → 报「名字「x」在赋值之前被用到了」（不再穿透到外层）；
- 外层有同名变量也不受影响（内层遮蔽）；
- 只读外层变量（不赋值）**照常**闭包捕获——这条最容易改坏，专门有用例。

**关键选择：判定「哪些名字是局部」直接复用编译器的收集器**（`compiler._collect_stmts`
+ `_Scope.bound`），不另写一遍。理由：那份逻辑已经决定了字节码执行器把哪些名字
当局部变量；另写一遍迟早会漂，而漂了就是「同一个程序在不同执行器里行为不同」
——正是本项目最防的一类问题。代价是 `UserFunction` 要懒缓存一次收集结果。

**报错文案是单一来源**（`runtime.unbound_local_error`）：三个执行器都调它。
对拍测试比的是 `(输出, 报错全文)` **整对**，文案差一个字就判成「执行器不一致」
——把文案集中到一处，比在三个地方各写一遍再靠人盯要可靠得多。

**验收**：`tests/test_cvm.py` 里那条 `xfail` 转成正常断言，另加一条「赋值前读
局部」的对拍；`tests/test_m40_scope.py` 20 项覆盖遮蔽 / 闭包 / 形参 / 解包 /
`+=` / 循环变量 / 两层嵌套 / 导入别名 / CLI 端到端。

## D33. C VM 的调试器：加四个只读入口，不猜执行器内部（M40）

D30 给 Python VM 定的做法是「编译器打语句标记 + 主循环查表回调」。C VM 复用了
同一个思路，但多了两层约束：**帧与值都在 C 里**，且**指令宽度是跨语言公开契约**。

**四个入口**（`cvm/include/jsvm.h`，全部只读）：

| 入口 | 作用 |
|------|------|
| `jsvm_set_stmt_marks` | 收下语句起始表（**单独一张 int32 数组**） |
| `jsvm_set_stmt_hook` | 装语句钩子（只在语句首指令回调） |
| `jsvm_frame_meta` | 问一帧的「代码下标 + 调用点」 |
| `jsvm_dump_locals` / `jsvm_dump_globals` | 把帧变量/全局交给宿主转换 |

三个决定值得记：

1. **语句起始表另发一张，不往指令里加字段**。指令宽度（6 个 int32）是 Node /
   Rust 宿主也按它读的公开格式，为一个调试功能改公开契约不划算。
2. **钩子用独立的 setter**（`jsvm_set_stmt_hook`），不动 `jsvm_load_module` 的
   签名：**不改已有 ABI**，而且「要不要调试」与「能不能装载」本来就是两件事。
3. **值的所有权用「借用」**：`debug_local` 回调收到的 `JVal` 是借的，宿主当场
   转成 Python 对象——不为调试发明第二套所有权规则。

**「退出」是这里最贵的一处**：它要穿 `最终`、又不能被 `捕获` 接住。做法是把
`DebugQuit` 当**卸载类信号**（`is_signal` 返回 3）交给 C 侧异常分发：跳过循环、
直接跳 `finally_ip`、`END_FINALLY` 后继续向外。为此在 C 侧补了两件事：
`END_FINALLY` 检查「有没有待重抛的异常」（否则信号被静静吞掉），以及
`make_error` 不许包装 `DebugQuit`（否则被用户 `捕获` 接住）。

**没做的一件事**：就地求值（`查看 表达式`）。C 侧没有「在任意帧上求一个表达式」
的入口，要做得把编译好的求值代码塞进当前帧执行，属另一件事。会话**明确说**
「C 虚拟机暂不支持就地求值」，而不是给个错值。

> **结论**：把「调试器要知道的事」压到最小的一组只读入口上，执行器内部就不必
> 为调试器让步。**对称不是目的，能对拍才是**——三个执行器的会话记录逐字相同，
> 这条断言比「三个都实现了」有意义得多。

## D34. 内部保留名：用户写不出的名字才安全（M40）

f-string 插值原先脱糖成内建 `文本(值)`——而 `文本` 正好是本项目**最常用的标准库
名**，一句 `导入 文本` 就把它遮蔽，于是**所有 f-string 当场报「模块不能直接调用」**。
这个缺陷藏了很久：语料里没有「既导入文本又用插值」的写法。

**做法**：脱糖目标改成 `$文本`。`$` 在词法阶段就是「无法识别的字符」，用户**写
不出来**这个名字，所以永远不会被遮蔽。三个执行器与两个宿主都注册它。

**配套的一条纪律**：内部名不许出现在**用户可见的地方**。新增
`runtime.is_internal_builtin`（判据两条：`$` 开头，或说明以「内部用」开头），
`ai.build_lang_spec()` 与编辑器补全都按它过滤——否则 `$文本` 会被当成可写的
函数推荐给用户（顺带修掉老早就在规格里的 `检查实参`）。

> **结论**：**「用户写不出来」是内部名唯一可靠的保护**。靠约定、靠文档、靠
> 命名前缀都不行——只要用户能拼出那个名字，它迟早会被遮蔽或被误用。

## D35. 标准库模块名不能撞内建名：`集合` → `容器`（M41）

路线图（§3.6 方向一）给 M41 定的标准库清单里有个「`集合`」模块（放 Counter
式的计数工具）。真动手时发现：**`集合` 是本项目的内建函数名**
（`集合([1,2,3])` 去重造集合），同名模块一 `导入` 就会把它遮蔽——正是 M40
刚修掉的 f-string 遮蔽坑（D34）同一类问题。

**做法**：改名**「容器」**。理由两条：

1. **避开遮蔽**：`导入 容器` 与内建 `集合(...)` 井水不犯河水，用户不用记
   「哪个名字要加别名」。
2. **语义更准**：这个模块装的是**装东西的工具**（计数、分组、取前），不是
   集合类型本身——集合类型是内建 `集合()` 与它自带的方法（`并集`/`交集`/
   `差集`/`对称差`，M24 就有了）。

> **结论**：**标准库模块名先查一遍内建名与关键字**。加模块是个「看起来零
> 风险」的动作，但名字撞上内建就是一次全局遮蔽——而且这种遮蔽只在「用户
> 同时用到模块与内建」时才发作，测试里不一定碰得到。

## D36. 解析期脱糖的第二例：`遍历` 的多变量解包（M41）

`令 甲, 乙 = …` 早就支持解包（M25 还加了 `*余`），但 `遍历` 只接受**单个**
循环变量。`examples/ai/few-shot.md` 的示例 34 就写着 `遍历 名字, 年龄 在 对们：`
——**AI 照着自己的 few-shot 写，必然报错**。

**做法**：与 M26.2 的 `用 … 为`、M34 的模式匹配同一手法——**解析期脱糖**：

```
遍历 名字, 年龄 在 对们：       遍历 __遍历项_3_5__ 在 对们：
    打印(名字, 年龄)      →          令 名字, 年龄 = __遍历项_3_5__
                                     打印(名字, 年龄)
```

**为什么这比「改三个执行器 + 两个宿主」好**：解包赋值本身已经是成熟路径
（`TargetList` 在解释器与编译器里都有实现），脱糖之后**五路一行都不用改**，
行为必然一致。代价只是循环体里多一句赋值，以及临时变量名要**用户写不出来**
（用 `__遍历项_行_列__` 前缀 + 行号，符合 D34 的「内部名」纪律）。

**顺带发现的一个真缺陷**（不是这次引入的）：`cvm_bind._cb_iter_next_batch`
的批量快路径原先用 `all(type(v) is int for v in chunk)` **预扫描**一遍再构造，
M41 把它改成**一趟**（边判边装，遇到非整数抛内部哨兵回退）。第一版把哨兵写成
**实例**而不是类，于是 `except (_struct.error, OverflowError, 哨兵)` 在运行时
炸成「catching classes that do not inherit from BaseException」——而且**只在
C VM 遇到「批量里有非整数」时触发**（`遍历 [[1,2],[3,4]]` 这种嵌套列表立刻
中招，单层整数列表则一路正常）。

> **结论**：**「只在某一路才触发」的缺陷，只有对拍能抓住**。这条如果只靠
> 「跑几个例子看看」，很容易漏——因为最常见的场景（整数列表）恰好不走那条
> 分支。这也解释了为什么 M41 的验收标准里写的是「五路逐字一致」而不是
> 「能跑通」。

## D37. 有状态的标准库模块要「每次导入造一份」（M41）

`日志`（级别 + 前缀）与 `测试`（用例记录）需要**跨调用保持状态**。第一版把
状态放在 Python 的**模块级全局**里——单跑没问题，但同一进程里跑第二个执行器
就串：五路对拍时，树遍历先跑一遍（级别被设成 `调试`、用例记了 1 条），
Python VM 紧接着跑同一段代码，读到的却是**上一轮留下的状态**。

**做法**：给这类模块一个约定钩子 `__基石新建__()`——`do_import` 每次导入
都调它，拿一份**全新的状态字典**（闭包捕获自己的状态）。三个执行器、两个
宿主各自独立，互不影响；同一进程里连跑两遍也不会累积。

**配套改了 AI 规格扫描**（`ai._stdlib_api`）：有状态模块的函数定义在工厂函数
内部，扫描器要**往里再看一层**（`_收集函数` 递归进 `__基石新建__` 的 body），
否则 `日志` / `测试` 的函数会从语言规格里消失——而规格是给 AI 看的唯一事实源。

> **结论**：**「模块级全局」在「同一进程跑多路」的架构里是错的**。本项目的
> 核心验收手段就是对拍，而对拍天然会在一个进程里跑多个执行器——所以状态
> 必须跟着「一次导入」而不是「一个模块」走。

## D38. few-shot 示例也要当代码测（M41）

`examples/ai/few-shot.md` 有 48 段示例，是喂给 AI 的「正确写法」样本。
M41 体检发现：**这些示例从没人跑过**，其中 **4 段是真错**——

| 示例 | 错在哪 | 后果 |

| 29 闭包计数器 | 内层函数给外层变量赋值（M40 起算新建局部变量） | 报「名字「计数」在赋值之前被用到了」 |

## D39. 语言客户端手写，不引 `vscode-languageclient`（M42）

M42 的验收标准是「每条能力在 VS Code 里手工演一遍」，而扩展此前**连 `main` 都没有**
（纯语法高亮）。所以必须先有客户端。

**做法**：自己写传输层（`editors/vscode-jishi/lsp-transport.js`，约 150 行：
`Content-Length` 分帧 + 请求应答 + 通知分发 + 服务器反向请求应答），
`extension.js` 只做「编辑器 API ↔ LSP 消息」的翻译。

**理由**：要的只有三件事（分帧、请求应答、通知分发），而
`vscode-languageclient` 会带来一整套依赖树。这与本项目在 C 内核（不引第三方 C 库）、
正则引擎（自写）、zip（自写）上的取舍一致：**能自己写清楚的就别引依赖**。

**顺带的好处**：手写之后，服务端支持的每一项能力在客户端**逐条可见**——
不会出现「装了客户端但某项功能悄悄没接上」；而且能写 `verify-lsp.js`，
用**同一份传输代码**脱离编辑器做端到端自检（25 项断言，已进回归）。

> **结论**：**为客户端的每一项能力都准备一条「不装编辑器也能验」的路**。
> 装进编辑器之后才发现「点了没反应」，排查成本高得多。

## D40. 重命名只做模块级符号：宁可少做，不可改坏（M42）

`rename` 看似简单（把同名的地方都换掉），真做起来有个硬问题：**没有作用域分析**。

- AST 里 `FuncDef.params` 只是一串名字，**不记位置**——形参的「定义处」根本不存在，
  改名会漏掉声明、只改用到的地方，**直接改坏代码**。
- 函数内局部变量虽然进了符号表，但按名字全局替换会把「另一个函数里的同名局部变量」
  一起改掉——同样是改坏代码。

**做法**：只接受**模块级**符号（`sym["container"] is None`），其余一律
`prepareRename` 返回 `null`，编辑器直接禁用重命名并显示「无法重命名」。

> **结论**：**「做不到」要说出来，不要给一个看起来能用、实际会改坏代码的编辑**。
> 返回 `null` 让编辑器明确拒绝，用户最多觉得「这里改不了」；给错编辑则是
> 静默损坏——两者代价差一个数量级。

## D41. 语义高亮：只上「语法文件看不出来」的色（M42）

语义高亮的差量编码有两处容易错，都是「单行测试发现不了」的：

1. **`deltaLine > 0` 时 `deltaStartCharacter` 是绝对值**（相对行首），
   只有同一行内才是相对上一个 token。混了的话客户端**只在跨行时**解错位。
2. **位置单位是 UTF-16 码元**，而词法器给的行列按 Python 字符数算——
   emoji 这类天文平面字符占 2 个码元，不换算就会偏。

另外两处**分类**上的取舍：

- **只上「语法文件看不出来」的色**：关键字 / 标准库（`defaultLibrary`）/
  用户函数与变量 / 形参 / 属性。字符串、数字、注释交给扩展自带的 TextMate 语法
  ——语义层再上一遍只会跟主题打架。
- **用户绑定的名字优先于标准库名**：M41 新增的模块名（`容器`/`迭代`/`参数`/
  `日志`/`测试`）**都是常用词**，`令 参数 = 1` 之后 `参数` 指的是变量而不是模块。
  顺序反了就会把用户变量上成模块色（这条有专门的回归钉子）。

> **结论**：**差量编码这类「只在特定维度才错」的协议细节，必须写一条专门
> 跨行的测试**；否则线上表现是「偶尔串色」，而本地单行样例永远是对的。

## D42. DAP 的线程模型：脚本线程阻塞，主线程读状态（M43）

**背景**：DAP 是「客户端随时可能来问」的协议——编辑器收到 `stopped` 事件后会
立刻连发 `stackTrace` / `scopes` / `variables`。适配器既要把程序跑起来，又要在
暂停时应答这些查询，还得让两者不打架。

**取舍**：

- **方案 A（没选）**：把调试器改成「问一次走一步」的协程式结构。要动 `_Session`
  的核心循环，三个执行器的钩子都得跟着改——等于把已经稳定下来的调试内核拆了重搭。
- **方案 B（选了）**：主线程只跑 DAP 消息循环，**脚本线程**跑程序；暂停时脚本
  线程阻塞在命令队列上。于是「暂停期间执行状态不变」是**天然成立**的，
  主线程读栈与变量不需要任何锁。

代价是多一条线程与一个队列；换来的是调试内核几乎一行没改——只在 `_pause` 开头
加了一个 `on_pause` 钩子、在 `_before_statement` 里加了一个 `pause_requested`
判定、给三个执行器各加了一个「按帧取句柄」的方法（编辑器要能点任意一帧看变量）。

**配套两条纪律**（都踩过才写下来）：

1. `stopped` 必须在**暂停判定成立时**发，不能等打印完——编辑器收到就来问栈，
   而那时脚本线程正要往下走去读命令，状态已经不会再变。
2. 「继续类」请求只在**确实停着**的时候才入队；否则命令会攒下来，下次命中断点
   时被立刻吃掉，表现为「断点失灵」。

## D43. 调试走 VS Code 内置的适配器进程，不自写传输层（M43）

语言服务那条路我们**自己写了** `lsp-transport.js`（约 150 行），理由是需要在
编辑器之外也能跑同一份代码（`verify-lsp.js` 与自检脚本都用它）。

调试这条路**没这么做**，改用 VS Code 的 `DebugAdapterExecutable`：它负责起子进程
并转发 DAP 消息，扩展侧一行传输代码都不用写。理由：

1. 没有「编辑器外也要跑同一份代码」的需求——协议级验证用 Python 直接喂 JSON-RPC
   更贴近真实（`tests/test_m43_dap.py` 就是这么做的）；
2. 自己转发意味着**多一层进程与管道**，出错时更难定位；
3. 少一份要维护的代码，就少一份与 VS Code 版本漂移的可能。

**代价**：扩展里就没有一份可复用的 DAP 传输层，所以**没有** `verify-dap.js`。
这是有意的取舍，不是遗漏——协议层由 Python 测试兜住，接线层面靠
`tests/test_m43_dap.py` 里的三条契约测试（扩展声明 ↔ 适配器行为）。

## D44. 高亮表与片段：从语言事实生成，并用测试钉住（M43）

**问题**：`syntaxes/*.tmLanguage.json` 与 `snippets/*.code-snippets` 是**手写的
副本**。语言里新增内建、新的库模块，不顺手同步的话编辑器里就悄悄少一块颜色。
这类「悄悄过时」靠眼睛发现不了——M41 的 few-shot 体检就是同类问题：
48 段示例里躺着 4 段真错，谁都没注意。

**做法**：

1. 高亮表里的四类词（关键字 / 内建 / 标准库模块 / 异常类型）**从
   `ai.build_lang_spec()` 生成**，不再手抄；
2. 测试比对「语言事实 ⊆ 高亮表」，忘了同步就红；
3. 片段里的占位符填成默认值后**必须能解析**（块头自动补空块、嵌套占位符要认），
   于是「插进去就是错语法」的片段跑不过测试。

**顺带修掉的两个真错**：`新建 X()` 与裸的插值文本**都不能单独成语句**（表达式
不能裸着当语句），原来的片段插进去就是错的——已改成 `令 对象 = 新建 类名(参数)`
与「把插值文本包在 `打印(...)` 里」。

**边界**：生成的是**词表**，不是整份 tmLanguage——正则结构、scope 名、字符串与
注释规则仍是手写的（那些管「怎么着色」，不是「有哪些词」）。

## D45. 基石库层：用基石写的标准库，在**编译期展开**成外壳函数（M52）

**问题**：标准库要**用三种语言各写一遍**（Python / JS / Rust）。`统计` 这类纯逻辑
模块，同一套算法维护三份，改一处要改三处 —— M51 的漂移检测就是被这个逼出来的
（当时 Node 少 12 个函数、Rust 少 6 个，**都是静默的**）。
内部架构评估（未公开） 量出的账：宿主层 17365 行里 **11161 行是标准库**，占 64%。

**解法**：纯逻辑模块只写一份（`jishi/stdlib-jishi/统计.jsh`，**就是基石源码**），
**在编译期展开**进主程序：

```
函数 __基石库_统计__():                ← 把整个模块包成**一个函数**
    <模块源码整体缩进一级>
    返回 {"求和": 求和, "平均": 平均, …}    ← 顶层名字打包成字典

# 主程序里的 `导入 统计` 被就地改写成：
统计 = $造模块("统计", __基石库_统计__())
```

于是「库」在字节码层面**只是一次普通的函数调用** —— 三个执行器与两个跨语言宿主
**一个字都不用改**，它们只是在跑同一份字节码。

### 为什么不是「运行时加载库的字节码」（走过的弯路）

第一版就是那样做的：把库模块的字节码塞进 `payload["modules"]`，宿主 `IMPORT`
时取出来执行。**撞上一个死结**：字节码的全局表是**每个 VM 一份**，
`LOAD_GLOBAL` 查的是「当前 VM 的全局表」。在子 VM 里造出来的函数被主 VM 调用时，
会拿**主程序的常量表**去执行 —— 实测直接 `IndexError: consts[ins.a]` 越界。

要绕过去得动一堆东西：给函数加「我属于哪个 VM」、跨 VM 调用协议、payload 新字段、
两宿主的加载逻辑…… 而**编译期展开把这些问题全绕开了** —— 库代码本来就是
「普通的基石函数」，本来就该参与同一份字节码。

> 顺带一提：第一版还撞过一个「代码编译进了产物、但用户代码跑的还是宿主层」的
> bug —— `_rewrite` 只把**子节点**的替换结果写回去了，**顶层节点**的返回值被丢掉，
> 于是 `导入 统计` 原样留着。教训是「树重写要接住每一层的返回值」。

### 三个关键设计决定

1. **包成函数，而不是「执行模块的 main 代码」** —— 模块顶层名字变成那个函数的
   **局部变量**，模块内互相引用走**闭包**（cellvars/freevars），天然与主程序隔离。
   （若直接执行 main：模块的函数定义会落进**主程序的全局表**，既污染命名空间，
   模块内函数之间也分不清彼此。）
2. **外面再套一层 `$造模块(名字, 字典)`** —— 让 `导入 统计` 拿到的仍是**模块对象**：
   `统计.求和(...)` 的语法**一个字都不用改**，`打印(统计)` 也还是 `<模块 统计>`
   （而不是一坨字典）。它是内部内建（`$` 开头，用户写不出来），只在编译器发射的
   代码里出现 —— 与 `$文本`、`检查实参` 同一类。
3. **`导入` 就地替换，位置语义不变** —— 写在函数体内、条件分支里的 `导入` 一样
   展开，且「什么时候导入」不提前也不推后。

### 代价（都实测过，如实记）

- ⚠️ **性能：慢 25–38 倍**。同机同时段交错 A/B（3000 次 `统计.求和(10 个数)`，
  取 6 轮最小值，计时放在程序内部所以不含编译）：

  | 引擎 | 宿主层 | 基石库 | 倍数 |
  |------|--------|--------|------|
  | 树遍历 | 5.61 µs | 212.02 µs | **37.8x** |
  | Python VM | 8.22 µs | 204.27 µs | **24.9x** |
  | C VM | 5.77 µs | 159.67 µs | **27.7x** |

  **比架构评估里说的 7 倍严重得多**（那里只量了 POC 的 `求和`）。原因是库代码内部
  每次调内建（`类型()`、`长度()`…）在 C VM 上都是**一次宿主回调**，而宿主层版
  把这一切做在**一次**调用里 —— 又是「墙是宿主回调次数」那条老规律。
  真实项目里标准库调用只有个位数到几十次，但**只要出现在循环体内，这个倍数就是
  致命的**。所以 M53 的「性能分层」不是可选项：热路径函数必须留在宿主层。
- **模块成员是普通函数值**：`统计.求和` 是外壳函数返回的字典里的一个 `函数`，
  不是「模块的绑定方法」。显示与宿主层一致（`<函数 求和>`），但调试器里分不出
  「模块的」还是「局部的」。
- **报错文件名**：库内报错的行号指向 `.jsh` 的真实行（外壳源码比模块源码多一行
  函数头，所以解析后**整体减 1** 修正 —— 不修正就差一行），但**宿主上显示的文件名
  仍是主程序**（字节码没有 per-code 的文件名）；宿主层版报的是调用点。如实记录。
- **编译产物变大**：用到的库模块整体内联，产物里多出十几个 code 对象。
- **编译多花一点**：`expand` 要扫一遍 AST 找 `导入`（362 行的真实项目实测多约
  **1.8 ms**，占编译时间约 11%；其中 `parse` 本身 14 ms）。
  另外改了 `.jsh` 之后，**主程序要重新编译**才看得到（库自身的编译产物有缓存，
  按 mtime 失效）。

### 边界与纪律

- **不是所有模块都能搬**：依赖宿主原语的搬不了。路线图本来建议先搬 `编码`，
  实际评估后**改成了 `统计`** —— `编码` 的 `文本字节`/`字节文本` 需要 UTF-8 编解码，
  而基石**没有 `序数`/`字符` 内建**，用基石写不出 UTF-8。
  **判据**：只用列表 / 字典 / 文本 / 整数 / 浮点 + 现有内建能表达出来的，才进这层。
- **模块里引别的模块要写成 `导入 X 为 _X`** —— 导出时排除下划线开头的名字，
  否则 `统计.数学` 这种内部依赖会漏到用户面前。
- **`JISHI_NO_JISHILIB=1` 能把整层关掉**（导入回落宿主层）：诊断、对拍、
  性能对比都靠它。
- **宿主层这一阶段不删**：它既是回落，也是「迁移没有改变行为」的对照基准
  （`tests/test_m52_jishilib.py` 逐字节比两者）。

### 顺手修掉的一个真缺陷

`stats` 的 `遍历 5`（不可迭代）在基石库版下走到 C VM 的 `GET_ITER` 回调，
报的是「内部错误（宿主回调）：TypeError: 'int' object is not iterable」——
而 Python VM / 树遍历 / 两个宿主都是清楚的中文。查出来是 `cvm_bind._cb_iter_new`
里**只有第二句 `iter(...)` 在 try 内，`_Iter(o)` 的构造在 try 外**，
于是 Python 的 `TypeError` 直接冒到 `_fail` 兜底。已修。
**纪律**：宿主回调里用户能触发的错误要**显式抛 JishiError**，
别让 Python 原生异常冒到 `_fail` —— 那层的文案对真 bug 是正确信号，但对用户输入
就成了天书。

### M53 的补充（2026-09-26）

**又搬了三个模块**：`容器`（7 函数）、`迭代`（12 函数）、`参数`（5 函数）。
至此基石库层有 **4 个模块 / 34 个函数**。

**三条新经验（都进了 `AGENTS.md` §1 的搬库判据与 §2 的备忘）**：

1. **`__X` 导出为 `X`**：有的导出名本身就是**关键字**，写不成函数名 ——
   `参数.新建` 的 `新建` 就是（`新建 类()` 的 `新建`）。约定 `__X` → 导出 `X`。
   顺带说明「外壳函数返回字典」这个设计**顺手**支持了「内部名 ≠ 导出名」。
2. **别在 `.jsh` 里手写外壳函数**：`jishilib` 会自动把整个文件包一层。
   `.jsh` 就是普通模块顶层 —— 顶层的 `令` 天然是外壳函数的局部变量，
   所以 `_解析器表` 这种模块级状态**一行就够**（而且每次 `导入` 天然一份新状态）。
3. **性能分层的第一例**：`迭代.求和` 直接**转发给内建 `总和`**。
   库代码内部每次调内建在 C VM 上都是一次宿主回调，热路径尤其经不起。
   代价：错误文案变成内建那套（类型仍一致，对拍只比类型）。

**顺手抓到一个真 bug（在编译器，影响四个引擎）**：

「**循环体里 `尝试/捕获`、捕获完继续循环**」会把栈搞脏，最终报
`TypeError: 'RunTypeError' object is not an iterator`。
根因：`_c_try` 生成的字节码里多了一句 `DUP_TOP`，而 `MATCH_EXC` 是
「弹出 cond、**读**栈顶的 err（不弹）、压结果」—— 复制出来的那份 err
**再没人弹**，永久留在栈上。三执行器 + 两宿主**共用这份字节码**，
所以四边一起崩；**只有树遍历（走 Python 的 try/except）是对的 ——
五引擎对拍才抓得住它**。已修，并加了两条回归测试。

**Rust 宿主的两条缺口（M53 撞到，如实记，M54 修）**：

1. **`文本.查找` 没实现**（报「查找」方法调用未实现）。
   ⚠️ 这暴露出 **M51 的漂移检测只比标准库函数名、完全不覆盖对象方法** ——
   `列表`/`字典`/`文本`/`集合`/`文件` 的方法表同样是**五份实现**，该扩检测。
2. **「外壳函数里的库函数接收**主程序传入的函数**」会崩**（`空不能调用`）——
   `容器.分组`、`迭代.计数` 都受影响（顶层函数互传函数是好的）。
   这**直接削弱「一份代码五引擎共用」的成色**：库代码不可能从不收函数参数。
   测试里用 `RUST_GAPS` **显式列出**（带断言 —— 哪天 Rust 修好了会报红提醒更新）。


## D46. 把「五引擎的账」结清：闭包单元的共享语义 + 方法漂移检测（M54）

**背景**：M52 / M53 把四个纯逻辑模块搬进基石库层之后，冒出来的坑**几乎全在
「同一个语义、五个实现」这条线上**。M54 集中还账 —— 一共抓到 **4 个真 bug
+ 1 个机制缺口**，每一个都值得记下来。

### 一、Rust 的**闭包单元不共享**（最重的一个）

**症状**：Rust 宿主上「**嵌套的递归函数**」直接崩 `「空」不能调用`。
顶层递归完全正常 —— 所以怎么写单测都碰不到，是 M53 搬 `迭代`（`组合`/`排列`
要递归）时撞出来的。

**根因**：`Cell` 在 Rust 侧是**值语义的 `struct`**，而 Python / Node 侧是**对象**。

| 指令 | Python / Node | Rust（改前） |
|---|---|---|
| `LOAD_CELL` | 压**单元本身**（引用） | `Val::Cell(Box::new(cell.clone()))` —— 克隆一份 |
| `MAKE_FUNCTION` | 闭包持有同一批单元对象 | `(*b).clone()` —— 又把**值**拷进 `Func` |
| `STORE_DEREF` | `cell.value = v` —— 改**它里面的值** | `cells[i] = Cell{..}` —— **整体替换** |

于是闭包拿到的是**独立快照**：「先创建闭包、后给它赋值」永远失效。

**为什么偏偏嵌套递归会炸**：编译器给嵌套函数的产物恰好是
「先 `LOAD_CELL` 捕获自己的单元 → `MAKE_FUNCTION` → 再 `STORE_DEREF` 填入函数体」
（这是**故意的**，就是为了让递归引用解析到同一个单元）。值语义下，
`LOAD_CELL` 那一刻单元还是空的，填进去的值闭包永远看不见 → 内层函数是 `空`。

**修法**：引入 `pub(crate) type JCell = Rc<RefCell<Cell>>`，`Func.cells` 与
`Frame.cells` 都改成 `Vec<JCell>`，`LOAD_CELL` 压同一个 `Rc`、
`STORE_DEREF` 改**里面的值**。与 `JList` / `JDict` / `JInst` 同一个手法 ——
**「要共享可变状态就得共享对象」这条在宿主的每一处都成立**。

**为什么只有五引擎对拍抓得住**：三个执行器都是对的（Python / Node 的 cell 是对象）。
**跨语言宿主的语义一致性，只能靠真去跑那个宿主来验。**

### 二、未绑定局部 / 单元：三种表现，两种是错的

同一个「没赋过值就读」，M54 之前五个引擎给出**四种**行为：

| 引擎 | 局部（`LOAD_FAST`） | 闭包单元（`LOAD_DEREF`） |
|---|---|---|
| 树遍历 / Python VM | E0301 找不到这个名字 ✅ | E0301 ✅ |
| C VM | E0301 ✅ | **E2000 运行期错误** ❌ 同一个执行器两套写法 |
| Node | 「异常：找不到名字」✅（与 Rust 对齐） | ✅ |
| Rust | **静默给 `空`** ❌❌ | **静默给 `空`** ❌❌ |

- **C VM**：`_cb_raise_unbound_cell` 自己造了个 `RunError`，而 `_cb_raise_unbound_local`
  走的是 `runtime.unbound_local_error`（**单一来源**，`SemanticNameError`）。
  对拍测试恰好**只覆盖了局部、没覆盖单元**。已改成一并走单一来源。
- **Rust**：`Val::None_` 既是「空」又是「没赋过值」的哨兵 —— **分不开**。
  **静默给个错答案比报错难查一百倍**（这是本项目的一条老规矩）。
  修法：`Frame` 加一个 `locals_set: Vec<bool>`，`bind_args` 顺带报出哪些槽
  真的绑上了；`LOAD_FAST` 先查它。**没有动 `Val`**（加一个 `Unset` 变体要碰
  180 多处 match，风险不划算）。

⚠️ **跨语言宿主的边界（如实记）**：Node / Rust 没有 Python 侧那套错误码目录，
报的是「错误（异常）：找不到名字「x」」；Rust 还**不带行列位置**
（它的 `Instr` 根本没解析 `line`/`col`）。所以测试只断言「三执行器同为 E0301、
两宿主首行相同」。要彻底对齐得让宿主也带一套错误码 —— 单独一笔账。

### 三、C VM 的「用后释放」崩溃（崩在 GC 里，最难查）

`run_source_c` 在 `finally` 里销毁 VM（`host.vm = None`），可这次运行
**返回出去的基石函数值**（`CvmFunction`）还活着。等 Python 的 GC 哪天顺手回收它，
`__del__` 就拿着 `None` 去回调 C 库 —— ctypes 把 `None` 当 NULL，
C 侧解引用空指针 → `Windows fatal exception: access violation`。

**最难查的地方是它崩在 GC 里**：报错位置跟出错的那行代码八竿子打不着，
`try/except` 捕不住段错误，而且它**看起来不像测试失败**（M53 的全量回归里
就有一堆这种噪音，被 `tail` 截掉了）。

**定位手法（值得复用）**：`git stash -u` 把工作区回退到上一个里程碑状态复跑 ——
一样崩 ⇒ **既有问题，不是本次引入**。这一步在「一堆红里分清新旧」时非常值。
修法：`__del__` 先看 `host.vm` 还在不在；不在就什么都不做
（`jsvm_destroy` 已经把计数一起释放了）。

### 四、方法漂移检测：M51 那份检测只覆盖了「标准库函数名」

M51 的漂移检测是**宿主自己 `--dump-stdlib` 报家底**，测试拿 Python 侧的
`--lang-spec` 去比 —— 这个模式很好用，**但它只比标准库的模块与函数名**。
`列表` / `字典` / `文本` / `集合` / `文件` / `小数` 的**方法表同样是五份实现**，
一条都没测。代价是两笔漏网，而且**都是偶然撞见的**：

- **Rust 缺 `文本.查找`**（M53 靠五引擎对拍撞见）；
- **Node 缺 `文件.位置 / 定位 / 刷新`**（M54 建检测时才发现：Python 侧 9 个，Node 只有 6 个）。

**做法**：把同一个模式扩到方法上。

- **Python 侧**：`--lang-spec` 的 `methods` 节从 3 类补到 **6 类** ——
  它本来就是「对象方法」在 Python 侧的单一来源，M54 之前只放了 3 类。
- **两个宿主**：各加 `--dump-methods`。
  - Node 的 `dumpMethods()` **直接读 `methodTable` 用的那几张表**，
    不是另抄清单（宿主自报家底必须报**实际能力**，否则检测就成了摆设）。
  - Rust 的分派是一个大 `match`（枚举不出名字），所以**把 6 张方法表都提成
    模块级 `const *_METHOD_NAMES`**，**分派用它挡名字、dump 报同一张** ——
    同源，所以不会各报各的。顺带统一了「不认识的方法名」的报错时机
    （以前只有 集合/文件/小数 在**取属性**时报，列表/字典/文本 要等到**调用**时）。
- **测试**：`tests/test_m51_consistency.py` 复用 M51 那套 `_missing` / `_extra`
  （所以「检测本身真的能报红」那条保险**自动覆盖到方法**），
  `METHOD_KNOWN_GAPS` 与 `KNOWN_GAPS` 同样是**带断言的显式账**。
  另加 `test_M54_补的方法真的能跑` —— **表里有名字 ≠ 真的能用**，
  把 M54 动过的方法在五引擎上真跑一遍、逐字节比。

**顺带补齐**：Rust `文本.查找`（注意 `str::find` 给**字节**偏移，
要数前缀字符数才对得上 `"你好吗".查找("吗") == 2`）、
Node `文件.刷新`（`fs.writeSync` 本来就无缓冲，空操作）/ `位置` / `定位`。

**Node 的文件对象顺带重写**：原来是 `_buf` + `_eof` 两个字段硬凑的，
**没有位置概念** —— 这也是它当初压根没法实现 `位置`/`定位` 的原因。
改成「懒加载全文 + 字符位置」的模型，口径与 Python 侧一致
（`读(n)` 读 n 个**字符**、`位置` 给已消耗的**字符数**）。

### 五、还记着一笔没结的账（如实记，不塞进 M54）

**`文件.位置` 在非 ASCII 上五个引擎给三个不同的值**：

- Python：`tell()` 的**字节式 cookie**，Windows 上还叠加了 `\n` → `\r\n` 的翻译
  （`"甲\n乙\n"` → 10）；Linux 上是 8；
- Node：**字符数**（4）—— 它与 Python 的差异还有一半来自**换行符翻译**
  （Python 的 `_b_open` 用默认 `newline=None`，Windows 上写出去的是 `\r\n`）；
- Rust：**字节偏移**（8）。

ASCII 下三方一致（`test_M54_补的方法真的能跑` 钉的就是这个）。
要彻底统一得：① 把 `位置`/`定位` 的口径明确定成「**字符位置**」；
② 改 Python 侧的 `tell`/`seek` 用法；③ 决定换行符要不要翻译（这会影响
`读所有行` 的字节口径）。**每一小步都会动到既有行为**，所以单独立一笔，
不塞进 M54（见 内部路线图（未公开） §九）。


## D47. 「一个字符」到底是什么：`序数`/`字符` + 文本按码点 + 内建的账（M55）

M55 回语言本体。主线看着是「加两个内建」，真正要定下来的是**一件事**：
**「一个字符」在五个引擎里必须是同一个东西** —— 因为 `序数`/`字符` 就是
「码点 ↔ 字符」，它们要成立，先得这件事有唯一答案。

### 一、口径：一个字符 = **一个 Unicode 码点**

`序数("中")` → 20013、`序数("😀")` → 128512；`字符(20013)` → `"中"`。
两者互为反函数。

**为什么必须先定这个**：三个引擎对文本的**底层表示**完全不同 ——
Python 是码点序列、Rust 的 `String` 是 UTF-8、**JS 的字符串是 UTF-16**。
不定口径，`长度` / 下标 / `查找` / 反转 就会各给各的答案。

⚠️ 而 M47 给 C VM 定文本时**已经**写死过这条（「文本是码点序列」，
`compare_fast` 直接 `memcmp` 就与 Python 的按码点比较逐位一致）——
M55 只是把 **Node 侧补齐到这个口径**。

### 二、🔴 Node 侧「文本 = UTF-16 码元」的真 bug

M55 实测（同一段源码、同一份字节码）：

| 表达式 | Python / Rust | Node（修前） |
|---|---|---|
| `长度("😀")` | `1` | **`2`** |
| `"😀"[0]` | `😀` | **`�`**（半个代理项） |
| `"a😀b".查找("b")` | `2` | **`3`** |
| `反转("a😀b")` | `b😀a` | 乱码（把 😀 拆成两半再反） |

有意思的是 **Node 自己内部就不一致**：`切片` 与 `遍历` **早就用了按码点的
`[...s]` / `for…of`**，只有 `长度` / 单下标 / `查找` / `反转` 四处漏着。
所以修起来是**四处小改**（`cpLen` / `cpAt` / `cpIndexOf` 三个小助手），
不是重写文本层。

**判据（值得复用）**：凡是「按**位置**处理文本」的操作，都要按码点；
按**子串**工作的（`拆分`/`替换`/`包含`/`大写`）跟位置无关，**别改** ——
改了既对不上 Python，也不会更好。

### 三、内建的账：第三个「宿主自报家底」的口子

M51 建了标准库的漂移检测（`--dump-stdlib`），M54 建了对象方法的
（`--dump-methods`），但**内建函数一条都没测**。而「加一个内建要同时动
Python / Node / Rust 三处」，漏一处的症状正是「在某个引擎上没定义过这个名字」。
M55 补上 `--dump-builtins`（过滤规则与 Python 侧 `is_internal_builtin` 对齐：
去 `$` 开头、去「内部用」、只留真正的内建函数）。

**建起来的当场就抓到两笔**（Node 与 Rust 上**同时**缺）：

- `断言(条件, 消息?)` —— M23.1 就有的内建，宿主一直没跟上；
- `是实例(值, 类)` —— 同上。
  顺带还带出「`断言错误` 这个**捕获类型**宿主也不存在」——
  于是 `捕获 断言错误` 在宿主上直接报「找不到名字」。

⚠️ **`超` 不参与比对**：它是**编译器形式**而不是可当值的内建函数
（只在类的方法里合法，别处一写就被编译器拒掉），`new_builtins()` 里有它
只是为了让名字能解析。测试里用 `BUILTIN_EXEMPT` 显式排除并写明理由。

**Rust 的 `是实例` 还牵出一个结构问题**：那边建类时是「**把基类的方法表
展开合并**」，基类指针**用完就丢** —— 没法沿继承链判断。`超()` 之所以一直
没事，是因为它走合并后的方法表，压根不需要链。
修法：给 `Class` 加 **祖先链的序号**（`base_ids`，建类时算一次），
用 `id` 做身份比较 —— 与 Python 侧 `_instance_of` 同语义。

### 四、顺手还的两笔「报错」账（都属于参数个数）

内建**参数个数不对**时，五个引擎给出**四种**行为：

| | 现状（M55 前） | M55 之后 |
|---|---|---|
| 三执行器 | 漏 Python 原生**英文**：`_b_len() missing 1 required positional argument: 'v'` | 「「长度」需要 1 个参数，但传了 0 个」（E2002 类型错误） |
| Rust | **12 个内建直接 panic**（`thread 'main' panicked`） | 补齐 30/30，文案与 Python 侧逐字一致 |
| Node | 文案不准（「「空」没有长度」），但不崩 | **仍是 20 个**（→ M56，见下） |

三条要点：

1. **Python 侧的收口点在 `call_value`，不只在 `__call__`**：
   `call_value` 里有一句 `fn = fn.fn`，**把 `_Builtin` 拆成裸函数**、
   绕过 `__call__` —— 只改 `__call__` 会「改了却毫无效果」（实测踩过）。
   所以抽了个 `check_arity`，两个入口共用。
2. **`_fn_arity` 用 `inspect.signature` 自动推**：不逐个内建声明参数个数
   （30 个内建、三个引擎，手写必漂）。`*args` 记为「不限」。
3. **`need_builtin_args` 与 `need_args` 在宿主侧要分开**（Node 早就是这样）：
   内建说「「长度」」、方法说「方法「追加」」——称呼不同，文案就该不同。
   Rust 原先只有一个 `need_args`，所以内建的报错里会冒出一个「方法」前缀。

### 五、M55 没做完、**明写进 M56** 的三条

1. **Node 的 20 个内建仍缺参数个数检查**。不是漏改，是**要改签名**：
   Node 的内建是 `(v) => …` 形式，而 `needBuiltinArgs` 需要 args 数组，
   得先改成 `(...args) => …`。清单已备好（见 内部路线图（未公开） §9.4.1）。
2. **Rust 的 `捕获 为 e` 拿到的只是异常**类型**，消息丢了**
   （`Val::ExcType(t)` 只带类型名）—— `打印(e)` 给「断言错误」。
   属**宿主异常对象模型**的缺口，与「Node 打完是 `Error: 故意失败`」同族。
   （M55 顺手把 Node 的 `JishiError.toString` 补成「错误（类型）：消息」，
   至少把那个**英文 `Error:`** 从用户眼前去掉了。）
3. **`文件.位置` / 定位 的口径**（M54 记的账）+ 换行符翻译（D46 末尾）。

> **M55 的取舍说明**：本来可以顺手把 Node 的 20 个也改掉，但那是**
> 20 处签名改写 + 逐条对拍**，属于「报错质量」这件事本身。M54/M55 一路挖出来
> 的报错类欠账已经有 **7 条**（见 §9.4.1），**攒成 M56 一次收口**比零散地
> 顺手改更可控 —— 这也符合「一里程碑只摊一件大事」。

## D48. 内建体检：从「比名字」到「真跑」（M56 第一批）

### 一、为什么会有这个工具

M55 建了内建的**名称**漂移检测（`--dump-builtins`），建起来当场抓到
`断言` / `是实例` 在宿主上根本没有。但那套检测**只比名字** ——
而 M53 已经吃过一次亏：「名字在表里 ≠ 真的能调用」（Rust 缺 `文本.查找`
就是靠五引擎对拍才发现的，名称检测一路绿灯）。

更要紧的是 M55 自己留了个**错误豁免**：

```python
BUILTIN_EXEMPT = frozenset({"超"})   # 注释：「超 是编译器形式，宿主不需要有它」
```

**这个判断是错的。** 编译器把 `超().方法(x)` 脱糖成 `超(自身, "定义类名")`，
字节码里就是 `LOAD_GLOBAL 超` + `LOAD_FAST 自身` + `LOAD_CONST "类名"` + `CALL 2`
—— 它是个**货真价实的运行期内建**。后果：

- 三个 Python 执行器全对（`超()` 正常调基类）；
- **Node 与 Rust 一直报「找不到名字「超」」**；
- 而**五引擎对拍覆盖不到它** —— 因为它被那个豁免排除在比对之外了。

`tests/test_m23_lang.py` 从 M23 起就在测 `超()`，但**只测 Python 侧**。

> **一条被豁免的项，就是一个不会被任何测试碰到的角落。**

### 二、工具做了什么（`tools/probe_builtins.py`）

三节，都是**真跑**，不看源码：

1. **名字清单**：三侧同宽（沿用 `--dump-builtins`，与分派同源）；
2. **正常用法**：给**每个内建**一条最小可跑程序，五个引擎跑，**输出逐字节一致**；
3. **参数个数错**：`名字()` —— 三执行器同类同码、两宿主首行一致，
   并含 **Rust panic 扫描**（M55 之前它 12 个内建会直接 `thread 'main' panicked`
   —— 那不是报错，是宿主崩溃）。

**写这个工具时自己踩的坑（记下来）**：`输入()` 在进程内跑会**真的去读 stdin**。
第一版没喂输入，工具什么输出都没打出来就被 SIGTERM 了。
`redirect_stdout` 管不到 stdin，得自己换 `sys.stdin`；再顺手把 stdout 设成
**行缓冲**，这样中途中断至少能看到跑到哪了。

### 三、体检结论（2026-09-27）

| 检查 | 结果 |
|---|---|
| 名字清单（三侧同宽） | ✅ 各 30 个 |
| 正常用法（每个内建 × 五引擎） | ✅ **30/30 逐字节一致**（含 `打印(超())` 给 `<超 乙>`）|
| 参数个数错 · 三执行器 | ✅ 30/30 同类同码（`E2002 类型错误`）|
| 参数个数错 · Rust 不 panic | ✅ 全部 |
| 参数个数错 · **两宿主彼此一致** | ⚠️ **16 个不一致** —— 全是 Node 那边的问题 |

**16 条不一致分两类**（完整对照见 内部路线图（未公开） §9.4.1）：

- **11 条「文案不同」**：Node 靠各自的兜底报错（「「空」没有长度」「「空」不能求和」…），
  Rust 统一是「「长度」需要 1 个参数，但传了 0 个」。
- **3 条「静默成功」——性质最重**：

  | 写法 | Python / Rust | Node（M56 前） |
  |---|---|---|
  | `文本()` | 报「需要 1 个参数」 | **返回「空」** |
  | `类型()` | 报「需要 1 个参数」 | **返回「空」** |
  | `退出上下文()` | 报「需要 1 个参数」 | **返回「空」** |

  **不报错的错答案，比报错文案不准难查得多** —— 这是「宿主对参数个数太宽松」
  的老毛病（M51 修过 kwargs 版：以前宿主对命名参数「收下、忘掉」）。

**一条判据**（写用例时定下的）：`位与`/`位或`/`位异或`/`左移`/`右移` 都是
**严格二元**（`位与(a, b)`），不是变参 —— 多给一个参数是一致的参数错，
但**跑不通**，所以「正常用法」的用例只给两个。

**两条「没法构造参数错」的**（记在工具的 `SKIP_ARITY` 里）：`超`（脱糖成固定
2 实参）、`打印`/`输入`/`集合`（0 个参数本来就合法）。

### 四、`超` 的修法

**Node**：有个天然优势 —— `JishiClass` **保留了 `base`**（M55 给 `是实例`
用它做继承链判断时留下的）。所以照着 Python 侧补三样就够：
`JishiSuper` 类、`getAttr` 的 `Super` 分支、`newBuiltins` 里的 `超`。

**Rust**：那边建类时是「**把基类的方法表展开合并**」，合并完
**把基类指针丢了**（只有 `base_ids` 一串序号，没法反查回类对象）。
所以必须给 `Class` 补 `base: Option<Rc<Class>>`：

```rust
// M56：`超()` 必须沿链找「定义类」再取它的基类，光有序号不够
base: Option<Rc<Class>>,
```

连带的两个细节：

1. `BUILD_CLASS` 里原本是 `for (k, v) in base.methods`（**移动**基类）——
   要保留 `base` 就不能再移动，改成借用迭代 + `clone`；
2. `Val` 加 `Super(Rc<SuperVal>)` 变体，`display` 的穷尽 match 要补分支
   （`<超 乙>`，与 Python 侧 `JishiSuper.__repr__` 一致）。

修完五引擎连 `打印(超())` 都是 `<超 乙>` 逐字一致。

### 五、教训

1. **豁免必须能被复核，否则它就是藏 bug 的地方。**
   现在 `BUILTIN_EXEMPT` 是空的，但**常量保留着** —— 以后真要豁免谁，
   必须在这里写清理由。理由写不出来的，多半就是 bug。
2. **「只比名字」的检测只配当第一道网。** 名字同宽 ≠ 能用；
   要真跑一遍，而且要用**真实用法**（多级继承 + `超().初始化(...)` 链，
   而不是 `超()` 单独一句）。
3. **跨语言宿主老是在「保留结构」这件事上偷工**：Rust 丢基类指针（本 D）、
   丢 `Class` 的字段语义（D46 的 `JCell`）、丢错误消息（D48 里记的待办，
   D49 已补）—— 同一个模式：**「够用就先不存」**，等到某个特性真的要用时
   才发现拿不回来。

## D49. M56 第二批：JS 的签名陷阱、宿主异常对象、错误码索引

### 一、`(v) => …` 是一个会「静默成功」的签名（Node）

体检报的那 16 条里，Node 侧最重的是**3 条「静默成功」**：

| 写法 | Python / Rust | Node（改前） |
|---|---|---|
| `文本()` | 报「需要 1 个参数」 | **返回「空」** |
| `类型()` | 报「需要 1 个参数」 | **返回「空」** |
| `退出上下文()` | 报「需要 1 个参数」 | **返回「空」** |

**根因不是忘了写检查，而是签名写成了 `(v) => …`**：

```js
'文本': new Builtin('文本', (v) => pyStr(v)),   // 0 个实参时 v === undefined
```

JS **不会**因为少传实参而报错 —— 形参就是 `undefined`，函数体照跑。
要拦住必须先把签名改成 `(...args) =>`，再在**拿到实参之后**做检查：

```js
'文本': new Builtin('文本', (...args) => {
  needBuiltinArgs('文本', args, 1, 1);
  return pyStr(args[0]);
}),
```

19 处（16 个公开 + `$文本`/`$造模块`/`检查实参`）都改了；另加
`needBuiltinArgsAtLeast` —— `最大`/`最小` 是**变参**（0 个不合法、但个数不限），
文案与 Python 侧 `_b_max`、Rust 侧 `need_at_least_args` 逐字一致（「至少要 N 个参数」）。

**顺带发现 Rust 侧还有 4 处自己抄的文案**（`精确` 少「，但传了 N 个」、
`范围` 没书名号、`进入上下文`/`退出上下文` 多了个空格）—— 说明「统一走一个检查
函数」这件事**没做彻底**，改完现在 **16/16 逐字一致**。

> **教训**：**「不报错的错答案」比「报错文案不准」严重一个量级**。
> 后者用户至少知道出事了；前者一路算下去，等发现时早不知道错在哪。
> 体检（`tools/probe_builtins.py`）逼着每个内建真跑一遍，才把这类问题翻出来 ——
> 只比名字的检测对它完全无感。

**而且这个坑有两半 —— 体检当场只测了「少给」那一半。**

补完「少给」之后顺手验「多给」，又抓到 `输入`：

| 写法 | Python | Node（改前） |
|---|---|---|
| `输入(1, 2, 3, 4, 5)` | 报「需要 0 到 1 个参数，但传了 5 个」 | **静默忽略多余的**（拿第一个当提示语） |

原因是默认参数把多给的实参吃掉了（`(prompt = '')`）。与「少给」是**同一类**问题，
只是方向相反。修完把「多给」也做成体检的**第四节**（`SKIP_TOO_MANY` 只排除
`打印`/`最大`/`最小` 这三个本来就没有个数上限的），这样以后不会再漏。

### 二、Rust 的异常对象模型：同一个「值语义 vs 对象语义」又栽一次

捕获处原来是：

```rust
// 把异常作为特殊值压栈（这里简化为放一个字符串标记 + 异常类型）
self.stack.push(Val::ExcType(e.type_name.clone()));
```

源码注释自己写着「**简化为**」—— 代价是：

- `打印(e)` 只给「类型错误」，**消息丢了**；
- `e.类型` / `e.消息` **直接报「没有属性」**（Python 与 Node 都能读）；
- `类型(e)` 给「异常类型」，而 Python / Node 给「异常」。

修法是新增 `Val::Exc(Rc<ExcValue>)`（`type_name` + `message`）：捕获时压**带内容
的对象**，并补上 `display`、`类型`/`消息` 属性、`exception_matches`、以及
**重抛时保住消息**（`抛出 e` 不再变成「错误（类型错误）：」）。

这与 D46 的 `JCell`、D48 的基类指针是**同一个模式**：宿主实现里凡是要「以后还要
用到」的东西，偷工省掉之后都得在某个时刻补回来。**这已经是第三次了，
下次写宿主代码时先问一句：这个字段三个月后会不会有人要？**

⚠️ **顺带查清一条更要紧的事**：**Rust 的 `JishiError` 只有 `type_name` 和
`message` 两个字段** —— 这就是「Rust 的全部报错都没有行列位置」的根因。
补它要动结构体本身与所有 `err(...)` 调用点，属第 5 条（宿主错误信息模型）的事。

### 三、错误码索引：`jishi 错误 <码>`

**要解决的问题**：报错里已经给了 `E0301`，但「E0301 是什么、我该怎么办」
以前只能翻源码 —— 对用户是门槛，**对模型是「猜一个修法」**。

设计上守住了项目的两条老规矩：

1. **单一来源**：码与标题从 `errors.py` 的 `JishiError` 子类**自动抽**，
   `errcodes.py` **只写说明**（什么意思 / 常见成因 / 怎么改），不重复码。
   两条约束都用测试钉住：`errors.py` 有的码必须有说明；说明表里不许有
   `errors.py` 没有的码 —— 「加了错误类型忘了写说明」和「删了忘了删」都报红。
2. **CLI 不是 markdown 渲染器**：说明文案里不许写 `**加粗**`（会字面显示出来），
   用「」代替 —— 这条也有测试钉着。

顺手做的两件事：码的写法容错（`301` / `E301` / `e0301` 都能查到，因为用户
从报错里抄的时候常常少抄字母或前导零）；`--ai-card` 末尾加一节
「报错怎么读、怎么查」（模型知道有 `jishi 错误 <码>` 这个口子，
就能自己查而不是猜）。

### 四、一条「账」本身也会过时

路线图里原写第 6 条：「**最像的候选名推荐** —— `找不到名字「prnit」` 现在不给候选，
`runtime.py` 已有 `最相似`（LSP 在用），接进报错即可」。

实测发现**描述是错的**：

- Python 侧**本来就有候选** —— 拼错内建时给「提示：你是不是想写「长度」？」
  （`lookup_name` 里的 `difflib.get_close_matches`）；
- `prnit` 之所以没候选，是因为它跟名字池里的「数据」**根本不相似** —— 这是对的，
  给候选反而误导；
- 真正缺的是**两个宿主完全没有 `hint` 机制**（`JishiError` 没有 hint 字段），
  所以要跟第 5 条一起做。

> **教训**：**待办清单也是会过时的**。写下的「现状」如果没有当场实测，就该
> 标成「未核实」。这次是动手前先跑了一遍才发现的 —— 否则会照着一句错描述
> 去实现一个本来就不需要做的东西。

## D50. M56 第三批：文件的三处口径、Rust 终于有行列了

### 一、「ASCII 上一致」不等于「口径一致」

第 3、4 条都是**同一类**问题：同一段程序，五个引擎给不同的东西。

| 项 | Python | Node | Rust |
|---|---|---|---|
| 非 ASCII 上的 `文件.位置` | 6（`tell()` 的字节 cookie） | 4（字符数） | 6（字节偏移） |
| `读(n)` 的 n | 字符 | 字符 | **字节** |
| 写出的换行 | `\r\n`（Windows） | `\n` | `\n` |

**关键是：口径其实早就定好了** —— `tests/test_m26_lang.py::test_file_position_and_seek`
在 M26 就写死「读 2 个字符 → 位置 = 2」，Node 侧 M54 也是照它实现的
（源码注释里就写着「口径与 Python 侧对齐」）。

**但那两条测试只在 ASCII 上跑**：`"abcdef"` 里一个字节恰好就是一个字符，
于是 `tell()` 的字节 cookie 与「字符数」看不出区别 —— **口径漂了也全绿**。

> **教训**：**锁口径的测试要用「会让口径分叉的数据」**。
> 中文、emoji、CRLF 就是这类数据；只用 ASCII 测「位置」，等于没测。

### 二、顺手抓到的比原账更重：Rust 的 `读(n)` 按字节

`read_n` 的注释就写着「读几个字节」。于是 `读(4)` 在「abc中文」上取到
`abc` + 汉字的前 1 个字节，解码时把汉字切成两半，报：

> 错误（文件错误）：**文件内容不是 UTF-8 文本，读不出来**

**而那个文件明明是合法的 UTF-8。** 用户看到这句会去查文件编码、查保存方式 ——
**方向全错**。

> **教训**：**误导性的报错比不报错更耗时**。报错说的是「文件不是 UTF-8」，
> 而真正的问题是「我们按字节切了字符」—— **报错把锅甩给了文件**。

### 三、Rust 的报错：一处填、全场受益

「Rust 的所有报错都没有行列」听着像要动几百处 `err(...)`。实际查下来，
根因是**两个很小的事实**：

1. `JishiError` 只有 `type_name` / `message` 两个字段（补两个 `Option<i64>` 即可）；
2. **反序列化时把 `line`/`col` 丢掉了** —— 字节码里**一直带着**
   （每条指令 6 个数字：`op,a,b,c,line,col`），Rust 的 `Instr` 只解了前 4 个。

而「补位置」这件事也只需要**一处**：`execute` 在错误冒泡时统一填
（`fill_error_loc`）—— 因为**所有**错误（内建抛的、VM 抛的、`抛出` 的）
最终都要从这里经过。再配合主循环每步把 `ip` 写回帧，就能查到「正跑到哪一行」。

> **通用手法**：**找「所有路径都会经过的那个点」**，在那里做统一处理，
> 而不是去每个产生错误的地方各写一遍。这与 D46 的「同一件事的报错要走
> 单一来源」是同一个道理，只是这次用在「补信息」上。

### 四、错误码的闭环

给宿主加错误码，价值不在「多一行字」，而在**接上了 `jishi 错误 <码>`**：

```
错误 E2001：不能除以零
  ← 第 3 行第 6 列
```

用户（和模型）拿到这个码，可以直接 `jishi 错误 E2001` 查「什么意思 / 常见成因 /
怎么改」—— 两条本来独立的账（第 5 条的「宿主码」、第 7 条的「错误码索引」）
在这里合上了。

⚠️ **但只给能确定的码**：宿主的「异常」是个**笼统**的类型（找不到名字、属性不存在、
参数个数不对…都归它），标成 E0301 会**骗人**。所以那张表只有 7 条
（除零 / 类型 / 索引 / 键 / 值 / 文件 / 断言），其余**宁可不给**（有测试钉住）。

> **教训**：**宁可少给，不要给错**。「有一个看起来对的码」比「没有码」更糟 ——
> 用户会照着那个错码去查，查到的是不相干的解释。

## D51. M56 第四批：把 difflib 复刻进两个宿主

### 一、为什么不用「编辑距离凑合一下」

宿主缺「你是不是想写」的候选名，最省事的做法是各写一个 Levenshtein。
但那样三侧的候选**可能不一样**：

- Python 侧：`difflib` 的 Ratcliff-Obershelp（按**最长公共块**打分）
- 宿主：Levenshtein（按**编辑次数**打分）

两者在边界情形下排序不同 —— 于是同一个拼写错误，Python 说「想写「长度」」、
Rust 说「想写「整数」」。**用户会以为另一侧才是对的，或者以为两边都坏了。**

> **教训**：**「三侧一致」是这类功能的硬指标，不是加分项。**
> 一个会给出**不同答案**的辅助功能，比「没有这个功能」更伤害信任。

所以选择了复刻。代价是要把算法抄准 —— 而这引出了下面两条。

### 二、两个「抄错就分叉」的点

**① DP 版 vs 暴力版：同样是「最长公共子串」，结果可能不同**

difflib 的 `find_longest_match` 用 DP（`j2len`），并且是：

```python
if k > bestsize:            # 严格大于 = 并列时保留**先遇到**的
```

「先遇到」的判据是 `i` 与 `j` 的**遍历顺序**。自己写一个「暴力枚举所有子串取最长」
看着等价，但并列时会选中**另一个块** —— 而 `get_matching_blocks` 是**递归**找的，
块不一样，M 就不一样，ratio 就分叉。

**② 元组顺序：是 `(分数, 名字)` 而不是 `(名字, 分数)`**

CPython 3.13 的实现是：

```python
result.append((s.ratio(), x))
result = _nlargest(n, result)      # == sorted(..., reverse=True)[:n]
```

分数在前，所以**同分时按名字比较** → 名字**降序**。
而「保持名字池原序」是**另一种**排序。实测：3000 组随机对拍里 **103 组**顺序不同。

> **教训**：「我读懂了这段代码」和「我抄对了这段代码」是两件事。
> **用对拍把两者分开** —— 见下一条。

### 三、方法论：先在能对拍的地方把算法钉死

复刻 difflib 的正确顺序**不是**「写完 Node、再写 Rust、然后一起调」：

1. **先在 Python 里写出复刻版**（同一门语言，能直接与 `difflib` 逐项对拍）；
2. 跑 **4000 组随机 ratio + 3000 组随机候选**，直到全一致；
3. 再把这份**已经验证过**的算法翻译成 JS 与 Rust（翻译只可能引入语法错误，
   不会引入算法分歧）；
4. 最后用五引擎对拍钉住三侧输出一致。

好处：**调试成本被压到最低**。第 2 步一旦不一致，立刻知道是算法抄错了 ——
而不是「到底是 Node 的某个边界有问题，还是 Rust 的浮点有问题」。

这套方法能推广到**任何「三侧要一致」的复刻**：先在**最容易对拍的那一侧**
把算法写成可对拍的形式，对拍通过再翻译。

### 四、顺带踩到的：JS 的字符串比较不是按码点

候选名要排序，就得比较字符串。三种语言的默认行为**各不相同**：

| | 比较依据 | 与 Python 的码点序 |
|---|---|---|
| Python | 码点 | —（基准） |
| JS | UTF-16 **码元** | ✗ 补充平面字符会排错位 |
| Rust | UTF-8 **字节** | ✅ 恰好一致（UTF-8 保序） |

所以 Node 侧写了 `cpCompare`（按 `Array.from` 后的码点比），Rust 侧直接用 `cmp`。

> 这是 M55「一个字符 = 一个码点」在**排序**上的又一次落地。
> 候选名几乎不会是 emoji，但既然定了规矩，就不留「只在特殊字符上分叉」的坑。

## D52. M49：自建分发源的落地，与「521 不是源站坏了」

**背景**：ICP 备案完成（`基石.cn`，苏ICP备2026073372号），M49「自主分发」可以落地。
目标不是「再挂个官网」，而是让 `jishi 安装` **在大陆真的能装上** ——
原先默认源是 `raw.githubusercontent.com`，大陆访问**时通时不通**。

### 一、两份索引，各自自洽

服务器上那份索引（部署时生成）下载地址指向自己；仓库里那份（推 GitHub）仍指 GitHub。

| 索引来源 | 索引里的下载地址 | 效果 |
|---|---|---|
| 自建源（`基石.cn`） | `基石.cn/packages/下载/…` | 索引 + 包**都在境内**，实测 0.11s |
| GitHub（兜底） | `raw.githubusercontent.com/…` | 慢，但**能用** |

**为什么不干脆只维护一份「下载地址指自建源」的索引推给 GitHub**：
那样自建源一挂，**谁都装不了** —— 索引拿得到、包拿不到。
「慢」可以忍，「装不上」不行。两份索引**各自自洽**，自建源故障时是**整条链路**
一起退到 GitHub，不会半路断掉。

> 📌 这也是「多源回退」的正确粒度：**回退要按「整条链」退，不是只退第一跳。**

### 二、🔴 「HTTPS 打不开」的定性过程（这一段最值钱）

现象：`http://基石.cn/` → **200**，`https://基石.cn/` → **521 Connection Reset by Origin Server**。

按直觉猜了三轮，全错：证书不对？CDN 缓存了 521？回源地址配错了？
（TLS 握手其实是成功的 —— TLSv1.3 + 正确的证书，说明证书没问题。）

**定性靠的是源站日志**：发一个 HTTPS 请求、再发一个 HTTP 请求，然后看源站 `access.log`：

| 请求 | 源站日志 | 结果 |
|---|---|---|
| HTTP | ✅ **有记录**（CDN 回源节点的 IP） | 200 |
| HTTPS | ❌ **完全没有记录** | 521 |

HTTPS 请求**根本没到源站 80**。唯一的解释是：**CDN 对 HTTPS 请求走的是另一条回源
路径**（HTTPS 回源到 443），而源站没有任何东西在 443 上监听。

**修法**：源站也开 443（Let's Encrypt 证书 + `tools/nginx-jishi-tls.conf`）。
这样**两种回源协议都能应答**，不用去赌 CDN 那侧是怎么配的
（另一条路是在 CDN 控制台把回源协议显式改成 HTTP —— 但那是「依赖对方的某项配置」，
不如让源站两种都能接）。

> **方法论：`access.log` 里有没有那条请求，比猜配置快十倍。**
> 它一刀切开三种可能 ——「源站坏了 / 链路坏了 / CDN 坏了」。
> 而且它顺便排除了一个陷阱：**CDN 缓存会让「看起来正常」变得不可信**
> （HTTP 那 200 有一半是缓存给的，不代表回源通）。
> 所以做这种判断要**用带随机参数的 URL 破缓存**，或看源站日志本身。

### 三、⚠️ 大陆服务器拉 GitHub 的真实数据

用户问「中国的服务器拉 GitHub 是不是就会超时」——**是的**，实测：

| 方式 | 结果 |
|---|---|
| `git ls-remote` | ✅ 能通（只读元信息） |
| `git fetch --depth 1`（约 3MB） | ❌ **300 秒超时** |
| tarball（`codeload.github.com`） | ⚠️ 一次成功，另一次**中途 `IncompleteRead`** |

⇒ 部署改为**本地构建 + `scp`**（`tools/deploy_push.sh`）；服务器自己拉只当备用。
**而这组数据本身就是「必须自建分发源」的证据**：凡是「部署/安装依赖 GitHub」的环节，
在大陆都是不可靠的。

### 四、几个具体的实现选择

**① 超时故意调短（6 秒）**。原先 15 秒 × 2 个源 = 最坏干等半分钟。
多源回退的前提是「快速失败」—— 不然第一个源慢慢超时，用户早就以为程序卡死了。

**② 单个源不通不算「环境异常」**。`jishi 医生` 里备用源不通只报 `[警告]`，
只有**全都不通**才置 `ok = False`。否则用户会去修一个本来不需要修的东西
（备用源在大陆常常不通，但主源好好的）。

**③ 提示要给「做法」，不是给「原因」**。全都读不到时列清试过哪些地址和失败原因，
然后给三条能照做的路：`--index <别的源>` / `--local-zip 包.zip` / `--local-dir 目录`。

**④ 抓到一个既存 bug**：`encode_url` 会把 Windows 盘符的冒号编成 `%3A`
（`file:///C:/…` → `file:///C%3A/…`），之后 urllib 就走不通了。
而 `file://` 的 base_url 是**注释里明说的预期用法**（本地镜像）。
—— 是「用本地文件当索引源」写测试时踩出来的：**测试里换个真实的数据形态，
就能把只在这条路上才犯的错翻出来**（同 M56 的教训：只在 ASCII 上测「位置」等于没测）。

**⑤ 站点规则单独成片段**。80 与 443 两个 server 块 include **同一份**
`nginx-jishi-locations.conf`：复制两份迟早会漂，而「只有一个端口有问题」的 bug
最难查（在 HTTP 上试半天，问题只在 HTTPS 上）。

### 五、顺手修的一处「提示误导」

`导入 X` 失败时说「试试：导入 随机 / 导入 数学」—— 但如果本地**装着同名包**，
用户真正想写的是 `导入 X 从 本地包`（本地包与标准库是**两种语法**）。
这时指向几个不相干的标准库模块是**反向指导**。现在装了同名包就直接给正确写法。

> 📌 教训与 M56 的「候选名推荐」同源：**报错的价值在于「下一步该做什么」**。
> 「找不到 X」后面接什么，取决于**用户本来想做什么** —— 能判出来就别给通用建议。
