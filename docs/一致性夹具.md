# 一致性夹具（R0）—— R 线的验收闸门

> **一句话**：把 Python 前端**现在的行为**逐字冻结成结构化基线（tokens / AST /
> 字节码 / 诊断），Rust 版每写一步就拿它比 —— **一致才叫这一步做完了**。
>
> 工具：`tools/conformance.py` · 基线：`tests/conformance/` · 守门测试：
> `tests/test_m57_conformance.py` · 验收标准见 `docs/架构迁移路径.md`

## 一、为什么先做这个

R 线要把前端从 Python 换成 Rust。这种改写最容易出的错**不是「崩了」**，而是
「**悄悄变了**」：

- 某个 token 的列号差 1（中文与 emoji 上才现形 —— M56 那次漂了很久）；
- 某条指令少了个字段（宿主照旧能跑，但行为微妙不同）；
- 某句报错的提示语措辞变了（用户与模型都按旧措辞写过文档）。

这类差异**跑得通、看起来正常**，等发现时早就扩散到几个特性上了。更麻烦的是：
到那时已经分不清「这是 Rust 实现错了」还是「本来就该是这样」——**没有基准，
争论没有意义**。

所以顺序是：**先立基准，再动手**。基准来自**现在能跑的 Python 前端**，
是「既成事实」而不是「重新设计」，所以它不需要谁来拍板 —— 它只需要**被看清**。

## 二、冻结哪四个阶段

| 阶段 | 产物内容 | 谁产生 | 由哪一步验收 |
|---|---|---|---|
| `tokens` | 类型 / 值 / 行 / 列 / 结束列 / 所在行原文 | `tokenizer.tokenize` | **R2** 分词器 |
| `ast` | 节点类型 + 全部字段（递归，含每节点行列） | `parser.parse` | **R3** 语法 |
| `bytecode` | 常量池 / 名字表 / 各函数的指令流与行号表 | `compiler.compile_source` | **R5** 编译器 |
| `diagnostics` | 第一个错误的**码 / 标题 / 消息 / 行列 / 提示** | 三个阶段都可能抛 | **R4** 报错 |

**四个阶段各自独立**：某语料在词法就失败，它的 `tokens` 就是 `null` 而
`diagnostics` 有内容 —— 不是「跳过」，是**如实记录它失败在哪一步**。

### ⚠️ 边界：只覆盖**编译期**诊断

35 个 `error_cases` 里有 20 个是**运行期**错误（除零、索引越界…），它们在
前端四阶段全部通过 —— 因为错误要跑起来才出现。所以：

| 范围 | 覆盖方式 |
|---|---|
| 编译期（词法/语法/语义） | **本夹具**（`diagnostics`） |
| 运行期（VM 抛的错误） | 既有的 `tests/test_golden.py` + `error_cases/*.err`；**R6 时再纳入夹具** |
| 程序输出 | 既有的 `tests/cases/*.out`（黄金文件） |

这条边界要记牢：**夹具没报错，不等于这个语料没毛病** —— 只是「前端这一步」没毛病。

## 三、三条设计规矩

### 1. 确定性：同一份语料必须产出逐字节相同的 JSON

否则夹具自己就是噪声源（每次跑都红，谁都不看）。措施：

- 一律 `sort_keys` + `indent=2` + `ensure_ascii=False`；
- 集合与字典键排好序再输出；
- **浮点的 NaN / ±Infinity 转成字符串标记** —— JSON 里没有这些字面量，
  Rust 的 `serde_json` 会直接拒收；
- 基线里的 `filename` 用**相对路径**（绝对路径换台机器就全红，还会把个人目录写进仓库）。

### 2. 逐语料分文件：`baseline/<扁平路径>.json`

`git diff` 能直接指出「哪个语料的哪个阶段变了」，而不是给一个几 MB 的大 JSON
让人猜。压缩后全部基线只有 **0.3 MB**（未压缩 4.2 MB），进仓库没有负担。

### 3. 语料内容也要钉住（`MANIFEST.json` 里记 sha256）

**改了语料却没重冻基线**时，`check` 必须报红。否则基线会悄悄变成
「另一份程序的输出」—— 而那正是夹具要防的事。

## 四、怎么用

```bash
python tools/conformance.py check        # 比对（默认；不一致退 1）—— CI 用这条
python tools/conformance.py check -v     # 不一致时多打几处差异
python tools/conformance.py list         # 语料清单与冻结状态
python tools/conformance.py freeze       # 重新冻结（**改完先看 git diff**）
```

它也在 `pytest` 里跑（`tests/test_m57_conformance.py`，17 项）与
`tools/ci.py` 里跑（第 3 步）——**判据同源**（都调 `compare_all()`），
只是入口不同：pytest 那套顺带验「工具本身可不可信」，ci.py 那条报告更聚焦。

### 加语料

放进已被扫描的目录即可，或改 `tools/conformance.py` 的 `CORPUS_SOURCES`：

| 类别 | 来源 |
|---|---|
| `lang` | `tests/cases/*.jsh` + `tests/error_cases/*.jsh` |
| `examples` | `examples/**/*.jsh`（含 6 个完整项目） |
| `stdlib` | `jishi/stdlib-jishi/*.jsh`（用基石写的标准库） |

加完跑 `freeze`，再看 `git diff` 确认新产物符合预期。

### check 会红的六种情形

| 报什么 | 意思 | 怎么办 |
|---|---|---|
| `产物不一致：X 在 \`y.z\`` | 前端行为变了 | **先判断改对没有**：改对了重冻，改错了改回来 |
| `语料内容已改动：X` | 源码变了、基线还在旧版本 | 有意改的就 `freeze` |
| `新增语料未冻结：X` | 有新语料没进基线 | `freeze` |
| `孤儿基线（语料已不存在）：X` | 删了语料、基线还在 | `freeze`（会清掉） |
| `实现有 bug：…` | 前端抛了**非基石错误** | **去修实现**，不许冻结 |
| `基线格式版本 ≠ 当前` | 产物结构变了 | `freeze` |

## 五、两条「不许」——这套工具最要紧的地方

### 1. 不许把 bug 冻成标准

工具第一次试跑就撞上了：我把 `serialize.dump_json` 写成了 `dumps_json`，
73 个语料的 bytecode 全变成「编译阶段：`<内部错误：ImportError>`」。
如果 `freeze` 照单全收，以后 Rust 版「忠实复刻这个 ImportError」才算一致 —— 荒谬。

所以 `run_stages` 里**只把 `JishiError` 记成诊断**；抛别的类型一律
`ImplementationBug` → **拒绝冻结**（且不留半成品清单）。

> 📌 这条的通用形式：**自动化工具分不清「事实」与「事故」**，
> 所以凡是「把当前状态升格为标准」的动作，都得有一道「这状态是正常的吗」的闸门。

### 2. 不许拿「没校验」充当「校验通过」

`check` 的输出只有两种：**全绿**或**报红并指出位置**。没有「跳过」「警告一下
继续」这种中间态 —— 那种状态在 CI 里与「通过」长得一模一样。

（同一课在 M49 也上过：`fetch_release_mirror.py` 拿上一版的 `SHA256SUMS` 校验
新包，四条全被静默跳过 → 已改成硬错误。）

## 六、实测（2026-09-30，同机）

| 项 | 数字 |
|---|---|
| 语料 | **73** 个（lang 45 / examples 24 / stdlib 4） |
| 四阶段全通过 | **58** 个；其余 15 个在编译期报错（词法 5 / 语法 10） |
| 冻结规模 | tokens **12,623** 个 · AST 节点 **7,444** 个 · 指令 **9,047** 条 |
| 指令集 | **50** 条（记在 MANIFEST 里一份） |
| 耗时 | `freeze` 与 `check` 各 **约 1.4 秒**（全量 73 个语料） |
| 产物体积 | 未压缩 4.2 MB → **gzip 后 0.3 MB** |
| **Python 3.10.9 vs 3.13.14** | **产物逐项一致**（73/73） |

最后一行值得单独说：它把「两个 Python 版本语义是否一致」变成一个**几秒就能
回答**的问题。建设性背景是 CI 里 Python 3.10 的任务一直失败 —— 而 3.10.9
跑这条夹具是**全绿**的，说明**那不是前端语义差异**，排查方向应转向
测试基础设施或平台假设（比如某些用例依赖了环境而不是语言）。

⚠️ 未度量：**尚未在 CI 上跑过**（本地与 CI 的环境差异本身就是怀疑对象之一）。

## 七、它在 R 线里的位置

```
R0 一致性夹具 ← 你在这里（本文件）
     ↓ 提供验收判据
R1 前端契约固化（schema + 差异定位）
     ↓
R2 分词器 ──[比 tokens]
R3 语法   ──[比 ast]
R4 报错   ──[比 diagnostics]
R5 编译器 ──[比 bytecode]
     ↓
R6 VM + 标准库（此时把「运行期」也纳入夹具：错误 + 程序输出）
R7 工具链
R8 单二进制 + wasm
```

**R0 不改任何架构**，所以它零风险；但它是后面每一步的**验收闸门** ——
没有它，R2 之后的「一致」都只是「看起来一样」。
