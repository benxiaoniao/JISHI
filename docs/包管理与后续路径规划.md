> ⚠️ 文中的「现状」都经过仓库核实（模块数、函数数、测试项数按**实际值**，不是清单里的旧数）。

## 一、包管理：先看清已经有什么

| 已有 | 在哪 | 说明 |
|---|---|---|
| `jishi 安装 / 卸载 / 列表 / 发布 / 索引 / 检查` | CLI 包管理子命令 | M49 起就有 |
| 包索引 `索引.json` | `packages/` | 结构：`{格式, 版本, 包: {名字: {版本, 下载地址, 描述, 校验和, 依赖}}}` |
| **依赖字段** | 同上 | `数学工具.依赖 = {基础库: …}` —— **字段有，但解析有多完整待核实** |
| 校验和 | 同上 | `sha256:…` |
| 自建源优先 + GitHub 兜底 | `packages.py` | M49 定的双通道 |
| 发布审计 | `jishi 发布` | 上传前的检查 |

### 我的判断：现在缺的不是「能不能装」，是**工程可靠性**

装了能用，但下面这些一旦有第三方包就会立刻痛：

| 缺口 | 会怎么痛 | 优先级 |
|---|---|---|
| **没有包自述文件**（`jishi.json`） | 包自己说不清「我是谁、要什么、提供什么」——全靠中心索引代劳。索引挂了/三方镜像不同步，包就成了黑盒 | **P0** |
| **版本约束语法不明确** | `依赖: {基础库: …}` 里填的是什么？精确版本还是范围？范围怎么写（`>=1.0` / `^1.0` / `~1.0`）？**不定死，将来必然各写各的** | **P0** |
| **没有锁定文件** | 今天装出 A+B，明天 B 发了新版，同一份代码装出不同的东西 —— **不可复现** | **P0** |
| **没有 `jishi 打包`** | `packages/下载/*.zip` 现在是手工拼的，元数据靠人填 | P1 |
| **传递依赖**（A→B→C） | 待核实现在解到第几层 | P1 |
| **冲突与循环检测** | A 要 B@1、C 要 B@2 怎么办 | P1 |
| **卸载的依赖清理** | 卸了 A，B 还留着（无害但脏）；反过来删了别人还用的 B 就是事故 | P2 |
| **私有源 / 多源** | 团队内部包 | P2 |

> 📌 **一句话**：现在的包管理是「**装得上**」，0.2.7 要把它做成「**装得可复现、出错能说清**」。

## 二、包管理怎么排（三个里程碑，各自能独立用起来）

### M129 · 包自述 + 版本约束（地基）

**做完了是什么样**：任何人在自己的项目里写一个 `jishi.json`，跑 `jishi 打包` 就能产出一个**带完整元数据**的包；`jishi 检查` 能看懂别人的包并说出「它要什么」。

**具体**：

1. **`jishi.json` 规范**（`格式`/`名字`/`版本`/`描述`/`作者`/`入口`/`依赖`/`许可`/`基石版本`）
2. **版本约束语法**——这块必须**一次定死**，建议 **只管三种**（够用且好教）：
   - `1.2.3` —— 精确
   - `>=1.2.3` —— 至少（配 `<2.0.0` 表达「别升大版」）
   - `*` —— 任意
   ⚠️ **不做 `^` / `~`**：它们依赖「语义化版本」的完整约定（主版本号意味着不兼容），
      而**第三方包的作者未必守**——守不住的东西不要写进语言规范。
3. **`jishi 打包 [目录]`** —— 按固定规则打 zip：
   - 成员顺序固定、时间戳写死（**字节可复现**，这条 M124 的能量法直接用上）
   - 自动算 sha256 写进索引条目
   - `jishi.json` 必填字段缺失 ⇒ **报错并说清缺哪个**
4. **`jishi 检查 <包>`** —— 读别人的包，报「它要什么、和我的环境冲不冲突」

**验收**：拿现有 `基础库`/`数学工具` 两个包，**用 `jishi 打包` 从源码重新打一遍**，与手拼的 zip 行为一致（`jishi 安装` 后 `导入` 能用）。

---

### M130 · 解析与锁定（可复现）

**做完了是什么样**：同一份 `jishi.json` + 同一个 `jishi.lock`，**在任何机器上装出逐字节一样的包集合**。

**具体**：

1. **传递依赖解析**（A→B→C），带**深度上限**（比如 32 层，防环）
2. **冲突检测**：两个包要同一个包的不同版本 ⇒ **明确报错**，不许静默挑一个
   > ⚠️ 不许「随便挑个高的」——那是 npm 早期最被诟病的行为，教学语言不能学
3. **`jishi.lock`**：记录每个包**实际装的版本 + 校验和 + 来源**
4. **`jishi 安装 --锁定`**：严格按 lock 装，**索引变了也不许变**

**验收**：故意让索引里某个依赖发新版，`--锁定` 装出来的东西必须**和上次完全一致**；把索引里那条依赖删掉，`--锁定` 仍能装（本地缓存优先）。

---

### M131 · 错误体验（教学语言的主场）

**做完了是什么样**：装包失败时，用户**知道自己该动什么**，而不是看到一串栈。

**具体**（都要带 E 码 + 修法建议）：

| 场景 | 现在大概会说 | 应该说什么 |
|---|---|---|
| 包不存在 | 找不到 | 「索引里没有「X」」+ **列出最接近的 3 个名字**（编辑距离） |
| 版本对不上 | 版本不符 | 「有 1.0.0 / 1.2.0，你要 >=2.0.0」+ 建议改约束还是换包 |
| 冲突 | ？（待核实） | 「A 要 B>=2，C 要 B<2」+ **把两边都点名** |
| 校验和不符 | ？（待核实） | 「下载到的文件和索引里的 sha256 不一致」+ **别只说失败**，要说「可能被改过或没下完」 |
| 基石版本太旧 | ？（待核实） | 「这个包要求基石 >=0.3.0，你是 0.2.7」+ 给出升级命令 |

> 📌 这一节是**最划算的投入**：包管理的口碑差，八成差在「装不上还说不清为什么」。

| 清单项 | 不采纳的理由 |

| **3.1 运算符重载**（列为 P0 第一位） | 🔴 **不做**，理由见 **D89**（2026-10-23 用户拍板）。最硬的一条不是成本，是**误会**：同一个 `+` 在不同类型上意思不同（Python 的列表拼接 vs numpy 逐元素），**人和模型都会错**，而本项目 §0.5 写着「底线是不产生歧义」。科学计算照做，改走 **`向量`/`矩阵` 内建类型 + 显式名字**（numpy 走的也是这条路，它**没给用户开放重载**） |

| **3.9 sqlite3**（P1 重点） | ⚠️ **这里清单判断错了**：本项目**已经有 `数据库` 模块**（M112，2026-10 交付）。✅ **已核实**：`--lang-spec` 的 30 个模块里有 `数据库`。清单没看到。⇒ **不需要补**（真要补的是「`数据库` 的文档和示例不够」，那是另一件事） |
| **3.20 类型标注 / 3.22 类型检查器** | 同意清单的「远期」，但更明确：**本项目的机器可读路线是 `--lang-spec` + E 码 + 修复建议**，那条走通了比类型标注对 AI 更有用 |

### 🔴 版本粒度的规矩（用户 2026-10-23 定）

> 原话：「目前我们生版本，提升的东西并不多，所以有时候我会让您修改路径图，把之后的往前放 ——
> 就是期望**每个版本的升级，都能带来更多的提升**。以后做路径图，**不要几个点就一个版本**。」

**每一版必须有「一件主菜 + 若干配菜」**，主菜是能让人「明显感觉到这个版本变了」的东西。
只堆六件小事的版本**不算一版**——那叫「顺手改了改」。

| 判断 | 标准 |
|---|---|
| 有主菜 | ✅ 能一句话说出「这一版最大的是什么」 |
| 主菜够大 | ✅ 用户/模型能立刻用上，不是内部重构 |
| 配菜配套 | ✅ 和主菜相关（主菜要用的、主菜暴露的坑） |
| 不硬凑 | ❌ 凑数的不算（比如「再补五个字符串方法」不是主菜） |

### 0.2.8 · **自己测自己**（主菜：用基石写一个跑得动黑盒用例的测试运行器）

> **触发**（用户 2026-10-24）：并行跑全量时 xdist 的 worker 会**静默硬崩**
>（`node down` → `--dist loadfile` 永久等），而那是**上游的 bug，我们改不了**。
> ⇒ 期望「用自己的语言测自己」：出了问题能改自己的工具，不用等上游。

#### 先划清能做到哪儿（核实过，不是估计）

| 现有 135 个测试文件 | 数量 | 能不能用基石重写 |
|---|---|---|
| 纯**黑盒**（起进程跑 `.jsh` → 比 stdout/退出码） | **17** | ✅ 能，**而且正是并行最痛的那批** |
| 含**白盒**（`import oracle.jishi` 的 API / 读 `rust/src/*.rs` 做结构断言） | **118** | ❌ 不能 —— 基石调不了 Python API，也做不了 Rust 源码级断言 |

⇒ **目标不是「pytest 本地全量退役」，而是「把重活挪到基石运行器」**：
重活（起进程、对拍、遍历）挪走之后，Python 那边只剩轻量白盒，
**并行卡死的根因（CPU 饥荒下 xdist worker 崩）自己就消失了**。

#### 底座已经有了（实测）

`系统.执行(命令, 超时)` **能起子进程、能拿输出、超时抛 `E2000`**（错误码清楚）；
`路径.临时目录` / `路径.按模式找` / `系统.CPU核数` / `时间.高精度时间` / `测试` 模块 11 个函数 —— 都在。

#### 两个真缺口（实测出来的，不是猜的）

1. `系统.执行` 返回的是 **stdout + stderr 合并**的文本 ⇒ **两条流没法分开比**。
   ⚠️ 这直接卡住 M128 那条判据（**「用户看到什么」= 两条流加起来**）——合并了就只能比一半。
2. **没有「并行执行命令」**：`并发` 只给了批量 IO（`批量读` / `并行取`），**不能起进程**。
   ⇒ 运行器只能串行，那自测会**比 pytest 还慢**，「换掉 pytest」就失去意义。

| **M133** ✅ | **`系统.执行详细(命令, 超时)`** → `{输出, 错误, 退出码}`（**两条流分开**） | ✅ 已交付（309 个函数；三宿主逐字一致） |

**做完是什么样**：`jishi tools/run_tests.jsh` 跑完那 20–30 条黑盒用例、
