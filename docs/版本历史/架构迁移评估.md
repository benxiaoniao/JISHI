# 前端换 Rust：可行性、收益与迁移路径（内部文档，未公开）

> **由来**：2026-09-30 作者提出「现有语言瓶颈很明显」——
> ① 前端是 Python：**启动慢、打包大、LSP 性能受限**；
> ② 多语言混杂：Python（前端）+ C（VM）+ 中文文档，**维护成本高**。
> 要求：**前端用 Rust 写、做桥接层、保留并增强 C VM、最终产出单二进制解释器**，
> 并评估可行性与收益、规划分步迁移。**原有 M57 及之后的规划作废**。
>
> **本文所有数字都是同机实测**（2026-09-30 · Windows · 取多次最快一次），
> 测法写在每张表下面。**没测到的一律标「未度量」**，不给估计值充数
> （这是本项目的老规矩：M52 那次就是因为把 7 倍估成 25–38 倍，被要求「量出来不一样的都留着」）。

---

## 一、结论先说

1. **可行性：高。** 核心理由不是「Rust 快」，而是——
   **目标接口已经存在且被跨语言验证过**：字节码 JSON 格式已经被 Rust 与 Node
   两个宿主各实现了一遍；**Rust 侧现有 13501 行里约 7900 行可以直接复用**
   （自写正则 / 加密 / 压缩 / HTTP / JSON / 精确小数 + 标准库逻辑）。
   这不是从零重写，是「补上前端 + 收拢工具链」。
2. **收益：一半是数量级的，一半是结构性的。**
   - 数量级：**包体 46MB → 2.6MB 量级**（Rust 宿主二进制实测 **2.63 MB**，
     里面已经含着整套自写标准库）；启动 285ms → 百毫秒以内。
   - 结构性（**这条最值钱**）：**4 种语言 → 2 种**。宿主层那 19792 行
     （= Python 全套的 0.96 倍，即「同一件事又写了一遍」）可以不再存在，
     M54/M55/M56 三批抓到的 bug 几乎全是它导致的漂移。
3. **代价：这是本项目最大的一次工程**，而且**迁移期间成本会先上升再下降**
   （要同时维护两套）。真正的风险不是「写不出来」，是
   **失去「独立实现互拍」这个验证资产** —— 有对策（见 §六）。
4. **建议的通道**：先做 **Rust 作为 Python 扩展**（渐进、每步可发布、可回退），
   再切到**独立单二进制**。**不要大爆炸重写**。
5. **可以现在就做的两件小事**（不改架构、立刻省一半包体）见 §十。

## 三、作者说的三条痛处，逐条核对

### 3.1「启动慢」—— 成立，但**量级比我一开始以为的小**

- 真相：**打包版 285 ms**（不是我最初量的 694 ms —— 那是 venv 源码跑法，
  打包版因为冻结了导入表反而更快）。同机 Rust 二进制 96.6 ms 里还含着
  进程创建与读字节码，所以真实可争取的是 **285 → 40~100 ms**，即 **3~7 倍**。
- ⚠️ **不是数量级的收益**。而且这个平台上「进程创建」本身就占几十毫秒，
  底下有地板。**别把启动当成迁移的主要理由**。

### 3.2「打包大」—— 成立，而且是**最大、最确定**的一条

- 46 MB（Linux）→ Rust 二进制量级 **2.6 MB**（含 C VM 后约 3~5 MB）：
  **10 倍以上**，而且是唯一一条「不用赌吞吐、纯赚」的收益。
- ⚠️ **但现在的体积里有一半是自己造成的**：`jishi` 与 `jishi-mcp` 是
  **两个 PyInstaller 包，各带一份 30.6 MB 的 `libpython`**。
  **这条不改架构就能省**（见 §十）。

### 3.3「LSP 性能受限」—— 部分成立，是三条里**最弱**的一条

- 成立的部分：整文件前端要 **2.13 s / 2 万行**，常驻 **44.8 MB**。
  「打开大文件」「全量静态检查」「格式化」这些**全量路径**确实慢。
- 不成立的部分：**M38 已经把编辑时最常见的路径做快了**
  （18001 行改末行：359.7 ms → **8.5 ms**，靠增量分词复用前缀）。
  也就是说，「编辑时卡」这件事基本已经解决，剩下的是冷启动与全量分析。
- 结论：换 Rust 会让这条变好（尤其大文件冷开、内存），但**别把它当第一顺位理由**。

### 3.4「多语言混杂」—— 成立，而且**这是最值钱的一条**

- 数字：宿主层 **19792 行 = Python 全套的 0.96 倍**；前端只占 Python 的 30%。
- **历史证据（比数字更有说服力）**：M54 / M55 / M56 三批修的真 bug，
  几乎全是「**同一语义写了 2~5 遍**」导致的漂移：

| 批次 | 抓到的漂移 | 根因 |
|---|---|---|
| M54 | Rust 闭包单元不共享（值语义 `Cell`）→ 嵌套递归全崩 | 同一个语义，宿主各写一遍 |
| M54 | Rust 未绑定局部**静默给 `空`** | 同上 |
| M55 | Node 把文本当 UTF-16 码元（`长度("😀")`=2） | 同上 |
| M56 | Node 16 个内建缺参数检查（3 个**静默给错答案**） | 同上 |
| M56 | Rust 异常对象**丢消息** | 同上 |
| M56 | `文件.位置` 在非 ASCII 上**五个引擎三个值** | 同上 |
| M56 | 要把 `difflib` 的候选名算法**逐字复刻进 JS 与 Rust** | 同上 |

- 为了看住这一类问题，专门建了「**漂移检测四道 + 内建体检**」
  （`--dump-stdlib` / `--dump-methods` / `--dump-builtins` / `probe_builtins.py`）。
  **换成一门语言之后，这个类别与这套机器都不再需要。**

> **所以真正的判断是**：迁移的主要回报不是「更快」，而是
> **「同一个语义只写一遍」** —— 更少的语言、更少的漂移、新特性只实现一次。
> 这也直接回答作者的动机：「离真正的自研更进一步」。

## 四、收益汇总（分清「数量级」与「倍数」）

| 收益 | 量级 | 确定性 |
|---|---|---|
| 包体（46 MB → 3~5 MB） | **10 倍以上** | 高（Rust 宿主 2.63 MB 已实测） |
| 不再依赖 Python 版本 / 不再需要打包运行时 | 质变 | 高 |
| 启动（285 ms → 40~100 ms） | 3~7 倍 | 中（下限受进程创建限制） |
| 前端吞吐（2.13 s / 2 万行 → ?） | **未度量** | 中 —— R2 交付时必须实测公布 |
| 常驻内存（45 MB → ?） | **未度量** | 中 |
| **语言数目 4 → 2，去掉「同一语义多份实现」** | **结构性** | 高 —— 这是最值钱的一条 |
| 新特性只实现一次（现在要动 3~5 处） | 结构性 | 高 |
| 跨语言分发从「三个宿主各写一遍」变成「编译到 native / wasm 两个目标」 | 结构性 | 中 |
| 浏览器 playground 由 wasm 承担（不必再维护 JS 宿主） | 结构性 | 中 |
| ⚠️ 性能上「`jishi` 跑得比现在快很多」 | **不一定** | C VM 本来就是快的那个；换前端的收益主要在**编译期与工具链**，不在**运行期**（运行期由 C VM 决定） |

> **一句要说清的话**：这次迁移**不是性能工程**，是**可持续性工程**。
> 运行期性能由 C VM 决定，不受影响；省的是「启动、体积、编译期、维护面」。

## 五、可行性：为什么我认为可行（以及难点在哪）

### 5.1 已有的资产（核心理由）

1. **目标接口已经冻结、且已被跨语言验证过** —— 字节码 JSON（`jishi/serialize.py`）
   已经被 **Rust 与 Node 两个宿主各实现了一遍**。新核心不用去设计接口，
   只要「产出/消费同一份东西」；而且**产错一眼就能发现**。
2. **Rust 侧已有 13501 行，其中约 7900 行直接可用**（§2.2）。
3. **426 项对拍测试 + 2300 项回归**是现成的安全网；`tools/probe_builtins.py`
   （每个内建在五个引擎上**真跑**）可以原地改成「新核心 vs 旧实现」。
4. **报错体系已经是单一、机器可读的**（错误码表 + 行列 + `hint`）→
   照抄有明确验收标准（逐字一致），这正是 M56 四批工作的复用。
5. 中文标识符、中文报错、时区/编码这些坑**全部有测试钉着** → 迁移可验证。

### 5.2 难点（按工作量排序，都如实说）

1. **「逐字一致」比想象的重**：不只是语法树，还有**错误信息与行列位置**
   （M56 整整四批都花在这上面）。这是前端迁移里最容易被低估的一块。
2. **工具链 8126 行要迁**：LSP（含增量同步）、DAP、格式化器、静态检查、
   包管理、REPL、沙箱、MCP Server —— 机械、量大、且**它们才决定编辑器体验**。
3. **浏览器 playground**：现在是 JS 宿主 + 内嵌 33 个模块。换 Rust 之后要编译到
   **wasm**（架构上更干净，但加载点、stdio、异常映射都要重做）。
4. **C VM 的桥接**：`jishi/cvm_bind.py` 就是现成规格；保留 C VM 需要静态链接
   进单二进制（可行，但要处理三平台工具链与构建）。
5. **包管理/分发链路**（M49 刚做完）要跟着换语言：安装器、包索引、`jishi 安装`
   —— 这些是**产品面**，不能因为底层换语言就断。

## 六、代价与风险（诚实清单）

1. 🔴 **最大的风险：失去「独立实现互拍」这个验证资产。**
   现在三执行器互拍的价值在于**语义独立**（树遍历走 Python 的 try/except，
   字节码走另一套）——M53 那个「`尝试/捕获` 把栈搞脏」的真 bug 就是
   五引擎对拍抓出来的。**若只剩「Rust 前端 + C VM」，两者共享同一套字节码生成，
   独立性下降。**
   **对策**：Rust 侧**也保留一个树遍历参考执行器**（写起来便宜，
   它就是「第二个独立视角」）。这条建议我认为必须写进方案。
2. **工期**：这是本项目**最大的一次工程**（相当于把 20.6k 行 Python 重做 +
   吸收 6.3k 行 JS）。**必须分步可发布**，不能大爆炸。
3. **迁移期间双份维护**：一段时间内 Python 与 Rust 两套并存，
   **维护成本会先上升**。收益在后半程才出现 —— 这一点要提前说清，
   否则中期最容易放弃。
4. **AI 协作节奏会变**：现在的 Python 前端改动小、迭代快、报错友好，
   这对「本项目主要由 AI 主导开发」是实打实的优势；换 Rust 后
   `cargo build` 的编译期反馈会明显变长。**这条不是反对意见，是必须纳入计划的成本。**
5. **未度量项**：Rust 前端的真实吞吐、单二进制的最终体积与启动、wasm 性能 ——
   **一律未度量**，等 R2 / R6 交付时实测公布，不许提前吹。

## 七、目标架构：三个方案

| 方案 | 形态 | 拿到的收益 | 拿不到的 |
|---|---|---|---|
| **甲（作者提的）** | Rust 前端 + C VM + **单二进制**；JS 宿主退役（wasm 顶替） | 体积、启动、语言数目、独立性 | 需要一次性完成度较高才能发布 |
| **乙（通道）** | Rust 作为 **Python 扩展**（`maturin`/`pyo3`），产品仍是 Python | 前端吞吐、LSP 冷启动；**每小步都能发布、能回退** | 体积与启动（仍是 Python 宿主） |
| **丙** | Rust 前端 + **Rust VM**（C VM 保留为可选快执行器） | 甲的全部 + 可能比 C VM 更快 | —— |

> **关于「丙里要不要留 C VM」的诚实判断**：C VM 现在的墙是
> **宿主回调次数（约 2.4 µs/次）**；如果标准库是**同进程的 Rust 原生实现**，
> 这个边界就没有了 —— **Rust VM 有可能反超 C VM**。
> 但这是**推测，未度量**。所以：**R6 做完先实测，再决定 C VM 的最终定位**
> （保留为「快执行器」还是退役）。**先量再说**，这是本项目的老规矩。

**建议路线**：**乙 → 甲（或丙）**。
用「Rust 作为 Python 扩展」做通道：每一小步都能发布、能回退
（`JISHI_FRONTEND=rust` 开关），且**立刻**改善 LSP 与静态检查；
等前端 + 工具链都搬完，再把产品形态切成独立单二进制（甲）。
**终点由 R6 的实测数据定：C VM 留还是不留。**

## 九、一句话总结

> **这次迁移买的是「同一个语义只写一遍」，不是「跑得更快」。**
> 运行期快不快由 C VM 决定，换前端不动它；
> 换来的是**体积小一个数量级、启动快几倍、语言从 4 种收敛到 2 种、
> 以及一整类「多份实现漂移」的 bug 从此消失**。
> 代价是**本项目史上最大的一次工程**，且**中期会先变贵**。
