**本轮还起了个头（R6.0 · 侦察与度量）**：

- `tools/benchmark.py` 与 `tools/check_engines.py` 都接进了 **Rust VM** 作**第四个执行器**
  （`JISHI_FRONTEND=rust` 编字节码 JSON → 二进制跑，**全程不经过 Python 对象**）。
- ⚠️ **Rust VM 是独立进程**，所以那一列**必须扣掉进程启动**（实测空程序 8~10 ms）
  —— 不扣就会把「VM 快慢」量成「进程启动快慢」。
- ✅ **已修掉其中第一个（R6.1）**：**Rust VM 的 `遍历` 原本是 O(n²)** ——
  迭代器的实现是「列表 + 每次 `remove(0)`」（`Vec::remove(0)` 要整体左移），
  而 Python VM / Node 用的都是真迭代器。改成「快照**反转** + 尾部 `pop()`」
  （顺序不变、每步 O(1)）：**同一个 n=20000，净耗时 2490 ms → 4.82 ms（约 500 倍）**，
  规模翻倍从 ×4.2 回到 **×2 线性**；行为逐字节不变。
- 🔴 **还摸出另外三个缺口（全在 Rust VM 一侧）**：
  ② `捕获 运行期错误` 接不住 `键错误`/`索引错误`；
  ③ 报错时 stdout 一个字都不冲出来；④ 报错渲染缺源码行/`^`/调用链。
- ✅ **「C VM 留不留」已测完并拍板（2026-10-04）：保留**。决定性数据是**长任务**
  （300 万次整数循环，进程启动成本已摊薄）：**C VM 净 489.0 ms vs Rust VM 净
  649.0 ms —— C VM 快约 1.33 倍**，且短任务上 Rust VM 还要多付约 100 ms 启动成本。
  17 个场景里 Rust VM 除 `递归斐波那契`、`当循环倒计数` 外全面落后；但**短场景那一列
  不可信**（净耗时小于启动成本时误差会被放大，`tools/benchmark.py` 自己会打 ⚠）。
  ⚠️ **这不是「Rust 不行」**：现有 Rust VM 是 M27/M33 时期的**兼容宿主**，
  与 C VM 的定位（**进程内**的快执行器）是**互补**关系，不是替代关系。

**再往前一轮（R6 收尾 + 主体验收 · 2026-10-04）做了什么**：

**① 宿主补全错误码表（M56-5 收尾）**：`抛出 一段文本` 以前**没有错误码**，
现在两个宿主都报 `E2009`；`捕获` 后面写了非异常类型 →
宿主以前（Rust）**悄悄不匹配**、现在报 `E2002`；模块属性不存在 →
`E0302` + 模块名 + 「怎么改」的提示。三处都在**码 / 消息 / 位置 / 提示**四个维度上
与 Python 侧逐字对齐（五执行器对拍）。
📌 **顺序不能反**：先把语义错误改成具体类型名，再给笼统的「异常」配码 ——
否则「找不到名字」这类错误会被误标成 E2009。

**② 编译器修复：捕获体里跳出时，「最终」块以前不跑**（R6 参考执行器抓到的那个 bug，
见下一节）—— 根因是 `c_try` 只把 `尝试` 体套进 finally。修法是给**每个捕获体再包
一层 `SETUP_TRY`**：`返回` 走 `finally_ip`、`中断/继续` 走 `catch_ip`、

**（再上一轮）R6 主体 · 函数调用：帧创建的三处开销 做了什么**：

把「调用」按参数个数拆开量，发现 Rust 一参调用比零参多 **350ns**、三参多 **595ns**，
而 **C VM 几乎与参数个数无关** —— 差的是**每次调用的固定开销**。三处：

- 🔴 **每进一次帧就克隆整个指令数组**（为了绕开借用检查）→ 把 `module` 换成
  `Rc<Module>`，借引用而不是克隆。**单这一项就让 `斐波(24)` 从 135ms 掉到 95.7ms。**
- 🔴 **用哈希表装参数**（通常只有 1~3 个）→ 换成数组。
- 🔴 **每帧两次堆分配** → **帧池**（弹帧回收、下次复用容量）。

**交错 A/B：`斐波(24)` 1.48×、一参调用 1.47×、三参 1.44×**；对 C VM 的差距从
**2.0~2.3 倍收窄到 1.2~1.5 倍**。

⚠️ 顺带更正上一轮的一句话：那儿说「`instrs.clone()` 只占 ~2%」**是错的**，
它其实是最主要的一处 —— 当时的估算拿最小的场景算、还没把「一次堆分配」算进去。

**（再上一轮）R6 主体 · 整数循环：全局变量表 + 整数比较 做了什么**：

基准里差距最大的一项（整数循环，Rust 比 C 慢 4.9 倍）。**先量再改**：把「循环」
拆成一段段量，再把**同一逻辑换个写法**量一遍 —— 模块级变量 vs 函数内局部：

```
                C VM        Rust VM
模块级变量      26.2ms      198.3ms     7.58x
函数内局部      27.8ms       90.7ms     3.27x
```

**C VM 两者一样，Rust 差一倍多** —— 矛头直接指向「全局变量」。根因：Rust 的
全局变量表是个哈希表，而且每次查之前还要**新建一个字符串**；而 C VM 一直是
「按名字下标索引的数组」。改成数组之后：**`当`循环 190.7 → 55.8ms（3.42x）**、
纯读写 **2.32x**，而且模块级与函数内终于持平。

🔴 **顺手撞出一个既有 bug**：`2 ** 62 > 2 ** 62 - 1` 在 Rust 宿主上给「假」
（它把整数**转成小数**再比），另外四个执行器都给「真」。语料里从来没有大整数
比较，所以它一直是绿的 —— 现在整数对整数直接精确比较。

**（再上一轮）R6 主体 · 集合 O(n) → O(1) 做了什么**：

D64 把字典的 O(n²) 收掉之后，集合按同一个思路走：原来是一个线性表，
「建 n 个元素」是 O(n²)。现在「**保序表 + 哈希索引**」，`添加` 去重 / `判断在不在` /
`删除` 都 O(1)，而集合**照旧是有序的**（打印与遍历稳定可复现）。

⚠️ **删除这里有个坑**：保序集合删中间元素如果前移整段，删 n 个**还是** O(n²)。
第一版就是这么写的 —— n=16000 的批量删除要 **1845ms**；改成**打墓碑 + 过半压缩**

**（上一轮）R5.1 · 把 R5 移植时挖出的四个既有 bug 清掉 做了什么**：

> 逐行移植为了搬对，每一行都得读懂；读懂之后，代码里**漏掉的那一支**就藏不住了。
> 这四个缺口**全都与 R5 无关**，而且两个前端上一直是**一致**的
> （所以一致性夹具全程是绿的）—— 它们只在**三个执行器之间**露出来。

| # | 在哪 | 症状 |
|---|---|---|
| ① | 编译器名字收集**漏了 `Try` 分支** | 「尝试/捕获/最终」里的赋值**漏成全局**；里面读的**闭包变量捕获不到**；里面**定义函数/类**会**编译期直接崩**（发射期 `KeyError`） |

| ④ | 调用链的挂载时机三处不一 | 「**显式 `抛出`** 的错误」在两个引擎下**没有调用链**（「除零」那种有）—— 同一种错误两种长相 |

  （否则全局与局部恰好等价）；②**模块级定义类侥幸没事**（模块帧以 `HALT`
  结束、不收 `RETURN`），而示例与语料里的类恰好都在模块级；③④只在报错文本里。

  （超 i64 整数、打印墙上时间的跑分示例）/ 不一致 0**。
  它管的是**「产物一样 ≠ 跑起来一样」**那一半 —— 上面四个里**有三个是在
  一致性夹具全程绿的情况下存在的**。

**M56 第四批 · 宿主的 `hint` 做了什么**：

- **两个宿主也能给「你是不是想写「长度」？」了** —— 以前宿主的错误对象
  **没有 `hint` 字段**，报错只说「找不到名字」，不告诉人可能该写什么。

  ```
  错误（异常）：找不到名字「长渡」
    ← 第 1 行第 4 列
    提示：你是不是想写「长度」？
  ```

- ⚠️ **难点不在「加个字段」，而在候选必须与 Python 侧一样**：Python 用 `difflib`，
  而两个宿主**都没有** —— 各**逐字复刻**了一份 Ratcliff-Obershelp。
  **不一致比不给候选更糟**（用户在两个引擎上看到不同候选，会以为另一侧是错的）。
  复刻里抓到两个抄错就分叉的点：最长公共块要用 difflib 的 **DP 版**
  （`k > bestsize` 严格大于，并列取先遇到的）；`get_close_matches` 收集的是
  `(分数, 名字)` → **同分时按名字降序**（不是保持原序）。
- 📌 **方法**：先在 **Python 里把复刻版与 `difflib` 对拍**（4000 组 ratio +
  3000 组候选全一致），确认算法钉死后再翻译成 JS / Rust。
- 「**宁可少给，不要给错**」：跟名字池都不像的（如 `prnit`）**不给提示行**，
  免得用户去改一个本来没错的名字。

**M54（结清「五引擎的账」）**：

- 集中还了一遍「**同一个语义、五个实现**」这条线上的欠账，抓到 **4 个真 bug**：
  - 🔴 **Rust 宿主的闭包单元不共享**（最重）：`Cell` 在 Rust 侧是值语义的
    `struct`（Python / Node 是对象），于是「先创建闭包、后给它赋值」永远失效 ——
    最典型的写法**嵌套的递归函数**直接崩 `「空」不能调用`。**顶层递归没事**，
    单测怎么写都碰不到；**三个执行器都是对的，只有真跑 Rust 才抓得住**。
    M53 记的三笔 Rust 缺口（`容器` / `迭代` / `参数`）**根因都是它**，一并解决。
  - 🔴 **Rust 未绑定局部静默给 `空`** —— 不报错的错答案（`空` 是合法值，
    跟「没赋过值」必须分得开）。
  - 🔴 **C VM 的未绑定「单元」报错类型**与另两个执行器不一致（同一个执行器两套写法）。
  - 🔴 **C VM 的「用后释放」崩溃**：函数值还在、VM 先销毁，GC 回收时
    回调 C 库 → `access violation`。**崩在 GC 里**，位置跟出错代码毫无关系。
- **补上「对象方法的漂移检测」**：M51 那份检测**只覆盖标准库函数名**，
  而 `列表`/`字典`/`文本`/`集合`/`文件`/`小数` 的方法表同样是**五份实现**。
  代价是两笔漏网 —— Rust 缺 `文本.查找`、Node 缺 `文件.位置/定位/刷新`，
  **都是偶然撞见的**。现在两个宿主都有 `--dump-methods`（**与分派同源**），
  测试接在 `tests/test_m51_consistency.py`，并补了一条「**表里有名字 ≠ 真的能用**」
  的实测。上面那几个缺口已全部补齐。

**M53（基石库层批量迁移）**：

- **又搬了三个模块**进基石库层：`容器`（7 函数）、`迭代`（12）、`参数`（5）——
  加上 `统计`，共 **4 模块 / 34 函数**，都是「用基石写一份、五个引擎共用同一份
  字节码」，且与宿主层实现**逐字节一致**（`tests/test_m52_jishilib.py`）。
- ⚠️ **顺手抓到一个影响四个引擎的真 bug**：「循环体里 `尝试/捕获`、捕获完继续
  循环」会把栈搞脏，最终报 `TypeError: 'RunTypeError' object is not an iterator`。
  根因在**编译器**（`尝试/捕获` 的字节码多了一句 `DUP_TOP`）。**三个执行器 +
  两个宿主里只有树遍历是对的** —— 五引擎对拍才抓得住。已修 + 加回归测试。

**M52（基石库层）**：

- **纯逻辑标准库从此只写一份**。以前 `统计` 这类模块要**用三种语言各写一遍**
  （Python / JS / Rust），改一处得改三处 —— M51 的漂移检测就是被这个逼出来的。
  现在 `jishi/stdlib-jishi/统计.jsh`（**就是基石源码**）在**编译期展开**成外壳函数，
  `导入 统计` 被改写成 `统计 = $造模块("统计", __基石库_统计__())`，
  于是**五个引擎跑的完全是同一份字节码，三个执行器与两个跨语言宿主一个字都没改**。
- **与宿主层实现逐字节一致**（`tests/test_m52_jishilib.py` 23 项：五引擎一致 +
  与宿主层一致 + 错误路径同类 + 机制 + 回落）。
- ⚠️ **性能如实公布：比宿主层慢 25–38 倍**（树遍历 37.8x / Python VM 24.9x /
  C VM 27.7x）—— 库代码内部每调一次内建，在 C VM 上都是一次宿主回调，而宿主层版
  把这一切做在一次调用里。**所以热路径函数必须留在宿主层**，这是下一阶段
  「性能分层」的存在理由。完整数据、走过的弯路与边界见 `docs/设计决策.md` D45。
- 顺带修掉一个报错翻译缺口：`遍历 <不可迭代的值>` 在 C VM 上报的是
  「内部错误（宿主回调）：TypeError: …」，现在是清楚的中文类型错误。

**M51（更早一轮，一致性止血）**：

- **宿主不再静默丢掉命名参数**。`加密.摘要("abc", 算法="md5")` 以前在 Node / Rust
  宿主上**悄悄用默认的 sha256**（Python 给 `900150…`、两宿主给 `ba7816bf…`），
  一声不响——这是本项目最危险的一类问题：**错了不报警**。现在两宿主按
  「模块.函数」查**由标准库源码自动生成的签名表**，把命名参数映射回位置参数；
  映射不了一律**明确报错**（类型「类型错误」，与 Python 侧一致）。
- **建了「漂移检测」**：两宿主各加 `--dump-stdlib`（**由宿主自己报家底**，
  不走正则解析源码），`tests/test_m51_consistency.py` 断言「Python 侧有的模块与
  函数，宿主一个都不能少、也不能多」，两宿主彼此也要对得上。
  **验收实测**：故意从 Node 删掉 `统计` 模块 → 3 条测试报红并点名缺哪个；
  把参数映射退回「静默丢掉」→ 7 条报红（含 `md5` vs `sha256` 那条）。
- **顺带补齐 13 个宿主静默缺失的标准库函数**（M50 及更早留下的洞）：
  `数学`（正弦 / 余弦 / 正切 / 对数 / 常用对数 / 角度转弧度）、
  `文本`（填充 / 截断）、`迭代`（累积 / 组合 / 排列 / 笛卡尔积）。
  补后两宿主与 Python 侧**同宽**，三个执行器 + 两个宿主逐字节一致。
- ⚠️ **只剩一个已知缺口**：`时间.计时` 在 Node / Rust 上仍缺失——它返回一个
  **带方法的对象**并支持上下文协议，而两宿主的上下文查找只认「Jishi 实例」与
  「内建容器」，标准库直接返回的宿主对象走不通。缺口**显式写在测试的
  `KNOWN_GAPS` 里**（不掩盖、也不让它静默），归属下一阶段：改成用**基石**写的
  库之后，它天然是 Jishi 实例，这类缺口会结构性消失。

**M50（更早一轮，分两批）**：

- **第一批**：标准库 **19 → 25 个模块、161 → 231 个函数**，新增 `统计` / `编码` /
  `配置` / `html` / `对比` / `标识`，并给 `迭代`（+累积/组合/排列/笛卡尔积）、
  `文本`（+截断/填充）、`时间`（+**计时**，上下文管理器式）补缺。
- **第二批**：把新模块补齐到 Node / Rust 宿主，新增 `tests/test_m50_hosts.py`
  （39 项）做**逐字节对拍**。Rust 侧的 base64、行级 diff、UUID 都是自写的
  （它零第三方依赖）。⚠️ 但当时说的「五个引擎同宽」**只针对这批新模块**——
  更早的 13 个函数缺口没人发现（M51 的漂移检测就是这么来的）。
- **验收看「真实项目少了几处绕道」**：`基石自述站/生成.jsh` 删掉手写的
  `转义()`（4 次 `替换`，而且**漏了引号**）改用 `html.转义`；
  `排序跑分/排序.jsh` 的手写计时改用 `时间.计时`。
- ⚠️ 顺带修掉 3 个坑，其中一个是**语言级**的：`用 … 为 …：` 原先**不认宿主对象**
  （只看了基石类实例与内建方法表），于是标准库返回的计时器不能当上下文管理器用。

**M48 阶段三（再往前）**：

- **方法调用融合**：`X.方法(实参)` 原本编译成 `GET_ATTR` + `CALL`，即
  **两次宿主回调**（实测每次约 4µs，其中必要工作只 2–3µs）。现在编译成
  一条 `METHOD_CALL`，一次回调做完。同机交错 A/B 实测：
  **方法调用 1.83× 快**、**端到端真实项目 `生成.jsh` 521.9ms → 334.8ms（1.56× 快）**。
- ⚠️ 该阶段另两个子项按实测判定**不做**，理由都量过：**常量折叠**全仓只 7 处
  可折叠（0.16%）；**窥孔候选 <1.7%** 且收益 ~0.2%；**文件 I/O** 的包装零开销
  （`按行读` 201µs vs 裸调 212µs）。不是做不动，是量完之后发现不值得——
  原计划「纯计算 +5–15%」的前提不成立。

**M47（更早）**：

- **C 侧原生字符串**（`JS_TAG_STR`）：拼接绝对快 **8.4 倍**、比较 **11.6 倍**；
  **AST 缓存**（361 行项目编译 14.13ms → **1.46ms**）。
- **顺带修掉一个先于该阶段就存在的内存泄漏**：C VM 的迭代器**每消费一个元素漏
  一份引用**（遍历 1000 个文本一次漏 33KB）。不报错、对拍全绿，只在长跑进程里
  涨内存——靠本轮新增的 `tools/leak_probe.py` 量出来。

**M46 阶段一（更早）**：

- ④②「延迟合并写」让**列表构建 3.0x → 14.1–19.1x**、**字典写入 0.78x → 5.7–6.3x**；
  ② 宿主回调路径提速约 10%。
- ⚠️ 实测**瓶颈是回调次数**（每次约 **4µs**，与被调函数做什么无关）；
  **读侧仍慢**（字典查找 0.96x）——要治它得让 C 侧真正持有容器内容。
  基准已按类型拆细，见 `tools/benchmark.py`。
