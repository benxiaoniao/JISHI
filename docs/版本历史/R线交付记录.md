### 11.1 ✅ R0 已交付（2026-09-30）：一致性夹具

**做了什么**：把 Python 前端**现在的行为**逐字冻结成结构化基线 ——
`tokens` / `ast` / `bytecode` / `diagnostics` 四个阶段，**73 个语料**。
工具 `tools/conformance.py`（`freeze` / `check` / `list`）、基线
`tests/conformance/`、守门测试 `tests/test_m57_conformance.py`（17 项）、
说明 内部一致性夹具说明（未公开）（内部）。

| 项 | 数字 |
|---|---|
| 语料 | **73** 个（语言 45 / 示例 24 / 基石库层 4） |
| 四阶段全通过 | **58** 个；15 个在编译期报错（词法 5 / 语法 10） |
| 冻结规模 | tokens **12,623** · AST 节点 **7,444** · 指令 **9,047** · 指令集 50 条 |
| 耗时 / 体积 | `freeze`、`check` 各约 **1.4 秒**；产物 4.2 MB（**gzip 后 0.3 MB**） |
| **Python 3.10.9 vs 3.13.14** | **产物逐项一致（73/73）** |

🔴 **立规矩时立刻抓到两件事**（都写进夹具文档）：

1. **差点把 bug 冻成标准**：我把 `serialize.dump_json` 写成 `dumps_json`，
   73 个语料的 bytecode 全变成「编译阶段：`<内部错误：ImportError>`」。
   于是加了硬闸门：**前端抛非基石错误一律拒绝冻结**（那是实现 bug，不是语言行为）。
   —— 自动化工具**分不清「事实」与「事故」**，所以「把当前状态升格为标准」的动作
   必须有这道闸门。
2. **同一课在 M49 也上过**：`fetch_release_mirror.py` 拿**上一版**的 `SHA256SUMS`
   校验新包（文件名不随版本变 + 「大小一致就跳过」），四条校验全被**静默跳过**。
   已改成硬错误：**清单里没有这个资产名 → 拒绝发布**。
   （「跳过校验」与「校验通过」在 CI 里长得一模一样。）

📌 **3.10 与 3.13 产物一致**这条对 CI 排障有直接价值：它说明 CI 里
**Python 3.10 的失败不是前端语义差异**。

🔴 **顺着这条线索查到了 CI 3.10 一直红的根因**（2026-09-30 当天修掉）：
**`tools/build_home.py` 里有 12 处 `{code('…\n…')}`** ——
**PEP 701 是 Python 3.12+ 才允许 f-string 表达式含反斜杠**，3.10/3.11 直接
`SyntaxError`（`import build_home` 失败 → 连带 7 个用例全红）。
**本地是 3.13，永远看不到。** 修法：含反斜杠的字符串提到 f-string 外面；
并加了一条 **AST 扫描**测试（任何 Python 版本下都能发现）。
⚠️ 顺带记一条口径：本地有 Rust 二进制、**CI 不编译 Rust** —— 本地结果不能
完全代表 CI。

### 11.2 ✅ R1 已交付（2026-10-01）：前端契约固化

**做了什么**：把「前端每个阶段要产出什么」写成**带版本号的契约**，并给出一把
**能定位的尺子**。R1 的定义就是「**不改行为，只定义接口**」。

| 交付 | 说明 |
|---|---|
| `conformance.py compare --from <目录>` | **外地产物 vs 基线**（R2 起 Rust 每写一步都用它验收） |
| `--stage tokens` | 只比某一阶段（R2 只做分词时用） |
| **差异明细带「这是什么元素」** | 从「`tokens[2].col` 5 vs 6」升级成「`tokens[2].col` —— **OP「=」（第 2 行第 5 列）** 基线 5 / 外部 6」 |
| 内部前端契约（未公开）（内部） | 顶层结构 / 四阶段字段 / **确定性要求** / **Rust 侧要产出什么**（含最小示例）/ 四条已知风险 |
| `tests/test_m58_frontend_contract.py` | 13 项：能定位 / 只比指定阶段 / 缺阶段要报 / 缺语料要报 / 读不动要报 / 文档与版本号一致 |

**验收演示**（R1 的验收标准正是「改坏一处能定位」）：

```
❌ 外部产物 vs 基线：72/73 个语料一致；共 1 处问题
  · 产物不一致：tests/cases/01_算术.jsh 在 `tokens[2].col`
差异明细：
      「tokens[2].col」 —— OP「=」（第 2 行第 5 列）
        基线：5
        外部：6
```

📌 **一条设计上的坚持**：外部**只提供部分阶段也行**（R2 只做分词），但
**没提供的阶段必须如实报「未提供」**，默认（不带 `--stage`）时那就是**没过** ——
**「没测」与「测过了」必须能分开**。同一个道理今天在 CI 上又验证了一遍。

### 11.3 ✅ R2 已交付（2026-10-01）：分词器换 Rust

**做了什么**：新建 `core/`（Rust crate，**pyo3 编成 Python 扩展**），
`tokenize()` 在 `JISHI_FRONTEND=rust` 时走 Rust、**默认仍是 Python**（有开关可回退）。

| 项 | 结果 |
|---|---|
| **逐 token 一致** | **85/85 语料** ✅（另 **2 万组随机源码对拍 0 分歧**；40 个脚本端到端跑出来也一样） |
| 端到端吞吐（2.07 万行 / 734 KB） | 490.8 → **132.0 ms（3.72x）** |
| 纯分词核心 | 490.8 → **69.6 ms（7.05x）** |
| ⚠️ **端到端天花板** | **4.23x** |
| 构建 | `python core/build.py`（产物 `jishi/_core.pyd`，**按 Python ABI 编，不进仓库**） |
| 守门测试 | `tests/test_m59_tokenizer_rust.py`（78 项） |
| 工具 | `tools/bench_frontend.py`（口径同机同时段交错 A/B + **把天花板推导印出来**） |

🔴 **最重要的一条：「≥5 倍」够不着，是接口决定的**

```
端到端 = Rust 纯核心（69.6 ms） + 把 Token 交回 Python（62.4 ms）
                                  其中 46.4 ms 是「纯造 11.7 万个 Token」的地板
天花板 = 490.8 ÷（69.6 + 46.4） = 4.23x   ← 与实现好坏无关
```

**建议**（待作者确认）：R2 的验收线改成「**纯核心 ≥5x + 逐 token 一致**」，
把「端到端 ≥5x」挪到 **R5** —— 那时下游（parser/compiler）才不吃 Python 对象。
✅ **2026-10-01 已拍板采纳**：R2/R3 这一层认「**纯核心 ≥5x + 产物逐项一致**」，
**「端到端 ≥5x」移到 R5** 验收（那时下游不再要 Python 对象）。

🔴 **顺手抓到的（都不是写错，是「本来就没测」）**

1. **R0 的 73 个语料里一个 emoji 都没有**（＝没测位置），而列号口径是这次迁移的
   头号风险。补 **12 个**语料：emoji 码点列号 / 多行注释三形态 / 全角归一化
   **44 项** / 三引号独占行 / 数字写法 / 插值分段表 / 5 个词法错误；
   并新增语料类别 **`tests/frontend_cases/`**（超 i64 整数 ⇒ C VM 有意报 E2005，
   放 `tests/cases/` 会破坏「三执行器都能跑」那条约定）。
   ⚠️ CRLF / 孤立 `\r` / BOM **进不了语料目录**（`read_text` 会归一化）→ 字符串级测试。
2. **`tokenizer.TOKEN_TYPES` 漏了 `FSTRING`**（M7 没补）。R2 的 `kind_name_index`
   用 `unreachable!` 兜底 → 当场 panic（宁可不跑也别给错值）。
3. **`emit` 没清空输出目录** ⇒ 中途失败后 `compare` 拿**旧产物**比出一个绿
   （「没跑成功」伪装成「通过」，第三次遇到同一个坑）。已改成「先删再写」。

### 11.4 ✅ R3 已交付（2026-10-01）：语法 → AST 换 Rust

**做了什么**：`core/src/parser.rs`（2600 行）—— 把 1968 行的 `jishi/parser.py`
**逐行移植**，含全部**解析期脱糖**（条件表达式 / `超()` / `匹配` / `枚举` /
推导式 / f-string），脱糖发生在与 Python **同一位置**。

| 项 | 结果 |
|---|---|
| **AST 逐项一致** | **88/88 语料** ✅（另 **5 万组随机源码对拍 0 分歧**；40 个脚本端到端一致） |
| 语法阶段诊断一致 | **88/88** ✅（码 / 行列 / 文案 / 提示 / `^` 下划线逐字） |
| 端到端吞吐（2.07 万行 / 735 KB） | 823.3 → **270.6 ms（3.04x）** |
| 纯语法核心 | 823.3 → **145.9 ms（5.64x）** |
| ⚠️ 端到端天花板 | **4.73x**（同 R2 的道理：交回 Python 的对象本身有地板） |
| 守门测试 | `tests/test_m60_parser_rust.py`（111 项）+ 3 个新错误语料 |

🔴 **最有价值的一条不是性能，是「接口原本就是错的」**

原计划让 Rust 从 `source_lines` 反拼源码。做到一半发现：`source_lines` 是
**有损**载体 —— `incremental.split_lines` 会去掉末尾空行，反拼回去
**报错行号整体少一行**（实测 9 例错 4 例，全在「块首后跟空行」这种形状上）。
而 LSP 那条路拿到的**正是** `inc.lines`。

改成：Rust `parse` 吃**源码文本**；新增 **`parse_source(源码)`** 作生产入口
（顺带**省掉一次重复分词**）；旧入口留给 LSP 增量分词，并加**精确守卫**
（拿 token 流末尾 EOF 的行号当标尺）—— **丢了内容当场报错，不猜**。

📌 手法可复用：**「反拼」这件事本身就是信号** —— 需要把 A 反拼成 B 才能让下游
干活时，多半是接口给错了；把**原始输入**直接递下去，比在两侧维持两条「口径」
的隐性约定可靠得多。

🔴 **顺手抓到的两处**：① 插值字符串的 `value` 是**分段表**，直接插进中文报错会把
Python 的 `repr` 泄给用户 → 两侧统一说「插值字符串」；② 类外 `超()` 那条错**漏了
`with_source` 与 `^` 下划线**（它是解析**之后**补的检查，不走 `_err`）→
**报错的补全要认「一个出口」，别按「谁抛的」分岔**。

**下一步**：**R4 前端报错** —— ⚠️ 范围已缩小：R3 顺手把**语法阶段**的 `diagnostics`
一起比过了，所以 R4 只剩「把比较面补全」这半边（执行期/编译期留给 R5/R6）。

### 11.5 ✅ R4 已交付（2026-10-01）：前端报错（契约升 v2）

**做了什么**

| 项 | 内容 |
|---|---|
| **契约 v2** | `diagnostics` 补 `下划线` / `修正` / **`渲染`**（用户真正看到的那段文本） |
| **错误码体检** | 新 `tools/probe_errcodes.py`：**「表里有这个码」≠「这个码真的会出现」** |
| **统一还原出口** | `errors.from_extension`（词法/语法不再各抄一份字段清单） |
| **语料 88 → 92** | 补 E0204 的两个形状 + E0205 的两个形状 |

🔴 **`渲染` 为什么进契约**：它是「事实」的下游产物，看着冗余，其实是**兜底** ——
哪天给错误加了一个事实字段却忘了列进契约，两个实现的渲染立刻不一样；而
「字段没进契约」**本身是看不出来的**（R3 就栽在「漏了一个字段、比对还是绿的」）。
**挑那个能连坐整个类的不变量，是一次就够的检查。**

🔴 **错误码体检第一次跑就抓到两笔**（以前从来没人查过）：
* **E0205「括号没有闭合」是死码** —— 定义在、说明在、`jishi 错误 E0205` 查得到，
  但**全仓库没有触发点**（括号没闭合其实报 E0201）。**一份永远兑现不了的承诺。**
  → ✅ **已拍板接上**：期望右括号而**已到文件末尾** ⇒ E0205，位置指向
  **那个没闭合的开括号**（EOF 的位置是「末行第 1 列」，指着它没用）。
  ⚠️ 只认「走到末尾都没等到」：中途撞上别的 token 仍报 E0201 并说出「看到了什么」——
  **别为了把码归拢而把信息丢掉**。
* **E0204 可达却一个语料都没有** —— 八个形状能触发它。

🔴 **词法那条还原路径漏读「修正」**：词法/语法**各抄一份字段清单**，词法那份少了
`fix` —— 而当时**恰好没有一个词法错误带 `fix`**，所以怎么测都是绿的。
→ 收成一个出口 + **字段表往返测试**把它们钉死。
**「两份清单并存 + 恰好没用到」＝ 测不出来，但问题在。**

**下一步**：**R5 编译器 → 字节码** —— 见 §11.6。

### 11.6 ✅ R5 已交付（2026-10-02）：编译器 → 字节码换 Rust

**做了什么**：`core/src/compiler.rs`（1151 行 Python 编译器的逐行移植）

| 项 | 结果 |
|---|---|

✅ **前端整条链（源码 → 词法 → 语法 → 字节码）现在都能在 Rust 里原生跑完。**

🔴 **兑现「端到端 ≥5x」靠的是换产物形态**：从「Python 对象」换成
**「字节码 JSON 文本」**。地板（造对象）在文本这条路上不存在 ——
**不是实现更快了，是接口换了**。⚠️ VM/CVM 那条路仍要对象，别拿它判 R5。

🔴 **移植时抓到四个既有 bug（与 R5 无关）** —— R5 逐字复刻，**R5.1 已全修**
（编译器漏 `Try` 分支 / Python VM 撞掉帧栈基址 / 树遍历「捕获 为」开子作用域 /
调用链时机不一）。见 内部前端契约（未公开） §12.4、`docs/设计决策.md` D59。

**下一步**：**R6 VM + 标准库（Rust 原生）** —— 验收 = 426 项对拍全绿；
**实测后定 C VM 去向**。

### 11.8 🔎 R7.0 侦察与度量（2026-10-05）：工具链迁移面台账（**待拍板**）

R7 的验收是「**编辑器不再依赖 Python；增量指标不倒退**」。开工前先把**面**摸清
——「搬得动/搬不动」都要有依据，不能靠感觉。

#### 一、好消息：边界**已经是「进程 + 协议」**，不是「import 我们的模块」

- 编辑器扩展**一直是 spawn 子进程**：`server.command` 默认 `jishi`、
  `server.args` 默认 `["lsp"]`（stdio JSON-RPC，自带最小传输层
  `lsp-transport.js`）；调试走 VS Code 的 `DebugAdapterExecutable` spawn `jishi dap`。
  → R7 换的是**协议那头是谁**，不是发明新接口。
- 工具链模块**没有一个依赖第三方 Python 库**（只有 `json`/`sys`/`pathlib`/
  `argparse`/`threading`/`zipfile`/`hashlib` 这类标准库）。
  → 「不再依赖 Python」的实际含义 = 把 **R2–R5 的 Rust 前端 + R6 的 Rust 宿主**
  接到同样的协议上，再补 Rust 侧还缺的几块。

#### 二、迁移面台账（逐项）

| 工具 | 规模 | 入口 / 协议 | 依赖的 Python 面 | Rust 侧现状 | 判断 |
|---|---|---|---|---|---|
| **格式化** | `formatter.py` 422 | `jishi 格式化 <文件>`、LSP `textDocument/formatting`、MCP `format_source` | 只要 parser/AST + 自己的排版规则 | 有 parser ✅，**无 formatter** | ★ 低（纯函数，最容易先做） |
| **静态检查** | `checker.py` 432 + `scope.py` 167 | `jishi 检查 <路径> --json`、MCP `check_source` | 四条 lint 共用 `scope.py`（与 LSP 未定义名**同一份规则**） | 编译器里有作用域收集，**四条 lint 都没有** | ★ 低 |
| **错误码查询** | `errcodes.py` 224 | `jishi 错误 <码>`、MCP `lookup_error`、LSP codeAction | 自带说明表 | 有「类型名 → 码」表（M56），**没有码 → 说明** | ★ 低 |

#### 🔴 开工时核实出的**前置条件**（§11.8 台账没写清，值得单记）

前端本体本来住在 `core/src/`，而 `core` 是**编成 Python 扩展**（pyo3）的 crate
—— 于是「**能解析源码的东西只有 Python 拿得到**」，独立宿主 `jishi-rs` 只能吃
**已经编译好的**字节码 / AST JSON（R6 的 `--walk` 也是吃 AST JSON）。
而 LSP / 格式化 / 静态检查**都必须自己拿到 AST** ⇒ **前端必须先解耦**。

📌 核实的结果是好消息：**这个搬家是干净的** —— 前端那五个文件**代码级零 pyo3 用法**
（翻遍 `tokenizer` / `parser` / `serialize` / `jishilib` / `opcodes`，命中的
"pyo3/Python" 全是注释里的「与 Python 侧对应关系」说明），而且跨模块引用本来就写
`crate::tokenizer::…` —— **整体搬到新 crate 根目录后一行引用都不用改**。

> 📌 教训：**「谁拿得到这个能力」要在侦察时就查清**，不能只看「这个能力在不在
> Rust 里」。台账当时写「tokenizer ✅ / parser ✅」是对的，但没说「它们住在 pyo3
> 扩展里、二进制用不上」—— 差一点就按「已经齐了」排期。

1. **`std::time::Instant::now()` 在 wasm 上 panic**（`time not implemented on this
