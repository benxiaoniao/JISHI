# 0.3.x 路径规划：包生态 + 内置测试工具

> 2026-10-22 用户提的两个方向。这里先摆**判断和选项**，不写实现细节 ——
> 具体里程碑等拍板后再排。

---

## 一、现状盘点（先说清我们**已经有什么**）

| 已有的 | 在哪 | 说明 |
|---|---|---|
| 包安装命令 | `jishi 安装 <包>` | 自建源优先、GitHub 兜底 |
| **包索引** | `https://基石.cn/packages/索引.json` | 格式 `{"格式": "jishi-package-index", "版本": 1, "包": {名: {版本, 下载地址, …}}}` |
| 自建分发源 | 同一台服务器 | 源码包 + 二进制发行版都在上面 |
| 包目录约定 | `packages/` | 打好的 `.zip` |

**结论：服务端最基础的那块已经有了。** 我们缺的不是「一个服务器」，
而是**发布流程、包规范、信任模型**这三样。

---

## 二、方向一：第三方包管理

### 2.1 先认清一件事：PyPI 的「索引」其实很简单

查了 GitHub 上的现成方案（2026-10 搜的）：

| 项目 | stars | 干什么 | 对我们有用吗 |
|---|---|---|---|
| **pypiserver** | 2.0k | 最小 PEP 503 索引：**从目录伺服**，htpasswd 管上传 | **有** —— 它的「目录 + 清单」结构和我们一样 |
| devpi | 1.2k | PyPI 缓存代理 + 暂存 + 索引继承 | 部分（暂存/审核流程可借鉴） |
| bandersnatch | 535 | 全量镜像 PyPI | 没用（我们不是 Python 生态） |
| 静态 PEP 503 目录 | — | `python -m http.server` 伺服一个目录就够 | **有** —— 证明「索引不需要数据库」 |

⇒ **别自建一个「服务」**。我们的 `索引.json` 已经是这个模式了，
真正要加的是**写入侧**（怎么让别人的包进来）。

### 2.2 三个必须回答的问题（按重要性排）

**① 信任 —— 这是基石的**特殊风险**，比 PyPI 严重得多**

基石的包能 `导入 文件` / `导入 网络` / `导入 进程`——
**一个恶意包可以直接读用户的文档、发出去**。Python 也有这个问题，
但 Python 生态大、有扫描、有举报、有 `pip` 的安全公告机制。

基石现在的处境是：**没有任何防护**。所以顺序必须是：

- **阶段 A（0.3.0）**：**只有我们审核过的包**。别人提 PR 到 `packages/` 仓库，
  我们审完合并 + 重新生成索引。**慢，但没有信任问题。**
- **阶段 B（0.3.x 后期）**：开放上传，但**只上源码，不给自动执行权限**：
  装包时明示「这个包会用到 文件 / 网络 / 进程」，要求用户确认（像 Android 权限）。
  📌 这一步的**前置条件**是语言层有「能力声明」机制 —— 见下。
- **阶段 C**：沙箱默认开启（用 M-cap 那套 `settrace` 的思路）+ 签名。

⚠️ **能力声明（capability declaration）** 是基石能做、而 Python 做不到的事：
`jishi.json` 里写 `"能力": ["文件", "网络"]`，`导入` 时校验。
**这是本方向真正的技术含量所在**，不是服务器。

**② 包规范：`jishi.json` 长什么样**

现在我们打包只有 `packages/*.zip`。要容纳第三方，至少要有：

```json
{
  "名字": "中文分词",
  "版本": "1.0.0",
  "作者": "…",
  "说明": "…",
  "基石版本": ">=0.3.0",
  "依赖": {"文本工具": ">=1.2.0"},
  "能力": ["文件"],
  "入口": "模块.jsh"
}
```

⚠️ **版本语义先定死**：`主.次.补` + `>=` / `==` **两种**就够，
**不要**一开始就上完整的 semver 区间求解（那是 `pip` 最复杂的部分，
我们没必要重造）。

**③ 命名冲突**

PyPI 是先到先得 + 名字规范化（`-` 和 `_` 等价）。
我们建议：**中文名 + 可选英文别名**，冲突时**后者加前缀**（`组织/包名`）。
⚠️ 别搞「抢注」那一套 —— 早期直接人工协调。

### 2.3 落地顺序（建议）

| 里程碑 | 做什么 | 做完了是什么样 |
|---|---|---|
| **M126** | `jishi.json` 规范 + `jishi 打包` 命令 | `jishi 打包` 能把一个目录打成合规的 `.zip` |
| **M127** | 索引生成器 + 官网「包列表」页 | 官网能看到所有包（人工上架） |
| **M128** | `jishi 安装` 支持**依赖**（一层，不递归） | 装 `A` 时自动装 `A` 依赖的 `B` |
| **M129** | **能力声明** + 装包时告警 | 装包前告诉你「它要读你的文件」 |

⚠️ **不建议做**：完整依赖求解（冲突回溯）、私有仓库、包签名 ——
**投入产出比太低**，等真的有 50 个第三方包再说。

## 三、方向二：内置测试工具

### 3.1 为什么这件事**比包管理更该先做**

包管理和测试工具是**配套**的：第三方包作者要**自己测自己的包**，
不能指望他装 Python + pytest。**没有测试工具，包生态长不起来。**

而且它对我们自己也有用：现在 3839 条判据全是 pytest 写的，
**基石自己一行测试都写不了** —— 这本身是个缺口（M40「别扭点清单」里该记一笔）。

### 3.2 设计（参考 `go test`，不参考 pytest）

pytest 的强大来自 fixture / 插件 / 参数化 —— 那套在基石里**先别碰**。
Go 的做法更合适：**约定优于配置，一个命令跑完**。

```jishi
# 求和_test.jsh
导入 断言

函数 测试_两数相加()：
    断言.相等(求和([1, 2]), 3)
    断言.相等(求和([]), 0)

函数 测试_负数也对()：
    断言.相等(求和([-1, 1]), 0)
```

```bash
jishi 测试              # 扫当前目录及子目录的 *_test.jsh 并跑
jishi 测试 求和的测试/   # 只跑某个目录
jishi 测试 --详细        # 每条都打印
```

**核心只有 4 个断言**（够用，且不需要反射/内省）：

| 断言 | 说明 |
|---|---|
| `断言.相等(实际, 期望, 说明="")` | 最常用；不等时打印两者 |
| `断言.为真(条件, 说明="")` | |
| `断言.抛错(函数, 错误码="")` | 断言会抛错，且（可选）错误码对 |
| `断言.近似(实际, 期望, 误差)` | 浮点比较 |

**输出格式**（对齐 `go test`，一眼能看出哪条挂了）：

```
=== 求和_test.jsh ===
  ✓ 测试_两数相加
  ✗ 测试_负数也对
      第 4 行：期望 0，实际 1
      断言.相等(求和([-1, 1]), 0)
                      ^^^^^^^^
汇总：2 条通过，1 条失败
```

### 3.3 为什么不做 fixture / 参数化 / 插件

- **fixture**（`pytest` 的 `@pytest.fixture`）解决的是「共享准备/清理」——
  基石里用**普通函数 + 顶层常量**就够了；
- **参数化**在 Go 里是「手写一个 `for` 循环调 `t.Run`」—— 我们也一样，
  **循环 + 断言**，不需要语法层支持；
- **插件**：等真有人需要再说。**过早抽象比重复更贵。**

### 3.4 落地顺序（建议）

| 里程碑 | 做什么 |
|---|---|
| **M130** | `断言` 模块（4 个函数）+ `jishi 测试` 命令（扫 `*_test.jsh`） |
| **M131** | 失败输出带**行列 + 源码片段**（复用现有的报错渲染） |
| **M132** | `jishi 测试 --覆盖`：用 `settrace` 思路记「哪些行被执行过」（可选，看需求） |

---

## 四、我的建议（如果只能选一个先做）

**先做测试工具（M130）**，理由三条：

1. **它是包管理的前置**：没有它，第三方包作者没法自测，生态起不来；
2. **投入小**：4 个断言 + 一个扫描命令，比包管理的信任模型简单一个量级；
3. **对自己立刻有用**：以后新判据可以用基石写，顺便**自测语言**（这是最狠的 dogfooding）。

包管理按 **M126 → M129** 慢慢来，**能力声明**那一步才是它的技术核心，
服务器只占 10%。
