# 测试用例退役流程

> 2026-10-24 立。起因：用户指出「随着语言功能拓展、前端从 Python 换成 Rust，
> 是不是有些测试会过时了？我们需要一个退役流程，**不是单纯地堆砌用例**。」

---

## 一、为什么「只加不减」是危险的

测试本来的作用是**给人信心**。一条过时的测试会做三件坏事：

1. **给假信心**——它绿着，但它测的东西早就不存在了（或不再是唯一实现）；
2. **误导后来的人**——读到「这个测试断言 Python 前端的行为」，会以为 Python 前端还是权威；
3. **拖慢一切**——134 个文件、3800 多项，全量跑 20–30 分钟。**没人愿意跑的测试等于没有测试**。

所以退役不是「删代码」，是**维护测试的可信度**。

---

## 二、什么算「过时」（五类，按证据强度排）

| 类型 | 特征 | 证据怎么来 |
|---|---|---|
| **A. 悬空引用** | 引用了已经搬走/删除的脚本、模块、文件 | `python tools/audit_tests.py` 直接列出来 |
| **B. 临时跳过忘了回来** | `@pytest.mark.skip(reason="等 M112 做完")` —— M112 早做完了 | 同上（按原因里的 `等/TODO/M\d+` 挑出来） |
| **C. 测实现细节而不是行为** | 断言 AST 节点结构、内部函数名、文件布局 | 同上（找 `assert` 里出现 `ast.xxx` / `node.xxx` 的行） |
| **D. 实现换了，它测的是旧的那套** | 前端从 Python 换 Rust 后，测 Python `tokenizer` 的用例**不再是**「唯一实现的判据」 | **人工判断**（工具只能给出「很久没动过」的线索） |
| **E. 重复覆盖** | 同一个行为被 3 个文件从 3 个角度测 | **人工判断** |

⚠️ **工具只找得到 A/B/C**。D 和 E 必须人看 —— 所以**流程里必须有人工环节**，不能指望脚本。

## 三、流程（四步）

### 第 1 步：跑体检

```bash
python tools/audit_tests.py          # 全量报告
python tools/audit_tests.py --简     # 只看「需要动」的
```

### 第 2 步：对每一处**先判类型**，再决定处置

| 情况 | 处置 | 判据 |
|---|---|---|
| **被测的东西还在，只是搬了位置**（脚本/模块搬仓） | **搬测试**（不是删） | 搬过去还能跑绿 ⇒ 说明判据本身没问题 |
| **被测的东西真的没了**（功能下线、API 删了） | **删测试**，并在 CHANGELOG 写一句「X 功能下线，判据已删」 | 删之前 `grep` 确认没有别处还在用 |
| **只是「临时跳过」** | 要么**修好解锁**，要么**改成永久边界**并写清为什么不会过期 | `reason` 里不许留 `等…/TODO` 这种会腐蚀的词 |
| **测的是实现细节** | 改成**测行为**；改不动就删 | 问一句：换个实现（比如前端再换一次）这条还成立吗？不成立就是实现细节 |
| **重复覆盖** | 留**最强的那条**（能覆盖最多行为的），其余删 | 「两条都留着更保险」是错觉：多一条就多一处要跟着改的地方 |

### 第 3 步：删之前**三问**（缺一个都不许删）

1. **有没有别的地方覆盖这个行为？** —— 说不出来就**不许删**（宁可留着，也不制造盲区）；
2. **删掉之后，出同样的 bug 会不会被测出来？** —— 会，才删；
3. **它是「过时」还是「只是我不喜欢」？** —— 「写得丑但有用」的测试**不许删**。

### 第 4 步：记一笔

删/搬都要在 CHANGELOG 里留一行：**删了什么、为什么、判据在哪补上**。
不是为了流程好看 —— 是为了**半年后有人问「X 怎么没测试」时能查到答案**。

---

## 四、什么时候跑这个流程

| 时机 | 为什么 |
|---|---|
| **换实现 / 搬仓之后**（必须） | 2026-10-23 拆官网那次**没跑全量**，于是 `test_m97` / `test_m110` /
`test_m49` / `test_release_sync` / `test_m10` 五个文件整整一天是坏的 —— 而**单跑每个文件都是绿的** |
| **每个版本收口时** | 和「文档更新」一起做（见 `M132` 清单） |
| **发现全量测试变慢时** | 慢往往不是「测试多了」，是「重复的测试多了」 |

## 五、这次的体检结果（2026-10-24，M130 附带）

工具跑出来 **15 处悬空引用 / 23 处 skip**，实际动了 **4 个文件**：

| 文件 | 问题 | 处置 |
|---|---|---|
| `test_m97_wasm_playground.py` | import 已搬走的 `build_playground` | **整个搬官网**（它验的就是试玩页） |
| `test_m110_selfupdate.py` | 其中一条读已搬走的 `fetch_release_mirror.py` | **只摘那一条**搬官网（文件主体是自升级器，留在主仓库） |
| `test_m49_distribution.py` | 依赖 `build_home` / `build_index_mirror` / `packages/` | **整个搬官网**（19 项） |
| `test_release_sync.py` / `test_m10_playground.py` | 同上 | **整个搬官网**（4 + 6 项） |

📌 **共同点**：全是「脚本搬走了，测试没跟着走」。
⇒ **推论（写进流程）**：**搬脚本的同一个提交里必须搬它的判据** ——
否则主仓库会在 collection 阶段 ERROR，或者（更糟）**晚到某个用例执行时才炸**，
而单跑别的文件全绿，很难发现。

## 六、这个流程自己的判据（别让它变成一句口号）

- `tools/audit_tests.py` **要能跑、要有输出**（不要求「零问题」，要求「问题可见」）；
- **每次搬脚本/退役功能，CHANGELOG 里必须有对应的一行**；
- ⚠️ **`audit_tests.py` 的「已退役」清单会过期**：某天脚本回来了，条目要删 ——
  和 `check_engines` 的登记表一个道理，**会过期的登记载比永久豁免可靠**。
