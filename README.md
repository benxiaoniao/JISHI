# 基石（jishi）

一门简单易用的**中文编程语言**。

`如果`、`遍历`、`函数`、`返回` 这些词**本身就是关键字** ——
你写下的和你脑子里想说的，是同一句话，**中间少一层英译**。

> **技术栈声明（公开透明）**
> - 前端（词法/语法/AST/中文报错）由 **Python 实现**
> - 三个执行器：**树遍历解释器**（默认，Python）/ **Python 字节码 VM** /
>   **C 字节码 VM**（`cvm/`，自研 C 栈式虚拟机，gcc 编成 DLL/SO，
>   纯计算场景提速最高 46x，wheel 内自带无需本机 gcc）
> - 通过桥接层**可调用任意 Python 库**，标准库为中文薄封装
> - 不 fork、不 patch CPython，也不宣称"完全自主"，以上技术栈如实标注
>
> 已是一条「拿到就能写」的完整通用语言：模块系统、面向对象、异常、包管理雏形、
> AI 原生工具链（语言卡 / 结构化报错 / 评测集）、沙箱 + MCP 集成、wheel 内带 C VM。
> 定位不是教学玩具，长期目标是可维护的开源项目。

## 安装

**三种装法，都是「自带运行时」，不用先装 Python。**

**Windows** —— 从[下载页](https://基石.cn/download.html)取
`jishi-<版本>-windows-x64-setup.exe`，双击安装即可
（用户级安装、免管理员；简体中文向导，含开始菜单快捷方式、可选加入 PATH、
标准卸载程序）。也有免安装的 `jishi-<版本>-windows-x64.zip`。

**Linux（x64）/ macOS（Apple 芯片 arm64）** —— 下载对应压缩包，
解压后运行 `install.sh`：

```bash
tar -xzf jishi-<版本>-linux-x64.tar.gz
cd jishi-<版本>-linux-x64 && bash install.sh
```

> ⚠️ macOS **目前只有 arm64 版**（没有 Intel / x64 版）。

**从源码安装** —— 给要改代码的人，需本机 Python 3.10+：

```bash
pip install git+https://github.com/benxiaoniao/JISHI.git
```

⚠️ **这条路要连 GitHub，大陆可能很慢甚至超时**（实测 `git fetch` 会整段超时）。
能用安装程序就别用这条。

**VS Code 扩展**（可选）：扩展市场装 `jishi-lang.vscode-jishi`，有语法高亮、
补全、跳转与调试器（断点 / 单步 / 看变量）。⚠️ **扩展不自带运行时** ——
要先按上面任意一种把 `jishi` 命令装好，它才跑得起来。

装完先跑一次自检，它会顺手告诉你包索引通不通：

```bash
jishi 医生
```

**安装包在[本站下载](https://基石.cn/download.html)** —— 托管在自己的服务器上，
大陆直连可用（不必翻 GitHub）。那一页还有 **逐版本的升级说明**（每个版本改了什么）
与 `SHA256SUMS` 校验和。同一份文件也在
[GitHub Releases](https://github.com/benxiaoniao/JISHI/releases) 上，**逐字节相同**。

> **没有 `pip install jishi` 这条命令**：基石**不发布到 PyPI**。
> 包管理走自己的链路 —— `jishi 安装 <包>`（M49 已落地）：
> 索引与发行包托管在自己的服务器 <https://基石.cn/> 上（**大陆直连**，
> 实测 0.11 秒），GitHub 那份留作**备用源**；两个源**按优先级依次尝试**，
> 第一个通了就用它。索引格式与打包流程见 `docs/语言规格.md`，
> wheel 构建细节见 `tools/build_wheel.py`。

## 快速上手

```bash
# 运行一个 .jsh 文件
jishi examples/01_猜数字.jsh

# 交互式 REPL
jishi -i

# 查看 AST（调试用）
jishi examples/01_猜数字.jsh --ast
```

第一个程序 `你好.jsh`：

```
# 你好，基石
打印("你好，世界！")
令 名字 = 输入("你叫什么名字？")
打印("欢迎你，", 名字)
```

## 语言示例

```
# 猜数字小游戏（判断/循环/输入）
导入 随机
令 答案 = 随机.随机整数(1, 100)
循环 10 次：
    令 猜测 = 整数(输入("猜一个 1-100 的数："))
    如果 猜测 < 答案：
        打印("太小了")
    否则如果 猜测 > 答案：
        打印("太大了")
    否则：
        打印("猜对了！")
        中断
```

```
# 异常处理（M5a：尝试/捕获/最终/抛出）
函数 折扣价(原价, 折扣):
    如果 折扣 <= 0 或 折扣 > 1:
        抛出 值错误("折扣必须在 0 到 1 之间")
    返回 原价 * 折扣

尝试:
    打印(折扣价(100, 2))
捕获 值错误 为 e:          # 异常对象可读 e.消息 / e.类型
    打印("出错了：", e.消息)
```

```
# 面向对象（M5b：类/继承/新建）
类 动物:
    函数 初始化(自身, 名字):      # 「初始化」是构造方法
        自身.名字 = 名字           # 「自身」是实例本身
    函数 叫(自身):
        打印(自身.名字, "在叫")

类 猫 继承 动物:
    函数 叫(自身):                 # 覆盖基类方法
        打印(自身.名字, "喵喵")

令 咪咪 = 新建 猫("咪咪")
咪咪.叫()
```

对拍（树遍历 / Python VM / C VM 输出逐字节一致），另有跨语言宿主对拍

同样失败）。跑到的这一轮它们**恰好没犯**（全绿），所以别把它当成「修好了」。

**最近一轮（M49 · 自主分发：自建源 + 官网 + HTTPS）做了什么**：

- **官网上了自己的域名**：<https://基石.cn/>。源站是大陆轻量云上的 Nginx，
  前面挂 EdgeOne CDN；页脚按法定要求放了 **ICP 备案号并链到工信部**。
- **`jishi 安装` 不再依赖 GitHub**：索引源改成**按优先级依次尝试** ——
  ① 自建源（基石.cn）② GitHub 备用。自建源那份索引里的「下载地址」
  也指向同一个域名，所以**整条安装链（索引 + 包）都在境内**，实测 0.11s。
- 🔴 **修掉「HTTPS 打不开」（521）**：源站只听 80，而 CDN 对 **HTTPS 请求
  走 HTTPS 回源**（443）—— HTTPS 必然失败。给源站配好证书、开 443 之后
  两条路都通。诊断依据是**源站访问日志里有没有那条请求**（HTTP 有、HTTPS 没有）。
- **报错给出可操作的办法**：全部源都读不到时，列清试过哪些地址，并给出
  `--index` / `--local-zip` / `--local-dir` 三条具体做法；`jishi 医生`
  新增**索引可达性自检**（`--no-net` 可跳过）。
- **部署链路也进了仓库**：`tools/site_sync.sh`（服务器侧同步 + 装 Nginx）、
  `tools/deploy_push.sh`（本地构建 + 推送）、`tools/nginx-jishi*.conf`。
  🔒 **密钥路径与服务器地址只从环境变量读**，绝不写进文件。

**M56 第四批 · 宿主的 `hint` 做了什么**：

- **两个宿主也能给「你是不是想写「长度」？」了** —— 以前宿主的错误对象
  **没有 `hint` 字段**，报错只说「找不到名字」，不告诉人可能该写什么。
  报错现在长这样：

  ```
  错误（异常）：找不到名字「长渡」
    ← 第 1 行第 4 列
    提示：你是不是想写「长度」？
  ```

- ⚠️ **难点不在「加个字段」，而在候选必须与 Python 侧一样**：Python 用 `difflib`，
  而两个宿主**都没有** —— 各**逐字复刻**了一份 Ratcliff-Obershelp。
  **不一致比不给候选更糟**（用户在两个引擎上看到不同候选，会以为另一侧是错的）。
  复刻里抓到两个抄错就分叉的点：最长公共块要用 difflib 的 **DP 版**
  （`k > bestsize` 严格大于，并列取先遇到的）；`get_close_matches` 收集的是
  `(分数, 名字)` → **同分时按名字降序**（不是保持原序）。
- 📌 **方法**：先在 **Python 里把复刻版与 `difflib` 对拍**（4000 组 ratio +
  3000 组候选全一致），确认算法钉死后再翻译成 JS / Rust。
- 「**宁可少给，不要给错**」：跟名字池都不像的（如 `prnit`）**不给提示行**，
  免得用户去改一个本来没错的名字。

**M56 第三批（文件语义 + 宿主报错）**：

- **文件的三处口径统一**：`文件.位置` / `定位` 统一成**字符数**（Python 原来给
  `tell()` 的字节 cookie、Rust 给字节偏移——**同一段程序三侧给三个值**）；
  **写文件一律用 `\n`**（Windows 上 Python 原来写 `\r\n`、两个宿主写 `\n` ——
  同一台机器上五个引擎产出的**字节**都不同）。
- 🔴 **修掉 Rust 的 `文件.读(n)` 按字节读**：非 ASCII 上会把汉字切成两半，
  报「文件内容不是 UTF-8 文本」—— **而那个文件明明是合法的 UTF-8**。
- 🔴 **Rust 的报错终于有行列了**（原来**全部没有**），**两个宿主也都带上错误码**：
  渲染成 `错误 E2001：不能除以零` + `  ← 第 3 行第 6 列`，与 Python 侧同形。
  📌 报错里的码可以**直接贴给 `jishi 错误 <码>`** 查「什么意思 / 常见成因 / 怎么改」。

**M56 第二批（宿主报错对齐 + 错误码索引）**：

- **Node 19 个内建的参数个数检查补齐** —— 其中 **3 条以前是「静默成功」**：
  `文本()` / `类型()` / `退出上下文()` 在 Node 上**直接返回值**，而 Python 与
  Rust 都报错（「不报错的错答案」最难查）。根因是签名写成 `(v) => …`，
  0 个实参时形参是 `undefined`、函数体照跑。顺带收口 **Rust 4 处自己抄的文案**。
  → 现在「参数个数错」在**五个引擎上逐字一致**。
- **Rust 的异常对象模型**：`捕获 … 为 e` 以前只拿到类型名（`e.类型` / `e.消息`
  直接报「没有属性」，`打印(e)` 只给「类型错误」）—— 现在带消息，与 Node 一致。
- 🆕 **`jishi 错误 [码]`**：查「什么意思 / 常见成因 / 怎么改」，不写码则列全部
  **32 个**错误码（按词法/语法/语义/运行期分段）。`--ai-card` 里也加了这一节。

**M56 第一批（内建体检）**：

- **新建 `tools/probe_builtins.py`**：给**每个内建**一条最小可跑程序，在
  **五个引擎上真跑**（正常用法 + 参数个数错 + **Rust panic 扫描**）——
  不再只比名字。**一建起来就抓到一条 M55 漏掉的账**。
- ⚠️ **`超()`（在方法里调基类）在 Node 与 Rust 上根本不能用**：M55 建内建检测时
  把 `超` 当「编译器形式、宿主不需要有它」而**排除在比对之外** —— **判断错了**，
  它是 `LOAD_GLOBAL 超` + `CALL` 的真运行期内建，于是两个宿主一直报
  「找不到名字「超」」而三个执行器全对。已修：Node 补 `JishiSuper`；
  **Rust 给 `Class` 补 `base` 字段**（那边建类时展开合并基类方法表后
  **把基类指针丢了**）。修完五引擎连 `打印(超())` 的 `<超 乙>` 都逐字一致。
- **体检结论**：名字三侧同宽（各 30）；**正常用法 30/30 五引擎逐字节一致**；
  参数个数错三执行器一致、**Rust 全部不再 panic**；⚠️ **Node 还有 16 个内建
  缺参数检查**，其中 **3 个是「静默成功」**（`文本()` / `类型()` / `退出上下文()`
  在 Node 上直接返回值，Python 与 Rust 都报错）。

**M55（定下「一个字符是什么」）**：

- **新增内建 `序数(字符)` / `字符(码点)`** —— `序数("中")` 给 20013、
  `字符(20013)` 给「中」，互为反函数。口径是**一个字符 = 一个 Unicode 码点**。
- 🔴 **修掉一个「同一段代码在不同引擎给不同答案」的真 bug**：Node 侧把文本当
  **UTF-16 码元** —— `长度("😀")` 给 **2**（另两个给 1）、`"😀"[0]` 只拿到
  **半个代理项**（打印出来是 `�`）、`"a😀b".查找("b")` 给 **3**、`反转` 出乱码。
- 🟡 **新增「内建函数」的漂移检测**（`--dump-builtins`，前两个口子管标准库与
  对象方法）—— 而它**建起来当场就抓到**：`断言` / `是实例` 在 **Node 与 Rust
  上根本没有**（一写就报「找不到名字」），`断言错误` 这个捕获类型也缺。
- 🔴 另外两个真 bug：**Rust 12 个内建参数个数不对会 panic**（宿主崩溃）；
  **Python 侧参数个数不对会漏英文原生错误**（`_b_len() missing 1 required…`）。

**M54（结清「五引擎的账」）**：

- 集中还了一遍「**同一个语义、五个实现**」这条线上的欠账，抓到 **4 个真 bug**：
  - 🔴 **Rust 宿主的闭包单元不共享**（最重）：`Cell` 在 Rust 侧是值语义的
    `struct`（Python / Node 是对象），于是「先创建闭包、后给它赋值」永远失效 ——
    最典型的写法**嵌套的递归函数**直接崩 `「空」不能调用`。**顶层递归没事**，
    单测怎么写都碰不到；**三个执行器都是对的，只有真跑 Rust 才抓得住**。
    M53 记的三笔 Rust 缺口（`容器` / `迭代` / `参数`）**根因都是它**，一并解决。
  - 🔴 **Rust 未绑定局部静默给 `空`** —— 不报错的错答案（`空` 是合法值，
    跟「没赋过值」必须分得开）。
  - 🔴 **C VM 的未绑定「单元」报错类型**与另两个执行器不一致（同一个执行器两套写法）。
  - 🔴 **C VM 的「用后释放」崩溃**：函数值还在、VM 先销毁，GC 回收时
    回调 C 库 → `access violation`。**崩在 GC 里**，位置跟出错代码毫无关系。
- **补上「对象方法的漂移检测」**：M51 那份检测**只覆盖标准库函数名**，
  而 `列表`/`字典`/`文本`/`集合`/`文件`/`小数` 的方法表同样是**五份实现**。
  代价是两笔漏网 —— Rust 缺 `文本.查找`、Node 缺 `文件.位置/定位/刷新`，
  **都是偶然撞见的**。现在两个宿主都有 `--dump-methods`（**与分派同源**），
  测试接在 `tests/test_m51_consistency.py`，并补了一条「**表里有名字 ≠ 真的能用**」
  的实测。上面那几个缺口已全部补齐。

**M53（基石库层批量迁移）**：

- **又搬了三个模块**进基石库层：`容器`（7 函数）、`迭代`（12）、`参数`（5）——
  加上 `统计`，共 **4 模块 / 34 函数**，都是「用基石写一份、五个引擎共用同一份
  字节码」，且与宿主层实现**逐字节一致**（`tests/test_m52_jishilib.py`）。
- ⚠️ **顺手抓到一个影响四个引擎的真 bug**：「循环体里 `尝试/捕获`、捕获完继续
  循环」会把栈搞脏，最终报 `TypeError: 'RunTypeError' object is not an iterator`。
  根因在**编译器**（`尝试/捕获` 的字节码多了一句 `DUP_TOP`）。**三个执行器 +
  两个宿主里只有树遍历是对的** —— 五引擎对拍才抓得住。已修 + 加回归测试。

**M52（基石库层）**：

- **纯逻辑标准库从此只写一份**。以前 `统计` 这类模块要**用三种语言各写一遍**
  （Python / JS / Rust），改一处得改三处 —— M51 的漂移检测就是被这个逼出来的。
  现在 `jishi/stdlib-jishi/统计.jsh`（**就是基石源码**）在**编译期展开**成外壳函数，
  `导入 统计` 被改写成 `统计 = $造模块("统计", __基石库_统计__())`，
  于是**五个引擎跑的完全是同一份字节码，三个执行器与两个跨语言宿主一个字都没改**。
- **与宿主层实现逐字节一致**（`tests/test_m52_jishilib.py` 23 项：五引擎一致 +
  与宿主层一致 + 错误路径同类 + 机制 + 回落）。
- ⚠️ **性能如实公布：比宿主层慢 25–38 倍**（树遍历 37.8x / Python VM 24.9x /
  C VM 27.7x）—— 库代码内部每调一次内建，在 C VM 上都是一次宿主回调，而宿主层版
  把这一切做在一次调用里。**所以热路径函数必须留在宿主层**，这是下一阶段
  「性能分层」的存在理由。完整数据、走过的弯路与边界见 `docs/设计决策.md` D45。
- 顺带修掉一个报错翻译缺口：`遍历 <不可迭代的值>` 在 C VM 上报的是
  「内部错误（宿主回调）：TypeError: …」，现在是清楚的中文类型错误。

**M51（更早一轮，一致性止血）**：

- **宿主不再静默丢掉命名参数**。`加密.摘要("abc", 算法="md5")` 以前在 Node / Rust
  宿主上**悄悄用默认的 sha256**（Python 给 `900150…`、两宿主给 `ba7816bf…`），
  一声不响——这是本项目最危险的一类问题：**错了不报警**。现在两宿主按
  「模块.函数」查**由标准库源码自动生成的签名表**，把命名参数映射回位置参数；
  映射不了一律**明确报错**（类型「类型错误」，与 Python 侧一致）。
- **建了「漂移检测」**：两宿主各加 `--dump-stdlib`（**由宿主自己报家底**，
  不走正则解析源码），`tests/test_m51_consistency.py` 断言「Python 侧有的模块与
  函数，宿主一个都不能少、也不能多」，两宿主彼此也要对得上。
  **验收实测**：故意从 Node 删掉 `统计` 模块 → 3 条测试报红并点名缺哪个；
  把参数映射退回「静默丢掉」→ 7 条报红（含 `md5` vs `sha256` 那条）。
- **顺带补齐 13 个宿主静默缺失的标准库函数**（M50 及更早留下的洞）：
  `数学`（正弦 / 余弦 / 正切 / 对数 / 常用对数 / 角度转弧度）、
  `文本`（填充 / 截断）、`迭代`（累积 / 组合 / 排列 / 笛卡尔积）。
  补后两宿主与 Python 侧**同宽**，三个执行器 + 两个宿主逐字节一致。
- ⚠️ **只剩一个已知缺口**：`时间.计时` 在 Node / Rust 上仍缺失——它返回一个
  **带方法的对象**并支持上下文协议，而两宿主的上下文查找只认「Jishi 实例」与
  「内建容器」，标准库直接返回的宿主对象走不通。缺口**显式写在测试的
  `KNOWN_GAPS` 里**（不掩盖、也不让它静默），归属下一阶段：改成用**基石**写的
  库之后，它天然是 Jishi 实例，这类缺口会结构性消失。

**M50（更早一轮，分两批）**：

- **第一批**：标准库 **19 → 25 个模块、161 → 231 个函数**，新增 `统计` / `编码` /
  `配置` / `html` / `对比` / `标识`，并给 `迭代`（+累积/组合/排列/笛卡尔积）、
  `文本`（+截断/填充）、`时间`（+**计时**，上下文管理器式）补缺。
- **第二批**：把新模块补齐到 Node / Rust 宿主，新增 `tests/test_m50_hosts.py`
  （39 项）做**逐字节对拍**。Rust 侧的 base64、行级 diff、UUID 都是自写的
  （它零第三方依赖）。⚠️ 但当时说的「五个引擎同宽」**只针对这批新模块**——
  更早的 13 个函数缺口没人发现（M51 的漂移检测就是这么来的）。
- **验收看「真实项目少了几处绕道」**：`基石自述站/生成.jsh` 删掉手写的
  `转义()`（4 次 `替换`，而且**漏了引号**）改用 `html.转义`；
  `排序跑分/排序.jsh` 的手写计时改用 `时间.计时`。
- ⚠️ 顺带修掉 3 个坑，其中一个是**语言级**的：`用 … 为 …：` 原先**不认宿主对象**
  （只看了基石类实例与内建方法表），于是标准库返回的计时器不能当上下文管理器用。

**M48 阶段三（再往前）**：

- **方法调用融合**：`X.方法(实参)` 原本编译成 `GET_ATTR` + `CALL`，即
  **两次宿主回调**（实测每次约 4µs，其中必要工作只 2–3µs）。现在编译成
  一条 `METHOD_CALL`，一次回调做完。同机交错 A/B 实测：
  **方法调用 1.83× 快**、**端到端真实项目 `生成.jsh` 521.9ms → 334.8ms（1.56× 快）**。
- ⚠️ 该阶段另两个子项按实测判定**不做**，理由都量过：**常量折叠**全仓只 7 处
  可折叠（0.16%）；**窥孔候选 <1.7%** 且收益 ~0.2%；**文件 I/O** 的包装零开销
  （`按行读` 201µs vs 裸调 212µs）。不是做不动，是量完之后发现不值得——
  原计划「纯计算 +5–15%」的前提不成立。

**M47（更早）**：

- **C 侧原生字符串**（`JS_TAG_STR`）：拼接绝对快 **8.4 倍**、比较 **11.6 倍**；
  **AST 缓存**（361 行项目编译 14.13ms → **1.46ms**）。
- **顺带修掉一个先于该阶段就存在的内存泄漏**：C VM 的迭代器**每消费一个元素漏
  一份引用**（遍历 1000 个文本一次漏 33KB）。不报错、对拍全绿，只在长跑进程里
  涨内存——靠本轮新增的 `tools/leak_probe.py` 量出来。

**M46 阶段一（更早）**：

- ④②「延迟合并写」让**列表构建 3.0x → 14.1–19.1x**、**字典写入 0.78x → 5.7–6.3x**；
  ② 宿主回调路径提速约 10%。
- ⚠️ 实测**瓶颈是回调次数**（每次约 **4µs**，与被调函数做什么无关）；
  **读侧仍慢**（字典查找 0.96x）——要治它得让 C 侧真正持有容器内容。
  基准已按类型拆细，见 `tools/benchmark.py`。

## 架构与数据流

```
源码 → tokenizer → parser → AST ──┬─→ Interpreter（树遍历，默认执行器）
                                  └─→ 编译器 → 字节码 ──┬─→ Python VM
                                                        └─→ C VM（jsvm.dll）
```

- 三个执行器（树遍历 / Python VM / C VM）共用 `jishi/runtime.py` 的语义，
  `tests/test_cvm.py` 对拍保证「换执行器不改变任何可观察行为」
  （stdout 与报错逐字节一致）。
- 默认仍走树遍历；`jishi/vm.py` / `jishi/cvm_bind.run_source_c` 可切换。
  性能：C VM **纯算术 11–48x**、**列表构建与遍历 14x 上下**、**字典写入 6x 上下**；
  **文本拼接约 3x、文本比较约 12x**（M47：文本改成 **C 侧原生字符串**，
  拼接与比较不再回调宿主）；**浮点 / 布尔遍历 6x 上下**。
  ⚠️ **宿主回调是 C VM 的已知瓶颈**：每次内建 / 方法 / 标准库调用固定约 **2.4µs**
  （C↔Python 的 FFI 往返，**与被调函数做什么无关**），所以「内建调用密集」只有
  0.91x。**要提速就得减少回调次数**，而不是把回调内部写得更快。
  **文本下标 / 切片**（要回调宿主执行切片协议）、**文本遍历 / 文本列表遍历**
  （循环体每元素至少一次回调）、**字典查找**（读没法合并）都受这条制约。
  这些边界都逐字记录在 `tools/benchmark.py`，是**已知边界、不是待修缺陷**。
- **AI 原生能力**（M8/M9）架在 AST 与报错之上：`jishi/ai.py` 从
  tokenizer/parser/runtime/stdlib 动态收集元数据，产出语言卡、语言规格、
  JSON 结构化报错；`jishi/mcp_server.py` 把执行能力暴露给任意 MCP 宿主。

## 关键技术决策（详见 docs/设计决策.md）

- **D1 技术栈透明**：Python 前端 + C 内核 + Python 生态桥接，不 fork/patch CPython
- **D2 分词消歧**：关键字粘连检查只针对**多字关键字**（如果/循环/导入…），
  单字关键字（类/当/真/空/非/令）不做前缀检查，否则 `类型`/`当时`/`空间` 等日常词全被误伤。
- **D3 全角标点**：字符串与注释外做一对一归一化（`＝`→`=` 等）；全角空格 U+3000 在缩进中报错。
- **D4 执行模型**：树遍历 → 字节码 + C VM（M4），语法不变，对拍测试保证一致。
- **D5 标准库**：中文 API 是薄壳，绝不重造轮子，真实价值来自 Python 生态。
- **D7 对象方法分派**：方法表按类型分派返回闭包，列表方法原地修改、文本方法返回新值。
- **D8 REPL**：顶层表达式非空回显（真/假/空中文化）；空行强制结束多行块。
- **D11 异常对象模型（M5a）**：异常即 `JishiError` 实例，`e.消息`/`e.类型` 可读；
  捕获条件按类型名匹配，用 isinstance 判断（基类抓子类）。
- **D12 语法用中文助词（M5a）**：`捕获 值错误 为 e:`、`继承 基类:` 用「为/继承」
  等助词连接，不用冒号嵌套的类 Python 写法，读起来更像自然语言。

## 已踩过的坑（避免重踩）

1. `re.fullmatch` 对 `[...]` 单字符类多字符永远 False，要用 `[...]+` 运行正则。
2. dataclass 继承字段顺序 → 全部 `@dataclass(kw_only=True)`。
3. 全角引号需配对表（`“` 配 `”`），不是同字符闭合。
4. 块语句以 DEDENT 结束，parser 主循环不能要求 NEWLINE。
5. `与/或` 右操作数要用 `parse_expr(prec+1)` 而非 `parse_unary()`，否则比较运算符逃逸。
6. `dump_ast` 用 `vars()` 前先判类型（tuple/list 无 `__dict__`）。
7. Windows venv 路径 `Scripts/` 不是 `bin/`。
8. 尾随逗号：列表/字典/调用参数/函数参数四处循环都要支持（M2 已修）。
9. `数学.幂` 用 `math.pow` 返回 float，整数期望 int → 用 `**` 运算符。
10. `导入 文本` 会遮蔽内建 `文本()` 转换函数（与 Python 导入遮蔽一致，文档已注明）。
11. 调用括号内的 `名字 = 值` 一律按关键字参数处理（parser 调用上下文无赋值语义）。
12. `_lookup` 查英文 True/False/None 的提示要在"你是不是想写"建议**之前**抛出，
    否则编辑距离建议会给出误导性结果。
13. 三执行器共享 runtime 语义，但异常穿透调用栈的「重入边界」必须一致
    （vm.py 的 stop_at / C VM 的 stop_depth），否则类方法里 `抛出` 会被错误接住。
14. `非` 的优先级必须**低于比较运算**（M23 修正）。写成一元（最紧）会让
    `非 年龄 >= 18` 变成 `(非 年龄) >= 18` 恒为假——**静默给错答案**，
    项目教程自己就踩过。现按 Python `not` 语义：`非` 吃掉右边的比较表达式，
    吃不掉 `与/或`。
15. 新增比较运算码（`在`/`不在`/`是`/`不是`）要放在 **6–9**，不能占用 0–5：
    0–5 是 C VM 的 `compare_fast` 快路径，6 以上自动回落宿主回调
    `host->compare`——这是「加语义比较运算符零 C 改动」的前提（见 opcodes.CmpOp）。
16. C VM 里同一个函数每次跨边界都会新建 `CvmFunction` 包装，直接按 `id()`
    判断同一性会与另两个执行器结果相反（`f 是 g`）。修法是按 `JVal.v.u`
    （底层 `JsFunc*` 指针）缓存包装（见 `cvm_bind.CvmHost._func_cache`）。
17. 加比较类关键字（`不在`/`不是`）必须同时加进 tokenizer 的
    `_GLUE_CHECK_SKIP`：它们本身是常用词前缀，否则 `不在列表`、`不是我`
    这类正常变量名会被「关键字粘连」检查误报。

## 设计原则

1. **像 Python 一样简洁**：缩进划分代码块，语法零冗余。
2. **中文是母语**：报错信息全中文，精确到行列，附"你是不是想写…"修正建议。
3. **生态即生命**：绝不重造标准库，薄封装 Python 生态。
4. **透明不吹牛**：技术栈如实标注，走长期演进路线。
